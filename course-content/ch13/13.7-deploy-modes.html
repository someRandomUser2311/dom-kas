Deploy modes, what-if & deployment stacks

You'll be able to predict what a Bicep deployment does with resources you removed from the file, read what-if output, and use deployment stacks to manage a set of resources as a unit and block drift.

1. Incremental mode (the default)

In incremental mode, ARM creates or updates the resources in the template and leaves everything else alone. That includes resources you removed from the file.

Without state, ARM has no memory that "this used to be in the template".

Terraform
The biggest difference. Delete a resource block in Terraform and the next apply destroys it, because state remembers it. Delete it in Bicep (incremental) and it keeps running, unmanaged and still billed.

2. Predict it

You delete the userPool agentPools resource from aks.bicep and redeploy (incremental). What happens to the user node pool in Azure?

  1. It's deleted That's Terraform's behaviour, or complete mode / a stack with delete.
  2. It stays, untouched and no longer managed by the template
  3. The deployment fails Incremental deployments ignore resources not in the template.
  4. It's scaled to zero Nothing touches it.
To remove it, delete it explicitly (az aks nodepool delete), or use a deployment stack (step 7).
The template on the left (resources can be ticked off) and the resource group on the right. Deploy as Incremental, Complete, or Stack (actionOnUnmanage detach/delete). Removed resources stay grey (detached), turn red and disappear (deleted), or are flagged "unmanaged".

3. Complete mode

--mode Complete makes the resource group match the template exactly: anything in the group that isn't in the template is deleted. That includes resources other people or tools put there.

It's powerful and dangerous. It works only at resource-group scope, and conditional resources set to false are deleted too.

Most teams avoid it in favour of deployment stacks.

Match each what-if symbol to its meaning.

+Will be created
~Will be modified
-Will be deleted (complete mode or stacks)

! means what-if can't predict the result (for example, values only known during deployment).

5. what-if noise

what-if sometimes reports changes that aren't real: properties ARM normalises, or read-only values. Learn your template's usual noise, and use --exclude-change-types NoChange Ignore to focus. Remember that what-if is a prediction, not a saved plan (lesson 13.8).

6. Drift without state

"Bicep has no state, so there's no drift" is wrong. Someone can still change the node count in the portal. Bicep just doesn't track it. A redeploy resets the properties it sets, and what-if shows the difference. Run what-if on a schedule as a drift report, or prevent drift with deny settings (next).

7. Deployment stacks

A deployment stack is an Azure resource that remembers the set of resources a template deployed, like a lightweight state that Azure keeps for you. That gives two powers:

  • actionOnUnmanage: what to do with resources removed from the template. detachAll keeps them; deleteResources or deleteAll deletes them, the Terraform-like behaviour.
  • denySettings: block changes made outside the stack. denyDelete or denyWriteAndDelete stop portal and CLI edits, preventing drift, with exclusions for named principals.
az stack group create \
  --name stack-orders-prod \
  --resource-group rg-orders-prod \
  --template-file main.bicep \
  --parameters main.prod.bicepparam \
  --action-on-unmanage deleteResources \
  --deny-settings-mode denyWriteAndDelete \
  --deny-settings-excluded-principals "$PIPELINE_SP_OBJECT_ID"

8. Stopping portal drift

Engineers keep changing the prod cluster in the portal during incidents and forgetting to update the code. Which Bicep-native feature stops that?

  1. Complete mode It deletes extra resources; it doesn't stop edits to managed ones.
  2. A deployment stack with denySettings (deny write and delete), excluding the pipeline identity
  3. what-if It shows drift; it doesn't prevent it.
  4. Resource locks on every resource Locks also block the pipeline unless removed each time; deny settings are designed for this.
Changes then go through Git and the pipeline. For emergencies, the excluded principal list, or a break-glass procedure, still allows changes.

9. Stack with delete: predict

The prod stack uses actionOnUnmanage: deleteAll. A PR removes the memory node pool from the parameters and the stack is updated. What happens?

  1. It stays, detached That's detachAll.
  2. The memory node pool is deleted, because the stack knows it previously managed it
  3. The stack update fails Removing resources is normal.
  4. The whole cluster is recreated Only the removed resource is affected.
That's why what-if (or a stack's own preview) in the PR matters: removals now have real consequences, as in Terraform.

10. When the stack itself is deleted

az stack group delete also takes --action-on-unmanage. Choose detachAll to remove the stack but keep the resources, or a delete option to tear everything down. For prod, protect the stack itself with RBAC: only the pipeline may change it.
