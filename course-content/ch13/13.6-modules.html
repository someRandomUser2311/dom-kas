Modules & registries

You'll be able to split Bicep into modules, deploy across resource groups and at subscription scope, use Azure Verified Modules, and publish your own modules to ACR.

1. A module is just a Bicep file

Any .bicep file can be used as a module. Its params are the inputs and its outputs the results.

The caller uses a module declaration, and each module becomes a nested deployment in the history.

module network './modules/network.bicep' = {
  name: 'network-${environment}'
  params: {
    nameSuffix: nameSuffix
    location: location
  }
}

module cluster './modules/aks.bicep' = {
  name: 'aks-${environment}'
  params: {
    nameSuffix: nameSuffix
    subnetId: network.outputs.aksSubnetId
    isProd: isProd
  }
}
Terraform
Same idea as module "aks" { source = "./modules/aks" }. network.outputs.aksSubnetId ↔ module.network.aks_subnet_id, and it creates the dependency.

2. Scope: another resource group

A module can deploy into a different resource group with scope:. That's how the AcrPull assignment on the shared registry works (lesson 13.4).

module acrPull './modules/acr-pull.bicep' = {
  name: 'acrpull-${environment}'
  scope: resourceGroup('rg-orders-shared')
  params: {
    acrName: 'contosoacr'
    principalId: cluster.outputs.kubeletObjectId
  }
}

3. targetScope

By default a file deploys to a resource group. To create the resource group itself, the file must deploy at subscription scope.

Other scopes are managementGroup and tenant.

Make this file deploy at subscription level so it can create the resource group.

?

resource rg 'Microsoft.Resources/resourceGroups@2024-03-01' = {
  name: 'rg-orders-${environment}'
  location: location
}

module platform './platform.bicep' = {
  name: 'platform-${environment}'
  scope: rg
  params: { environment: environment }
}
  • targetScope = 'subscription'
  • scope = subscription() That's how you reference a scope; the file's own scope is set with targetScope.
  • @scope('subscription') Not a decorator.
  • deploymentScope: 'subscription' Not Bicep.
Deploy it with az deployment sub create -l westeurope -f main.bicep -p …. Then the module deploys into the new group.

4. Azure Verified Modules

Azure Verified Modules (AVM) are Microsoft-maintained modules in the public Bicep registry, referenced as br/public:avm/…:<version>.

The AKS one wraps every managedClusters option with tested defaults.

module aks 'br/public:avm/res/container-service/managed-cluster:0.10.0' = {
  name: 'aks-${environment}'
  params: {
    name: 'aks-${nameSuffix}'
    primaryAgentPoolProfiles: [ /* … */ ]
    disableLocalAccounts: true
    enableOidcIssuerProfile: true
    enableWorkloadIdentity: true
    // …
  }
}

The version shown is illustrative. Check the AVM index for the current version and parameter names, and pin exactly that.

5. Pin the version

In step 4's code, tap the line that fixes which module version is used.

The :0.10.0 tag in the module reference. Bicep has no "latest". An upgrade is a deliberate edit, reviewed with what-if.

Why pin AVM module versions and upgrade them deliberately?

  1. Unpinned references are slower Speed isn't the issue.
  2. A new module version can change defaults or parameters, and with them many resource properties. Review it with what-if first
  3. AVM is unsupported It's supported and maintained.
  4. Pinning is required by ACR Unrelated.
The same reason you pin Terraform providers and modules (lesson 12.6).

6. Your own module registry in ACR

Publish Contoso's modules to ACR, the same registry as images and Helm charts. Every team can then use br:contosoacr.azurecr.io/bicep/modules/aks:1.2.0.

az bicep publish --file modules/aks.bicep \
  --target br:contosoacr.azurecr.io/bicep/modules/aks:1.2.0 \
  --documentation-uri https://dev.azure.com/contoso/platform/_wiki/aks-module

8. Template specs

Template specs are another way to share templates. They're stored as Azure resources, versioned, and controlled with RBAC. Bicep registries in ACR are generally preferred for module sharing, because they're OCI artifacts like everything else.

9. Nested deployment names

Each module call's name becomes a deployment in history and must be unique within the scope for concurrent runs. Include the environment (and, for loops, an index): 'aks-${environment}'. Names over 64 characters fail.

10. Module outputs and secrets

Module outputs are stored in deployment history, so never output secrets from a module. To pass a secret between modules, use a @secure() output (supported in recent Bicep), or have the consumer read it from Key Vault itself.

Modules, sorted

  • Any Bicep file is a module; module x './file.bicep' = { name, params }; read x.outputs.
  • scope: resourceGroup('…') for other groups; targetScope = 'subscription' to create groups.
  • AVM from br/public:avm/…:<pinned version>.
  • Publish your own to ACR with az bicep publish; aliases and linter rules in bicepconfig.json.
