Identity & role assignments

You'll be able to write role assignments that redeploy cleanly, grant AcrPull to the kubelet, and create a workload identity with its federated credential in Bicep.

1. A role assignment is an extension resource

Microsoft.Authorization/roleAssignments is attached to another resource through scope:. It has three parts:

  • the role definition ID;
  • the principal ID;
  • a principal type.

Its name must be a GUID.

var acrPullRoleId = subscriptionResourceId('Microsoft.Authorization/roleDefinitions', '7f951dda-4ed3-4680-a7ca-43fe172d538d')

resource kubeletAcrPull 'Microsoft.Authorization/roleAssignments@2022-04-01' = {
  name: guid(acr.id, aks.id, acrPullRoleId)
  scope: acr
  properties: {
    roleDefinitionId: acrPullRoleId
    principalId: aks.properties.identityProfile.kubeletidentity.objectId
    principalType: 'ServicePrincipal'
  }
}
Terraform
azurerm_role_assignment generates the GUID name and remembers it in state. Bicep has no state, so you must compute a name that's the same on every deployment.

2. Why the name must be deterministic

guid(acr.id, aks.id, acrPullRoleId) hashes its inputs. The same registry, cluster and role always give the same GUID.

A redeploy finds the existing assignment by that name and leaves it alone.

A colleague writes name: newGuid() for the role assignment. The first deployment succeeds. What happens on the second?

  1. Nothing changes A new GUID means a new resource name.
  2. It fails with RoleAssignmentExists: a different-named assignment for the same principal, role and scope already exists
  3. A second identical assignment is created Azure refuses duplicates of principal + role + scope.
  4. The old one is replaced Incremental mode doesn't delete the old one.
newGuid() is only allowed as a parameter default, and changes every time. Always use guid() with stable inputs: scope, principal and role.

3. The kubelet identity path

In step 1's code, tap the line that targets the identity that actually pulls images.

identityProfile.kubeletidentity.objectId is the kubelet's identity, not aks.identity (the control plane). It's the same distinction as lesson 5.4.

4. principalType avoids a race

A just-created identity may not have reached every Entra ID replica yet. Without principalType, ARM looks the principal up and can fail with PrincipalNotFound.

Setting principalType: 'ServicePrincipal' (managed identities count as service principals) skips that lookup.

5. Diagnose the deployment error

A first deployment of a new environment fails intermittently. What's the fix?

{"code":"PrincipalNotFound","message":"Principal 4e7a… does not exist in the directory 72f9…. Check that you have
the correct principal ID. If you are creating this principal and then immediately assigning a role, this error might be
related to a replication delay. In this case, set the role assignment principalType property to a value, such as
ServicePrincipal, User, or Group."}
  1. Add dependsOn on the identity The reference already orders it; the issue is directory replication.
  2. Set principalType: 'ServicePrincipal' on the role assignment
  3. Use newGuid() for the name That causes RoleAssignmentExists later.
  4. Wait a day Only seconds of replication are involved, and the property avoids the lookup.
The error message itself suggests the fix. Read deployment errors to the end.

6. The cluster identity and its network grant

resource aksIdentity 'Microsoft.ManagedIdentity/userAssignedIdentities@2023-01-31' = {
  name: 'id-aks-${nameSuffix}'
  location: location
}

var networkContributorId = subscriptionResourceId('Microsoft.Authorization/roleDefinitions', '4d97b98b-1d4f-4787-a291-c67834d212e7')

resource aksNetwork 'Microsoft.Authorization/roleAssignments@2022-04-01' = {
  name: guid(aksSubnet.id, aksIdentity.id, networkContributorId)
  scope: aksSubnet
  properties: {
    roleDefinitionId: networkContributorId
    principalId: aksIdentity.properties.principalId
    principalType: 'ServicePrincipal'
  }
}
// on the cluster: dependsOn: [ aksNetwork ]   (hidden dependency, as in lesson 12.5)

7. A workload identity

resource ordersApiId 'Microsoft.ManagedIdentity/userAssignedIdentities@2023-01-31' = {
  name: 'id-orders-api-${environment}'
  location: location
}

resource ordersApiFed 'Microsoft.ManagedIdentity/userAssignedIdentities/federatedIdentityCredentials@2023-01-31' = {
  parent: ordersApiId
  name: 'fc-${aks.name}-orders-api'
  properties: {
    issuer: aks.properties.oidcIssuerProfile.issuerURL
    subject: 'system:serviceaccount:orders:orders-api'
    audiences: [ 'api://AzureADTokenExchange' ]
  }
}

output ordersApiClientId string = ordersApiId.properties.clientId

Deploy federated credentials for one identity one at a time (@batchSize(1) in loops). Concurrent writes to the same identity's credentials can conflict.

9. Cross-scope assignments

The shared registry lives in rg-orders-shared, a different resource group from the deployment. A role assignment's scope must be a resource in the deployment's own scope.

So put the AcrPull assignment in a small module deployed with scope: resourceGroup('rg-orders-shared') (lesson 13.6), and pass it the kubelet object ID as a parameter.

10. Who can deploy role assignments?

As with Terraform (lesson 12.5), the deploying identity needs Microsoft.Authorization/roleAssignments/write. Grant it Role Based Access Control Administrator, with a condition limiting the assignable roles. Contributor isn't enough.

Role assignments, sorted

  • Extension resource with scope:; the name is guid(scope, principal, role), never newGuid().
  • Kubelet: aks.properties.identityProfile.kubeletidentity.objectId → AcrPull.
  • principalType: 'ServicePrincipal' avoids PrincipalNotFound for new identities.
  • Federated credential: a child of the identity, with issuer = oidcIssuerProfile.issuerURL and an exact subject.
  • Cross-resource-group scopes go through a module.
