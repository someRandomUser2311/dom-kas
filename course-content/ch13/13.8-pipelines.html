Bicep in Azure Pipelines & choosing a tool

You'll be able to build a Bicep infra pipeline (lint → what-if → approval → deploy) with workload identity federation, and choose between Bicep and Terraform for a given team.

1. The same shape as Chapter 12

  • PR: build and lint, build the parameters, what-if against the target, results in the run summary.
  • Main: what-if stage → environment approval → deploy stage.

Authentication uses the same WIF service connection, with the same least-privilege identities.

Terraform
what-if ↔ plan; deploy ↔ apply. One important gap: there's no saved what-if to apply. The deploy re-evaluates the template, so re-run what-if right before deploying (step 5).
GitHub Actions
azure/login (OIDC) + azure/arm-deploy or az deployment; the same stages behind environment protection rules.
GitLab CI
az CLI jobs with OIDC id_tokens; manual deploy job for prod.
Jenkins
az CLI stages with a federated credential plugin, or a managed identity on the agent.
Classic pipelines
The ARM template deployment task in a release stage, now in YAML.

2. PR checks

- task: AzureCLI@2
  displayName: Lint, build, what-if
  inputs:
    azureSubscription: sc-orders-infra-readonly
    scriptType: bash
    scriptLocation: inlineScript
    workingDirectory: infra/bicep
    inlineScript: |
      set -euo pipefail
      az bicep lint --file main.bicep                  # rules from bicepconfig.json; errors fail the step
      az bicep build-params --file main.prod.bicepparam --outfile /tmp/params.json
      az deployment group what-if -g rg-orders-prod -f main.bicep -p main.prod.bicepparam \
        --exclude-change-types NoChange Ignore --no-pretty-print > whatif.json
      az deployment group what-if -g rg-orders-prod -f main.bicep -p main.prod.bicepparam \
        --exclude-change-types NoChange Ignore > whatif.txt
- script: |
    { echo '## What-if (prod)'; echo '```'; cat infra/bicep/whatif.txt; echo '```'; } > summary.md
    echo "##vso[task.uploadsummary]$(System.DefaultWorkingDirectory)/summary.md"
  displayName: Publish what-if summary

3. The main pipeline

trigger:
  branches: { include: [main] }
  paths: { include: [infra/bicep/*] }

stages:
  - stage: WhatIf
    jobs:
      - job: whatif
        steps:
          - task: AzureCLI@2
            inputs:
              azureSubscription: sc-orders-infra-prod
              scriptType: bash
              scriptLocation: inlineScript
              workingDirectory: infra/bicep
              inlineScript: |
                az bicep lint --file main.bicep
                az deployment group what-if -g rg-orders-prod -f main.bicep -p main.prod.bicepparam

  - stage: Deploy
    dependsOn: WhatIf
    condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
    jobs:
      - deployment: deploy
        environment: infra-prod            # approval check
        strategy:
          runOnce:
            deploy:
              steps:
                - checkout: self
                - task: AzureCLI@2
                  inputs:
                    azureSubscription: sc-orders-infra-prod
                    scriptType: bash
                    scriptLocation: inlineScript
                    workingDirectory: infra/bicep
                    inlineScript: |
                      set -euo pipefail
                      az stack group create --name stack-orders-prod -g rg-orders-prod \
                        -f main.bicep -p main.prod.bicepparam \
                        --action-on-unmanage deleteResources \
                        --deny-settings-mode denyWriteAndDelete \
                        --deny-settings-excluded-principals "$(pipelineSpObjectId)" --yes

4. The task alternative

AzureResourceManagerTemplateDeployment@3 deploys a .bicep file directly (csmFile), with the service connection and resource group as inputs. It's useful if you prefer tasks to scripts. Deployment stacks need the CLI step shown above.

- task: AzureResourceManagerTemplateDeployment@3
  inputs:
    deploymentScope: Resource Group
    azureResourceManagerConnection: sc-orders-infra-prod
    resourceGroupName: rg-orders-prod
    location: westeurope
    csmFile: infra/bicep/main.bicep
    csmParametersFile: infra/bicep/main.prod.bicepparam
    deploymentMode: Incremental

5. what-if isn't a saved plan

Terraform applies the exact plan the approver saw (lesson 12.8). Bicep can't: the deploy evaluates the template and Azure as they are at deploy time. Keep the gap between what-if and deploy short, run what-if again inside the deploy job just before the deployment, and use an exclusive lock so nothing else changes the target in between.

6. Arrange the stages

Arrange the Bicep infra pipeline so a deploy can only happen after an approved what-if.

Cards: "lint + build-params", "what-if (published to summary)", "approval on infra-prod", "what-if again + deploy (stack)", plus decoys "deploy on PR" and "skip what-if on main". Success: lint → what-if → approval → re-check + deploy, with the decoys discarded.
The approver reviews the what-if; the deploy step re-checks right before acting.

7. Identities and permissions

  • PR identity: Reader on the target, enough for what-if.
  • Deploy identity: Contributor on the resource group(s), RBAC Administrator (conditioned) for role assignments, and rights to manage deployment stacks there.
  • That deploy identity is excluded from the stack's deny settings, so it's the only way to change prod.

8. Bicep vs Terraform: the decision matrix

9. Scenarios

A company runs workloads on Azure and AWS, and manages GitHub repos and Datadog monitors as code. Which IaC tool fits best as the standard?

  1. Bicep Azure only.
  2. Terraform (or OpenTofu)
  3. ARM JSON Azure only, and verbose.
  4. az CLI scripts Not declarative.
One tool and one workflow across every provider.

An Azure-only team wants new AKS preview features the day they ship, and doesn't want to manage a state backend. Which fits?

  1. Bicep, with deployment stacks for lifecycle
  2. Terraform with azurerm only Workable, but they'd wait for provider support (or use azapi) and manage state.
  3. Portal Not IaC.
  4. Pulumi Also needs a state backend.
There's no wrong answer in general. Pick by context, then use the tool well.

10. What's required either way

Select what Contoso's infra pipeline needs whichever language it uses.

  1. PR checks with a preview of changes (plan or what-if)
  2. An approval before changing prod
  3. Workload identity federation, no client secrets
  4. Least-privilege identities (read-only for PRs)
  5. A remote state backend Only Terraform needs one.
  6. Complete deployment mode Neither needs it; it's risky.
The pipeline discipline is the same; only the commands differ.

11. Mixing tools

It's fine to use both for different layers: Terraform for landing zones and shared networking, Bicep for an app team's resources. Never let two tools manage the same resource. They'll fight, and each will undo the other's changes.

12. The capstone accepts either

In Chapter 17 you submit infra/terraform/ or infra/bicep/. Both are graded against the same requirement rules, and submitting both earns the "Bilingual IaC" badge.

Bicep pipelines & choosing, sorted

  • PR: az bicep lint, build-params, what-if to the run summary.
  • Main: what-if → approval (deployment job + environment) → re-check + deploy (stack or az deployment group create).
  • what-if isn't a saved plan; keep the gap short and lock the environment.
  • Choose by clouds, feature timing, state preferences and team skills; never let two tools own one resource.
