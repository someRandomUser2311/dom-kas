Bicep & ARM: the model

You'll be able to explain how a Bicep file becomes Azure resources, why there's no state file, and how to deploy and inspect a deployment.

1. Bicep compiles to ARM

Every Azure change, whether from the portal, the CLI, Terraform or Bicep, goes through Azure Resource Manager (ARM). ARM accepts deployments described as ARM JSON templates.

Bicep is a much friendlier language that compiles to that JSON. The az CLI compiles it for you when you deploy.

Two panes: a Bicep file (editable) and the ARM JSON it compiles to, updated live. Highlighting links each Bicep line to its JSON. Shows how vnet.id becomes [resourceId(...)] and how implicit dependsOn is generated.
Terraform
Terraform calls ARM's REST API resource by resource through the azurerm provider. Bicep instead hands ARM a whole template, and ARM does the ordering and execution. There's no init and no provider download: the "provider" is ARM itself.
Portal/ARM
If you've exported or edited ARM JSON, Bicep is the same model with a tenth of the syntax.
az CLI scripts
You keep using az; you just call az deployment group create with a file instead of many commands.
CloudFormation
Bicep ≈ CloudFormation's role on AWS: the provider's native template language.
Pulumi
Pulumi's azure-native provider uses the same ARM resource types and API versions.

2. No state file

Bicep keeps no state. When you deploy, ARM compares the template with what currently exists in the target scope, and creates or updates resources to match.

Azure itself is the source of truth. There's no state to lock, store, protect or lose.

Where does Bicep keep track of the resources it has deployed?

  1. In a .bicepstate file There's no such file.
  2. In a storage account backend That's Terraform.
  3. Nowhere separately: ARM reads the current resources in Azure (plus deployment history)
  4. In the Bicep registry Registries hold modules, not state.
The trade-off: no state to manage, but also no memory of what you removed from the file. Lesson 13.7 explains why that matters.

3. Resource types and API versions

Every resource is declared with its type and an API version: 'Microsoft.ContainerService/managedClusters@2024-09-01'.

The API version fixes which properties exist and what they mean. New AKS features appear in new API versions, often the day they launch. You choose when to move up.

resource vnet 'Microsoft.Network/virtualNetworks@2024-05-01' = {
  name: 'vnet-orders-dev'
  location: resourceGroup().location
  properties: {
    addressSpace: { addressPrefixes: [ '10.20.0.0/16' ] }
  }
}

4. Deploying

A deployment targets a scope, usually a resource group. The parameters file supplies values per environment.

az deployment group create \
  --resource-group rg-orders-dev \
  --template-file main.bicep \
  --parameters main.dev.bicepparam \
  --name orders-$(date +%Y%m%d%H%M)

5. Deployment history

Every deployment is recorded on its scope, with its template, parameters (secure ones hidden), outputs and status. That's your audit trail: az deployment group list -g rg-orders-dev -o table, or "Deployments" in the portal.

$ az deployment group list -g rg-orders-dev --query "[].{name:name, state:properties.provisioningState, time:properties.timestamp}" -o table

6. Preview with what-if

what-if asks ARM what a deployment would change, without changing anything. It's Bicep's equivalent of a plan. Lesson 13.7 covers its output in detail.

az deployment group what-if -g rg-orders-dev -f main.bicep -p main.dev.bicepparam

8. Tooling

  • The Bicep CLI comes with az (az bicep install / upgrade), or is available standalone.
  • The VS Code Bicep extension gives completion, type checking for every resource and API version, and the linter.
  • az bicep build -f main.bicep shows the ARM JSON; az bicep decompile turns existing ARM JSON into Bicep.

9. Day-zero Azure support

Because Bicep uses ARM types directly, any new resource property is usable as soon as its API version ships. You never wait for a provider release. The VS Code extension may warn that a type isn't in its local schema yet, but the deployment works.

The model, sorted

  • Bicep → ARM JSON → ARM deploys it; every resource has type@apiVersion.
  • No state file: Azure is the source of truth; deployment history is the audit trail.
  • what-if previews; az deployment group create deploys with a .bicepparam.
  • New Azure features are available immediately through new API versions.
