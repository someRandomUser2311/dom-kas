Which setting makes a stage start in parallel with the stage above it?

  1. parallel: true
  2. dependsOn: []
  3. condition: always()
  4. strategy: parallel
By default each stage depends on the previous one. An empty dependsOn removes that implicit dependency.

Why tag images with $(Build.BuildId) instead of latest?

  1. latest isn't allowed by ACR
  2. Each tag maps to exactly one run, so deployments are traceable and rollbacks deterministic
  3. It makes images smaller
  4. AKS can only pull numeric tags
latest changes underneath you.

Predict the pipeline run (3 scenarios)

All three scenarios use this pipeline. Predict each stage: Succeeded, Failed, Skipped or Waiting.

trigger: [main]
pr: [main]                         # repo is on GitHub

stages:
  - stage: Build
    jobs:
      - job: test_and_build
        steps:
          - script: go test ./...
          - task: Docker@2
            condition: and(succeeded(), ne(variables['Build.Reason'], 'PullRequest'))
            inputs: { command: buildAndPush, containerRegistry: acr-connection, repository: orders-api }

  - stage: Lint
    dependsOn: []
    jobs:
      - job: lint
        steps:
          - script: golangci-lint run && kube-linter lint k8s/

  - stage: DeployDev
    dependsOn: [Build, Lint]
    condition: and(succeeded(), ne(variables['Build.Reason'], 'PullRequest'))
    jobs:
      - deployment: dev
        environment: dev
        strategy: { runOnce: { deploy: { steps: [ ... ] } } }

  - stage: DeployProd
    dependsOn: DeployDev
    condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
    jobs:
      - deployment: prod
        environment: prod          # has a required approval check
        strategy: { runOnce: { deploy: { steps: [ ... ] } } }

  - stage: Report
    dependsOn: [Build, Lint]
    condition: succeededOrFailed()
    jobs:
      - job: publish
        steps:
          - task: PublishTestResults@2

Write lab A: a multi-stage pipeline

Brief: Finish azure-pipelines.yml for orders-api. Graded by pipeline-rules, with a live stage graph drawn from your YAML.

# azure-pipelines.yml for orders-api
# TODO: only build pushes to main
trigger:
  - main

pool:
  vmImage: ubuntu-latest

stages:
  - stage: Build
    jobs:
      - job: build
        steps:
          - script: go test ./...
            displayName: Unit tests
          # TODO: build & push the image to ACR with a traceable tag

  # TODO: add a Deploy stage that
  #  - only runs for main AND when Build succeeded
  #  - uses a deployment job targeting the 'prod' environment
  #  - deploys k8s/*.yaml to namespace 'orders' with the new image
  • The YAML is valid.
  • Only known top-level keys (trigger, pr, pool, variables, stages, resources, …).
  • The CI trigger is for main only.
  • The Build stage runs Docker@2 with command: buildAndPush, containerRegistry: acr-connection, repository orders-api.
  • The image tag is traceable ($(Build.BuildId) or $(Build.SourceVersion)), never latest.
  • The Deploy stage depends on Build.
  • Deploy runs only for main AND when Build succeeded.
  • Prod deploys only through a deployment job targeting environment prod (which carries the approval).
  • The deployment job checks out the repo (- checkout: self).
  • Azure access only through service connections: KubernetesManifest@1 uses a service connection to deploy k8s/*.yaml to namespace orders with the new image (no kubeconfig or credentials in the YAML).
  • No plaintext secrets in the YAML.
Reference solution 
trigger:
  - main

pool:
  vmImage: ubuntu-latest

variables:
  imageRepo: orders-api
  tag: $(Build.BuildId)

stages:
  - stage: Build
    jobs:
      - job: build
        steps:
          - script: go test ./...
            displayName: Unit tests
          - task: Docker@2
            displayName: Build & push image
            inputs:
              command: buildAndPush
              containerRegistry: acr-connection
              repository: $(imageRepo)
              tags: $(tag)

  - stage: Deploy
    dependsOn: Build
    condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
    jobs:
      - deployment: deploy_orders
        environment: prod
        strategy:
          runOnce:
            deploy:
              steps:
                - checkout: self
                - task: KubernetesManifest@1
                  inputs:
                    action: deploy
                    connectionType: azureResourceManager
                    azureSubscriptionConnection: sc-orders-prod
                    azureResourceGroup: rg-orders-prod
                    kubernetesCluster: aks-orders-prod
                    namespace: orders
                    manifests: k8s/*.yaml
                    containers: contosoacr.azurecr.io/orders-api:$(tag)

A kubernetesServiceConnection (e.g. aks-prod) is also accepted instead of the Azure Resource Manager connection inputs.

Write lab B: templates and extends

Brief: Contoso's platform team publishes templates/secure-pipeline.yml in the platform/pipeline-templates repo. It wraps any build in mandatory scan and publish stages. Make orders-api's pipeline use it with extends, passing its build steps as a parameter. Graded by pipeline-rules.

parameters:
  - name: buildSteps
    type: stepList
    default: []
  - name: imageRepository
    type: string

stages:
  - stage: Build
    jobs:
      - job: build
        steps:
          - ${{ each step in parameters.buildSteps }}:
            - ${{ step }}
          - task: Docker@2
            inputs:
              command: buildAndPush
              containerRegistry: acr-connection
              repository: ${{ parameters.imageRepository }}
              tags: $(Build.BuildId)
  - stage: Scan
    dependsOn: Build
    jobs:
      - job: trivy
        steps:
          - script: trivy image --exit-code 1 --severity CRITICAL contosoacr.azurecr.io/${{ parameters.imageRepository }}:$(Build.BuildId)
  • A resources.repositories entry references platform/pipeline-templates, pinned to a ref (a tag or refs/heads/main).
  • The top level uses extends: template: templates/secure-pipeline.yml@<alias>.
  • parameters.buildSteps contains the test step(s); parameters.imageRepository is orders-api.
  • No stages: or jobs: defined outside extends, so the template can't be bypassed.
  • The template ref is pinned (a tag preferred over a moving branch).
  • No plaintext secrets.
Reference solution 
trigger: [main]

resources:
  repositories:
    - repository: platform
      type: git
      name: platform/pipeline-templates
      ref: refs/tags/v2.3.0

extends:
  template: templates/secure-pipeline.yml@platform
  parameters:
    imageRepository: orders-api
    buildSteps:
      - script: go test ./...
        displayName: Unit tests

On the prod environment, add a "Required template" check for templates/secure-pipeline.yml@platform, so pipelines that don't extend it can't deploy.

Walkthrough: what the pipeline automates, by hand

A scripted terminal (not graded). The same steps a pipeline performs, run one at a time, signed in with workload identity federation as the pipeline would be:

  1. az login --service-principal -u $AZURE_CLIENT_ID --federated-token "$OIDC_TOKEN" --tenant $AZURE_TENANT_ID: no client secret. (The legacy client-secret version is shown only for comparison.)
  2. az acr login -n contosoacr
  3. docker build -t contosoacr.azurecr.io/orders-api:$BUILD_ID . then docker push …
  4. az aks get-credentials -g rg-orders-dev -n aks-orders-dev then kubelogin convert-kubeconfig -l workloadidentity
  5. kubectl apply -n orders -f k8s/ with the new image tag
  6. kubectl rollout status deploy/orders-api -n orders and kubectl get pods -n orders

The built preview (app-preview/lab-terminal.html) also creates the resource group, registry and cluster. In the course those now come from Chapters 4–6 and IaC (Chapters 12–13).
