1. Variables: name it once

Define values once under variables and use them anywhere with $(name). Change the image name in one place, not five.

variables:
  imageRepo: orders-api
  namespace: orders

steps:
  - script: echo "Deploying $(imageRepo) to $(namespace)"

2. Predefined variables

Azure Pipelines gives you dozens of variables for free. Three you'll use constantly:

  • Build.BuildId: unique per run, the perfect image tag
  • Build.SourceBranch: e.g. refs/heads/main
  • Build.Reason: IndividualCI, PullRequest, Manual…
variables:
  imageRepo: orders-api
  namespace: orders
  tag: $(Build.BuildId)

steps:
  - script: echo "Deploying $(imageRepo):$(tag) to $(namespace)"
  - script: echo "Branch $(Build.SourceBranch), reason $(Build.Reason)"
GitHub Actions
github.run_id, github.ref, github.event_name.
GitLab CI
CI_PIPELINE_ID, CI_COMMIT_REF_NAME, CI_PIPELINE_SOURCE.
Jenkins
BUILD_NUMBER, BRANCH_NAME.

4. Your turn: print the updated value

Step 1 sets env to prod at runtime. Make step 2 print prod.

variables:
  env: dev

steps:
  - script: echo "##vso[task.setvariable variable=env]prod"
  - script: echo "I see: ?"

Which syntax completes the line?

  • ${{ variables.env }} Compile-time: it was replaced with dev before the run even started.
  • $(env)
  • $[ variables.env ] Runtime expressions don't work inline in scripts. They belong in variable definitions and conditions.
$(env) is expanded just before the step runs, after step 1 changed it.

5. Quick check: compile time strikes again

A step sets tag to v2. A later step is wrapped in ${{ if eq(variables.tag, 'v2') }}:.

variables:
  env: dev

steps:
  - script: echo "##vso[task.setvariable variable=env]prod"
  - script: echo "I see: $(env)"

Does the later step run?

  1. No. The ${{ if }} was evaluated at compile time, before tag changed
  2. Yes, because tag is v2 by then By then the if has already been evaluated and the step removed.
  3. Only if tag is an output variable Output variables help across jobs, but compile-time expressions still can't see them.
${{ }} is resolved when the YAML is compiled, long before any script runs. Use a runtime condition: eq(variables.tag, 'v2') instead.

6. Secrets never live in YAML

Put secrets in a variable group, ideally linked to Azure Key Vault, so rotation happens in Key Vault and nothing sensitive is in Git.

Secret variables are masked as *** in logs and are not passed to scripts automatically. Map them explicitly with env:.

variables:
  - group: orders-prod-secrets   # linked to Key Vault kv-orders-prod

steps:
  - script: ./migrate.sh
    env:
      DB_PASSWORD: $(db-password)  # explicit mapping
GitHub Actions
Like repo/environment secrets read with ${{ secrets.X }}; Key Vault linking ≈ fetching from a vault action.
GitLab CI
Masked/protected CI variables, or the Vault integration.
Jenkins
Credentials store + withCredentials.
Classic pipelines
The same Library variable groups.

Masking isn't security. A script can still leak a secret by encoding it. Restrict who can edit pipelines, and protect variable groups with pipeline permissions and approvals.

7. Spot the leak

Security review. One line in this file is a real problem.

variables:
  - group: orders-prod-secrets
  - name: imageRepo
    value: orders-api
  - name: dbPassword
    value: 'S3cr3t-Pa55!'

steps:
  - script: ./migrate.sh
    env:
      DB_PASSWORD: $(db-password)

Tap the line that leaks a secret.

A plaintext value in YAML is in Git history forever, even after you delete it. Move it to the Key Vault-backed group and rotate it.

8. Templates: write it once

A template is a YAML file with parameters that other pipelines include. Platform teams use them to publish a hardened golden path.

# templates/build.yml
parameters:
  - name: imageName
    type: string
  - name: runTests
    type: boolean
    default: true

stages:
  - stage: Build
    jobs:
      - job: build
        steps:
          - ${{ if eq(parameters.runTests, true) }}:
            - script: go test ./...
          - task: Docker@2
            inputs:
              command: buildAndPush
              containerRegistry: acr-connection
              repository: ${{ parameters.imageName }}
GitHub Actions
Reusable workflows (workflow_call) and composite actions.
GitLab CI
include: + extends: / CI components.
Jenkins
Shared libraries.
Classic pipelines
Task groups, now with real parameters.

9. Use the template

Now each service's pipeline is tiny: include the template and pass parameters. At compile time, Azure Pipelines expands it into one full pipeline.

For security, extends goes further: your pipeline must fit inside an approved template, and environments can require it.

trigger: [main]

stages:
  - template: templates/build.yml
    parameters:
      imageName: orders-api
      runTests: true

Tap the line whose value ends up as the Docker task's repository.

imageName is substituted into ${{ parameters.imageName }} at compile time, so the expanded task reads repository: orders-api.

Variables, secrets & templates, sorted

You know when ${{ }}, $[ ] and $( ) are evaluated, how to keep secrets in Key Vault-backed groups, and how templates turn a golden path into a five-line pipeline.
  • $(var): default, just before each task
  • $[ ]: runtime, in variables & conditions
  • ${{ }}: compile time, shapes the pipeline
  • Secrets: Key Vault-linked group + explicit env:
  • Templates + extends = reusable, enforceable pipelines
