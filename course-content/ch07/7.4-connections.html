1. How does a pipeline prove who it is?

Your pipeline needs to push to ACR and deploy to AKS. Both are protected Azure resources.

The tempting shortcut is on the right. Every person who can read the repo can now use that password, and it lives in Git history forever.

# ❌ please never do this
variables:
  AZ_CLIENT_ID: 6f1c…
  AZ_CLIENT_SECRET: 'Q8~kz.Yt2-…'

steps:
  - script: az login --service-principal -u $(AZ_CLIENT_ID) -p $(AZ_CLIENT_SECRET) --tenant …

The fix is a chain of three ideas: an identity in Entra ID, a service connection in Azure DevOps that uses it, and RBAC roles on the resources. That's this lesson.

2. The identity: who is the pipeline?

Four terms you'll hear constantly. The key one: RBAC roles are assigned to a service principal (or a managed identity, which is just an SP whose credentials Azure manages).

TermWhat it is
App registrationGlobal definition of an app in Entra ID: client ID, credentials, federated credentials
Service principalThe app's identity in your tenant; what RBAC roles attach to
Managed identityAn SP whose credentials Azure rotates for you
Service connectionAzure DevOps object that knows how to authenticate as one of the above

3. Reference it by name

With a service connection, the YAML only contains its name. Azure DevOps handles authentication at runtime, and admins control which pipelines may use it.

steps:
  - task: AzureCLI@2
    inputs:
      azureSubscription: azure-orders-dev   # service connection name
      scriptType: bash
      scriptLocation: inlineScript
      inlineScript: az aks list -o table
GitHub Actions
Like azure/login@v2 with OIDC (id-token: write), except the trust config lives in an Azure DevOps object instead of repo secrets.
GitLab CI
Like id_tokens: + az login --federated-token, packaged up so you don't script it.
Jenkins
Like a Credentials-plugin entry bound with withCredentials, but secretless when you use federation.
Classic pipelines
The same service connections you selected in Classic task dropdowns.

6. Quick check

You're creating a new Azure Resource Manager service connection for a team.

steps:
  - task: AzureCLI@2
    inputs:
      azureSubscription: azure-orders-dev   # service connection name
      scriptType: bash
      scriptLocation: inlineScript
      inlineScript: az aks list -o table

Which credential should it use?

  1. Client secret with 24-month expiry It works, but it's a long-lived secret that will eventually leak or expire at 2 a.m.
  2. Workload identity federation
  3. A personal access token (PAT) PATs authenticate people to Azure DevOps, not pipelines to Azure.
  4. The subscription owner's username and password Never use a human's credentials for automation.
Federation uses short-lived OIDC tokens, so there's no secret to store, leak or rotate.

7. Least-privilege RBAC

An identity with no roles can sign in but do nothing. Give each identity exactly what it needs, scoped as narrowly as possible.

Notice there are two identities: the pipeline pushes, the cluster pulls.

Anti-pattern: one SP with Owner on the subscription, shared by every pipeline, with a 2-year secret.

8. Quick check: ImagePullBackOff

The pipeline pushed the image successfully, but pods are stuck in ImagePullBackOff with 401 Unauthorized from contosoacr.azurecr.io.

steps:
  - task: AzureCLI@2
    inputs:
      azureSubscription: azure-orders-dev   # service connection name
      scriptType: bash
      scriptLocation: inlineScript
      inlineScript: az aks list -o table

What's most likely missing?

  1. AcrPush for the pipeline SP The push already worked, so the pipeline side is fine.
  2. A Docker Registry service connection Service connections are for the pipeline. Pods don't use them.
  3. Workload identity federation on the connection That affects how the pipeline signs in, not how nodes pull.
  4. AcrPull for the AKS kubelet identity
Pulling is done by the nodes, which authenticate as the kubelet identity. It needs AcrPull, e.g. via az aks update --attach-acr.

10. ACR in one screen

Azure Container Registry is a private Docker registry. Its login server is <name>.azurecr.io.

These are the commands a pipeline runs under the hood. You'll type them yourself against the local floci-az emulator in the terminal lab.

# create a registry and let the cluster pull from it
az acr create -g rg-orders-dev -n contosoacr --sku Standard
az aks update -g rg-orders-dev -n aks-orders-dev --attach-acr contosoacr

# what Docker@2 buildAndPush does for you
az acr login -n contosoacr
docker build -t contosoacr.azurecr.io/orders-api:1427 .
docker push contosoacr.azurecr.io/orders-api:1427

Tap the command that gives AKS permission to pull from the registry.

--attach-acr assigns AcrPull on the registry to the cluster's kubelet identity.

Secretless, least-privilege delivery

Pipelines authenticate through service connections, ideally with workload identity federation. RBAC gives the pipeline AcrPush and the cluster AcrPull, each scoped as narrowly as possible.
  • Never put credentials in YAML
  • Service connection = named, permissioned way to authenticate
  • Prefer workload identity federation
  • Pipeline pushes (AcrPush); kubelet pulls (AcrPull)
  • Scope to a resource group; don't grant to all pipelines
