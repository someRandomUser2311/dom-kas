1. Shipping by hand doesn't scale

In earlier chapters you deployed to AKS like this, straight from your laptop.

It works for one person on a quiet afternoon. With ten engineers and twenty changes a day, someone skips the tests, someone pushes latest over a good image, and someone deploys uncommitted code.

# what "deploying" looked like so far
docker build -t contosoacr.azurecr.io/orders-api:latest .
docker push contosoacr.azurecr.io/orders-api:latest
kubectl apply -f k8s/
# tests? "I ran them yesterday" 🤞

The real cost isn't typing commands. It's no audit trail (who deployed what, from which commit?) and no consistency (every laptop has different tool versions).

2. CI: every push is built and tested

Continuous Integration means every push is built and tested automatically, on a clean machine, within minutes.

Broken code is caught while the change is still fresh in the author's head, not at release time.

  4. A Classic release pipeline That's how it might be built, not what the practice is called.

7. Azure DevOps, the product

Azure Pipelines is one service inside Azure DevOps, a separate product from the Azure portal. An organization holds projects, and each project can switch these services on or off.

ServiceWhat it does
ReposGit hosting (GitHub works just as well)
Pipelines this chapterBuild, test and deploy: CI/CD
ArtifactsPackage feeds: npm, NuGet, Maven, pip
BoardsWork items, sprints, Kanban
Test PlansManual & exploratory testing
GitHub Actions
GitHub bundles the same ideas: Repos ≈ GitHub repos, Pipelines ≈ Actions, Artifacts ≈ Packages, Boards ≈ Projects/Issues.
GitLab CI
GitLab is one app with all of these built in. Azure DevOps splits them into services you toggle per project.
Jenkins
Jenkins only covers the Pipelines part. Repos, packages and boards live in other tools.
Classic pipelines
Same product you already use. Only the way pipelines are defined is changing.

8. Quick check: do I need an Azure subscription?

A common confusion, and it matters for this course.

# what "deploying" looked like so far
docker build -t contosoacr.azurecr.io/orders-api:latest .
docker push contosoacr.azurecr.io/orders-api:latest
kubectl apply -f k8s/
# tests? "I ran them yesterday" 🤞

Which statement is true?

  1. You need an Azure subscription to create an Azure DevOps organization An organization needs a Microsoft account, not a subscription.
  2. Pipelines can't run at all without a subscription Pipelines run on agents; the free tier covers small teams with no subscription.
  3. The subscription is for the Azure resources you deploy to, and for buying extra capacity
An Azure DevOps organization only needs a Microsoft account and has a free tier. An Azure subscription matters for what you deploy to (AKS, ACR…) and for buying extra parallel jobs. In this course those targets are emulated locally by floci-az.

9. Classic vs YAML pipelines

Azure Pipelines has two ways to define a pipeline. You'll meet both at work, but every new pipeline should be YAML: it lives in the repo, is reviewed in pull requests, and does build and deploy in one file.

🖱️ Classic
  • Built by clicking in the UI
  • Separate Build & Release pipelines
  • Hard to review or reuse
📄 YAML Use this
  • azure-pipelines.yml in your repo
  • Reviewed in PRs, versioned with code
  • Reusable via templates
Classic pipelines
Your Classic definitions keep working, but new features land in YAML first. Next lesson shows how your Build + Release map onto stages.

10. The smallest useful pipeline

Here's a complete, working pipeline in eight lines. The next lesson takes it apart line by line. For now, just find one thing in it.

# azure-pipelines.yml
trigger:
  - main

pool:
  vmImage: ubuntu-latest

steps:
  - script: echo "Hello from $(Agent.OS)"

Tap the line that picks which machine runs the pipeline.

vmImage: ubuntu-latest asks for a fresh Microsoft-hosted Ubuntu VM. You'll go deep on agents in L7.3.

CI/CD, demystified

You know why we automate, the difference between CI, Continuous Delivery and Continuous Deployment, where Azure Pipelines sits in Azure DevOps, and why YAML beats Classic.
  • CI = every push built & tested on a clean machine
  • Continuous Delivery = every green build deployable; a human ships it
  • Continuous Deployment = no human gate
  • Azure DevOps org needs no Azure subscription
  • New pipelines: YAML, in the repo
