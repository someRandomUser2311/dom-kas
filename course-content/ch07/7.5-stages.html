Stages, conditions, environments & approvals

1. Stages run in order by default

Without any extra keys, each stage implicitly depends on the one above it and only runs if that one succeeded.

Good for a simple Build → Deploy. Real pipelines need more shape.

stages:
  - stage: Build
    jobs: [ ... ]

  - stage: Deploy        # implicitly: dependsOn: Build
    jobs: [ ... ]
GitHub Actions
Like jobs chained with needs:, except here the chain is implicit.
GitLab CI
Identical to stage ordering in stages:.
Jenkins
Sequential stage blocks.
Classic pipelines
Release stages triggered "after previous stage".

2. Run things in parallel

A security scan doesn't need the build to finish. dependsOn: [] removes the implicit dependency so Scan starts immediately, alongside Build.

stages:
  - stage: Build
    jobs: [ ... ]

  - stage: Scan
    dependsOn: []         # no dependencies, so it starts right away
    jobs: [ ... ]
GitHub Actions
A job without needs:.
GitLab CI
Put both jobs in the same stage, or use needs: [].
Jenkins
A parallel { } block.
Classic pipelines
Parallel release stages.

3. Fan in: wait for both

Give dependsOn a list and the stage waits for all of them. Deploy-dev now needs Build and Scan to succeed.

stages:
  - stage: Build
    jobs: [ ... ]

  - stage: Scan
    dependsOn: []         # no dependencies, so it starts right away
    jobs: [ ... ]

  - stage: DeployDev
    dependsOn: [Build, Scan]
    jobs: [ ... ]

The run view draws this as a graph: Build and Scan side by side, both feeding DeployDev. You'll see it in the simulator in two steps.

4. Conditions decide whether a stage runs

condition is evaluated after dependencies finish. The default is succeeded().

Prod should deploy only from main. ⚠️ A custom condition replaces the default, so include succeeded() yourself.

stages:
  - stage: Build
    jobs: [ ... ]

  - stage: Scan
    dependsOn: []         # no dependencies, so it starts right away
    jobs: [ ... ]

  - stage: DeployDev
    dependsOn: [Build, Scan]
    jobs: [ ... ]

  - stage: DeployProd
    dependsOn: DeployDev
    condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
    jobs: [ ... ]
GitHub Actions
if: github.ref == 'refs/heads/main'. In Actions, success() is implicitly ANDed; in Azure it's replaced.
GitLab CI
rules: - if: $CI_COMMIT_BRANCH == "main".
Jenkins
when { branch 'main' }.
Classic pipelines
Stage trigger filters / custom conditions.

Other useful functions: failed(), succeededOrFailed() (not when cancelled), always(), ne(variables['Build.Reason'], 'PullRequest') to never deploy from PRs.

5. Quick check: the dangerous condition

Someone writes condition: eq(variables['Build.SourceBranch'], 'refs/heads/main') on DeployProd. On main, the tests fail.

stages:
  - stage: Build
    jobs: [ ... ]

  - stage: Scan
    dependsOn: []         # no dependencies, so it starts right away
    jobs: [ ... ]

  - stage: DeployDev
    dependsOn: [Build, Scan]
    jobs: [ ... ]

  - stage: DeployProd
    dependsOn: DeployDev
    condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
    jobs: [ ... ]

What happens to DeployProd?

  1. Skipped, because a dependency failed That's what succeeded() would do, but this condition doesn't include it.
  2. It runs and deploys the broken build
  3. The pipeline fails to compile The expression is valid; it's just wrong.
The custom condition replaced succeeded(), so it only checks the branch. A broken build ships to prod! Always write and(succeeded(), …).

9. Quick check: why not in YAML?

Approvals and checks are configured on the environment in the Azure DevOps UI, not in azure-pipelines.yml.

stages:
  - stage: Build
    jobs: [ ... ]

  - stage: Scan
    dependsOn: []         # no dependencies, so it starts right away
    jobs: [ ... ]

  - stage: DeployDev
    dependsOn: [Build, Scan]
    jobs: [ ... ]

  - stage: DeployProd
    dependsOn: DeployDev
    condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
    jobs: [ ... ]

Why?

  1. YAML doesn't support approvals yet It's a deliberate design choice, not a missing feature.
  2. So that people who can edit the pipeline can't remove the gate
  3. It's faster to evaluate checks in the UI Performance has nothing to do with it.
Anyone who can push a branch can edit YAML. Checks owned by the environment's admins can't be removed by the people they're meant to control.

10. Deployment strategies

runOnce is the common choice on AKS, because the Kubernetes Deployment already does a rolling update.

canary sends a slice of traffic to the new version first, then you promote or reject. (rolling in Azure Pipelines is for VM environments.)

Interactive in the preview (onShow handler).

You can shape a delivery pipeline

Parallel stages, fan-in, conditions that keep succeeded(), gates owned by environments, and the right deployment strategy for AKS.
  • dependsOn: [] → parallel
  • dependsOn: [A, B] → fan-in
  • Custom conditions replace succeeded()
  • Approvals & checks live on environments
  • AKS: runOnce + Deployment rolling update, or canary
