Anatomy of azure-pipelines.yml

Converted from the built preview lesson. Interactive panels are kept as their rendered HTML inside .widget blocks.

1. Meet the pipeline file

A whole pipeline is one YAML file committed to your repo, usually azure-pipelines.yml at the root.

Azure Pipelines reads it from the exact commit being built, so pipeline changes are reviewed in pull requests just like code. Over the next steps you'll build a real one, line by line.

# azure-pipelines.yml
# Lives at the root of your repo, next to the Dockerfile.
GitHub Actions
Same idea as .github/workflows/ci.yml. The difference: you point an Azure pipeline at a YAML file when you create it, so the name and path are up to you.
GitLab CI
Very close to .gitlab-ci.yml: one declarative file at the repo root.
Jenkins
Think Jenkinsfile, but declarative YAML instead of Groovy. There's no scripting language around it.
Classic pipelines
This replaces the click-built Build and Release definitions with a file you can diff, review and roll back.

You can have several YAML pipelines in one repo (e.g. ci.yml, release.yml). Each is registered once in Azure DevOps, and from then on the YAML in the branch being built is what runs.

2. Decide when it runs

trigger lists the branches whose pushes start a run. Here only main does.

Leave trigger out and every branch triggers. trigger: none turns CI off completely.

# azure-pipelines.yml
trigger:
  - main
GitHub Actions
on: push: branches: [main], the same thing in a different shape.
GitLab CI
Like rules: - if: $CI_COMMIT_BRANCH == "main" on your jobs, but declared once for the whole pipeline.
Jenkins
Similar to a webhook-triggered multibranch job limited with when { branch 'main' }.
Classic pipelines
Triggers tab → Enable continuous integration → branch filter main.

The long form supports filters:

trigger:
  batch: true
  branches:
    include: [main, release/*]
  paths:
    exclude: [docs/*]

PR validation is separate: the pr: key works for GitHub and Bitbucket. For Azure Repos you configure a build validation branch policy instead.

3. Quick check: who triggers a run?

Look at the file on the right. A teammate pushes a commit to the branch feature/login.

# azure-pipelines.yml
trigger:
  - main

What does Azure Pipelines do?

  1. Starts a run for feature/login Only branches listed under trigger start a run, and feature/login isn't one of them.
  2. Nothing. Only pushes to main trigger CI
  3. Starts a run but skips every step Runs are either queued or not. There's no "empty run" for unlisted branches.
  4. Waits for someone to approve the run Approvals belong to environments (later in this lesson), not to triggers.
Only branches listed under trigger start CI runs. (PR validation would be a separate trigger.)

4. Pick a machine

Every job runs on an agent, a machine with build tools on it. pool chooses where.

vmImage: ubuntu-latest asks for a fresh Microsoft-hosted Ubuntu VM that's thrown away after the job. Nothing leaks between runs.

# azure-pipelines.yml
trigger:
  - main

pool:
  vmImage: ubuntu-latest
GitHub Actions
runs-on: ubuntu-latest, practically identical. Microsoft-hosted agents and GitHub-hosted runners even share image definitions.
GitLab CI
Runner selection via tags:, plus a container image:. Here the VM image is the environment.
Jenkins
agent { label 'linux' }. Microsoft-hosted agents are like ephemeral cloud agents you never maintain.
Classic pipelines
Agent job → Agent pool: Azure Pipelines, Agent specification: ubuntu-latest.

Use pool: name: my-pool for self-hosted agents, e.g. when you must reach a private AKS cluster. Lesson L7.3 covers this in depth.

5. Tell it what to do

steps is an ordered list of work. script runs a shell command (bash on Linux).

If a command exits non-zero, the step fails and the job stops. That's exactly how a failing test blocks a release. displayName is the label you'll see in the run log.

# azure-pipelines.yml
trigger:
  - main

pool:
  vmImage: ubuntu-latest

steps:
  - script: go mod download
  - script: go test ./...
    displayName: Unit tests
GitHub Actions
- run: go test ./... with name:. Azure calls it script and displayName.
GitLab CI
Like the script: list inside a job, except each entry here is its own step with its own log section.
Jenkins
steps { sh 'go test ./...' }
Classic pipelines
Each script is the Command line task you used to drag in.

Variants: bash: (bash everywhere, even on Windows), pwsh: (PowerShell Core). Useful step options: condition, continueOnError, timeoutInMinutes, env, workingDirectory.

6. Your turn: add a lint step

Add a step that runs npx eslint . after the tests. Pick the keyword that runs a shell command in Azure Pipelines.

# azure-pipelines.yml
trigger:
  - main

pool:
  vmImage: ubuntu-latest

steps:
  - script: go mod download
  - script: go test ./...
    displayName: Unit tests
  - ?: npx eslint .
    displayName: Lint

Which keyword completes the highlighted line?

  • run run is GitHub Actions syntax. Azure Pipelines would reject it as an unknown step type.
  • script
  • sh sh is the Jenkins step. In Azure Pipelines use script (or bash).
  • exec exec isn't a step type in any of the big CI systems.
script runs a command with the agent's default shell.

7. Give it structure: stages → jobs → steps

When you write only steps, Azure Pipelines silently wraps them in one job inside one stage. Once you deploy, you'll want that structure explicit:

  • Stage: a phase like Build or Deploy, with its own conditions and approvals.
  • Job: runs on one agent, start to finish.
  • Step: one command or task inside a job.
pipeline›stage: Build›job: Test›steps
# azure-pipelines.yml
trigger:
  - main

pool:
  vmImage: ubuntu-latest

stages:
  - stage: Build
    jobs:
      - job: Test
        steps:
          - script: go mod download
          - script: go test ./...
            displayName: Unit tests
          - script: npx eslint .
            displayName: Lint
GitHub Actions
Actions has no stages; a workflow is a set of jobs linked with needs:. Think of an Azure stage as a group of jobs that can be gated and approved as one unit.
GitLab CI
Almost a 1:1 match with stages: plus jobs that declare stage:. Here jobs are nested inside their stage instead.
Jenkins
stages { stage('Build') { steps { … } } }. Azure adds the job level in between, which decides the agent.
Classic pipelines
The old Build pipeline becomes the Build stage; Release pipeline stages become Deploy stages in the same file.

Stages run in order by default (each depends on the one above). Jobs inside a stage run in parallel by default. You change both with dependsOn.

8. Quick check: sharing files

Imagine you split Test into two jobs: Compile produces dist/, and Package needs it.

# azure-pipelines.yml
trigger:
  - main

pool:
  vmImage: ubuntu-latest

stages:
  - stage: Build
    jobs:
      - job: Test
        steps:
          - script: go mod download
          - script: go test ./...
            displayName: Unit tests
          - script: npx eslint .
            displayName: Lint

What's true?

  1. Jobs in the same stage share the agent's disk automatically Each job may land on a different agent. Nothing is shared by default.
  2. Publish dist/ as a pipeline artifact and download it in the second job
  3. Put both jobs in different stages, because stages share disks Stages don't share disks either. Every job starts on a clean agent.
  4. It's impossible; merge them into one job Merging works, but it isn't the only option. Artifacts are the standard way to hand files between jobs.
A job is the unit that lands on an agent. Two jobs may run on two different machines, so files travel as pipeline artifacts (PublishPipelineArtifact → DownloadPipelineArtifact).

9. Use a task instead of a script

A task is a packaged, versioned step; @2 pins its major version. inputs configure it.

containerRegistry: acr-connection names a service connection, so no password appears in the YAML. $(Build.BuildId) is unique per run, giving every image a traceable tag.

# azure-pipelines.yml
trigger:
  - main

pool:
  vmImage: ubuntu-latest

stages:
  - stage: Build
    jobs:
      - job: Test
        steps:
          - script: go mod download
          - script: go test ./...
            displayName: Unit tests
          - script: npx eslint .
            displayName: Lint
          - task: Docker@2
            displayName: Build & push image
            inputs:
              command: buildAndPush
              containerRegistry: acr-connection
              repository: orders-api
              tags: $(Build.BuildId)
GitHub Actions
Tasks ≈ actions: uses: docker/build-push-action@v6 + with: ↔ task: Docker@2 + inputs:. The service connection plays the role of docker/login-action + secrets.
GitLab CI
GitLab has no task marketplace. You'd run docker build/push in script: using $CI_REGISTRY_* variables, or pull in an include: template.
Jenkins
Like calling a plugin step such as docker.build(...).push() with credentials from the credentials store.
Classic pipelines
The very same Docker task you dragged into a Classic pipeline; YAML just writes its settings down.

Hundreds of built-in tasks exist (AzureCLI@2, HelmDeploy@0, PublishTestResults@2…) plus Marketplace extensions. Pin the major version; minor and patch updates roll out automatically.

Service connections and ACR permissions are covered in L7.4.

11. Ship it: a deployment job

dependsOn: Build makes Deploy wait for Build to succeed.

deployment: is a special job that targets an environment (prod). It records deployment history and honours approvals configured on that environment. containers: rewrites the image in your manifests to the exact tag just built.

# azure-pipelines.yml
trigger:
  - main

pool:
  vmImage: ubuntu-latest

stages:
  - stage: Build
    jobs:
      - job: Test
        steps:
          - script: go mod download
          - script: go test ./...
            displayName: Unit tests
          - script: npx eslint .
            displayName: Lint
          - task: Docker@2
            displayName: Build & push image
            inputs:
              command: buildAndPush
              containerRegistry: acr-connection
              repository: orders-api
              tags: $(Build.BuildId)

  - stage: Deploy
    dependsOn: Build
    jobs:
      - deployment: ToAKS
        environment: prod
        strategy:
          runOnce:
            deploy:
              steps:
                - checkout: self
                - task: KubernetesManifest@1
                  inputs:
                    action: deploy
                    kubernetesServiceConnection: aks-prod
                    namespace: orders
                    manifests: k8s/*.yaml
                    containers: contosoacr.azurecr.io/orders-api:$(Build.BuildId)
GitHub Actions
needs: build + environment: production: same idea, including required reviewers on the environment.
GitLab CI
environment: production on a deploy job, with when: manual or protected environments for the gate.
Jenkins
A Deploy stage with an input step for approval; Azure moves the gate out of the pipeline file into the environment.
Classic pipelines
This is the Release pipeline stage, with pre-deployment approvals now living on the environment.

Why approvals aren't in YAML: anyone who can push a branch can edit YAML. Checks on the environment (approvals, branch control, business hours, exclusive lock) are owned by its administrators. L7.5 lets you simulate them.
