Agents and agent pools

Converted from the built preview lesson. Interactive panels are kept as their rendered HTML inside .widget blocks.

1. Who actually runs your YAML?

Your YAML is only instructions. An agent executes them: a small program on a VM or container that polls Azure DevOps for work, runs the job's steps, and streams logs back.

Because the agent polls outwards, it doesn't need any inbound ports. That's important for agents inside private networks.

🔷Azure DevOpsjob queue
⇄
🖥️Agentpolls over HTTPS 443
→
🛠️Your stepsgit, go, docker…

One agent runs one job at a time.

2. Agent pools

Agents are grouped into pools. A job asks for a pool, and Azure DevOps hands it to any free agent in that pool.

The built-in Azure Pipelines pool is Microsoft-hosted; you select an image with vmImage.

pool:
  vmImage: ubuntu-latest   # Microsoft-hosted, fresh VM per job
GitHub Actions
runs-on: ubuntu-latest ↔ pool: vmImage: ubuntu-latest.
GitLab CI
Like shared SaaS runners selected by tag.
Jenkins
agent { label 'ubuntu' }, but the cloud agents are ephemeral and maintained for you.
Classic pipelines
Agent pool: Azure Pipelines + Agent specification.

3. Microsoft-hosted: the easy default

Zero maintenance: a fresh, patched VM for every job with Docker, kubectl, Azure CLI, Helm and Node preinstalled. Nothing leaks between runs.

The catch: it runs on the public internet.

✓ Pros
  • No servers to patch
  • Clean every run
  • Many tools preinstalled
✕ Cons
  • Can't reach a private AKS API or private ACR
  • No warm caches
  • Time limits, limited free parallelism

4. Self-hosted: your machine, your network

Install the agent on your own VM (or container) and register it into a pool. It can sit inside your VNet, next to a private AKS cluster.

You select it by pool name and can add demands, requirements the agent must meet.

pool:
  name: linux-builders     # your self-hosted pool
  demands:
    - docker
    - Agent.OS -equals Linux
GitHub Actions
Self-hosted runners with runs-on: [self-hosted, linux]. Labels ≈ demands.
GitLab CI
Your own GitLab Runner registered with tags.
Jenkins
Your own Jenkins nodes; labels ≈ demands.
Classic pipelines
Pick your private pool in the Agent job settings.

Self-hosted means you patch the OS, update the agent and clean workspaces. A compromised agent sits inside your network, so treat build agents as sensitive hosts and never share one pool between untrusted projects.

5. Quick check: private cluster

Your AKS cluster is private: its API server has no public IP. The deploy job uses vmImage: ubuntu-latest and times out calling the API server.

pool:
  name: linux-builders     # your self-hosted pool
  demands:
    - docker
    - Agent.OS -equals Linux

What's the best fix?

  1. Raise the job's timeoutInMinutes It's not slow; it's unreachable. Waiting longer won't help.
  2. Run the job on a self-hosted agent / Managed DevOps Pool inside a VNet that can reach the cluster
  3. Use vmImage: windows-latest Every Microsoft-hosted image is on the public internet.
  4. Add the hosted agent's IP to authorized IP ranges Authorized IP ranges apply to public API servers. A private cluster has no public endpoint at all.
A private API server is only reachable from inside the network. Run the deploy job on an agent in a VNet that can reach it.

6. The middle ground: Managed DevOps Pools

Want private-network access and a fresh machine per job, without patching servers? Azure can run the pool for you.

🧩 Managed DevOps Pools recommended

Azure creates and recycles agent VMs in your subscription and VNet. You choose image, size and scaling.

🧱 VM Scale Set agents

The older approach: you own a scale set and Azure DevOps scales it.

9. Parallel jobs

Parallel jobs are a licensing limit: how many jobs can run at the same time across your organization, counted separately for Microsoft-hosted and self-hosted.

pool:
  name: linux-builders     # your self-hosted pool
  demands:
    - docker
    - Agent.OS -equals Linux

Two people push at once. You have 5 idle self-hosted agents but 1 self-hosted parallel job. What happens?

  1. One run starts; the other queues until the first job finishes
  2. Both run, because there are enough idle agents Agents aren't the limit here; the parallel-job licence is.
  3. The second run fails immediately Runs queue; they don't fail for lack of capacity.
Parallel jobs cap concurrency regardless of how many agents exist. The second run waits in the queue.

You know where pipelines run

Agents poll for jobs, pools group them, Microsoft-hosted is the easy default, and self-hosted or Managed DevOps Pools reach private networks. Demands pick the right agent, and parallel jobs cap concurrency.
  • vmImage → Microsoft-hosted, fresh VM per job
  • pool: name → your own agents
  • Private AKS → agent inside the VNet
  • Demands must all match an agent's capabilities
  • Parallel jobs ≠ number of agents
