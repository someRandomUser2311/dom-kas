Probes

You'll be able to choose between startup, readiness and liveness probes, configure each safely, and avoid the probe mistake that turns a slow database into a full outage.

1. Running isn't the same as working

A process can be alive and still useless: still loading, deadlocked, or out of connections. Kubernetes can only react to what it can see.

Probes let the kubelet ask the container about its state. They can run an HTTP GET, a TCP connect, a gRPC health check, or a command inside the container.

There are three probes. Each answers a different question and causes a different action.

ProbeQuestionOn failure
startupHas it finished starting?Keep waiting; the other probes are paused. If it never succeeds, the container is restarted.
readinessShould it get traffic right now?Removed from Service endpoints. Not restarted.
livenessIs it stuck beyond repair?Container is restarted.
Windows/IIS admin
Readiness is like a load balancer health probe taking a server out of the pool. Liveness is like IIS rapid-fail protection recycling a broken app pool.
Linux admin
Readiness = the HAProxy health check; liveness = a watchdog that restarts the service.
Developer (Compose)
Compose's healthcheck is closest to liveness, but it only marks the container unhealthy. Kubernetes splits it into three, and acts on each.
Other clouds
Like target-group health checks (readiness) plus ECS container health checks (liveness).

2. Readiness: take me out of rotation

Readiness gates traffic. While it fails, the pod stays running but is removed from the Service's endpoints. When it passes again, the pod is added back.

Readiness also drives rollouts: a new pod only counts as available, and old pods are only removed, once it's ready.

readinessProbe:
  httpGet:
    path: /readyz
    port: http
  periodSeconds: 5
  failureThreshold: 3

An orders-api pod's readiness probe starts failing. What does Kubernetes do?

  1. Restarts the container That's liveness.
  2. Stops sending it Service traffic; the pod keeps running
  3. Deletes the pod and creates a new one Nothing deletes pods because of probes.
  4. Nothing until the rollout ends Readiness is checked continuously, not only during rollouts.
Readiness is the safe probe: a pod that is temporarily overloaded or warming a cache just steps aside until it can serve again.

3. Liveness: restart me

Liveness restarts the container when it fails failureThreshold times in a row. Use it for one thing only: a state the app can't recover from on its own, such as a deadlock.

A liveness endpoint should check only the process itself: "can I answer at all?". It must never check anything outside the container.

livenessProbe:
  httpGet:
    path: /healthz      # only checks the process itself
    port: http
  periodSeconds: 10
  failureThreshold: 3
  timeoutSeconds: 2

4. The liveness death spiral

Contoso once pointed liveness at /health/db, which checks the database. Then the database got slow for two minutes:

  1. Every orders-api pod's liveness fails at the same moment.
  2. Every pod is restarted at once, so there's zero capacity.
  3. The restarted pods all reconnect to the struggling database at the same time, which makes it slower.
  4. Liveness fails again, and the loop continues.

A two-minute database slowdown became a 40-minute full outage. Restarting the API never fixes a database problem.

A timeline with 3 pods and the database's latency. The learner picks which endpoint liveness and readiness call (/healthz or /health/db), then clicks "DB slow for 2 minutes". With liveness on /health/db, all pods restart repeatedly. With readiness on /health/db and liveness on /healthz, pods briefly leave rotation and recover with no restarts.

5. Spot the dangerous probe

One line here can turn a database blip into an outage. Tap it.

readinessProbe:
  httpGet:
    path: /readyz
    port: http
livenessProbe:
  httpGet:
    path: /health/db
    port: http
  periodSeconds: 10
Liveness depends on the database, so a slow database restarts every pod. Point liveness at /healthz (process only). If you want dependency checks, put them in readiness, and even then be careful, because every pod failing readiness at once still means no capacity.

6. Startup: slow starters

Some apps take a minute or more to start: JVM warm-up, migrations, loading a cache. With only a liveness probe, they get killed before they're up.

A startup probe pauses the liveness and readiness probes until it succeeds once. Allow up to failureThreshold × periodSeconds for start-up, then hand over to fast liveness checks.

It's better than a large initialDelaySeconds on liveness: that delay is fixed, so it's too long for fast starts and too short for slow ones.

The app sometimes needs up to 2 minutes to start. Liveness should still detect a hang within 30 seconds once it's running. What should you add?

?:
  httpGet: { path: /healthz, port: http }
  periodSeconds: 10
  failureThreshold: 12        # 12 × 10s = up to 120s to start
livenessProbe:
  httpGet: { path: /healthz, port: http }
  periodSeconds: 10
  failureThreshold: 3
  • startupProbe
  • initialDelaySeconds A field, not a probe. A 120 s delay would also wait 2 minutes after every quick restart.
  • readinessProbe Readiness doesn't pause liveness.
  • preStopHook That runs at shutdown.
The startup probe allows a long start-up once; after that, liveness can be strict.

7. Probe settings that matter

  • periodSeconds: how often (default 10).
  • timeoutSeconds: how long to wait for an answer (default 1, often too short under load).
  • failureThreshold and successThreshold: how many failures or successes in a row flip the state.
  • Keep probe endpoints cheap: no database queries, no locks. They run constantly on every pod.

8. Graceful shutdown

The other end of the lifecycle: when a pod is removed, Kubernetes sends SIGTERM and waits up to terminationGracePeriodSeconds (default 30) before SIGKILL.

Endpoints are removed at about the same time, but not instantly everywhere. A short preStop sleep keeps the pod serving while the routing rules catch up. The app should stop accepting new work on SIGTERM, then finish in-flight requests.

lifecycle:
  preStop:
    sleep:
      seconds: 5

The sleep action is built in, so you don't need a shell in the image. Older examples use exec: command: ["sleep", "5"], which fails on distroless images.

9. Contoso's probe set

ports:
  - name: http
    containerPort: 8080
startupProbe:
  httpGet: { path: /healthz, port: http }
  periodSeconds: 5
  failureThreshold: 24
readinessProbe:
  httpGet: { path: /readyz, port: http }
  periodSeconds: 5
  failureThreshold: 3
livenessProbe:
  httpGet: { path: /healthz, port: http }
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3

Probes, sorted

  • startup = has it started (pauses the others); readiness = traffic on/off; liveness = restart.
  • Readiness failing removes the pod from endpoints; it doesn't restart it.
  • Liveness must check only the process, never a dependency.
  • Use a startupProbe, not a long initialDelaySeconds.
  • Handle SIGTERM; a short preStop sleep smooths rollouts.
