Steering pods: selectors, affinity, taints

You'll be able to put pods on the right nodes, keep them off the wrong ones, spread them across zones, and read the scheduler's "why not" messages.

1. Why steer at all?

By default the scheduler puts a pod on any node with room. Sometimes that's not enough:

  • A GPU workload must land on GPU nodes, and nothing else should waste them.
  • orders-api's replicas should be in different zones, so one datacentre failure doesn't take them all.
  • System add-ons should stay on the system node pool (Chapter 4).

There are four tools, from simple to precise.

2. nodeSelector: the simple filter

nodeSelector lists node labels that must all match. A node without them is never chosen.

spec:
  nodeSelector:
    kubernetes.io/os: linux
    kubernetes.azure.com/agentpool: user

3. Node affinity: required and preferred

Node affinity is nodeSelector with operators (In, NotIn, Exists, Gt…) and two strengths:

  • requiredDuringSchedulingIgnoredDuringExecution: a hard rule; no match means Pending.
  • preferredDuringSchedulingIgnoredDuringExecution: a weighted wish; it's used if possible, ignored if not.

"IgnoredDuringExecution" means that if a node's labels change later, running pods aren't moved.

affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: gpu
              operator: In
              values: ["true"]

4. Taints and tolerations: keeping pods away

A taint on a node repels pods. Only pods with a matching toleration may be scheduled there.

Effects:

  • NoSchedule: no new pods without a toleration.
  • PreferNoSchedule: avoid if possible.
  • NoExecute: also evicts running pods that don't tolerate it.

Our GPU node has gpu=true:NoSchedule, so ordinary pods stay off it.

tolerations:
  - key: gpu
    operator: Equal
    value: "true"
    effect: NoSchedule

5. A toleration allows, it doesn't attract

This is the most common mistake. A toleration only says "I may go to tainted nodes". The scheduler can still put the pod on any untainted node.

To get a pod onto the GPU node and only there, you need both:

  • a toleration, so it's allowed on the tainted node;
  • node affinity (or nodeSelector) for gpu=true, so it isn't allowed anywhere else.

In the scheduler simulator, make the train-model pod land on gpu-1, and make sure it can never land on any other node.

Success when the spec has a toleration for gpu=true:NoSchedule AND a required node affinity (or nodeSelector) on gpu=true. Feedback:
  • Toleration only: "It landed on node-2. A toleration lets it in; it doesn't pull it there."
  • Affinity only: "Pending: gpu-1 has a taint the pod doesn't tolerate."
Solution
spec:
  nodeSelector:
    gpu: "true"
  tolerations:
    - key: gpu
      operator: Equal
      value: "true"
      effect: NoSchedule
Taints keep others out; affinity keeps this pod in. Dedicated node pools on AKS use exactly this pair.

6. Pod anti-affinity: not next to each other

Pod affinity and anti-affinity place pods relative to other pods, by label, within a topology such as a node (kubernetes.io/hostname) or a zone (topology.kubernetes.io/zone).

For example: "don't put two orders-api pods on the same node".

affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          topologyKey: kubernetes.io/hostname
          labelSelector:
            matchLabels:
              app: orders-api

7. Topology spread: even across zones

For spreading replicas evenly, topologySpreadConstraints is simpler and more precise than anti-affinity.

maxSkew: 1 means no zone may have more than one pod more than any other zone. whenUnsatisfiable sets what happens when it can't comply:

  • DoNotSchedule: hard.
  • ScheduleAnyway: soft.
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: orders-api

On AKS, nodes in a zonal node pool carry topology.kubernetes.io/zone=westeurope-1 (and -2, -3). A non-zonal pool's nodes all report the same value. Spreading then does nothing useful, so create pools with zones (Chapter 4).

8. Reading "why Pending?"

The pod is Pending. Read the event: what's the fix?

Events:
  Type     Reason            From               Message
  ----     ------            ----               -------
  Warning  FailedScheduling  default-scheduler  0/4 nodes are available: 1 node(s) had untolerated taint {gpu: true},
           3 node(s) didn't match Pod's node affinity/selector. preemption: 0/4 nodes are available:
           4 Preemption is not helpful for scheduling.
  1. Add more CPU to the nodes No node is listed as "Insufficient cpu".
  2. Add a toleration for gpu=true:NoSchedule: the only node matching the affinity is tainted
  3. Remove the node affinity Then it would run on a non-GPU node, which isn't what's wanted.
  4. Restart the scheduler The scheduler is working fine; it's explaining itself.
The scheduler's message counts the reasons per node. 3 fail the affinity and 1 fails the taint, so the pod needs the toleration.

9. Priority and preemption, briefly

A PriorityClass gives pods a priority. When a high-priority pod can't fit, the scheduler may preempt (evict) lower-priority pods to make room.

AKS system components use the built-in system-cluster-critical and system-node-critical classes. Most apps don't need custom priorities.

11. The AKS system pool taint

On AKS you'll often taint the system node pool with CriticalAddonsOnly=true:NoSchedule. AKS system add-ons tolerate it; your apps don't, so they go to user pools.

You'll configure this in Chapter 4, and again in Terraform and Bicep in Chapters 12–13.

Steering pods, sorted

  • nodeSelector for simple must-haves; node affinity for operators and required vs preferred.
  • Taints repel; a toleration only allows. For dedicated nodes, use a taint plus affinity.
  • Pod (anti-)affinity places pods relative to pods; topology spread balances across zones.
  • FailedScheduling events count the reasons per node; read them.
