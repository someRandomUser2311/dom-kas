Autoscaling & disruption

You'll be able to configure a HorizontalPodAutoscaler, calculate what it will do, explain how it works with the cluster autoscaler, and protect availability during maintenance with a PodDisruptionBudget.

1. Three kinds of scaling

  • Horizontal Pod Autoscaler (HPA): more or fewer pods, from metrics.
  • Cluster autoscaler: more or fewer nodes, when pods can't fit or nodes sit empty.
  • Vertical Pod Autoscaler (VPA): bigger or smaller requests per pod (mostly used for recommendations).

HPA and the cluster autoscaler work as a pair. HPA adds pods; if they're Pending for lack of room, the cluster autoscaler adds nodes.

Windows/IIS admin
Like VM Scale Set autoscale rules, but for app instances, and reacting in seconds rather than minutes.
Linux admin
Think of a control loop that adjusts the replica count from averaged metrics, with hysteresis built in.
Developer (Compose)
Compose has no autoscaling; you'd run --scale by hand.
Other clouds
HPA is the same on EKS and GKE. The cluster autoscaler is built into AKS; on EKS you might know Karpenter. AKS has a Karpenter-based option too, called Node Auto Provisioning (Chapter 4).

2. An HPA for orders-api

Use autoscaling/v2. This HPA keeps average CPU around 70% of the requested CPU, with between 2 and 10 replicas.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: orders-api
  namespace: orders
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: orders-api
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

Which field sets the target percentage?

        target:
          type: Utilization
          ?: 70
  • averageUtilization
  • targetCPUUtilizationPercentage That's the old autoscaling/v1 field.
  • averageValue averageValue is an absolute amount (e.g. 500m), used with type: AverageValue.
  • threshold Not an HPA field.
averageUtilization is a percentage of each pod's request.

3. The formula

Every 15 seconds the HPA computes:

desired = ceil( currentReplicas × currentMetric / target )

Example: 3 replicas averaging 140% CPU against a 70% target gives ceil(3 × 140 / 70) = 6.

Then it limits the result to min and max. It also ignores changes within 10%, and by default waits 5 minutes before scaling down, so it doesn't flap.

A load slider (requests per second) drives average CPU per pod. The widget shows the formula filled in with live numbers, the desired replicas (clamped to min/max), and pods appearing over time. A toggle removes CPU requests, and the HPA shows <unknown>/70% and does nothing.

4. No requests, no scaling

The HPA above shows TARGETS: <unknown>/70% and never scales. The Deployment's containers have a memory limit but no CPU request. Why?

  1. metrics-server is too slow Possible in general, but here the cause is in the spec.
  2. CPU utilisation is a percentage of the CPU request; with no request, there's nothing to compute a percentage of
  3. The HPA needs autoscaling/v1 v2 is the current API.
  4. minReplicas is too high That limits scaling down, not the metric.
Set CPU requests on every container in the pod (sidecars too), and check that metrics-server is running.

5. Other metrics

CPU is a poor fit for some apps. HPA v2 can also scale on:

  • memory;
  • custom metrics per pod, such as requests per second;
  • external metrics, such as queue length.

On AKS, the KEDA add-on is the easy way to scale on Azure Service Bus queue depth and many other sources, and it can even scale to zero.

6. The cluster autoscaler

When pods are Pending because no node has room, the cluster autoscaler adds nodes to that node pool, within the pool's min and max. When nodes stay underused and their pods can move elsewhere, it removes them.

New nodes take a few minutes to arrive, so HPA scale-ups can briefly show Pending pods. AKS configuration (per-pool min/max, profiles, Node Auto Provisioning) is in Chapter 4.

7. Voluntary disruptions

Pods also disappear on purpose:

  • node upgrades;
  • the cluster autoscaler removing a node;
  • kubectl drain for maintenance.

These are voluntary disruptions: they go through the eviction API, which respects a PodDisruptionBudget (PDB).

A PDB says how many pods must stay available (minAvailable) or may be down at once (maxUnavailable). An eviction that would break the budget is refused, and the drain waits.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: orders-api
  namespace: orders
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: orders-api

8. A PDB that blocks everything

A Deployment has 2 replicas and a PDB with minAvailable: 2. AKS starts a node upgrade and drains the node running one of them. What happens?

  1. The pod is evicted and recreated elsewhere Evicting it would leave 1 available, below the minimum of 2.
  2. The eviction is refused; the drain retries and the upgrade stalls on that node
  3. The PDB is ignored during upgrades Upgrades use the eviction API and respect PDBs, at least until a timeout.
  4. The Deployment scales to 3 first PDBs don't create pods.
A budget equal to the replica count allows zero disruptions. Use maxUnavailable: 1, or minAvailable lower than replicas, and run at least 2 replicas. AKS upgrades fail with a PDB-related error if a drain can't finish.

9. PDBs don't stop everything

Involuntary disruptions ignore PDBs:

  • a node crashing
  • an out-of-memory eviction
  • a zone outage

That's what replicas, topology spread and zones are for. A PDB only makes planned work careful.

When the HPA manages replicas, remove replicas from the Deployment YAML (or ignore it in your tooling). Otherwise every kubectl apply resets the count the HPA chose.

Autoscaling, sorted

  • HPA (pods) + cluster autoscaler (nodes); use autoscaling/v2.
  • desired = ceil(current × metric / target), clamped to min/max, with a scale-down delay.
  • CPU utilisation needs CPU requests; KEDA scales on queues and events.
  • PDBs protect against voluntary disruptions (drains, upgrades), never crashes.
  • Never set a PDB that allows zero disruptions.
