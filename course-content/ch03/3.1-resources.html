Requests, limits & QoS

You'll be able to set CPU and memory requests and limits, predict what happens when a container exceeds them, and read a pod's QoS class.

1. Two numbers per resource

Each container can declare, for CPU and memory:

  • request: what it needs. The scheduler uses this to choose a node with that much free.
  • limit: the most it may use. The kubelet and the kernel enforce it on the node.

CPU is measured in cores: 250m is a quarter of a core. Memory is measured in bytes: 256Mi is 256 mebibytes.

resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    memory: 512Mi
Windows/IIS admin
Like IIS app-pool CPU and private-memory limits, plus a reservation the load balancer respects when it places the site.
Linux admin
Requests feed the scheduler and cgroup CPU weights; limits become cgroup cpu.max and memory.max.
Developer (Compose)
Like deploy.resources.reservations and limits in Compose. Here, reservations really decide placement.
Other clouds
Same as ECS task CPU/memory, except at container level and with separate request and limit.

2. Requests decide placement

Each node has allocatable CPU and memory: its capacity minus what the OS and Kubernetes reserve.

The scheduler adds up the requests of the pods already on a node, not their actual use. It only places a new pod where its request still fits.

If no node fits, the pod stays Pending with Insufficient cpu or Insufficient memory.

Three node bars (each 3.8 CPU / 12 GiB allocatable) filling as the learner adds pods with chosen requests. When a pod can't fit anywhere, it's shown as Pending, with the event 0/3 nodes are available: 3 Insufficient cpu. A second toggle shows actual usage as a lighter bar, which is often far below the requests.

3. Limits: CPU throttles, memory kills

The two resources behave very differently at the limit:

  • CPU is compressible. A container at its CPU limit is throttled: it gets slower, but keeps running.
  • Memory is not compressible. A container that goes over its memory limit is killed by the kernel (OOMKilled, exit code 137), then restarted.

Common guidance: always set a memory limit, usually equal to or a bit above the request. Many teams don't set a CPU limit, so idle CPU on the node can be used. Throttling under a tight CPU limit causes latency spikes.

4. Diagnose: what happened?

The pod restarts every few minutes. What's the cause?

$ kubectl describe pod orders-api-7d9c5f6b8-z5t2n -n orders
    State:          Running
      Started:      Tue, 03 Nov 2026 10:42:07
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137
    Restart Count:  6
    Limits:
      memory:  128Mi
    Requests:
      cpu:     250m
      memory:  128Mi
  1. The CPU limit is too low There's no CPU limit, and CPU overuse throttles rather than kills.
  2. The app needs more than its 128Mi memory limit and is killed when it exceeds it
  3. The node is out of memory That would show an eviction, not OOMKilled with the container's own limit.
  4. A liveness probe is failing A probe kill shows as an event ("Liveness probe failed") and a different reason.
Measure real usage (kubectl top pod, Container Insights), then raise the memory request and limit, or fix a leak. Restarts alone won't fix it.

5. Limits don't reserve anything

A limit is a ceiling, not a reservation. The node only guarantees the request.

If many pods have limits much higher than their requests, the node is overcommitted. When they all get busy together, the node runs out of memory and the kubelet evicts pods. It evicts the ones using the most above their requests first.

6. Quality of Service classes

From its requests and limits, every pod gets a QoS class. It decides who is evicted first under memory pressure:

  • Guaranteed: every container has CPU and memory requests equal to its limits. Evicted last.
  • Burstable: at least one request or limit is set, but it isn't Guaranteed.
  • BestEffort: no requests or limits at all. Evicted first.

  2. Burstable Requests equal limits for both CPU and memory, which makes it Guaranteed.

Guaranteed requires requests = limits for both CPU and memory in every container. Check with kubectl get pod -o jsonpath='{.status.qosClass}'.

7. Choosing numbers

  1. Start from measured usage under realistic load (kubectl top, Azure Monitor).
  2. Request around the typical usage; set the memory limit at the peak plus headroom.
  3. Revisit after real traffic. The Vertical Pod Autoscaler can recommend values in recommendation-only mode.

Requests that are too high waste money: nodes look full while sitting idle. Requests that are too low cause noisy neighbours and evictions.

8. Namespace defaults and quotas

  • LimitRange: default requests and limits for containers that don't set any, plus minimums and maximums.
  • ResourceQuota: a cap on the total requests and limits (and object counts) in a namespace.

Chapter 8 uses both to share a cluster between teams.

kubectl top needs metrics-server, which AKS installs by default. The node shows requests at 75% even though actual use is far lower. Scheduling works from requests.

10. Changing resources

Changing resources in a Deployment is a template change, so it rolls out new pods.

Kubernetes also supports in-place pod resize (GA since 1.35), which adjusts a running pod's resources without recreating it. That's useful for one-off fixes; Deployments still roll out normally.

Resources, sorted

  • Requests decide placement; limits cap usage.
  • Over the CPU limit you're throttled; over the memory limit you're OOMKilled (exit 137).
  • Always set a memory limit; be careful with CPU limits.
  • QoS: Guaranteed (requests = limits) > Burstable > BestEffort in eviction order.
  • Size from measurements; namespaces can enforce defaults and quotas.
