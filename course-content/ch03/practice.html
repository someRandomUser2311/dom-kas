Write lab: harden the orders-api Deployment

Brief: Start from the Chapter 2 Deployment. Make it production-ready and add an HPA and a PDB. The app exposes /healthz (process) and /readyz (ready to serve), plus /health/db. Graded by manifest-lint and cross-ref.

  • CPU and memory requests are set on every container.
  • A memory limit is set on every container.
  • A readiness probe exists.
  • A liveness probe exists.
  • The liveness probe doesn't depend on the database (not /health/db, and no command that connects to the DB).
  • topologySpreadConstraints on topology.kubernetes.io/zone with maxSkew: 1, selecting the pod's own labels.
  • An autoscaling/v2 HPA targets the Deployment with minReplicas: 2 and maxReplicas: 10.
  • A PDB selects the same pods and allows at least one disruption.
  • The Deployment doesn't hard-code replicas above the HPA's max.
Reference solution (Deployment pod spec excerpt, HPA, PDB) 
    spec:
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels: { app: orders-api }
      containers:
        - name: api
          image: contosoacr.azurecr.io/orders-api:1.4.2
          ports:
            - { name: http, containerPort: 8080 }
          resources:
            requests: { cpu: 250m, memory: 256Mi }
            limits:   { memory: 512Mi }
          startupProbe:
            httpGet: { path: /healthz, port: http }
            periodSeconds: 5
            failureThreshold: 24
          readinessProbe:
            httpGet: { path: /readyz, port: http }
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /healthz, port: http }
            periodSeconds: 10
            timeoutSeconds: 2
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: orders-api, namespace: orders }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: orders-api }
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: orders-api, namespace: orders }
spec:
  maxUnavailable: 1
  selector:
    matchLabels: { app: orders-api }

Walkthrough: scale up under load, then drain a node

  1. Start load: kubectl get hpa -w shows CPU climbing and replicas going from 2 to 6.
  2. Two pods are Pending with "Insufficient cpu"; the cluster autoscaler adds a node, and they schedule.
  3. Stop the load; after ~5 minutes the HPA scales down.
  4. kubectl drain <node> --ignore-daemonsets --delete-emptydir-data: evictions respect the PDB, one pod at a time.
  5. kubectl uncordon <node>.
