Jobs, CronJobs & DaemonSets

You'll be able to run work that finishes, run it on a schedule, run one agent per node, and pick the right controller for any workload.

1. Not everything is a web server

Deployments keep pods running forever. Contoso also has work that should finish:

  • a database migration on every release;
  • a nightly report;
  • a log agent that must run on every node.

Each has its own controller.

Windows/IIS admin
A Job ≈ a script run once; a CronJob ≈ a Task Scheduler task; a DaemonSet ≈ an agent installed on every server by Group Policy.
Linux admin
A CronJob is cron, but cluster-wide and highly available. A DaemonSet is what you'd otherwise install with a configuration management tool on every host.
Developer (Compose)
A Job ≈ docker compose run --rm migrate.
Other clouds
Like AWS Batch or EventBridge-scheduled tasks, but in-cluster.

2. A Job runs to completion

A Job creates pods until the requested number have succeeded. Key fields:

  • backoffLimit: retries before the Job is marked failed (default 6).
  • activeDeadlineSeconds: an overall time limit.
  • ttlSecondsAfterFinished: delete the finished Job (and its pods) automatically.
  • The pod's restartPolicy must be OnFailure or Never.
apiVersion: batch/v1
kind: Job
metadata:
  name: orders-db-migrate-1-5-0
  namespace: orders
spec:
  backoffLimit: 2
  activeDeadlineSeconds: 600
  ttlSecondsAfterFinished: 3600
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: contosoacr.azurecr.io/orders-api:1.5.0
          args: ["migrate", "--up"]

A Job's pod template can't be changed after creation. That's why the name includes the version: each release runs a new Job. For parallel work, use completions and parallelism, or indexed Jobs.

3. A CronJob runs Jobs on a schedule

A CronJob creates a Job from its jobTemplate on a cron schedule: minute, hour, day of month, month, day of week. Set timeZone explicitly; otherwise it uses the controller's time zone, which is UTC on AKS.

concurrencyPolicy decides what happens if the previous run is still going:

  • Allow: run both.
  • Forbid: skip the new run.
  • Replace: stop the old run.
apiVersion: batch/v1
kind: CronJob
metadata:
  name: daily-sales-report
  namespace: orders
spec:
  schedule: "30 2 * * *"
  timeZone: Europe/Amsterdam
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 1
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: report
              image: contosoacr.azurecr.io/orders-report:1.2.0

Tap the line that makes this run at 02:30 every day.

30 2 * * * = minute 30, hour 2, every day, every month, every weekday, in the timeZone given.

4. A DaemonSet: one pod per node

A DaemonSet runs one copy of a pod on every node, or on every node matching a nodeSelector or affinity. When a node joins, it gets a pod; when it leaves, the pod goes.

Typical uses: log and metrics agents, security agents, storage and network drivers. AKS runs several itself: kube-proxy or Cilium, the CSI drivers, and the Azure Monitor agent if enabled.

DaemonSets often need tolerations so they also run on tainted nodes, such as the system pool and GPU nodes.

5. Jobs and Helm hooks

Release-time Jobs, such as migrations, are often run by the deploy tooling: a Helm pre-upgrade hook (Chapter 10), or a pipeline step that runs the Job and waits for completion (kubectl wait --for=condition=complete job/…) before rolling out the app.

6. Pick the controller

Match each workload to its controller.

orders-api, a stateless web APIDeployment
A 3-node queue cluster, each with its own diskStatefulSet
A log shipper on every nodeDaemonSet
A one-off schema migrationJob
The nightly sales reportCronJob
Forever and interchangeable → Deployment; forever with identity → StatefulSet; one per node → DaemonSet; finishes → Job; finishes on a schedule → CronJob.

7. Watching a Job

$ kubectl get jobs -n orders
NAME                       STATUS     COMPLETIONS   DURATION   AGE
orders-db-migrate-1-5-0    Complete   1/1           24s        2m
$ kubectl logs job/orders-db-migrate-1-5-0 -n orders
applied 2 migrations: 0041_add_shipping_method, 0042_index_orders_created_at

Workload controllers, sorted

  • Job: run to completion; backoffLimit, deadlines, TTL clean-up.
  • CronJob: Jobs on a schedule; set timeZone and concurrencyPolicy.
  • DaemonSet: one pod per (matching) node; add tolerations for tainted nodes.
  • Deployment for stateless, StatefulSet for identity and disks.
