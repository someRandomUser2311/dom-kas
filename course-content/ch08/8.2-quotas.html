Quotas & limit ranges

You'll be able to cap a namespace's total resource use, give containers sensible defaults, and fix the two errors these produce.

1. Fair sharing

Namespaces share nodes. Without limits, one team's runaway deployment, or a bad HPA, can claim the whole cluster.

Two objects fix this:

  • ResourceQuota: a budget for the whole namespace.
  • LimitRange: per-container defaults and bounds.
Windows/IIS admin
Like disk quotas on a shared file server, plus default sizes for new folders.
Linux admin
Like cgroup slices per team, plus defaults applied to every new process.
Developer (Compose)
Your manifests now need resources set, or the defaults decide for you.
Other clouds
The same objects on EKS and GKE; GKE Autopilot fills in defaults much like a LimitRange.

2. A ResourceQuota

A quota caps the sum of requests and limits, plus object counts, across all pods and objects in the namespace. A new object that would push the total over the cap is rejected when it's created.

apiVersion: v1
kind: ResourceQuota
metadata:
  name: orders-budget
  namespace: orders
spec:
  hard:
    requests.cpu: "8"
    requests.memory: 16Gi
    limits.memory: 32Gi
    pods: "40"
    services.loadbalancers: "0"
    persistentvolumeclaims: "5"

services.loadbalancers: "0" stops this team from creating public LoadBalancer Services. Traffic must come through the shared gateway (lesson 8.4).

3. The catch: requests become mandatory

Once a quota limits requests.cpu or requests.memory, every new pod must declare that request. Otherwise Kubernetes can't count it against the budget, and rejects it.

That's the most common surprise after a platform team adds quotas.

4. A LimitRange fills in defaults

A LimitRange adds a default request and limit to containers that don't set one, and can enforce a minimum and maximum. With both in place, a pod without resources gets defaults and is admitted.

Which field gives containers a default request?

apiVersion: v1
kind: LimitRange
metadata:
  name: orders-defaults
  namespace: orders
spec:
  limits:
    - type: Container
      ?:
        cpu: 100m
        memory: 128Mi
      default:
        memory: 256Mi
      max:
        memory: 2Gi
  • defaultRequest
  • default default sets the default limit; it's already used below.
  • requests Not a LimitRange field.
  • min min rejects smaller values; it doesn't fill anything in.
defaultRequest → default requests; default → default limits; min/max → bounds.

5. Diagnose two rejections

After the platform team added a quota, two Deployments stopped creating pods. Match the error to the fix: what's wrong in the first one?

$ kubectl describe rs orders-worker-5d9c8 -n orders | tail -2
  Warning  FailedCreate  replicaset-controller  Error creating: pods "orders-worker-5d9c8-7qk2n" is forbidden:
           failed quota: orders-budget: must specify requests.cpu for: worker; requests.memory for: worker

$ kubectl describe rs orders-api-6b7f9 -n orders | tail -2
  Warning  FailedCreate  replicaset-controller  Error creating: pods "orders-api-6b7f9-x8m2c" is forbidden:
           exceeded quota: orders-budget, requested: requests.cpu=500m, used: requests.cpu=7800m, limited: requests.cpu=8
  1. orders-worker has no CPU or memory requests: add them, or add a LimitRange with defaults
  2. orders-worker exceeded the CPU budget That's the second message.
  3. The quota is invalid The quota works; it's doing exactly its job.
  4. The nodes are full Node capacity gives a scheduling error (Pending), not a quota rejection at creation.
"must specify" = missing requests; "exceeded quota" = the namespace's budget is used up (lower the requests, scale something down, or ask for a bigger quota). Both show on the ReplicaSet, not the Deployment or a pod, because no pod was created. A common first-debug trap.

7. Quotas and autoscaling

An HPA can't scale past the quota. New pods are rejected, and the HPA shows replicas it can't reach.

Size quotas for max replicas plus a rollout's maxSurge, not for normal load. Otherwise a rollout at peak time can stall.

8. The namespace template

  • ResourceQuota and LimitRange

Quotas, sorted

  • ResourceQuota caps a namespace's total requests, limits and object counts.
  • With compute quotas, pods must set requests; a LimitRange supplies defaults.
  • "must specify" = add requests; "exceeded quota" = over budget. Look at ReplicaSet events.
  • Size quotas for max replicas plus surge.
