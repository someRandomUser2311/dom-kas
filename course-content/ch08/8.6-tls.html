TLS

You'll be able to decide where HTTPS is terminated, automate certificates with cert-manager or Key Vault, redirect HTTP to HTTPS, and recognise the fake-certificate symptom.

1. Where does HTTPS end?

Traffic from the browser is HTTPS. Somewhere it gets decrypted, or terminated:

  • At the gateway (the usual choice): one certificate per hostname, managed centrally; plain HTTP inside the cluster.
  • At the gateway, then re-encrypted to the pods: needed when policy says "encrypted everywhere". A service mesh with mTLS does this automatically.
  • Passthrough to the pod: the gateway doesn't decrypt at all, so there's no path routing.
Windows/IIS admin
Like SSL offloading on the load balancer instead of binding certificates in IIS on every server.
Linux admin
Like terminating TLS in an nginx front end and proxying HTTP to the app servers.
Developer (Compose)
Your app listens on plain HTTP 8080; the gateway handles certificates.
Other clouds
Similar to ACM on an ALB, or Google-managed certificates on GKE Ingress.

2. Certificates as Secrets

Gateways and Ingresses read certificates from a Secret of type kubernetes.io/tls, containing tls.crt and tls.key.

The private key must never be committed to Git. If it leaks, anyone can impersonate the site until the certificate is revoked. Certificates should be created and renewed by automation, not pasted in by hand.

3. The TLS block

Tap the line where the Gateway learns which certificate to present.

listeners:
  - name: http
    protocol: HTTP
    port: 80
  - name: https
    protocol: HTTPS
    port: 443
    hostname: "shop.contoso.example"
    tls:
      mode: Terminate
      certificateRefs:
        - kind: Secret
          name: shop-contoso-tls
certificateRefs points at the kubernetes.io/tls Secret (in an Ingress, the equivalent is tls.secretName).

4. cert-manager and ACME

cert-manager is the standard Kubernetes tool for certificates. You declare an Issuer (for example Let's Encrypt via ACME, or your internal CA) and a Certificate. cert-manager then obtains the certificate, writes the TLS Secret, and renews it before it expires.

With the Gateway API, an annotation on the Gateway is enough: cert-manager creates certificates for its listeners automatically.

apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: platform@contoso.example
    privateKeySecretRef: { name: letsencrypt-account }
    solvers:
      - http01:
          gatewayHTTPRoute:
            parentRefs:
              - { name: shop-gateway, namespace: gateway-infra, kind: Gateway }
metadata:
  name: shop-gateway
  namespace: gateway-infra
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt

5. Key Vault certificates

Many enterprises already manage certificates in Azure Key Vault, with renewal from their CA. Two common ways to use them:

  • The application routing add-on reads a Key Vault certificate directly. Annotate the Ingress with kubernetes.azure.com/tls-cert-keyvault-uri, and the add-on keeps the Secret in sync.
  • The Key Vault Secrets Store CSI driver can sync a certificate into a TLS Secret for any controller (Chapter 15).

Either way, the key never sits in Git.

6. Redirect HTTP to HTTPS

Keep an HTTP listener only to redirect. With the Gateway API, that's a standard filter, with no annotations needed.

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: https-redirect
  namespace: gateway-infra
spec:
  parentRefs:
    - { name: shop-gateway, sectionName: http }
  rules:
    - filters:
        - type: RequestRedirect
          requestRedirect:
            scheme: https
            statusCode: 301

7. Diagnose the browser warning

Browsers warn "Your connection is not private" for https://shop.contoso.example. You inspect the certificate:

$ curl -vk https://shop.contoso.example 2>&1 | grep -E "subject|issuer"
*  subject: O=Acme Co; CN=Kubernetes Ingress Controller Fake Certificate
*  issuer: O=Acme Co; CN=Kubernetes Ingress Controller Fake Certificate
$ kubectl get secret shop-contoso-tls -n orders
Error from server (NotFound): secrets "shop-contoso-tls" not found
  1. The browser is out of date The server is presenting a placeholder certificate.
  2. The TLS Secret the Ingress references doesn't exist (not issued yet, wrong name, or wrong namespace), so the NGINX controller falls back to its default fake certificate
  3. Port 443 is blocked The connection succeeded and returned a certificate.
  4. The Service has no endpoints That causes 503s after the TLS handshake, not a fake certificate.
Check that the Secret exists in the same namespace as the Ingress, then check cert-manager's Certificate status (kubectl describe certificate). With Let's Encrypt, a failing HTTP-01 challenge is the usual reason.

8. Checking a certificate

$ kubectl get certificate -n gateway-infra
NAME                READY   SECRET              AGE
shop-contoso-tls    True    shop-contoso-tls    12d
$ echo | openssl s_client -connect shop.contoso.example:443 -servername shop.contoso.example 2>/dev/null | openssl x509 -noout -dates -subject
notBefore=Oct 25 09:12:03 2026 GMT
notAfter=Jan 23 09:12:02 2027 GMT
subject=CN=shop.contoso.example

9. Good TLS habits

  • Automate issuance and renewal; alert on certificates expiring within 14 days (Chapter 14).
  • Never commit keys, and keep TLS Secrets readable only by the gateway and platform team.
  • Use HTTP only for redirects; consider HSTS once you're confident.
  • Internal services: a private CA through cert-manager, or a mesh with mTLS.

TLS, sorted

  • Terminate at the gateway (re-encrypt or use a mesh if policy requires).
  • Certificates live in kubernetes.io/tls Secrets, referenced by certificateRefs or tls.secretName.
  • cert-manager (ACME or a private CA), or Key Vault certificates, never keys in Git.
  • Redirect HTTP → HTTPS with a RequestRedirect filter.
  • A "Fake Certificate" means the Secret is missing or in the wrong place.
