Ingress

You'll be able to route HTTP traffic for several apps through one entry point using host and path rules, and know why an Ingress does nothing without a controller.

1. One front door

Lesson 5.2 ended with a problem: one public LoadBalancer per HTTP service means many IPs, many certificates and no shared routing.

Instead, run one HTTP proxy behind one load balancer, and let it route requests by host and path to ordinary ClusterIP Services:

  • shop.contoso.example/ → web
  • shop.contoso.example/api → orders-api
Windows/IIS admin
Like IIS ARR or URL Rewrite in front of several back-end sites: host headers and paths decide where requests go.
Linux admin
It's an nginx or HAProxy reverse proxy whose config is generated from Kubernetes objects.
Developer (Compose)
Like putting Traefik or nginx in front of your Compose services, with routing labels.
Other clouds
Like the AWS Load Balancer Controller creating an ALB from an Ingress, or GKE Ingress creating a Google HTTP(S) load balancer.

2. Ingress vs ingress controller

  • An Ingress is just a Kubernetes object: a list of routing rules.
  • An ingress controller is software running in (or next to) the cluster that reads those objects and actually proxies the traffic.

A cluster can have several controllers. Each one owns an IngressClass, and every Ingress names the one it's for with ingressClassName.

No controller, or the wrong class name, means the Ingress is accepted and nothing happens.

3. A first Ingress

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  namespace: orders
spec:
  ingressClassName: webapprouting.kubernetes.azure.com
  rules:
    - host: shop.contoso.example
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: orders-api
                port:
                  number: 80

webapprouting.kubernetes.azure.com is the class of AKS's application routing add-on (lesson 8.5). Other controllers have their own class names.

4. Path types

  • Exact: only that exact path. /api matches /api, not /api/orders.
  • Prefix: matches by path segments. /api matches /api and /api/orders, but not /apiary.
  • ImplementationSpecific: up to the controller. Avoid it.

When several rules match, the longest path wins, and Exact beats Prefix for the same path.

A URL bar and the current Ingress rules. Typing a URL (e.g. https://shop.contoso.example/api/orders/42) highlights the matching rule, the Service and the pod it would reach, or shows "default backend / 404". The rules are editable, so learners can test shadowing and path types.

5. Route the shop

In the router widget, make /api (and everything under it) go to orders-api:80, and everything else on shop.contoso.example go to web:80.

Success when these test URLs route correctly:
  • / → web
  • /products/7 → web
  • /api → orders-api
  • /api/orders/42 → orders-api
  • /apiary → web
Solution 
rules:
  - host: shop.contoso.example
    http:
      paths:
        - path: /api
          pathType: Prefix
          backend: { service: { name: orders-api, port: { number: 80 } } }
        - path: /
          pathType: Prefix
          backend: { service: { name: web, port: { number: 80 } } }
Longest-prefix matching means order in the file doesn't matter here. / as a Prefix is the catch-all.

6. The rule that doesn't do what you think

Users report every page except the home page returns 404. Tap the cause.

rules:
  - host: shop.contoso.example
    http:
      paths:
        - path: /api
          pathType: Prefix
          backend: { service: { name: orders-api, port: { number: 80 } } }
        - path: /
          pathType: Exact
          backend: { service: { name: web, port: { number: 80 } } }
Exact on / only matches the bare home page. /products/7 matches nothing and gets a 404. Use Prefix for a catch-all.

7. Host-based routing

Several rules with different host values let one entry point serve many sites. Point every DNS name at the controller's single IP.

rules:
  - host: shop.contoso.example
    http: { paths: [ { path: /, pathType: Prefix, backend: { service: { name: web, port: { number: 80 } } } } ] }
  - host: api.contoso.example
    http: { paths: [ { path: /, pathType: Prefix, backend: { service: { name: orders-api, port: { number: 80 } } } } ] }

8. TLS in an Ingress

A tls block names the hosts and the Secret of type kubernetes.io/tls that holds the certificate. The controller terminates HTTPS and forwards plain HTTP to the Services. Lesson 8.6 covers where certificates come from.

tls:
  - hosts: [shop.contoso.example]
    secretName: shop-contoso-tls

9. Annotations are controller-specific

The Ingress spec is small: hosts, paths, TLS. Everything else, such as redirects, rewrites, timeouts, body size and auth, is done with annotations that only one controller understands (for example nginx.ingress.kubernetes.io/proxy-body-size).

That makes Ingress manifests hard to move between controllers. It's the main reason the Gateway API was created (next lesson).

10. One Ingress per namespace

An Ingress can only send traffic to Services in its own namespace. To route / to web (namespace web) and /api to orders-api (namespace orders), create one Ingress in each namespace with the same host. Most controllers merge them.

With many teams sharing a hostname, it gets fiddly. The Gateway API's role split handles it better.

11. Checking an Ingress

$ kubectl get ingress -n orders
NAME   CLASS                                HOSTS                  ADDRESS        PORTS     AGE
shop   webapprouting.kubernetes.azure.com   shop.contoso.example   20.50.40.11    80, 443   5m
$ curl -s -o /dev/null -w "%{http_code}\n" -H "Host: shop.contoso.example" http://20.50.40.11/api/healthz
200

An empty ADDRESS usually means no controller has claimed the Ingress: check ingressClassName.

Ingress, sorted

  • One controller and one IP route HTTP by host and path to ClusterIP Services.
  • The Ingress object is only rules; a controller (named by ingressClassName) does the work.
  • Prefix matches by path segments; the longest match wins; Exact is exact.
  • A TLS block references a kubernetes.io/tls Secret.
  • Annotations aren't portable; same-namespace backends only.
