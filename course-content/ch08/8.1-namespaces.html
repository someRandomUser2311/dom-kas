Namespaces as boundaries

You'll be able to explain exactly what a namespace isolates and what it doesn't, choose a namespace strategy, and tell namespaced objects from cluster-wide ones.

1. More teams, one cluster

Contoso's cluster now runs three things:

  • orders-api and its worker;
  • the web frontend;
  • a new payments team's services.

Everyone deploying into default would be chaos: name clashes, everybody able to change everything, and no way to see who uses what.

Namespaces divide one cluster into named sections.

Windows/IIS admin
Like separate IIS sites or OUs: separate names and permissions, but still on the same servers.
Linux admin
Careful: not Linux namespaces. A Kubernetes namespace is an API grouping, not kernel isolation.
Developer (Compose)
Like separate Compose projects: same names can repeat in each.
Other clouds
Same Kubernetes concept everywhere. In Azure terms it's closer to a resource group inside the cluster than to a subscription.

2. What a namespace isolates

  • Names: orders-api can exist in both orders-dev and orders-prod.
  • Access: RBAC roles can be granted per namespace (lesson 5.5).
  • Resource budgets: quotas and limit ranges apply per namespace (next lesson).
  • Policies: NetworkPolicies (Chapter 9) and Pod Security levels (Chapter 15) are set per namespace.
  • Cleanup: deleting a namespace deletes everything in it.

3. What it doesn't isolate

  • Nodes: pods from all namespaces share the same nodes, kernel and CPU, unless you steer them (Chapter 3).
  • Network: by default, any pod can reach any pod in any namespace. Namespaces are not a network boundary until you add NetworkPolicies.
  • Cluster-wide objects: CRDs, nodes, StorageClasses and ClusterRoles affect everyone.
  • The control plane: one noisy namespace can still load the shared API server.

Contoso runs dev and prod in the same cluster, separated only by namespaces orders-dev and orders-prod. What's still shared?

  1. Nothing; namespaces fully isolate them They isolate names and API access, not compute or network.
  2. Nodes, the network (pods can reach each other), the control plane and cluster-wide objects
  3. Only the names Names are exactly what is not shared.
  4. Only RBAC RBAC can be separated per namespace.
A dev load test can starve prod pods, and a compromised dev pod can call prod Services. That's why Contoso runs separate clusters for prod.

4. Namespaced vs cluster-scoped

Some kinds live inside a namespace, others are cluster-wide. kubectl api-resources --namespaced=true (or false) lists them.

Match each object to its scope.

DeploymentNamespaced
NodeCluster-scoped
ConfigMapNamespaced
StorageClassCluster-scoped
ClusterRoleCluster-scoped
PersistentVolumeClaimNamespaced (its PV is cluster-scoped)
Cluster-scoped objects need more care: only platform admins should change them.

5. Strategies

StrategyExampleGood for
Per teamteam-orders, team-paymentsClear ownership and quotas
Per apporders, web, paymentsFine-grained policies per app
Per app and environmentorders-dev, orders-testSeveral non-prod environments in one shared cluster

Contoso uses per app namespaces (orders, web, payments), with dev and prod in separate clusters. The same manifests then work in both, with only the cluster changing.

6. A namespace manifest

Create namespaces from YAML, with labels. Policies, Pod Security levels and cost reports select on them.

apiVersion: v1
kind: Namespace
metadata:
  name: orders
  labels:
    team: orders
    pod-security.kubernetes.io/enforce: restricted
    kubernetes.io/metadata.name: orders   # added automatically

7. Reserved namespaces

  • kube-system: system add-ons. Never deploy apps here.
  • kube-public and kube-node-lease: internal.
  • default: where objects go if you don't say. Leave it empty in real clusters.
  • AKS add-ons create their own, such as app-routing-system and gatekeeper-system.

8. Cross-namespace references

Most references must stay in the same namespace:

  • a pod can't mount a Secret or ConfigMap from another namespace;
  • a Service only selects pods in its own namespace.

Network calls cross namespaces freely through DNS (lesson 2.5). The Gateway API has an explicit mechanism, ReferenceGrant, for the few allowed cross-namespace references (lesson 8.4).

9. Who creates namespaces?

Namespaces are cluster-scoped, so creating one needs a cluster-level permission.

Contoso's platform team creates them, with labels, quotas, limit ranges, default NetworkPolicies and RBAC bindings, all from one template. App pipelines only deploy into them. They don't create them.

10. Deleting a namespace

kubectl delete namespace orders deletes everything in it, including PVCs and therefore disks with the Delete reclaim policy (lesson 3.4).

A namespace stuck in Terminating usually has an object with a finalizer that can't complete. Investigate with kubectl get all,pvc -n orders and the namespace's status conditions.

Namespaces, sorted

  • Isolate names, access, quotas and policies, and allow bulk cleanup.
  • Don't isolate nodes, network (without policies), cluster-scoped objects or the control plane.
  • Contoso: per-app namespaces; separate clusters for dev and prod.
  • The platform team creates namespaces from a template; pipelines deploy into them.
