The Gateway API

You'll be able to write GatewayClass, Gateway and HTTPRoute resources, explain who owns each one, and debug a route that won't attach.

1. Why a new API?

Ingress has three problems:

  • It's a single object mixing infrastructure and app concerns.
  • Every interesting feature is a non-portable annotation.
  • Sharing one entry point between teams is awkward.

The Gateway API (gateway.networking.k8s.io) is the newer standard. Its features, such as header matching, traffic splitting and redirects, are in the spec, so they behave the same across implementations. And it's split into resources owned by different roles.

New platforms should start here.

Windows/IIS admin
Think of the network team owning the load balancer and its listeners, while each app team adds its own URL rewrite rules, without touching each other's config.
Linux admin
It's like nginx's main config owned by ops, with conf.d/ snippets owned by app teams, but with permissions enforced.
Developer (Compose)
You'll mostly write HTTPRoutes: "send /api to my Service".
Other clouds
EKS (VPC Lattice / AWS LB controller) and GKE (GKE Gateway controller) implement the same API.

2. Three resources, three roles

ResourceOwned bySays
GatewayClassInfrastructure provider (the controller / Azure)"This type of load balancer exists" (like a StorageClass)
GatewayCluster operator / platform team"Listen on HTTPS 443 for *.contoso.example, with this certificate, and allow routes from these namespaces"
HTTPRouteApp developer"For host shop.contoso.example, path /api, send traffic to my Service"

RBAC can follow this split: app teams may create HTTPRoutes in their namespace, but not Gateways.

3. The Gateway

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: shop-gateway
  namespace: gateway-infra
spec:
  gatewayClassName: azure-alb-external      # Application Gateway for Containers
  listeners:
    - name: https
      protocol: HTTPS
      port: 443
      hostname: "*.contoso.example"
      tls:
        mode: Terminate
        certificateRefs:
          - kind: Secret
            name: wildcard-contoso-tls
      allowedRoutes:
        namespaces:
          from: Selector
          selector:
            matchLabels:
              shop-routes: "allowed"

The Gateway lives in a platform namespace. allowedRoutes decides which namespaces may attach routes to it.

4. An HTTPRoute

The app team writes a route in its own namespace:

  • parentRefs names the Gateway (and, optionally, the listener) to attach to.
  • hostnames and matches select requests.
  • backendRefs name Services and ports.

Attach the route to shop-gateway in gateway-infra.

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: orders-api
  namespace: orders
spec:
  ?:
    - name: shop-gateway
      namespace: gateway-infra
      sectionName: https
  hostnames: ["shop.contoso.example"]
  rules:
    - matches:
        - path: { type: PathPrefix, value: /api }
      backendRefs:
        - name: orders-api
          port: 80
  • parentRefs
  • gatewayRef Not a field; routes attach through parentRefs.
  • backendRefs Those point to Services, not to the Gateway.
  • ingressClassName That's Ingress, not the Gateway API.
"Parent" because a route attaches to a parent (a Gateway, or a Service for mesh traffic). sectionName picks a specific listener.

5. Route the shop with two routes

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: web
  namespace: web
spec:
  parentRefs:
    - { name: shop-gateway, namespace: gateway-infra, sectionName: https }
  hostnames: ["shop.contoso.example"]
  rules:
    - matches:
        - path: { type: PathPrefix, value: / }
      backendRefs:
        - { name: web, port: 80 }
The router from lesson 8.3, now driven by the Gateway and two HTTPRoutes from different namespaces. Requests to /api/… match the orders route (longest path prefix), and everything else matches the web route. A status panel shows each route as Accepted or not.

6. Why isn't my route attached?

The orders team's HTTPRoute shows this status. The namespace orders has no labels except the defaults. Why?

status:
  parents:
    - parentRef: { name: shop-gateway, namespace: gateway-infra }
      conditions:
        - type: Accepted
          status: "False"
          reason: NotAllowedByListeners
  1. The Service orders-api doesn't exist That gives ResolvedRefs: False, not NotAllowedByListeners.
  2. The Gateway's allowedRoutes only accepts namespaces labelled shop-routes: allowed
  3. HTTPRoutes must be in the Gateway's namespace Cross-namespace attachment is allowed when the Gateway permits it.
  4. The hostname is wrong A hostname mismatch gives a different reason (NoMatchingListenerHostname).
The platform team labels the namespace (kubectl label ns orders shop-routes=allowed, done in the namespace template). The default for allowedRoutes is from: Same, meaning routes only from the Gateway's own namespace.

7. Matching more than paths

rules:
  - matches:
      - path: { type: PathPrefix, value: /api }
        headers:
          - name: x-canary
            value: "true"
    backendRefs:
      - { name: orders-api-canary, port: 80 }
  - matches:
      - path: { type: PathPrefix, value: /api }
        method: GET
    backendRefs:
      - { name: orders-api, port: 80 }

Headers, query parameters and methods are first-class matches, with no annotations needed. Filters add redirects, header changes, URL rewrites and request mirroring.

8. Weighted backends

backendRefs can carry weights, and traffic is split in proportion to them. This is how Chapter 11 does canary releases.

backendRefs:
  - { name: orders-api-stable, port: 80, weight: 90 }
  - { name: orders-api-canary, port: 80, weight: 10 }
A weights slider (0–100) between stable and canary; sending 100 test requests shows the split as a bar.

9. Cross-namespace backends: ReferenceGrant

An HTTPRoute may point at a Service in another namespace only if that namespace allows it, with a ReferenceGrant. The owner of the target has to agree, so one team can't route traffic into another's Services uninvited.

The same applies to a Gateway's certificateRefs pointing at a Secret in another namespace.

apiVersion: gateway.networking.k8s.io/v1beta1
kind: ReferenceGrant
metadata:
  name: allow-web-routes
  namespace: orders          # the namespace being referenced
spec:
  from:
    - group: gateway.networking.k8s.io
      kind: HTTPRoute
      namespace: web
  to:
    - group: ""
      kind: Service
      name: orders-api

11. Status tells you everything

$ kubectl get gateway -n gateway-infra
NAME           CLASS                ADDRESS                               PROGRAMMED   AGE
shop-gateway   azure-alb-external   a1b2c3d4.fz12.alb.azure.com          True         2d
$ kubectl get httproute -A
NAMESPACE   NAME         HOSTNAMES                  AGE
orders      orders-api   ["shop.contoso.example"]   1h
web         web          ["shop.contoso.example"]   1h
$ kubectl describe httproute orders-api -n orders | grep -A3 Conditions
    Conditions:
      Type: Accepted        Status: True
      Type: ResolvedRefs    Status: True

Accepted = attached to the Gateway; ResolvedRefs = all backends exist and are allowed. Both must be True.

12. Versions

GatewayClass, Gateway, HTTPRoute and GRPCRoute are v1 (GA). ReferenceGrant is v1beta1. The Gateway API CRDs are installed by your implementation, or by the AKS add-on, not by Kubernetes itself. Keep their version in step with the controller.

Gateway API, sorted

  • GatewayClass (provider) → Gateway (platform) → HTTPRoute (app team).
  • Routes attach with parentRefs; Gateways allow them with allowedRoutes.
  • Matches, filters and weighted backendRefs are in the spec, not in annotations.
  • ReferenceGrant permits cross-namespace references.
  • Check route status: Accepted + ResolvedRefs.
