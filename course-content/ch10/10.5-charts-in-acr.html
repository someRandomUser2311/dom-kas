Charts in ACR (OCI)

You'll be able to package a chart, push it to ACR as an OCI artifact, install it from there, and version charts separately from apps.

1. Why publish a chart?

Installing from a folder in Git works for one repo. When other teams, or other pipelines, use the chart, publish a versioned package.

Helm charts can be stored as OCI artifacts in any OCI registry, including ACR, right beside the images.

Windows/IIS admin
Like publishing an MSI to an internal software repository instead of copying it from a share.
Linux admin
Like pushing a package to your internal repository.
Developer (Compose)
Same registry, same login: oci:// URLs instead of image names.
Other clouds
ECR and Artifact Registry store Helm OCI charts the same way.

2. Package and push

helm package charts/orders-api                     # → orders-api-0.3.0.tgz
TOKEN=$(az acr login -n contosoacr --expose-token --query accessToken -o tsv)
helm registry login contosoacr.azurecr.io \
  --username 00000000-0000-0000-0000-000000000000 --password "$TOKEN"
helm push orders-api-0.3.0.tgz oci://contosoacr.azurecr.io/helm

The chart lands in repository helm/orders-api with tag 0.3.0, the chart version. The pushing identity needs AcrPush (or repository Writer).

Push the packaged chart orders-api-0.3.0.tgz to the helm namespace of contosoacr.

helm push orders-api-0.3.0.tgz oci://contosoacr.azurecr.io/helm

Only the oci:// form is accepted; the chart name and version come from the package.

Don't include the chart name in the destination; Helm appends it.

3. Install from the registry

helm upgrade --install orders-api oci://contosoacr.azurecr.io/helm/orders-api \
  --version 0.3.0 -n orders -f values-prod.yaml --set image.tag=1.4.2 --atomic --wait
helm show values oci://contosoacr.azurecr.io/helm/orders-api --version 0.3.0

4. Two versions: chart and app

  • version: the chart's version. Bump it whenever templates or default values change.
  • appVersion: the app version the chart deploys by default. Informational, and used as the default tag in our template.

Most releases change only the image tag, passed as a value, not the chart. Version the chart only when the chart itself changes.

You add a PodDisruptionBudget template to the chart. The app is still 1.4.2. What changes?

  1. Only appVersion, to 1.4.3 The app didn't change.
  2. The chart version (e.g. 0.3.0 → 0.4.0); appVersion stays
  3. Nothing; templates aren't versioned Templates are the chart, so they're exactly what's versioned.
  4. Both must always change together They're independent.
Chart versions follow semantic versioning of the chart's interface (its values and templates). Pushed chart versions should be immutable.

5. Immutability and provenance

  • Never re-push the same chart version with different content. Lock it in ACR, as you would image tags.
  • Pin chart versions in deployments (--version 0.3.0); never install "latest".
  • Charts can be signed like images (Chapter 16).

6. Dependencies

A chart can depend on other charts, declared in Chart.yaml dependencies: with OCI or HTTP repositories. helm dependency update downloads them into charts/, and Chart.lock pins the exact versions. Commit the lock file.

7. Public charts through your registry

Third-party charts, such as cert-manager or Kyverno, can be imported into ACR (az acr import, or helm pull then helm push). Clusters then only pull from your registry. That works with private endpoints and supports the allowed-registries policy in Chapter 16.

Charts in ACR, sorted

  • helm package → helm push … oci://contosoacr.azurecr.io/helm.
  • Install with oci://…/orders-api --version x.y.z.
  • Chart version ≠ appVersion; bump the chart only when the chart changes.
  • Immutable, pinned versions; mirror third-party charts into ACR.
