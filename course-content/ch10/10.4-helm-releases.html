Releases: install, upgrade, rollback

You'll be able to install and upgrade a chart safely in one idempotent command, roll back a bad release, and get out of a stuck release.

1. A release

Installing a chart creates a release: a named instance of the chart in a namespace, such as orders-api in orders. Every install, upgrade or rollback adds a numbered revision.

Helm stores each revision (rendered manifests and values) as a Secret in that namespace.

Windows/IIS admin
Like an installed program with version history and "restore previous version".
Linux admin
Like a package's install history, with a downgrade command that actually works.
Developer (Compose)
Compose has no history; Helm remembers what each deploy looked like.
Other clouds
The same on any cluster.

2. One command for install and upgrade

helm upgrade --install installs the release if it's missing and upgrades it if it exists. It's idempotent, so the pipeline can always run the same command. Add the safety flags:

  • --wait: wait until resources are ready (Deployments rolled out).
  • --atomic: if the upgrade fails or times out, roll back automatically. Helm 4 renames it --rollback-on-failure; --atomic remains as an alias.
  • --timeout 5m: how long to wait.

Install or upgrade release orders-api from charts/orders-api into namespace orders with values-prod.yaml, waiting for readiness and rolling back automatically on failure.

helm upgrade --install orders-api charts/orders-api -n orders -f values-prod.yaml --atomic --wait --timeout 5m

Also accepted: --rollback-on-failure instead of --atomic; --namespace; --values; any timeout; --create-namespace; flags in any order. --atomic (or --rollback-on-failure) is required.

This is the safe default for pipelines. A failed rollout leaves the previous revision running, and the pipeline step fails.

3. History and rollback

$ helm history orders-api -n orders
REVISION  UPDATED                   STATUS      CHART             APP VERSION  DESCRIPTION
1         Mon Nov  2 09:10:11 2026  superseded  orders-api-0.3.0  1.4.1        Install complete
2         Tue Nov  3 14:22:40 2026  superseded  orders-api-0.3.0  1.4.2        Upgrade complete
3         Wed Nov  4 10:05:02 2026  deployed    orders-api-0.3.1  1.5.0        Upgrade complete
$ helm rollback orders-api 2 -n orders
Rollback was a success! Happy Helming!

A rollback creates a new revision (4) with revision 2's manifests. As with kubectl rollout undo, fix the source too, or the next pipeline run re-deploys the bad version.

4. Values per environment

The pipeline passes the environment's values file and the image tag:

  • dev: -f values-dev.yaml --set image.tag=$(Build.BuildId)
  • prod: -f values-prod.yaml --set image.tag=$(Build.BuildId)

The same chart version and image go to both; only the values differ.

5. No secrets in values

Values files live in Git, and Helm stores every revision's values in the cluster. A password in values ends up in both places.

Reference secrets instead: a SecretProviderClass for Key Vault (Chapter 15), or an existing Secret's name. Never the value itself. --set password=… from a pipeline variable still lands in Helm's release Secret.

6. Stuck releases

The pipeline fails immediately on every run since yesterday. Why?

$ helm upgrade --install orders-api charts/orders-api -n orders -f values-prod.yaml --atomic --wait
Error: UPGRADE FAILED: another operation (install/upgrade/rollback) is in progress
$ helm history orders-api -n orders | tail -2
3         Wed Nov  4 10:05:02 2026  deployed         orders-api-0.3.1  1.5.0   Upgrade complete
4         Thu Nov  5 16:41:19 2026  pending-upgrade  orders-api-0.3.2  1.5.1   Preparing upgrade
  1. Two pipelines are running right now Possible, but the pending revision is from yesterday: nothing is actually running.
  2. A previous upgrade was interrupted (e.g. the agent was cancelled) and left revision 4 in pending-upgrade, which locks the release
  3. The chart version is invalid That gives a different error.
  4. The namespace is full Quota errors look different.
Recover with helm rollback orders-api 3 -n orders, which completes the release from the last good revision. Prevent it with pipeline concurrency limits (one deploy per environment at a time) and generous timeouts.

7. Upgrades that change immutable fields

If a chart change alters a Deployment's selector (an immutable field), the upgrade fails. That's why selectorLabels must never change between chart versions (lesson 10.3). Helm's --force recreates objects, which means downtime. Avoid it.

8. Hooks

Annotate a Job with helm.sh/hook: pre-upgrade to run it before each upgrade, for example the database migration from lesson 3.6. If the hook fails, the upgrade fails, and --atomic rolls back.

9. Seeing what's deployed

helm list -n orders
helm get values orders-api -n orders          # values in effect
helm get manifest orders-api -n orders        # exact YAML applied
helm diff upgrade orders-api charts/orders-api -n orders -f values-prod.yaml   # with the helm-diff plugin

Releases, sorted

  • Release = named install; every change is a revision stored in the namespace.
  • helm upgrade --install --atomic --wait --timeout (--rollback-on-failure in Helm 4).
  • helm history / rollback; fix the source too.
  • No secrets in values; recover stuck releases with a rollback; keep selectors stable.
