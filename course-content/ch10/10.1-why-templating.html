Why templating?

You'll be able to explain why copied YAML per environment goes wrong, and when to reach for Kustomize, Helm, or both.

1. The copy-paste trap

Contoso's first approach: k8s/dev/ and k8s/prod/, two full copies of every manifest. Within a month:

  • someone added a readiness probe in dev and forgot prod;
  • prod's memory limit was raised during an incident and never written back to dev;
  • nobody can say which differences are intentional.

The fix: keep one description of the app, plus a small, explicit list of differences per environment.

Windows/IIS admin
Same problem as hand-edited web.config on each server, solved the way config transforms did: one base, small per-environment changes.
Linux admin
Like Ansible roles with per-group variables instead of copied playbooks.
Developer (Compose)
Like docker-compose.yml plus docker-compose.prod.yml overrides. Kustomize is that idea for Kubernetes.
Other clouds
Kustomize and Helm are the same tools on every Kubernetes platform.

3. When each fits

Contoso wants to deploy its own app to dev and prod with a few differences, keep plain YAML that reviewers can read, and avoid learning a template language. Which tool fits best?

  1. Kustomize
  2. Helm It works, but templating is more than this needs, and the files stop being plain YAML.
  3. Copy-paste per environment That's the problem we're solving.
  4. sed in the pipeline Fragile, and invisible in reviews.
Kustomize suits your own apps with modest per-environment differences. Helm shines for distributing configurable software, such as third-party apps, or a platform team's chart used by many teams.

4. You'll use both

In practice most teams use both:

  • Helm to install third-party software, such as cert-manager, Kyverno and monitoring agents, from their official charts.
  • Kustomize for their own apps.

Kustomize can even render a Helm chart and patch the result (helmCharts:), so they're not either/or.

5. Feature → tool

Match each feature to the tool known for it.

helm rollback to a previous revisionHelm
images: to set a tag without editing YAMLKustomize
Versioned packages pushed to a registryHelm (charts as OCI artifacts)
Works with kubectl aloneKustomize
Loops and conditionals in manifestsHelm
Pick by need, not fashion.

6. What should differ between environments?

Keep the list short and deliberate:

  • replicas and HPA bounds;
  • resource requests and limits;
  • namespace or cluster;
  • hostnames;
  • config values such as log level and URLs;
  • the image tag, set by the pipeline.

Probes, security settings and policies should be identical. A difference there is how prod surprises you.

7. Build once, deploy many

Whatever the tool, the image is built once, by CI, and the same image (same digest) is promoted from dev to prod. Only configuration changes per environment.

Rebuilding per environment means prod runs something that was never tested. Lesson 10.6 enforces this in the pipeline.

Templating, sorted

  • Copied YAML drifts; keep one base plus explicit differences.
  • Kustomize = plain YAML + patches; Helm = templates + values + releases.
  • Kustomize for your apps, Helm for distributed software; combine freely.
  • Same image everywhere; only config differs.
