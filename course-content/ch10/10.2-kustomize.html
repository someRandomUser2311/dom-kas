Kustomize base & overlays

You'll be able to build a Kustomize base and per-environment overlays that set the namespace, replicas, image tag and resource patches, and preview exactly what will be applied.

1. The layout

k8s/
├─ base/
│  ├─ kustomization.yaml
│  ├─ deployment.yaml
│  ├─ service.yaml
│  ├─ hpa.yaml
│  ├─ pdb.yaml
│  └─ default-deny.yaml
└─ overlays/
   ├─ dev/
   │  └─ kustomization.yaml
   └─ prod/
      ├─ kustomization.yaml
      └─ resources-patch.yaml

The base is the app as plain YAML: everything from Chapters 2, 3 and 9. Each overlay points at the base and lists only what's different.

Windows/IIS admin
The base is web.config; overlays are web.Release.config transforms, but declarative and per environment.
Linux admin
Like a base config file plus conf.d drop-ins that override specific keys.
Developer (Compose)
Same as docker compose -f base.yml -f prod.yml merging, but for Kubernetes objects.
Other clouds
Identical everywhere; Kustomize is built into kubectl.

2. The base kustomization

apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yaml
  - service.yaml
  - hpa.yaml
  - pdb.yaml
  - default-deny.yaml
labels:
  - pairs:
      app.kubernetes.io/part-of: contoso-orders

Use labels: (newer) rather than the deprecated commonLabels:. By default labels doesn't touch selectors, which avoids accidentally changing an immutable Deployment selector.

3. A dev overlay

apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: orders
resources:
  - ../../base
replicas:
  - name: orders-api
    count: 1
images:
  - name: contosoacr.azurecr.io/orders-api
    newTag: "1.4.2"
  • namespace: set on every object.
  • replicas: change the count without a patch.
  • images: replace the tag (or name, or digest) of every container using that image. The pipeline sets it (lesson 10.6).

4. Preview before applying

kubectl kustomize (or kustomize build) prints the fully rendered YAML. Review it, diff it against the cluster with kubectl diff -k, and then apply it.

kubectl kustomize k8s/overlays/dev | less
kubectl diff -k k8s/overlays/dev
kubectl apply -k k8s/overlays/dev
Three panes: the base files (read-only), the overlay's kustomization.yaml and patches (editable), and the rendered output with changed lines highlighted against the base. A target spec can be shown for checks.

5. Patches

For anything without a dedicated field, use patches:. A strategic merge patch is a partial copy of the object: only the fields you change, matched by name. Lists of containers merge by container name.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
spec:
  template:
    spec:
      containers:
        - name: api
          resources:
            requests: { cpu: 500m, memory: 512Mi }
            limits:   { memory: 1Gi }

6. JSON 6902 patches for precision

For one exact change, such as removing a field or editing a list item by index, use a JSON patch with op and path.

patches:
  - target:
      kind: HorizontalPodAutoscaler
      name: orders-api
    patch: |-
      - op: replace
        path: /spec/maxReplicas
        value: 20

7. The prod overlay

apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: orders
resources:
  - ../../base
replicas:
  - name: orders-api
    count: 4
images:
  - name: contosoacr.azurecr.io/orders-api
    newTag: "1.4.2"
patches:
  - path: resources-patch.yaml
  - target: { kind: HorizontalPodAutoscaler, name: orders-api }
    patch: |-
      - op: replace
        path: /spec/maxReplicas
        value: 20

Which line decides the version of orders-api that prod runs?

The images entry's newTag. The base's tag is overridden here, and the pipeline updates it with kustomize edit set image, never by editing deployment.yaml.

8. Make prod right

In the kustomize-lite widget, edit the prod overlay so the rendered Deployment has 4 replicas and image contosoacr.azurecr.io/orders-api:1.4.2, in namespace orders.

Success when the rendered output's Deployment has replicas: 4, the container image ends in :1.4.2, and the namespace is orders, without editing the base.
Use the replicas, images and namespace fields; no patch is needed for these three.

9. Replicas vs the HPA

If an HPA manages the Deployment, setting replicas only affects the first apply. Then the HPA takes over (lesson 3.5). For HPA-managed apps, patch minReplicas/maxReplicas instead, as the prod overlay does for max.

10. ConfigMap generators

configMapGenerator creates a ConfigMap with a content hash in its name (orders-api-config-7k2m9h), and rewrites references to it. Change a value and the name changes, so the Deployment's template changes, and the pods roll out with the new config automatically.

That solves lesson 2.6's "env vars don't update" problem.

configMapGenerator:
  - name: orders-api-config
    literals:
      - LOG_LEVEL=warn
      - FEATURE_EXPRESS_SHIPPING=true

11. Precedence

Kustomize processes the base, then each transformation in the overlay. When the same field is set in several places, the overlay wins over the base. Between patches in one overlay, they're applied in the order listed, so the last change to a field wins.

When in doubt, render it and look.

12. Secrets and Kustomize

secretGenerator exists, but it reads secret values from files, which must not be in Git. Contoso doesn't use it. Secrets come from Key Vault through the CSI driver (Chapter 15), and the overlay only references the SecretProviderClass.

Kustomize, sorted

  • A base of plain YAML; overlays reference it and list the differences.
  • namespace, replicas, images, labels, plus patches (strategic merge or JSON 6902).
  • Preview with kubectl kustomize and kubectl diff -k; apply with -k.
  • configMapGenerator rolls pods on config change.
