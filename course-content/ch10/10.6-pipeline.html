Chapter 10 · Lesson 10.6 · ~12 steps · ~15 min

In the pipeline

You'll be able to build an image once and promote the same artifact through dev and prod with Kustomize or Helm, using a reusable deploy template.

1. The shape

One pipeline, three stages:

  • Build: test, build and push the image once, tagged with $(Build.BuildId). Record the digest.
  • DeployDev: deploy that exact image with the dev overlay or values.
  • DeployProd: after approval, deploy the same image with the prod overlay or values.

Nothing is rebuilt along the way.

GitHub Actions
Build job outputs the tag; deploy jobs use environment: with protection rules, the same pattern.
GitLab CI
A build stage with artifacts, then deploy jobs with environment: and when: manual for prod.
Jenkins
One pipeline with an input step before prod; pass the image tag between stages.
Classic pipelines
A build pipeline producing an artifact, and a release pipeline with dev and prod stages, now in one YAML file.

2. Kustomize: set the image at deploy time

The overlay in Git holds a placeholder tag. The deploy job sets the real tag with kustomize edit set image (or the bake task), renders, and applies.

parameters:
  - name: environment
    type: string
  - name: overlay
    type: string
  - name: serviceConnection
    type: string
  - name: resourceGroup
    type: string
  - name: cluster
    type: string

jobs:
  - deployment: deploy
    environment: ${{ parameters.environment }}
    strategy:
      runOnce:
        deploy:
          steps:
            - checkout: self
            - task: AzureCLI@2
              displayName: Deploy ${{ parameters.overlay }}
              inputs:
                azureSubscription: ${{ parameters.serviceConnection }}
                scriptType: bash
                scriptLocation: inlineScript
                inlineScript: |
                  set -euo pipefail
                  cd k8s/overlays/${{ parameters.overlay }}
                  kustomize edit set image contosoacr.azurecr.io/orders-api=contosoacr.azurecr.io/orders-api:$(Build.BuildId)
                  az aks get-credentials -g ${{ parameters.resourceGroup }} -n ${{ parameters.cluster }} --overwrite-existing
                  kubelogin convert-kubeconfig -l azurecli
                  kubectl apply -k .
                  kubectl rollout status deploy/orders-api -n orders --timeout=5m

3. Where the tag is injected

In the template above, tap the line that makes this deployment use the image built by this run.

kustomize edit set image … :$(Build.BuildId) rewrites the overlay's images entry in the agent's working copy, not in Git. Every environment gets the same Build ID.

4. Or the KubernetesManifest bake action

KubernetesManifest@1 can render with action: bake (renderType: kustomize or helm), and then deploy the rendered output with action: deploy and the containers input to substitute the image. It's handy if you prefer tasks to scripts.

- task: KubernetesManifest@1
  name: bake
  inputs:
    action: bake
    renderType: kustomize
    kustomizationPath: k8s/overlays/prod
- task: KubernetesManifest@1
  inputs:
    action: deploy
    connectionType: azureResourceManager
    azureSubscriptionConnection: sc-orders-prod
    azureResourceGroup: rg-orders-prod
    kubernetesCluster: aks-orders-prod
    namespace: orders
    manifests: $(bake.manifestsBundle)
    containers: contosoacr.azurecr.io/orders-api:$(Build.BuildId)

5. Helm in the pipeline

With Helm, the deploy step is the safe upgrade from lesson 10.4, using the environment's values file and the run's tag. Use the HelmDeploy task, or helm inside AzureCLI@2 (shown).

helm upgrade --install orders-api oci://contosoacr.azurecr.io/helm/orders-api \
  --version 0.3.0 -n orders \
  -f deploy/values-${{ parameters.environment }}.yaml \
  --set image.tag=$(Build.BuildId) \
  --atomic --wait --timeout 5m

6. The main pipeline

trigger: [main]

stages:
  - stage: Build
    jobs:
      - job: build
        steps:
          - script: go test ./...
          - task: Docker@2
            inputs:
              command: buildAndPush
              containerRegistry: acr-connection
              repository: orders-api
              tags: $(Build.BuildId)

  - stage: DeployDev
    dependsOn: Build
    jobs:
      - template: templates/deploy-kustomize.yml
        parameters: { environment: dev, overlay: dev, serviceConnection: sc-orders-dev, resourceGroup: rg-orders-dev, cluster: aks-orders-dev }

  - stage: DeployProd
    dependsOn: DeployDev
    condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
    jobs:
      - template: templates/deploy-kustomize.yml
        parameters: { environment: prod, overlay: prod, serviceConnection: sc-orders-prod, resourceGroup: rg-orders-prod, cluster: aks-orders-prod }

The prod job targets the prod environment, which has the approval check (Chapter 7). aks-orders-prod is private, so the prod stage runs on the Managed DevOps Pool (Chapter 6). Add pool: { name: mdp-orders-prod } to its job.

7. Put the stages in order

The stage list is scrambled. Arrange it so one artifact moves through dev to prod, with prod gated.

Draggable stage cards:
  • "Build & push image (once)"
  • "Deploy dev (overlay dev, same tag)"
  • "Smoke test dev"
  • "Approval on prod environment"
  • "Deploy prod (overlay prod, same tag)"
  • A decoy, "Rebuild image for prod"
Success when the order is Build → Deploy dev → Smoke test → Approval → Deploy prod, with the rebuild card discarded. The decoy gives the hint "Prod would run an image that dev never tested."
Promote, don't rebuild. The approval is where a human checks dev before the same bits reach prod.

8. Promote by digest for extra safety

A tag could in theory be re-pushed between dev and prod. For certainty, capture the image digest in the Build stage and pass it on as an output variable. Deploy orders-api@sha256:…. Chapter 16 also verifies its signature before prod.

9. Validate in PRs

The PR pipeline (Chapter 7) renders every overlay and lints it. Typos fail the PR, not the deploy:

  • kubectl kustomize k8s/overlays/dev and k8s/overlays/prod;
  • helm lint and helm template;
  • kube-linter or kubeconform on the output.

10. Don't commit the rendered tag back

Some teams commit the new tag into the overlay so Git always says what's deployed. That's the GitOps approach, with Flux or Argo CD pulling from Git.

It's a valid design, but different: the pipeline writes to Git, and a controller in the cluster deploys. This course uses push-based pipelines; the AKS GitOps (Flux) extension is the managed option if you choose pull.

11. Same template, many apps

templates/deploy-kustomize.yml is reusable for web and payments too. With extends and a required-template check (Chapter 7), the platform team can guarantee every app deploys the same safe way.

In the pipeline, sorted

  • Build once; deploy the same tag or digest to every environment.
  • Kustomize: kustomize edit set image + kubectl apply -k (or KubernetesManifest bake).
  • Helm: helm upgrade --install --atomic --wait with per-environment values.
  • A reusable deploy template; prod gated by its environment; PRs render and lint every overlay.
