Walkthrough: template → install → bad upgrade → automatic rollback

  1. helm lint and helm template … -f values-prod.yaml; read the output.
  2. helm upgrade --install … --atomic --wait → revision 1, deployed.
  3. Upgrade with --set image.tag=does-not-exist: pods in ImagePullBackOff, then the timeout, then the automatic rollback to revision 1.
  4. helm history shows revision 2 failed and revision 3 is the rollback.

Try it locally

10.2 Overlays.

cd lab/examples/ch10/k8s
kubectl kustomize overlays/prod | grep -E "replicas|image:|namespace:" | sort -u
kubectl create ns orders; kubectl apply -k overlays/dev
kubectl get deploy -n orders

Expected: prod renders 4 replicas and tag 1.0.0; dev is applied with 1 replica.

Cleanup: kubectl delete ns orders

10.3–10.4 Atomic rollback.

cd lab/examples/ch10
helm upgrade --install oa ./charts/orders-api -n orders --create-namespace --set image.tag=1.0.0 --atomic --wait --timeout 2m
helm upgrade --install oa ./charts/orders-api -n orders --set image.tag=does-not-exist --atomic --wait --timeout 1m
helm history oa -n orders

Expected: the second command fails after ~1 minute and reports a rollback. The history shows deployed, failed, then rolled back.

Cleanup: helm uninstall oa -n orders; kubectl delete ns orders

10.5 Push a chart to the local registry.

cd lab/examples/ch10
helm package charts/orders-api
helm push orders-api-0.1.0.tgz oci://localhost:5001/helm --plain-http
helm show chart oci://localhost:5001/helm/orders-api --version 0.1.0 --plain-http

Expected: Pushed: localhost:5001/helm/orders-api:0.1.0, then the Chart.yaml contents.

Cleanup: rm orders-api-0.1.0.tgz

On ACR: no --plain-http; log in with an Entra ID token.
