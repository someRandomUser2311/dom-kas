Signing & verification

You'll be able to sign images in the pipeline with a Key Vault key, verify signatures before deploy and at admission, and choose between Notation and cosign.

1. What a signature proves

A signature over an image digest proves two things:

  • integrity: the image hasn't changed since it was signed;
  • provenance: it was signed by a key you trust, Contoso's pipeline.

Verification at deploy time turns "anything in the registry can run" into "only images our pipeline vouched for can run".

3. The signing key lives in Key Vault

Create a signing certificate in Key Vault. The private key never leaves the vault: Notation's azure-kv plugin asks Key Vault to sign.

The pipeline identity needs Key Vault Crypto User (to sign) and Key Vault Certificate User on that key, and nothing more.

There's no key material in the repo or the pipeline.

4. Sign in the pipeline

- task: AzureCLI@2
  displayName: Sign image
  inputs:
    azureSubscription: sc-orders-signing          # WIF, Key Vault Crypto User on the signing key
    scriptType: bash
    scriptLocation: inlineScript
    inlineScript: |
      set -euo pipefail
      az acr login -n contosoacr
      notation sign --signature-format cose \
        --id "$(signingKeyId)" --plugin azure-kv \
        contosoacr.azurecr.io/orders-api@$(imageDigest)

The signature is pushed to ACR as a referrer of the image digest (lesson 16.3, step 8).

5. Verify

Verification needs a trust policy: which registries, which trusted certificates (trust store), and what to do on failure.

{
  "version": "1.0",
  "trustPolicies": [{
    "name": "contoso-images",
    "registryScopes": [ "contosoacr.azurecr.io/orders-api" ],
    "signatureVerification": { "level": "strict" },
    "trustStores": [ "ca:contoso-signing" ],
    "trustedIdentities": [ "x509.subject: CN=Contoso Release Signing, O=Contoso" ]
  }]
}
notation verify contosoacr.azurecr.io/orders-api@sha256:3f5a9c0d…

6. The flow

Order the sign-and-verify flow.

  1. The pipeline builds and scans the image
  2. It pushes the image and records the digest
  3. It signs the digest with the Key Vault key (signature stored in ACR)
  4. The deploy stage applies manifests that reference the digest
  5. The admission controller verifies the signature against the trust policy, and admits or denies
The last step is what makes signing worth doing: unsigned or tampered images can't run.

7. Verification at admission

On AKS, verification at admission uses Ratify, a verification engine. Ratify works with Gatekeeper and Azure Policy, which AKS packages as its image integrity feature.

A policy assignment says "images must have a valid Notation signature from this trust store", in audit or deny mode.

Kyverno's verifyImages rules are the common alternative, especially with cosign.

8. Deny mode in action

Image verification runs in deny mode. Someone applies a Deployment with an unsigned image from contosoacr.azurecr.io. What happens?

  1. The pod runs, and an audit event is recorded That's audit mode.
  2. Admission rejects the pod; the ReplicaSet reports FailedCreate with the policy message
  3. The image is signed automatically Nothing signs on your behalf.
  4. The node refuses to pull it Verification happens at admission, before scheduling.
As with Pod Security, roll out in audit first, fix whatever's unsigned (including add-on images, or exclude system namespaces), then switch to deny.

9. Verify in the pipeline too

Add a notation verify step before the prod deploy. It fails fast with a clear message, and covers clusters where admission enforcement isn't on yet.

10. Key management

  • Separate signing keys for dev and release builds; only the release pipeline can use the release key.
  • Rotate certificates before they expire. Old images stay verifiable if the trust store keeps the previous certificate.
  • Monitor the key's use in Key Vault logs: any signing outside the pipeline is an incident.

11. cosign in one minute

cosign generate-key-pair                                  # local lab only
cosign sign --key cosign.key localhost:5001/orders-api@sha256:…
cosign verify --key cosign.pub localhost:5001/orders-api@sha256:…

Signing, sorted

  • Signatures prove integrity and provenance, not safety.
  • Notation + the Key Vault plugin in the pipeline; the key never leaves the vault.
  • Sign the digest after the scan; the signature is stored as an OCI referrer.
  • Verify at admission (Ratify / image integrity, or Kyverno) and in the pipeline; audit, then deny.
