Scanning & SBOM in the pipeline

You'll be able to scan images in the pipeline with a fail policy people can live with, generate an SBOM, and attach it to the image in ACR.

1. Where to scan

  • In the pipeline, after the image is built and before it can be deployed. That's fast feedback, and it blocks bad builds.
  • In the registry, continuously (Defender for Containers): new vulnerabilities found in old images.
  • In the cluster, running images (Defender): what's actually exposed right now.
GitHub Actions
aquasecurity/trivy-action or Microsoft Defender for DevOps; the same fail-threshold thinking.
GitLab CI
GitLab's container scanning template, using Trivy underneath.
Jenkins
A Trivy or Grype stage with a quality gate.
Classic pipelines
The same scanner as a command-line task in the build pipeline.

2. A Trivy scan step

- task: Docker@2
  displayName: Build
  inputs: { command: build, containerRegistry: acr-connection, repository: orders-api, tags: $(Build.BuildId) }
- script: |
    trivy image --exit-code 1 --severity HIGH,CRITICAL --ignore-unfixed \
      --format table contosoacr.azurecr.io/orders-api:$(Build.BuildId)
  displayName: Scan image (fail on fixable HIGH/CRITICAL)
- task: Docker@2
  displayName: Push
  inputs: { command: push, containerRegistry: acr-connection, repository: orders-api, tags: $(Build.BuildId) }

3. The fail policy

Fail the build only for high and critical findings.

trivy image --exit-code 1 ? HIGH,CRITICAL --ignore-unfixed contosoacr.azurecr.io/orders-api:$(Build.BuildId)
  • --severity
  • --level Not a Trivy flag.
  • --fail-on Not Trivy's flag (some other scanners use it).
  • --exit-code Already set; it decides the exit status when findings match.
--ignore-unfixed skips findings with no fix yet. Failing on something nobody can fix only teaches people to disable the scan. Track those separately.

4. Read a scan

The scan step failed. What's the right fix?

contosoacr.azurecr.io/orders-api:20261105.3 (debian 12.7)
Total: 2 (HIGH: 1, CRITICAL: 1)
┌────────────┬────────────────┬──────────┬───────────────────┬───────────────┬─────────────────────────────┐
│  Library   │ Vulnerability  │ Severity │ Installed Version │ Fixed Version │            Title            │
├────────────┼────────────────┼──────────┼───────────────────┼───────────────┼─────────────────────────────┤
│ libssl3    │ CVE-2026-1234  │ CRITICAL │ 3.0.14-1~deb12u1  │ 3.0.15-1~deb12u1 │ openssl: buffer overread │
│ curl       │ CVE-2026-2345  │ HIGH     │ 7.88.1-10+deb12u6 │ 7.88.1-10+deb12u8 │ curl: header injection  │
└────────────┴────────────────┴──────────┴───────────────────┴───────────────┴─────────────────────────────┘
  1. Add both CVEs to an ignore list Fixes exist; ignoring is for unfixable or not-applicable findings, with a reason and an expiry date.
  2. Rebuild on an updated base image, and better, move the runtime stage to distroless, which has no curl or full OpenSSL package at all
  3. Remove the scan step That's how vulnerable images reach prod.
  4. Lower the severity threshold That hides real risk.
Both are OS packages from a Debian-based runtime image. That's a sign the multi-stage distroless pattern isn't in use.

5. Exceptions done right

When a finding doesn't apply (the vulnerable function is never used) or can't be fixed yet, record it in .trivyignore with the CVE, a reason and a review date. Review the list in PRs, like code.

CVE-2026-3456  # stdlib net/http2 issue; orders-api doesn't serve HTTP/2 — review 2026-12-31

6. Scan before or after push?

Two valid orders:

  • build → scan → push → sign: nothing failing ever reaches the registry.
  • build → push → scan → sign: the image is in the registry (e.g. a quarantine repository) but unsigned. Admission policy (16.4) stops unsigned images being deployed.

Either way, sign only after the scan passes, and deploy only signed digests.

Arrange the Build stage steps for Contoso (scan before push).

Draggable step cards: "go test", "docker build", "trivy scan (fail on fixable HIGH/CRITICAL)", "docker push (capture digest)", "generate & attach SBOM", "notation sign digest", plus a decoy "sign before scan". Success: test → build → scan → push → SBOM → sign, with the decoy discarded. Placing push before scan is also accepted if sign is after scan.
The signature means "this passed our checks". It must come last.

7. Generate an SBOM

trivy image --format spdx-json --output sbom.spdx.json contosoacr.azurecr.io/orders-api@$(imageDigest)
# or: syft contosoacr.azurecr.io/orders-api@$(imageDigest) -o spdx-json=sbom.spdx.json

SPDX and CycloneDX are the two common formats. Keep the SBOM with the image, not just as a pipeline artifact that expires.

8. Attach it to the image in ACR

OCI registries support referrers: artifacts linked to an image digest. Attach the SBOM, the signature and the provenance to the image, so they travel with it and can be listed and verified later.

oras attach --artifact-type application/spdx+json \
  contosoacr.azurecr.io/orders-api@$(imageDigest) sbom.spdx.json
oras discover contosoacr.azurecr.io/orders-api@$(imageDigest) -o tree
contosoacr.azurecr.io/orders-api@sha256:3f5a9c0d…
├── application/spdx+json
│   └── sha256:8c1e…
└── application/vnd.cncf.notary.signature
    └── sha256:b77d…

9. Defender for Containers

With the Defender plan on, images in ACR are scanned on push and re-assessed regularly. Running images are mapped to their findings. Results appear as recommendations, and can feed a gate ("block deploy if the image has critical findings").

10. Dependencies, before the image

Scan source dependencies in PRs too: govulncheck for Go, Dependabot alerts, or GitHub Advanced Security for Azure DevOps dependency scanning. Catching a vulnerable module in a PR is cheaper than in an image.

11. Pin the scanner

The scanner is part of your supply chain too. Pin its version or digest, and update its vulnerability database in the job, or mirror it for private agents.

Scanning & SBOM, sorted

  • Scan in the pipeline (block), in the registry and cluster (continuous).
  • --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1; exceptions with reasons and expiry.
  • Sign only after the scan passes; deploy only signed digests.
  • SBOM (SPDX/CycloneDX) attached to the image as an OCI referrer.
