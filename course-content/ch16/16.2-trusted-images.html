Images you can trust

You'll be able to choose minimal base images, pin them by digest, keep them patched automatically, and deploy images by digest.

1. Less in the image, less to attack

A full OS base brings a shell, a package manager and hundreds of packages. Most are never used by the app, but every one can have vulnerabilities, and every tool can help an attacker.

Minimal bases (distroless, Azure Linux distroless, scratch for static binaries, chiseled Ubuntu images for .NET) contain only what the app needs.

2. Multi-stage builds, again

Lesson 1.1's Dockerfile already builds in a full Go image and ships only the binary in distroless. That single change removes most vulnerability findings.

3. Pin by digest

FROM golang:1.23 can point to a different image tomorrow. Pin with a digest (golang:1.23@sha256:…), so builds are reproducible, and a compromised re-push of the tag can't reach you.

One FROM isn't pinned. Tap it.

FROM golang:1.23@sha256:6c5c9590f169f77c8046e45c611d3b28fe477789acd8d3762d23d4744de69812 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/orders-api ./cmd/orders-api

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/orders-api /orders-api
USER nonroot:nonroot
ENTRYPOINT ["/orders-api"]
The runtime base has only a tag. Pin it too, with @sha256:…. Tools such as Dependabot or Renovate keep the pins up to date with PRs.

4. Pinning without going stale

A pinned digest never gets security fixes by itself. Let a bot (Renovate or Dependabot) open a PR whenever the upstream tag moves. The PR pipeline scans the new image, and merging rebuilds and redeploys. That gives you pinned and patched.

5. Rebuild on base updates

ACR Tasks can trigger a rebuild automatically when a base image in ACR is updated. Teams that mirror base images into their own registry (lesson 10.5) get patched images quickly, with the pipeline still scanning before anything is deployed.

6. Deploy by digest

Why should the release pipeline deploy orders-api@sha256:… rather than orders-api:1.4.2?

  1. Digests download faster The bytes are the same.
  2. The digest is exactly what was scanned and signed; a tag could be re-pushed between scan and deploy
  3. AKS can't pull tags It can.
  4. Policies don't work with tags They do, but signature verification resolves to a digest anyway.
Capture the digest at push time (docker push prints it) and pass it to the deploy stages. Lock tags in ACR as a second guard.

7. Only your registry

Mirror every external image you depend on (base images, add-on images, Helm chart images) into ACR (az acr import), scan it there, and have clusters pull only from contosoacr.azurecr.io. Lesson 16.5's policy enforces it.

az acr import -n contosoacr --source gcr.io/distroless/static-debian12:nonroot --image base/distroless-static:nonroot

8. Keep the registry clean

Old images with known vulnerabilities are an attack surface too, if anyone can still deploy them. Purge CI images on a schedule (lesson 6.3), and keep only the releases that are actually deployed.

9. Know what's in it

A Software Bill of Materials (SBOM) lists every package in the image, with its version. When the next big vulnerability lands, you can answer "are we affected?" in minutes. Lesson 16.3 generates one in the pipeline.

Trusted images, sorted

  • Minimal (distroless) runtime bases via multi-stage builds.
  • Pin FROM by digest; bots keep the pins fresh.
  • Rebuild on base updates; mirror external images into ACR.
  • Deploy by digest; purge old images; generate SBOMs.
