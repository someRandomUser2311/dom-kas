The attack surface

You'll be able to name every point where untrusted code can enter Contoso's path from source to cluster, and the type of control for each.

1. Your app is mostly other people's code

orders-api is a few thousand lines of Contoso code. Its image also contains:

  • a base image;
  • dozens of Go modules;
  • CA certificates and libraries.

It was built by a pipeline running on an agent, using tasks and tools downloaded at build time. Every one of those is a way in. That's the software supply chain.

A pipeline drawn as hops: source repo → dependencies → base image → build agent/tasks → registry → deploy → cluster. Clicking a hop shows a real-world-style attack (typosquatted package, compromised base image tag, a poisoned build tool, a re-pushed tag in the registry, a manifest pointing at an attacker's image) and the control for it.
Windows/IIS admin
Like trusting every DLL and MSI you install, plus the build server that made them.
Linux admin
Like trusting your distro's package mirrors, signing keys and build farm. The same model applies to containers.
Developer (Compose)
Every FROM and every go get in your Dockerfile is a trust decision.
Other clouds
The same problem everywhere; only the tool names differ (ECR scanning, Artifact Analysis, Binary Authorization).

3. Match the attack

Match each attack to the hop where it happens.

A typosquatted Go module (github.com/gorila/mux) added to go.modDependencies
FROM node:20 silently starts pointing at an image with a new vulnerabilityBase image
A self-hosted agent kept from a previous job modifies the next buildBuild
Someone with AcrPush re-pushes orders-api:1.4.2 with different contentRegistry
A manifest is changed to use docker.io/evil/orders-apiDeploy
Each needs its own control. No single tool covers the whole chain.

4. Provenance

Provenance is a signed record of how an artifact was built: which source commit, which pipeline, which builder. With it, a deploy can check not only "is this our image?" but "was it built from main by our pipeline?".

5. SLSA in one picture

SLSA (Supply-chain Levels for Software Artifacts) grades build integrity in levels:

  • builds are scripted, and provenance exists;
  • builds run on a hosted build service, which signs the provenance;
  • builds are hardened and isolated from each other.

Contoso aims for: pipeline-only builds, ephemeral agents, signed images, and provenance stored as an OCI referrer. That's roughly the middle level.

6. Scanning isn't a one-time thing

New vulnerabilities are published every day for code that was fine yesterday. Scan at build time, and continuously in the registry and the cluster (Defender for Containers). Rebuild regularly so fixes in the base image actually reach production.

7. Signing isn't a safety certificate

A signature proves who built the image and that it wasn't changed. It says nothing about whether the code is safe. A signed image can still have vulnerabilities. You need both scanning and signing.

8. Contoso's target pipeline

test → build image → scan (fail on fixable HIGH/CRITICAL) → push → SBOM attach
     → sign (Key Vault key) → deploy by digest → admission verifies signature + policies

Attack surface, sorted

  • Dependencies, base images, build, registry, deploy: each is a way in.
  • Controls: pin and scan, minimal bases, ephemeral builds, locked tags and signing, admission policy.
  • Provenance and SLSA describe how much you can trust a build.
  • Scanning is continuous; signing proves origin, not safety.
