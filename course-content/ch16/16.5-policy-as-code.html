Policy-as-code

You'll be able to enforce cluster-wide rules (allowed registries, no :latest, limits required, no privileged containers) with Azure Policy or Kyverno, roll them out safely, and run the same checks in CI.

1. Admission control

Every create or update passes through admission controllers before it's stored. Policy engines plug in as admission webhooks, and can:

  • validate: allow or deny, with a reason;
  • mutate: add defaults, such as labels or a securityContext.

Writing these rules as files in Git is policy-as-code.

Windows/IIS admin
Like Group Policy plus AppLocker for the cluster: rules applied centrally, whatever people try to deploy.
Linux admin
Like an approval hook on every config change, with rules in code.
Developer (Compose)
Your manifest may be rejected with a clear message; the same rules run in CI, so you find out earlier.
Other clouds
Gatekeeper and Kyverno run on any cluster; Azure Policy is the Azure-managed way to distribute Gatekeeper rules.

2. Azure Policy for AKS

The Azure Policy add-on installs Gatekeeper (OPA) in the cluster and syncs policy assignments from Azure. Use built-in policies and initiatives, such as:

  • "Kubernetes cluster containers should only use allowed images";
  • "… should not run privileged containers";
  • "… CPU and memory resource limits should not exceed …";
  • the Pod Security baseline and restricted initiatives.

Each assignment has an effect: audit or deny. Compliance shows in Azure Policy, next to every other Azure resource.

az aks enable-addons -g rg-orders-prod -n aks-orders-prod -a azure-policy
az policy assignment create --name aks-allowed-images --scope "$AKS_ID" \
  --policy "<built-in: allowed images>" \
  --params '{"allowedContainerImagesRegex":{"value":"^contosoacr\\.azurecr\\.io/.+$"},"effect":{"value":"deny"}}'

3. Kyverno

Kyverno is a Kubernetes-native policy engine. Policies are plain YAML resources, and it can validate, mutate, generate resources and verify image signatures.

Teams often find it easier to read and write than Rego. You install and run it yourself (Helm); it isn't an AKS-managed add-on.

4. Write an allowed-registries rule

Write a Kyverno ClusterPolicy that denies any Pod whose containers (and init containers) use images outside contosoacr.azurecr.io/.

A YAML editor for the policy, plus six sample pods it's evaluated against:
  • orders-api from contosoacr: admit
  • nginx from docker.io: deny
  • an init container from quay.io: deny
  • contosoacr.azurecr.io.evil.com/x: deny
  • a pod in kube-system: excluded
  • an ephemeral debug container from contosoacr: admit
Success when every expectation matches.
Solution 
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: allowed-registries
spec:
  validationFailureAction: Enforce
  background: true
  rules:
    - name: only-contosoacr
      match:
        any:
          - resources:
              kinds: [Pod]
      exclude:
        any:
          - resources:
              namespaces: [kube-system]
      validate:
        message: "Images must come from contosoacr.azurecr.io/"
        pattern:
          spec:
            =(initContainers):
              - image: "contosoacr.azurecr.io/*"
            =(ephemeralContainers):
              - image: "contosoacr.azurecr.io/*"
            containers:
              - image: "contosoacr.azurecr.io/*"
Note the trailing /. A prefix without it would allow contosoacr.azurecr.io.evil.com. =(field) means "if present".

6. Audit, then deny

Contoso is adding the "probes required" rule to a cluster with 40 existing apps. What's the safest rollout?

  1. Deny immediately everywhere The next deploy of any non-compliant app fails, often during an incident fix.
  2. Audit in all environments, publish the violation report, fix the apps, then deny in dev, then in prod
  3. Never enforce, only audit Audit alone doesn't stop new violations.
  4. Enforce only in prod Developers then discover rules for the first time in prod.
Same pattern as Pod Security (warn/audit → enforce). Communicate dates, and give teams the CI check (step 8) first.

7. Mutation: fix it for them

Some rules are better as mutations. Kyverno can add seccompProfile: RuntimeDefault or a default label if missing. Use mutation for safe defaults, and validation for things the team must decide (resources, image source).

8. Shift left: the same rules in CI

Run the policies against rendered manifests in the PR pipeline. Developers see the violation in their PR, not at deploy time.

kubectl kustomize k8s/overlays/prod > rendered.yaml
kyverno apply k8s/policies/cluster/ --resource rendered.yaml --policy-report
# or for Gatekeeper constraints: gator test, or conftest with Rego

9. Policy exceptions

Sometimes a workload legitimately needs an exception, such as a monitoring agent needing hostPath. Use the engine's exception mechanism (Kyverno PolicyException, or exclusions in the Azure Policy assignment), scoped to that workload, with an owner and a review date. Never weaken the rule itself.

10. Policy for Azure resources too

Azure Policy also governs the Azure side:

  • clusters must have local accounts disabled;
  • registries must not allow public access;
  • Defender must be on.

Assigned at the management group, these rules catch IaC mistakes in every subscription.

11. See it decide

The policy-rules widget with Contoso's baseline set applied to a bundle of six manifests. Each shows admit or deny, with the exact messages; editing a manifest re-evaluates live.

Policy-as-code, sorted

  • Admission policies validate and mutate every object.
  • Azure Policy add-on (Gatekeeper, managed via Azure) or Kyverno (YAML policies, signature checks).
  • Baseline: allowed registries, no latest, resources, no privileged, probes, signed images.
  • Audit → fix → deny; the same rules in CI; scoped, owned exceptions.
