How pods get IPs: CNI options

You'll be able to pick an AKS network model, size the subnets and ranges it needs, and avoid running out of IP addresses.

1. Every pod needs an IP

Kubernetes requires every pod to have its own IP, reachable from every other pod without NAT. A CNI plugin (Container Network Interface) makes that happen. It hands out IPs and wires up routes whenever a pod starts.

On AKS the plugin choice decides where pod IPs come from, and that drives your whole IP plan.

Windows/IIS admin
Think of DHCP scopes: the question is whether pods get addresses from the same scope as servers (VNet) or from a private scope behind each server (overlay).
Linux admin
Overlay means pod traffic is routed or encapsulated between nodes; VNet-routed means pods are first-class IPs in the subnet, like secondary IPs on a NIC.
Developer (Compose)
Compose's bridge network is an overlay on one host. Overlay on AKS is the same idea across many hosts.
Other clouds
VNet-routed pod IPs ≈ the default Amazon VPC CNI on EKS. Overlay ≈ EKS custom networking, or GKE's VPC-native setup with secondary ranges.

2. Azure CNI Overlay (recommended default)

  • Nodes get IPs from your VNet subnet.
  • Pods get IPs from a separate private pod CIDR (e.g. 192.168.0.0/16) that isn't part of the VNet.

Each node gets a block of that range. Traffic leaving the cluster is SNATed to the node's IP, so VNet resources and the internet see the node.

Why it's the default choice:

  • the subnet only needs room for nodes;
  • up to 250 pods per node;
  • the same pod CIDR can be reused in every cluster.
--network-plugin azure --network-plugin-mode overlay --pod-cidr 192.168.0.0/16

3. Azure CNI with VNet-routed pod IPs

Here, pods get real IPs from the VNet. Anything in the VNet, or connected networks, can reach a pod directly by its IP without NAT. Some network appliances and on-premises integrations need that.

The price is IP addresses: the subnet must hold every node and every pod. There are two flavours:

  • Classic: pod IPs pre-allocated per node from the node subnet.
  • Dynamic IP allocation: a separate pod subnet (--pod-subnet-id), allocated as needed.

4. Do the IP maths

IP-planning mode, built on the lesson 0.3 calculator. Inputs:
  • plugin (Overlay or VNet-routed)
  • node count and max surge
  • max pods per node
  • node subnet size
Output: addresses needed versus available (after Azure's 5 reserved), with a red "exhausted" state and the error you'd see. Overlay counts nodes only; VNet-routed counts nodes × (1 + max pods).

Using classic VNet-routed pod IPs, a cluster has 50 nodes with 30 max pods each, in a /24 subnet. What happens?

  1. It fits comfortably 50 × (30 + 1) = 1,550 addresses are needed; a /24 has 251.
  2. It runs out of IPs long before 50 nodes: node and pod IPs both come from the 251 usable addresses
  3. Pods share node IPs, so only 50 are needed That's how overlay looks from outside; VNet-routed pods each take a VNet IP.
  4. Azure automatically expands the subnet Subnets never grow on their own.
With overlay, the same cluster needs only ~50 subnet IPs, plus surge nodes during upgrades. IP exhaustion shows up as nodes failing to scale or pods stuck in ContainerCreating with IP allocation errors.

5. Don't forget surge and growth

Size the node subnet for the maximum node count across all pools (autoscaler max), plus surge nodes during upgrades (lesson 4.4), plus room for growth.

For overlay, a /22 (1,019 usable) node subnet supports a large cluster with plenty of headroom. That's the size Contoso planned in lesson 0.3.

6. Three ranges that must never overlap

  • VNet / node subnet: e.g. 10.20.0.0/22.
  • Pod CIDR (overlay): e.g. 192.168.0.0/16. It must not overlap the VNet or anything the cluster talks to.
  • Service CIDR: e.g. 172.16.0.0/16, with --dns-service-ip inside it (e.g. 172.16.0.10). It's virtual and only exists inside the cluster.

Overlaps with on-premises or peered networks cause confusing routing failures. Plan them all together, once.

--vnet-subnet-id /subscriptions/<sub>/resourceGroups/rg-orders-net/providers/Microsoft.Network/virtualNetworks/vnet-orders/subnets/snet-aks-nodes \
--pod-cidr 192.168.0.0/16 \
--service-cidr 172.16.0.0/16 \
--dns-service-ip 172.16.0.10

7. The dataplane: Azure CNI powered by Cilium

The dataplane is the part that actually forwards packets and enforces policy. With --network-dataplane cilium, AKS uses Cilium, which is built on eBPF in the Linux kernel. Cilium:

  • replaces kube-proxy for Service routing;
  • enforces NetworkPolicy (Chapter 9);
  • scales better on large clusters.

It works with overlay or VNet-routed IPs. It's the recommended dataplane for new clusters.

8. kubenet is retiring

Older clusters used kubenet: pods behind the node, with routes managed in a route table. It has been announced for retirement (31 March 2028). It lacks features newer clusters rely on, and Azure CNI Overlay replaces it with the same IP efficiency.

Existing kubenet clusters can be upgraded in place to Azure CNI Overlay. New clusters should never choose kubenet.

9. Network policy engines

NetworkPolicies only work if something enforces them. On AKS:

  • Cilium: comes with the Cilium dataplane. Recommended.
  • Calico: a long-standing open-source option (--network-policy calico).
  • Azure Network Policy Manager: being retired; don't choose it for new clusters.

The engine is chosen when the cluster is created. Chapter 9 is all about writing the policies.

Match each option to what it's known for.

11. Can overlay pods reach VNet resources?

Yes, a common misconception. A pod calling a database's private endpoint at 10.20.5.4 works fine. The packet leaves the node with the node's IP as its source.

What you can't do is reach a pod directly from outside the cluster by its pod IP. You go through a Service, load balancer or gateway instead, which is the right design anyway.

CNI, sorted

  • Overlay: nodes in the VNet, pods in a private range. The default choice.
  • VNet-routed: pods get VNet IPs; size the subnet for nodes × pods.
  • Cilium dataplane for performance and policy; kubenet is retiring.
  • VNet, pod CIDR and Service CIDR must never overlap; size for max nodes plus surge.
