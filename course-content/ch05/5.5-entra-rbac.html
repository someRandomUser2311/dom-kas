Humans in: Entra ID + Azure RBAC

You'll be able to explain how people sign in to an AKS cluster with Entra ID, and grant them exactly the Kubernetes permissions they need, down to one namespace, with Azure role assignments.

1. Two questions for every request

Every kubectl call hits the API server, which asks two questions:

  • Who are you? This is authentication. With Entra ID integration, the answer is an Entra ID token for your user, group membership included.
  • What may you do? This is authorisation. It's answered by Azure RBAC (role assignments in Azure) or Kubernetes RBAC (Role and RoleBinding objects in the cluster), or both.
Windows/IIS admin
It's like Windows authentication plus NTFS permissions: you sign in with your directory account, and permissions are granted to groups.
Linux admin
It's like SSO via OIDC plus sudoers rules, but the rules live in Azure.
Developer (Compose)
Docker has no per-user permissions on a host; this is new territory.
Other clouds
Like EKS access entries with IAM, or GKE with Google Groups RBAC. Careful: with Azure RBAC, permissions live in Azure, not in an in-cluster ConfigMap.

2. Signing in: kubelogin

With --enable-aad, the kubeconfig from az aks get-credentials doesn't contain a secret. It tells kubectl to run kubelogin, which gets an Entra ID token on demand.

kubelogin convert-kubeconfig -l azurecli makes it reuse your az login session, so there's no extra prompt. Pipelines use other login modes, such as workload identity or a service principal.

az login
az aks get-credentials -g rg-orders-dev -n aks-orders-dev
kubelogin convert-kubeconfig -l azurecli
kubectl get pods -n orders

3. Azure RBAC for Kubernetes

With --enable-azure-rbac, Azure role assignments decide what you can do inside the cluster. There are four built-in roles:

  • Azure Kubernetes Service RBAC Reader: view most objects (not Secrets).
  • Azure Kubernetes Service RBAC Writer: create, change and delete most objects, and read Secrets. It can't change roles or bindings.
  • Azure Kubernetes Service RBAC Admin: full control of a namespace, including RBAC within it.
  • Azure Kubernetes Service RBAC Cluster Admin: everything, cluster-wide.

Users also need Azure Kubernetes Service Cluster User Role on the cluster resource. It lets them download the kubeconfig (get-credentials), but grants nothing inside the cluster.

4. Scope: down to a namespace

The scope can be the whole cluster, or a single namespace, by appending /namespaces/<name> to the cluster's resource ID.

As always, grant to Entra ID groups, not to individuals.

AKS_ID=$(az aks show -g rg-orders-dev -n aks-orders-dev --query id -o tsv)

az role assignment create \
  --assignee-object-id "$DEV_GROUP_ID" --assignee-principal-type Group \
  --role "Azure Kubernetes Service RBAC Writer" \
  --scope "$AKS_ID/namespaces/orders"

Developers must deploy and debug in namespace orders in dev, and nothing else. Which assignment?

  1. RBAC Cluster Admin at the cluster Far too broad.
  2. RBAC Writer scoped to …/namespaces/orders (plus Cluster User Role on the cluster)
  3. RBAC Reader at the cluster They need to deploy, not just read.
  4. Contributor on the resource group Contributor manages the Azure resource; it doesn't grant permissions inside the cluster.
Writer is enough to deploy; namespace scope keeps it contained. Give Admin only to people who manage RBAC inside the namespace.

5. Do it from the CLI

Give the group with object ID $SRE_GROUP_ID read-only access to the whole cluster ($AKS_ID).

az role assignment create --assignee-object-id $SRE_GROUP_ID --assignee-principal-type Group --role "Azure Kubernetes Service RBAC Reader" --scope $AKS_ID

Also accepted: --assignee $SRE_GROUP_ID instead of the object-id pair.

Cluster scope = the cluster's resource ID with no /namespaces/… suffix.

6. Contributor isn't kubectl access

Azure has two planes for AKS:

  • The Azure resource (control plane of Azure): scale pools, upgrade, delete the cluster. Contributor and Owner work here.
  • The Kubernetes API (data plane): pods, Deployments, Secrets. The AKS RBAC roles work here.

A Contributor on the resource group can delete the whole cluster but, with Azure RBAC, can't list its pods without an AKS RBAC role. Grant each plane deliberately.

7. Local accounts off

Even with Entra ID enabled, AKS still has a local admin certificate unless you disable it. az aks get-credentials --admin gives full cluster-admin with no Entra ID sign-in and no audit trail of who used it.

--disable-local-accounts removes it. Do it in every environment, after confirming an Entra ID group holds Cluster Admin, so you can't lock yourself out.

This cluster's settings fail the security review. Tap the reason.

"aadProfile": {
  "managed": true,
  "enableAzureRbac": true
},
"disableLocalAccounts": false,
"oidcIssuerProfile": { "enabled": true },
"securityProfile": { "workloadIdentity": { "enabled": true } }
Entra ID and Azure RBAC are on, but a static admin credential still exists. Set disableLocalAccounts: true.

8. Kubernetes RBAC: the alternative

Instead of Azure RBAC, you can use Entra ID for sign-in and native Kubernetes RBAC for permissions: Role/ClusterRole objects bound to Entra ID group object IDs with RoleBindings.

That's more flexible: custom verbs and resources, managed as YAML. But permissions then live inside each cluster rather than in Azure. Chapter 15 covers Kubernetes RBAC in depth, because you still need it for ServiceAccounts.

9. Debugging "Forbidden"

$ kubectl get secrets -n orders
Error from server (Forbidden): secrets is forbidden: User "aisha@contoso.com" cannot list resource "secrets"
in API group "" in the namespace "orders": User does not have access to the resource in Azure.
Update role assignment to allow access.

The message names the user, verb, resource and namespace. Here, Aisha has RBAC Reader, which can't read Secrets, by design. kubectl auth can-i list secrets -n orders checks before you try.

10. Just-in-time access

For production, combine Azure RBAC with Entra ID Privileged Identity Management (PIM). Engineers are eligible for a role, and activate it for a few hours with a reason and, optionally, an approval.

Nobody holds standing write access to production. Pipelines do the deploying (Chapter 7).

Human access, sorted

  • Entra ID signs people in (through kubelogin); Azure RBAC decides what they may do.
  • Four AKS RBAC roles (Reader, Writer, Admin, Cluster Admin), scoped to the cluster or /namespaces/<ns>; plus Cluster User Role to get credentials.
  • Azure Contributor ≠ Kubernetes access.
  • Disable local accounts; use groups and PIM.
