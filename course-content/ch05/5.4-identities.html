The identities in a cluster

You'll be able to name every identity an AKS cluster uses, say which one performs each action, and grant each one only what it needs.

1. Who is calling Azure?

An AKS cluster calls Azure APIs constantly: creating load balancers, attaching disks, pulling images, reading secrets. Each call is made by an identity, and each identity needs the right role assignment (lesson 0.4).

Most "permission denied" problems on AKS come from granting a role to the wrong identity.

The cluster drawn with three identity badges:
  • the cluster identity, on the control plane;
  • the kubelet identity, on each node;
  • workload identities, on individual pods.
Action buttons ("create a public IP", "attach a disk", "pull an image from ACR", "orders-api reads a Key Vault secret", "a developer runs kubectl") light up the identity that performs the action and the role it needs.
Windows/IIS admin
Like having separate service accounts for the cluster service, the machine accounts and each app pool, instead of one shared domain admin.

Like separate service users for the orchestrator, the host agent and each app.
Developer (Compose)
In Compose, everything uses your Docker login and your env vars. Here every layer has its own identity.
Other clouds
Cluster identity ≈ the EKS cluster IAM role; kubelet identity ≈ the node instance role; workload identity ≈ IRSA / EKS Pod Identity, or GKE Workload Identity.

2. The cluster (control-plane) identity

This identity is used by AKS's own components, mainly the cloud-controller-manager, to manage Azure resources for the cluster:

  • load balancer rules and public IPs;
  • disks for PVCs;
  • routes.

It already has rights on the node resource group. If you use your own VNet, or IPs in other resource groups, grant it Network Contributor there (as in lesson 5.2).

Use a user-assigned managed identity, so you can grant those rights before creating the cluster.

3. The kubelet identity

Each node's kubelet has its own identity, a user-assigned managed identity that AKS creates in the node resource group. The kubelet uses it to pull images from ACR.

So the kubelet identity needs AcrPull on the registry. az aks update --attach-acr grants exactly that (Chapter 6).

$ az aks show -g rg-orders-dev -n aks-orders-dev --query identityProfile.kubeletidentity
{
  "clientId": "9b2d…",
  "objectId": "4e7a…",
  "resourceId": "/subscriptions/…/resourceGroups/rg-orders-dev-nodes/providers/Microsoft.ManagedIdentity/userAssignedIdentities/aks-orders-dev-agentpool"
}

Pods fail with ImagePullBackOff … 401 Unauthorized pulling from contosoacr.azurecr.io. Who needs AcrPull?

  1. The cluster (control-plane) identity It manages Azure infrastructure; it doesn't pull images.
  2. The kubelet identity
  3. The pod's workload identity Image pulls happen before the pod's code even runs, and they're done by the kubelet.
  4. The developer who deployed it Their permissions aren't used at pull time.
The kubelet pulls images. That's also why the kubelet identity is not your app's identity: giving it Key Vault access would let every pod on every node use it.

4. Workload identities

Your apps also need to call Azure: orders-api reads a Key Vault secret and writes to Storage. Each app gets its own user-assigned managed identity, linked to its Kubernetes ServiceAccount through workload identity (lesson 5.6).

Only pods using that ServiceAccount can get its tokens, so different apps have different permissions.

5. Humans and pipelines

Two more callers reach the cluster's API rather than Azure resources:

  • People using kubectl: Entra ID users and groups (next lesson).
  • Pipelines deploying manifests: a service principal or managed identity behind an Azure DevOps service connection (Chapter 7).

With Azure RBAC enabled, both get Kubernetes permissions through Azure role assignments.

6. Match the action to the identity

Which identity performs each action?

Create the public IP for a LoadBalancer ServiceCluster (control-plane) identity
Pull orders-api:1.4.2 from ACRKubelet identity
orders-api reads a secret from Key VaultThe orders-api workload identity
A developer runs kubectl get podsThe developer's Entra ID user
The release pipeline applies manifestsThe service connection's identity
Five actions, five identities. Granting a role to the wrong one is the most common AKS permission bug.

7. Managed identity vs service principal

Older clusters used a service principal with a client secret as the cluster identity. The secret expired, often after a year, and the cluster stopped managing load balancers and disks until someone rotated it.

Managed identities have no secret to store, leak or rotate. Use them everywhere in AKS; clusters can be migrated from service principals with az aks update --enable-managed-identity.

10. A tempting shortcut

"Just give the kubelet identity Key Vault access, then every app can read secrets." It works, and it means every pod on every node, including a compromised one, can read every secret that identity can reach.

Workload identity exists to avoid exactly that.

Identities, sorted

  • Cluster identity: Azure infrastructure (LBs, IPs, disks); Network Contributor on your network.
  • Kubelet identity: image pulls; AcrPull.
  • Workload identity: one per app, for that app's Azure access.
  • Humans and pipelines: Entra ID + Azure RBAC on the cluster.
  • Managed identities everywhere; never use the kubelet identity as an app identity.
