Egress

You'll be able to choose an AKS outbound type, recognise SNAT port exhaustion, and send all cluster egress through a firewall when security requires it.

1. Traffic going out

Pods call things outside the cluster all the time:

  • payment APIs
  • package mirrors
  • Microsoft Entra ID
  • ACR

Nodes need outbound access too: AKS nodes must reach certain Azure endpoints to work at all.

How that traffic leaves the VNet, and with which public IP, is the cluster's outbound type (--outbound-type).

Windows/IIS admin
It's the same decision as "which proxy or firewall do servers use to reach the internet?"
Linux admin
It's your default route plus a NAT device; the choices differ in capacity and control.
Developer (Compose)
On one VM, outbound just used the VM's IP. A cluster needs a deliberate choice.
Other clouds
Like choosing between a NAT gateway and routing through a firewall appliance in your VPC.

2. The outbound types

--outbound-typeHow it worksWhen to use it
loadBalancer (default)Outbound rules on the cluster's Azure Load Balancer, with its public IP(s)Simple clusters, moderate outbound traffic
managedNATGatewayAKS creates and manages a NAT gatewayLots of outbound connections
userAssignedNATGatewayYour own NAT gateway, already attached to the node subnetWhen a central network team owns it
userDefinedRoutingYour route table sends 0.0.0.0/0 to a firewall (e.g. Azure Firewall); AKS creates no outbound IPSecurity requires inspecting and allow-listing all egress

Changing the outbound type of an existing cluster is supported for some combinations, but it's disruptive. Decide early.

3. SNAT ports: the hidden limit

Each outbound connection from behind a public IP uses a SNAT port on that IP. Ports are limited, about 64,000 per IP, and with the load balancer they're shared out between nodes in fixed blocks.

An app that opens many short-lived connections to the same destination, without connection reuse, can use up its node's allocation. New connections then wait and time out, intermittently, and only under load.

A NAT gateway allocates ports on demand and supports more IPs, which makes exhaustion much rarer.

4. Diagnose the intermittent timeout

At peak, about 3% of calls from orders-api to the payment provider time out. At night there are no errors. Here's what you find:

orders-api log:  dial tcp 52.168.10.20:443: i/o timeout   (x 1,284 in 10 min)
Azure Monitor → Load Balancer "kubernetes" → SNAT Connection Count (Failed): rising at peak
Cluster: --outbound-type loadBalancer, 1 outbound public IP, 40 nodes
App code: new HttpClient per request, no keep-alive
  1. The payment provider is rate-limiting That would give HTTP 429s, not TCP connect timeouts tied to the LB's SNAT metric.
  2. SNAT port exhaustion: many short-lived connections from each node use up its share of the outbound IP's ports
  3. DNS is failing The error shows an IP address, so DNS already worked.
  4. A network policy is blocking egress That would block every call, all the time.
Fix both sides: reuse connections in the app (one shared HTTP client with keep-alive), and add capacity by moving to a NAT gateway or adding outbound IPs.

5. All egress through a firewall

Many organisations require every outbound connection to be inspected and allow-listed. With userDefinedRouting:

  1. The node subnet has a route table sending 0.0.0.0/0 to Azure Firewall's private IP.
  2. The firewall allows only what's needed: AKS's required endpoints (the AzureKubernetesService FQDN tag covers most), plus your app's destinations.
  3. Everything else is denied and logged.

In a hub-and-spoke design, the firewall lives in the hub VNet (Chapter 17's architecture).

Security says: "All traffic leaving the cluster must pass through Azure Firewall." Which outbound type?

  1. loadBalancer with network policies Policies control pod-to-pod traffic; egress still leaves through the LB's public IP, not the firewall.
  2. managedNATGateway A NAT gateway doesn't inspect or filter traffic.
  3. userDefinedRouting, with a route table pointing 0.0.0.0/0 at the firewall
  4. A private cluster Private clusters make the API server private; outbound traffic still needs a path.
UDR hands egress to your network design. Remember to allow AKS's required endpoints, or nodes won't even register.

6. What AKS itself needs to reach

With a locked-down firewall, allow at least the documented required outbound rules. The main ones:

  • the cluster's API server address (*.hcp.<region>.azmk8s.io, or its private endpoint);
  • mcr.microsoft.com and *.data.mcr.microsoft.com for system images;
  • management.azure.com and login.microsoftonline.com;
  • packages.aks.azure.com (and related package endpoints) for node binaries;
  • your ACR and its data endpoints.

The exact list changes over time; take it from the AKS "outbound network and FQDN rules" docs, or use the firewall's AzureKubernetesService tag.

7. Private endpoints instead of the internet

For Azure services, such as ACR, Key Vault, Storage and databases, use private endpoints. Traffic then stays on the Microsoft backbone, through your VNet, instead of going out to public IPs.

That needs fewer firewall rules and gives a smaller attack surface. Chapter 6 does this for ACR.

8. Egress at the pod level

The outbound type controls traffic at the cluster level. To restrict which pods may talk to the internet at all, use egress NetworkPolicies (Chapter 9). With Cilium, FQDN-based policies are also possible through Advanced Container Networking Services.

Egress, sorted

  • --outbound-type: loadBalancer (default), managedNATGateway / userAssignedNATGateway, userDefinedRouting.
  • SNAT port exhaustion = intermittent outbound timeouts under load; reuse connections and use a NAT gateway.
  • Firewall-inspected egress = UDR + Azure Firewall + AKS's required FQDNs.
  • Private endpoints keep Azure-service traffic off the internet.
