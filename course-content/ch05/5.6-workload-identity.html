Workload identity

You'll be able to give a pod its own Azure identity with no secrets anywhere, wire up all six links in the chain, and find the broken link when it fails.

1. The goal: no secrets in pods

orders-api needs to read a secret from Azure Key Vault. The old way was to store a service principal's client secret in a Kubernetes Secret. That secret can leak, expires, and must be rotated.

Workload identity lets the pod prove who it is using a token Kubernetes already gives it, and swap that for an Entra ID token. No secret is stored anywhere.

Windows/IIS admin
Like a gMSA or app-pool identity that can reach SQL Server without a password in web.config, but for pods calling Azure.
Linux admin
It's OIDC federation: Entra ID trusts tokens signed by the cluster's issuer, for one specific service account.
Developer (Compose)
Instead of AZURE_CLIENT_SECRET in your .env, the Azure SDK finds credentials automatically.
Other clouds
This is AKS's version of IRSA / EKS Pod Identity on AWS, and Workload Identity Federation on GKE.

2. The chain, end to end

  1. The cluster has an OIDC issuer: a public URL with the keys that sign its ServiceAccount tokens.
  2. A user-assigned managed identity (id-orders-api) holds the Azure permissions.
  3. A federated credential on that identity says: "trust tokens from this issuer for this subject", where the subject is system:serviceaccount:orders:orders-api.
  4. The Kubernetes ServiceAccount orders-api is annotated with the identity's client ID.
  5. The pod uses that ServiceAccount and carries the label azure.workload.identity/use: "true". A webhook then injects a token file and environment variables.
  6. The app's Azure SDK (DefaultAzureCredential / WorkloadIdentityCredential) exchanges the Kubernetes token for an Entra ID token.
The same token-flow widget as the Chapter 7 service-connection lesson, with the same mental model. Pod → (projected SA token, signed by the cluster) → Entra ID checks the issuer and subject against the federated credential → Entra ID token for id-orders-api → Key Vault. Each hop can be clicked; a "break a link" menu shows the error each broken link produces.

3. Steps 1–2: issuer and identity

RG=rg-orders-dev; CLUSTER=aks-orders-dev
ISSUER=$(az aks show -g $RG -n $CLUSTER --query oidcIssuerProfile.issuerUrl -o tsv)
# https://westeurope.oic.prod-aks.azure.com/<tenant>/<guid>/

az identity create -g $RG -n id-orders-api
CLIENT_ID=$(az identity show -g $RG -n id-orders-api --query clientId -o tsv)
PRINCIPAL_ID=$(az identity show -g $RG -n id-orders-api --query principalId -o tsv)

# give the identity what the app needs, and nothing more
az role assignment create --assignee-object-id $PRINCIPAL_ID --assignee-principal-type ServicePrincipal \
  --role "Key Vault Secrets User" --scope $(az keyvault show -n kv-orders-dev --query id -o tsv)

4. Step 3: the federated credential

This is where the trust is defined. The subject must match exactly: system:serviceaccount:<namespace>:<serviceaccount>.

The audience is always api://AzureADTokenExchange.

az identity federated-credential create \
  --name fc-aks-orders-dev-orders-api \
  --identity-name id-orders-api -g $RG \
  --issuer "$ISSUER" \
  --subject system:serviceaccount:orders:orders-api \
  --audience api://AzureADTokenExchange

5. Step 4: the ServiceAccount

Annotate the ServiceAccount with the managed identity's client ID.

apiVersion: v1
kind: ServiceAccount
metadata:
  name: orders-api
  namespace: orders
  annotations:
    ?: "6c1f2a9e-0000-4b1d-9c55-1a2b3c4d5e6f"
  • azure.workload.identity/client-id
  • azure.workload.identity/use That's the pod label, not the ServiceAccount annotation.
  • aadpodidentity/client-id That's from the old, deprecated AAD Pod Identity.
  • azure.workload.identity/tenant-id Optional; the client ID is the one that's required.
The client ID (not the object or principal ID) tells the SDK which managed identity to request a token for. It isn't a secret.

6. Step 5: the pod

The Deployment must use the ServiceAccount and label its pods. The label is what tells the mutating webhook to inject the token volume and the AZURE_* environment variables.

Which line decides the subject of the pod's token, and so whether it matches the federated credential? Tap it.

template:
  metadata:
    labels:
      app: orders-api
      azure.workload.identity/use: "true"
  spec:
    serviceAccountName: orders-api
    containers:
      - name: api
        image: contosoacr.azurecr.io/orders-api:1.4.2
serviceAccountName: orders-api is how the pod gets that ServiceAccount's token, whose subject matches the federated credential. Without it the pod uses default, and Entra ID rejects the subject.

7. What the webhook injects

$ kubectl exec -n orders deploy/orders-api -- env | grep AZURE_
AZURE_CLIENT_ID=6c1f2a9e-0000-4b1d-9c55-1a2b3c4d5e6f
AZURE_TENANT_ID=72f988bf-0000-41af-91ab-2d7cd011db47
AZURE_FEDERATED_TOKEN_FILE=/var/run/secrets/azure/tokens/azure-identity-token
AZURE_AUTHORITY_HOST=https://login.microsoftonline.com/

The token file is a short-lived, automatically rotated ServiceAccount token with audience api://AzureADTokenExchange. The Azure SDK reads these variables. There's still no secret anywhere.

8. Step 6: the app code

cred, err := azidentity.NewDefaultAzureCredential(nil)   // picks up the AZURE_* variables
client, err := azsecrets.NewClient("https://kv-orders-dev.vault.azure.net/", cred, nil)
resp, err := client.GetSecret(ctx, "payments-api-key", "", nil)

The same code works on a developer's laptop, using their az login, because DefaultAzureCredential tries several credential types in turn.

9. Fix the broken chain

The app logs an error. Find and fix the broken link in the token-flow widget.

AADSTS700213: No matching federated identity record found for presented assertion subject
'system:serviceaccount:orders-dev:orders-api'. Check your federated identity credential Subject,
Audience and Issuer against the presented assertion.
The configuration panel shows: federated credential subject system:serviceaccount:orders:orders-api; the pod runs in namespace orders-dev with ServiceAccount orders-api. Success when the learner edits the federated credential subject to system:serviceaccount:orders-dev:orders-api, or adds a second federated credential for it. Changing the ServiceAccount annotation gets the hint "The client ID is fine. Read the subject in the error."
The subject includes the namespace. Moving an app to another namespace, or another cluster with a different issuer, needs a matching federated credential. One identity can hold several (up to 20).

10. Errors and what they mean

SymptomBroken link
No AZURE_* env vars in the podMissing pod label, or workload identity not enabled on the cluster
AADSTS700213 No matching federated identity recordSubject (namespace/SA) or issuer mismatch
AADSTS700016 / application not foundWrong client ID in the SA annotation
Token obtained, but 403 Forbidden from Key VaultThe identity lacks the role on that resource (or the vault uses access policies, not RBAC)

11. One identity per app

Give each app its own managed identity and ServiceAccount: orders-api, web, orders-worker. Each identity gets roles on exactly the resources that app uses.

A compromised web pod can then only do what web could do.

12. Beyond Key Vault

The same identity works for any Entra ID-protected service:

  • Storage (Blob Data roles)
  • Service Bus
  • Cosmos DB
  • Azure SQL and PostgreSQL with Entra ID authentication

Many apps can drop database passwords entirely. Chapter 15 uses it with the Key Vault Secrets Store CSI driver.

Workload identity, sorted

  • OIDC issuer → user-assigned identity → federated credential (issuer + system:serviceaccount:ns:sa).
  • ServiceAccount annotation azure.workload.identity/client-id.
  • Pod: serviceAccountName + label azure.workload.identity/use: "true".
  • SDK: DefaultAzureCredential reads the injected AZURE_* variables.
  • No secrets; one identity per app; a subject mismatch is the #1 error.
