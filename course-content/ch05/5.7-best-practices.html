Best practices recap

You'll be able to review any AKS cluster's network and identity settings against a baseline checklist, and spot what's missing.

1. The baseline

Everything in Chapters 4 and 5 boils down to this checklist. Contoso applies it to every cluster: dev, prod, and the next one.

AreaBaseline
Pod networkingAzure CNI Overlay + Cilium dataplane; planned, non-overlapping VNet / pod / Service ranges
EgressNAT gateway for most clusters; UDR through Azure Firewall where policy requires inspection
IngressOne gateway for HTTP (Chapter 8); internal load balancers for private services
Cluster identitiesUser-assigned managed identities only; Network Contributor and AcrPull scoped narrowly
Human accessEntra ID + Azure RBAC, groups only, namespace-scoped where possible, PIM for production
Static credentialsLocal accounts disabled
App identityWorkload identity, one managed identity per app, no secrets in pods
Azure servicesPrivate endpoints for ACR, Key Vault, databases
Windows/IIS admin
Treat this like a server hardening baseline (CIS), but for the cluster's network and identity.
Linux admin
Same idea as a build standard for every host; Azure Policy can enforce parts of it (Chapter 15).
Developer (Compose)
Most items are the platform team's job, but "no secrets in pods" and "one identity per app" are yours.
Other clouds
It maps closely to the EKS and GKE best-practice guides; only the product names differ.

2. Why each item matters

  • Overlay: you won't run out of VNet IPs as you scale.
  • NAT gateway or firewall: predictable egress IPs, no SNAT exhaustion, optional inspection.
  • Managed identities: nothing expires at 2 am.
  • Entra ID + Azure RBAC + no local accounts: every action is a named person or pipeline, and auditable.
  • Workload identity: a leaked pod spec or image contains no credentials.

3. Review a cluster

A colleague's cluster has these settings. Select every baseline violation.

networkProfile:
  networkPlugin: kubenet
  outboundType: loadBalancer
identity:
  type: SystemAssigned
servicePrincipalProfile: { clientId: msi }
aadProfile: { managed: true, enableAzureRbac: true }
disableLocalAccounts: false
securityProfile:
  workloadIdentity: { enabled: false }
k8s/base/deployment.yaml:
  env: [ { name: AZURE_CLIENT_SECRET, valueFrom: { secretKeyRef: { name: sp-creds, key: secret } } } ]
  1. kubenet networking (retiring; use Azure CNI Overlay)
  2. Local accounts still enabled
  3. Workload identity disabled, and the app uses a client secret instead
  4. Entra ID with Azure RBAC is enabled That's correct, and part of the baseline.
  5. outboundType loadBalancer Acceptable for a simple cluster; consider a NAT gateway at scale. Not a violation by itself.
  6. A system-assigned cluster identity It's a managed identity, which is fine. User-assigned is preferred for rebuilds, but it's not a violation.
Three must-fix items: network model, static admin access, and a secret in the pod. The rest are judgement calls.

4. Turning the checklist into code

A checklist in a wiki drifts. Contoso enforces it in three places:

  • IaC (Chapters 12–13): the cluster is defined in Terraform or Bicep, so the settings are reviewed in pull requests.
  • Pipeline checks (Chapter 16): manifests are scanned for secrets and bad patterns before they deploy.
  • Azure Policy (Chapter 15): non-compliant clusters and pods are flagged or blocked.

5. Tools that check for you

  • Azure Advisor and Microsoft Defender for Cloud recommendations for AKS.
  • AKS deployment safeguards, which warn about or enforce good manifests (on by default in AKS Automatic).
  • The AKS baseline architecture reference from Microsoft, the source of most of this list.

6. What's next

Contoso's cluster is now well-networked and secretless. Next, Chapter 6 adds the container registry (ACR) and decides how the cluster's API server is exposed: public or private.

Baseline, sorted

  • Overlay + Cilium; planned ranges; NAT gateway or firewall egress.
  • Managed identities only; narrow role scopes.
  • Entra ID + Azure RBAC, groups, no local accounts.
  • Workload identity per app; no secrets in pods.
  • Enforce with IaC, pipeline checks and Azure Policy.
