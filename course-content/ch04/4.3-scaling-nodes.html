Scaling nodes

You'll be able to configure the cluster autoscaler on a node pool, explain Node Auto Provisioning, and trace how a traffic spike turns into new VMs.

1. Pods scale fast; nodes must follow

In lesson 3.5 the HPA added pods in seconds. But pods need room. When the user pool is full, new pods stay Pending.

On AKS, two features add nodes for you:

  • the cluster autoscaler, per node pool;
  • Node Auto Provisioning, cluster-wide and Karpenter-based.
Windows/IIS admin
Like VMSS autoscale, but triggered by "work is waiting with nowhere to run" instead of a CPU threshold.
Linux admin
Capacity follows demand; you set floors and ceilings.
Developer (Compose)
There's no Compose equivalent; this is the "more servers" part you'd otherwise do by hand.
Other clouds
Cluster autoscaler ≈ the EKS/GKE cluster autoscaler. Node Auto Provisioning ≈ Karpenter on EKS or GKE node auto-provisioning.

2. The cluster autoscaler

You enable it per pool with a min and max node count. About every 10 seconds it checks two things:

  • Scale up: are there pods Pending because they don't fit, which would fit on a new node of this pool? If so, add nodes (up to max).
  • Scale down: has a node been underused (requests below ~50%) for a while, and can its pods move elsewhere? If so, drain it and remove it (down to min).

It looks at requests, not real usage, which is one more reason to set them.

az aks nodepool update -g rg-orders-dev --cluster-name aks-orders-dev -n user \
  --enable-cluster-autoscaler --min-count 2 --max-count 10

# tune behaviour cluster-wide with a profile
az aks update -g rg-orders-dev -n aks-orders-dev \
  --cluster-autoscaler-profile scale-down-unneeded-time=10m scan-interval=10s

3. From load to a new VM

An extended version of the lesson 3.5 simulator, now with a node strip underneath. Load goes up: the HPA raises replicas, new pods turn Pending (amber), the cluster autoscaler adds a node (it fades in over ~3 minutes), and the Pending pods schedule onto it. Lowering the load reverses it, with the scale-down delay shown as a countdown.

Put the chain in order.

  1. Traffic rises and CPU per pod climbs
  2. The HPA raises the Deployment's replicas
  3. New pods are Pending: no node has room for their requests
  4. The cluster autoscaler adds a node to the pool
  5. The new node joins and the Pending pods are scheduled on it
The cluster autoscaler never looks at CPU usage; it reacts to Pending pods. Adding a node takes a few minutes, so keep some headroom for sudden spikes.

4. When the autoscaler can't help

Pods stay Pending even with the autoscaler on if:

  • the pool is at max;
  • no pool's VM size could ever fit the pod (it requests 32 GiB on 16 GiB nodes);
  • the pod needs a node label or toleration no pool has;
  • the subscription has no vCPU quota left for that VM family in the region;
  • the subnet has run out of IPs (Chapter 5).

The pod's events say pod didn't trigger scale-up with a reason.

Events:
  Normal   NotTriggerScaleUp  cluster-autoscaler  pod didn't trigger scale-up: 1 max node group size reached

5. Scale-down blockers

The autoscaler won't remove a node whose pods can't be safely moved:

  • pods that would break a PDB;
  • pods with local storage (emptyDir, unless configured otherwise);
  • bare pods with no controller;
  • pods annotated cluster-autoscaler.kubernetes.io/safe-to-evict: "false".

If your bill stays high after traffic drops, look for these.

6. Node Auto Provisioning

With the classic autoscaler, you pre-define pools and sizes. Node Auto Provisioning (NAP), based on the open-source Karpenter project, picks VM sizes itself.

It looks at the Pending pods' requests, zones and constraints, then creates right-sized nodes. It also consolidates them later to save money.

You give it rules (allowed VM families, limits) with NodePool and AKSNodeClass resources. NAP is used by default in AKS Automatic (lesson 4.5).

az aks update -g rg-orders-dev -n aks-orders-dev --node-provisioning-mode Auto

7. Which one?

Contoso runs a few predictable services on one VM size and wants simple, explicit control. Which node scaling fits best?

  1. The cluster autoscaler on the user pool with sensible min/max
  2. Node Auto Provisioning Great for varied workloads and cost optimisation; more than Contoso needs right now.
  3. No autoscaling; scale by hand That works until a traffic spike at 2 am.
  4. Only the HPA The HPA adds pods, not nodes.
Start simple. Move to NAP when you have many differently-shaped workloads or want automatic bin-packing and consolidation.

8. Headroom and cost

  • Set min high enough that normal traffic never waits for a new node.
  • Set max to cap cost, and make sure your vCPU quota and subnet IPs can actually reach it.
  • Requests that are too generous make nodes look full: you pay for idle capacity and the autoscaler adds even more.

Scaling nodes, sorted

  • HPA adds pods; the cluster autoscaler adds nodes when pods are Pending.
  • Per-pool min/max; decisions are based on requests.
  • It can't help at max, without quota or IPs, or if no pool could fit the pod.
  • PDBs, local storage and bare pods block scale-down.
  • Node Auto Provisioning (Karpenter) picks VM sizes itself.
