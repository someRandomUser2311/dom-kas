Upgrades & maintenance

You'll be able to keep an AKS cluster on a supported version, choose upgrade channels for Kubernetes and node images, set maintenance windows, and make sure upgrades don't take your app down.

1. Two different things get upgraded

  • Kubernetes version (e.g. 1.32 → 1.33): new API features and removals. It covers the control plane, then each node pool's kubelet.
  • Node image: the OS and runtime on each node (Ubuntu or Azure Linux, security patches, containerd). Azure publishes new images often, at least weekly for security fixes.

They have separate settings, and you need both. A cluster on the latest Kubernetes version can still have nodes missing months of OS patches.

Windows/IIS admin
Kubernetes upgrades are like moving to a new Windows Server version; node image upgrades are like Patch Tuesday. Both happen by replacing nodes, not patching them in place.
Linux admin
No apt upgrade on nodes; you roll new images instead. Think immutable infrastructure.
Developer (Compose)
Like rebuilding from a newer base image rather than patching a running container.
Other clouds
Like EKS control-plane upgrades plus managed node group AMI updates, or GKE release channels plus node auto-upgrade.

2. The support window

  • Kubernetes releases a minor version roughly every 4 months.
  • AKS supports about three GA minor versions at a time, each for roughly 12 months. Fall behind and you're out of support.
  • Control-plane upgrades go one minor version at a time (1.31 → 1.32 → 1.33). You can't skip.
  • Long-term support (LTS), on the Premium tier, keeps selected versions supported for about two years, for teams that can't upgrade often.

Check what's available with az aks get-upgrades and az aks get-versions.

$ az aks get-upgrades -g rg-orders-dev -n aks-orders-dev -o table
Name     ResourceGroup   MasterVersion   Upgrades
-------  --------------  --------------  -------------------
default  rg-orders-dev   1.32.6          1.33.1, 1.33.2

3. How an upgrade runs

  1. The control plane is upgraded first. Running pods aren't affected.
  2. Then each node pool, node by node:
    1. a new surge node is added with the new version;
    2. an old node is cordoned, so no new pods go there;
    3. it's drained: pods are evicted through the eviction API, respecting PDBs;
    4. it's deleted.

--max-surge sets how many extra nodes are added at once. Higher is faster but needs more quota and IPs; 33% is a common production setting.

Order the steps of an AKS version upgrade.

  1. Upgrade the control plane
  2. Add a surge node running the new version
  3. Cordon an old node
  4. Drain it, evicting pods with respect to PDBs
  5. Delete the old node and repeat for the next
Pods move only during the drain. That's where PDBs, replicas and readiness probes decide whether users notice.

4. Kubernetes auto-upgrade channels

The cluster's --auto-upgrade-channel decides whether AKS upgrades the Kubernetes version for you:

  • none: you upgrade manually.
  • patch: the latest patch of your current minor version (e.g. 1.33.1 → 1.33.2).
  • stable: the latest patch of the second-newest minor version (N-1).
  • rapid: the newest supported minor version.
  • node-image: only node images. Prefer the separate node OS channel for that (next step).

A common choice is patch, with minor upgrades done deliberately: tested in dev first, by a pipeline or IaC change.

5. Node OS upgrade channels

--node-os-upgrade-channel decides how nodes get OS patches:

  • NodeImage (the default for new clusters): roll nodes onto the newest node image, regularly.
  • SecurityPatch: apply only security patches to the existing image, with fewer reimages.
  • Unmanaged: the OS's own unattended updates; reboots are up to you.
  • None: nothing; you're responsible.

6. Planned maintenance windows

Maintenance configurations restrict when automatic upgrades may start, for example Sunday 01:00–05:00 in your time zone. There are two named configurations:

  • aksManagedAutoUpgradeSchedule for Kubernetes upgrades;
  • aksManagedNodeOSUpgradeSchedule for node OS upgrades.
az aks maintenanceconfiguration add -g rg-orders-prod --cluster-name aks-orders-prod \
  --name aksManagedNodeOSUpgradeSchedule \
  --schedule-type Weekly --day-of-week Sunday --interval-weeks 1 \
  --start-time 01:00 --duration 4 --utc-offset +01:00

7. Making upgrades invisible

Upgrades replace every node, so every pod is moved at least once. Your app survives that if it has:

  • at least 2 replicas, spread across nodes and zones;
  • a PDB that allows at least one disruption;
  • a readiness probe, so replacements only get traffic when ready;
  • graceful shutdown on SIGTERM.

AKS settings like --drain-timeout and --node-soak-duration control how long it waits for drains, and the pause between nodes.

8. An upgrade that blocks

A single-replica Deployment has a PDB with maxUnavailable: 0. A node pool upgrade reaches the node it runs on. What happens?

  1. The pod is moved and briefly unavailable The PDB forbids any unavailability, so the eviction is refused.
  2. The drain is blocked by the PDB; after the drain timeout the upgrade fails (or the node is left cordoned, depending on settings)
  3. AKS deletes the PDB AKS never deletes your objects.
  4. The node is upgraded in place without moving the pod AKS upgrades replace nodes.
A PDB that allows zero disruptions plus one replica makes the node impossible to drain. Fix it with 2+ replicas and maxUnavailable: 1.

9. Deprecated APIs

New Kubernetes minor versions sometimes remove old API versions. Manifests that use them stop applying after the upgrade. AKS can detect clusters still using deprecated APIs and stop the upgrade, warning you first.

Check your manifests in CI (Chapter 10) and upgrade dev first. The release notes list each removal.

10. Manual upgrades

# control plane + all node pools
az aks upgrade -g rg-orders-dev -n aks-orders-dev --kubernetes-version 1.33.2

# one pool's node image only
az aks nodepool upgrade -g rg-orders-dev --cluster-name aks-orders-dev -n user --node-image-only

# set surge on a pool
az aks nodepool update -g rg-orders-dev --cluster-name aks-orders-dev -n user --max-surge 33%

Upgrades, sorted

  • Kubernetes versions and node images are separate. Keep both current.
  • Upgrade one minor version at a time, within the support window; LTS on Premium.
  • Control plane first, then pools node by node (surge, cordon, drain, delete).
  • Channels: --auto-upgrade-channel (none/patch/stable/rapid/node-image) and --node-os-upgrade-channel (None/Unmanaged/SecurityPatch/NodeImage), plus maintenance windows.
  • Replicas + PDB (allowing 1) + readiness = invisible upgrades.
