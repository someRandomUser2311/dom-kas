Who manages what

You'll be able to say, for any part of an AKS cluster, whether Azure looks after it, you do, or it's shared, and what that means for patching, scaling and outages.

1. "Managed" Kubernetes

Remember the cluster diagram from lesson 1.3: a control plane on top, nodes underneath.

AKS is managed Kubernetes: Azure runs the top half for you. You still own a lot of the bottom half, and everything you deploy.

Knowing exactly where that line is matters. "I thought Azure did that" is how clusters end up unpatched or unsupported.

The lesson 1.3 diagram, now split by a dashed line. Above the line, labelled "Azure-managed, hidden from you": kube-apiserver, etcd, scheduler, controller manager, cloud-controller-manager. Below it, labelled "Your subscription": node VMs (VM Scale Sets), kubelet, containerd, add-ons, your pods.
Windows/IIS admin
Like moving from your own SQL Server to Azure SQL Managed Instance: the engine is patched for you, but your schemas, logins and queries are still yours.

Developer (Compose)
You go from "I run Docker on a VM" to "Azure runs the orchestrator; I bring workloads and choose the VMs".
Other clouds
The same split as EKS and GKE Standard. AKS Automatic is closer to GKE Autopilot (lesson 4.5).

2. What Azure manages

  • The control plane: API server, etcd, scheduler and controller managers. Azure runs, scales, patches and backs them up, in an Azure-owned subscription.
  • Control-plane availability. On the Standard and Premium tiers this comes with a financially backed uptime SLA; on Free there's no SLA (lesson 4.5).
  • Images for nodes. Azure publishes patched node images weekly or more often. Whether your nodes take them is up to your settings.
  • Integrations: the cloud-controller-manager, CSI drivers, and add-ons you turn on.

3. What you own

  • Workloads: manifests, images, probes, resources, scaling.
  • Nodes' lifecycle: VM sizes, pool counts, zones, and choosing when Kubernetes versions and node images are upgraded, or setting channels that do it for you.
  • Network design: VNet, subnets, IP plan, ingress, egress, network policy.
  • Identity and access: who can reach the API, Azure RBAC, workload identity.
  • Security of what runs: pod security, image provenance, secrets.
  • Cost: you pay for nodes, disks, load balancers and IPs. On Free, the control plane costs nothing.

4. The grey zone: shared

  • Upgrades. Azure provides versions and images and runs the upgrade. You choose when (channels, maintenance windows) and make sure workloads survive it (PDBs, replicas).
  • Node OS security. Azure ships patched images; you choose the node OS upgrade channel.
  • Monitoring. Azure exposes metrics and logs; you turn them on and act on them (Chapter 14).

6. You can't reach the control plane

On AKS you'll never see an etcd pod, can't SSH to a control-plane VM, and can't change API server flags directly. You configure the control plane through AKS settings instead, for example:

  • authorized IP ranges
  • private cluster
  • Entra ID integration

Its logs, such as the API server audit log, are available through diagnostic settings (Chapter 14).

7. Who fixes a broken etcd?

AKS's etcd crashes at 3 am. Who restarts it?

  1. Your on-call engineer, via kubectl etcd isn't visible to you at all.
  2. Azure: the control plane is fully managed
  3. Nobody until the next upgrade Azure monitors and repairs control-plane components continuously.
  4. The cluster autoscaler It manages nodes, not the control plane.
Control-plane health is Azure's job. Your running pods keep working during a control-plane blip (lesson 1.3).

8. The node resource group

When you create a cluster in rg-orders-dev, AKS creates a second resource group, named like MC_rg-orders-dev_aks-orders-dev_westeurope, for the infrastructure it manages on your behalf:

  • the VM Scale Sets
  • the load balancer
  • public IPs
  • managed disks

It's in your subscription and you pay for it, but AKS owns it. Changing things there directly breaks AKS's view of the world (next lesson). Name it yourself with --node-resource-group.

9. Support boundaries

Microsoft support covers AKS when you stay within its rules:

  • run a supported Kubernetes version;
  • don't modify the node resource group's resources directly;
  • keep the system node pool healthy.

Fall outside them and your cluster can become "out of support". You'll get best effort only, until you're back in line.

10. What still breaks on a managed cluster

Real incidents on AKS are almost always on your side of the line:

  • a bad release;
  • a missing PDB during an upgrade;
  • a node pool too small to schedule pods;
  • an expired secret;
  • a subnet out of IPs;
  • an image registry the nodes can't pull from.

The rest of this part (Chapters 4–6) is about getting those right.

11. Optional: Fleet Manager and add-ons

As Contoso grows to several clusters, Azure Kubernetes Fleet Manager can coordinate upgrades across them.

Managed add-ons and extensions shift more work to Azure, at the cost of some flexibility. Examples are KEDA, the Key Vault CSI driver, app routing and the Istio-based service mesh. This course uses them where they're the simplest path.

Shared responsibility, sorted

  • Azure: the control plane (run, scale, patch, back up), node images, integrations.
  • You: workloads, node pools, network, identity, security, cost.
  • Shared: upgrades and node patching. Azure supplies them; your channels and PDBs decide how they land.
  • The MC_ node resource group is AKS's; don't edit it by hand.
  • Stay on supported versions to stay in support.
