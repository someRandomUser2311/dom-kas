Node pools

You'll be able to design an AKS cluster's node pools (system vs user, VM size, zones, spot), add one with the CLI, and avoid breaking AKS by editing its resources directly.

1. A node pool is a group of identical nodes

AKS groups nodes into node pools. Every node in a pool has the same VM size, OS, zones, labels and taints.

Under the hood, each pool is an Azure Virtual Machine Scale Set in the node resource group.

A cluster can have many pools, for example a general-purpose pool, a memory-heavy pool and a GPU pool. Pods are steered to them with the Chapter 3 tools.

2. System pools vs user pools

Every pool has a mode:

  • System: hosts critical add-ons such as CoreDNS, metrics-server and konnectivity. Every cluster needs at least one system pool, and AKS keeps it from being removed or scaled to zero.
  • User: for your apps. It can scale to zero and be added or removed freely.

Best practice is a small, dedicated system pool, tainted CriticalAddonsOnly=true:NoSchedule, with at least 2–3 nodes across zones. Your apps then run in separate user pools.

That way a runaway app can't starve CoreDNS, and you can resize app pools without touching system components.

Contoso's cluster has a system pool (tainted CriticalAddonsOnly) and a user pool. Where should orders-api run?

  1. On the system pool, because it's important "System" means cluster add-ons, not "business critical".
  2. On the user pool. It doesn't tolerate the system taint, so it goes there automatically
  3. On both, for redundancy Redundancy comes from replicas and zones within the user pool.
  4. On a new pool per replica Unnecessary; one user pool across zones is enough.
The taint keeps apps off the system pool without anyone having to remember a nodeSelector.

3. Choosing a VM size

  • General purpose D-series (e.g. Standard_D4ds_v5, 4 vCPU / 16 GiB) is the usual start.
  • Memory-heavy apps: E-series. GPU work: NC/ND-series.
  • Bigger nodes waste less to per-node overhead and fit large pods, but each one you lose takes more pods with it.
  • Allocatable is less than the VM's size: AKS reserves CPU and memory for the kubelet and the OS. Check kubectl describe node.
  • Prefer sizes with a local temporary disk (the d in Dds) for ephemeral OS disks, which are faster and cheaper.

4. Zones

Create pools with --zones 1 2 3 and AKS spreads their nodes across availability zones. Nodes get the label topology.kubernetes.io/zone=westeurope-1 (and so on), which topology spread uses (lesson 3.2).

Zones are chosen when the pool is created and can't be changed afterwards. Get this right the first time; fixing it means adding a new pool and moving workloads.

Remember zonal disks (lesson 3.4): a pod with an LRS disk is tied to that disk's zone.

5. Adding a user pool

az aks nodepool add \
  --resource-group rg-orders-dev \
  --cluster-name aks-orders-dev \
  --name user \
  --mode User \
  --node-vm-size Standard_D4ds_v5 \
  --zones 1 2 3 \
  --enable-cluster-autoscaler --min-count 2 --max-count 10 \
  --labels workload=general

Tap the option that you can't change after the pool exists.

A pool's zones are fixed at creation. VM size is also fixed per pool; to change either, add a new pool and drain the old one. Autoscaler bounds and labels can be updated later.

6. Spot pools for cheap, interruptible work

Spot pools use spare Azure capacity at a large discount. Azure can take the VMs back at any time, with about 30 seconds' notice.

AKS taints spot nodes with kubernetes.azure.com/scalesetpriority=spot:NoSchedule, so only pods that tolerate it land there.

Spot pools are good for batch jobs, CI agents and dev environments. They're not for orders-api in production.

az aks nodepool add -g rg-orders-dev --cluster-name aks-orders-dev \
  --name spot --priority Spot --eviction-policy Delete --spot-max-price -1 \
  --enable-cluster-autoscaler --min-count 0 --max-count 5

7. Don't touch the MC_ resource group

Contoso's cluster upgrade fails. What went wrong?

$ az aks upgrade -g rg-orders-dev -n aks-orders-dev --kubernetes-version 1.33.2
(OperationNotAllowed) ... The node pool 'user' is in a failed provisioning state.
$ az aks nodepool show -g rg-orders-dev --cluster-name aks-orders-dev -n user --query "{count:count, vm:vmSize}"
{ "count": 3, "vm": "Standard_D4ds_v5" }
$ az vmss list -g MC_rg-orders-dev_aks-orders-dev_westeurope --query "[].{name:name, cap:sku.capacity, size:sku.name}"
[ { "name": "aks-user-12345678-vmss", "cap": 5, "size": "Standard_D8ds_v5" } ]
  1. The Kubernetes version doesn't exist The error is about the node pool's state, not the version.
  2. Someone resized and scaled the VMSS directly in the MC_ group, so it no longer matches what AKS thinks the pool is
  3. The cluster autoscaler is broken The autoscaler would change the count through AKS, and never the VM size.
  4. The subscription is out of quota That gives a quota error.
AKS believes the pool is 3 × D4ds_v5; the VMSS is 5 × D8ds_v5. Always change pools through az aks nodepool (or IaC). To recover, reconcile through AKS: az aks nodepool update, or add a new pool and delete the broken one. Some organisations block edits to MC_ groups with Azure Policy or deny assignments.

8. OS and node images

Linux pools default to Ubuntu. Azure Linux is Microsoft's own smaller, hardened distro, chosen with --os-sku AzureLinux.

Windows pools exist for Windows containers. They need a Linux system pool too.

Each pool runs a node image version, which Azure updates regularly (lesson 4.4).
