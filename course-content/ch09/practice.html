Predict the outcome (4 connectivity puzzles)

1 · AND vs OR: orders has ingress default-deny plus an allow whose from has two items: namespaceSelector: web and podSelector: app=web. A pod web/debug (no labels) calls orders-api:8080.

  1. Allowed: the first item allows any pod in namespace web
  2. Denied
  3. Allowed only on port 80
Two items = OR.

2 · Missing namespace label: the allow uses namespaceSelector: { matchLabels: { team: shop } }, but namespace web has no team label. web → orders-api?

  1. Allowed
  2. Denied: no namespace matches the selector
  3. Allowed for pods with app=web
Use kubernetes.io/metadata.name, or label the namespace.

3 · DNS: web has default-deny (Ingress + Egress) and an egress allow to orders-api:8080 only. curl http://orders-api.orders/healthz from web?

  1. Succeeds
  2. Fails: "could not resolve host" (DNS egress blocked)
  3. Connection refused
Add allow-dns.

4 · Additive: db has default-deny, plus allow-orders-api (from orders-api:5432) and, added by another team, allow-reporting (from namespace reporting, all ports). Can a reporting pod reach postgres:5432?

  1. Yes: the policies are added together
  2. No: allow-orders-api restricts it
  3. Only if applied first
Review every allow; there's no "only" in NetworkPolicy.

Write lab: secure the Contoso namespaces

Brief: Namespaces web, orders and db exist, with pods web (app=web, :8080), orders-api (:8080), orders-worker and postgres (app=postgres, :5432). Write the policies in k8s/policies/. Graded by netpol-eval against this target matrix:

FlowTarget
gateway-infra → web:8080, orders-api:8080✓
web → orders-api:8080✓
orders-api → postgres:5432✓
orders-worker → postgres:5432✓
Every pod → kube-dns:53 (UDP+TCP)✓
Everything else✗

The results show each cell that differs from the target.

  • A default-deny (Ingress + Egress) policy exists in every namespace (web, orders, db).
  • Nothing other than orders-api and orders-worker can reach postgres.
  • DNS works from every pod.
  • Every allowed flow has both its egress and its ingress side.
  • No allow-all rules (ingress: [{}] or egress: [{}]).
  • The matrix matches the target exactly.
Reference solution (outline)
  • Each namespace: default-deny + allow-dns (lessons 9.2 and 9.4).
  • web: ingress from gateway-infra:8080; egress to orders/orders-api:8080.
  • orders: orders-api ingress from gateway-infra and web/web (AND form) on 8080; orders-api and orders-worker egress to db/postgres:5432.
  • db: postgres ingress from orders pods with app in (orders-api, orders-worker) on 5432 (namespaceSelector AND podSelector with matchExpressions).

Walkthrough: default-deny breaks the app, then open flows one by one

  1. Apply default-deny to all three namespaces; the shop returns 502s, and the logs show DNS timeouts.
  2. Add allow-dns: now the errors are connection timeouts.
  3. Add gateway → web, web → orders-api and orders → db, in order, checking the site after each.
  4. Verify a denied flow: web → postgres times out.

Try it locally

Run ./lab/addons/netpol.sh first. It makes sure the lab enforces NetworkPolicy (installing a policy engine if the pinned kind version's default CNI doesn't). Results should match the in-browser matrix.

Default-deny blocks traffic.

kubectl apply -f lab/examples/ch09/contoso-apps.yaml          # namespaces web, orders, db + pods + services
kubectl exec -n web deploy/web -- wget -qO- -T 3 http://orders-api.orders/healthz
kubectl apply -f lab/examples/ch09/default-deny-all.yaml
kubectl exec -n web deploy/web -- wget -qO- -T 3 http://orders-api.orders/healthz

Expected: ok, then "bad address" (DNS blocked).

Cleanup: keep it for the next box, or kubectl delete -f lab/examples/ch09/

DNS, then the flow.

kubectl apply -f lab/examples/ch09/allow-dns.yaml
kubectl exec -n web deploy/web -- wget -qO- -T 3 http://orders-api.orders/healthz
kubectl apply -f lab/examples/ch09/allow-web-to-orders.yaml
kubectl exec -n web deploy/web -- wget -qO- -T 3 http://orders-api.orders/healthz

Expected: a timeout (DNS works, but the flow isn't allowed yet), then ok.

Cleanup: none.

AND vs OR.

kubectl run debug -n web --image=busybox:1.36 -- sleep 3600
kubectl apply -f lab/examples/ch09/allow-web-OR.yaml;  kubectl exec -n web debug -- wget -qO- -T 3 http://orders-api.orders/healthz
kubectl apply -f lab/examples/ch09/allow-web-AND.yaml; kubectl exec -n web debug -- wget -qO- -T 3 http://orders-api.orders/healthz

Expected: ok with OR (any pod in web), then a timeout with AND (debug lacks app=web). Both files use the same policy name, so the second replaces the first. The lab's egress allow in web covers every pod there, so only the ingress side on orders-api differs.

Cleanup: kubectl delete pod debug -n web; kubectl delete -f lab/examples/ch09/
