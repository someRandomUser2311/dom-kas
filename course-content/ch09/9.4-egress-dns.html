Egress & DNS

You'll be able to write egress rules, never forget DNS again, allow traffic to Azure services, and know when IP-based rules aren't enough.

1. Egress rules mirror ingress

An egress rule lists to peers and ports, with the same selectors and the same AND/OR rules as from.

With default-deny egress, a client needs an egress allow, and the server needs an ingress allow.

podSelector:
  matchLabels: { app: web }
policyTypes: [Egress]
egress:
  - to:
      - namespaceSelector:
          matchLabels: { kubernetes.io/metadata.name: orders }
        podSelector:
          matchLabels: { app: orders-api }
    ports:
      - port: 8080
Windows/IIS admin
Outbound firewall rules, which most servers never had. That's exactly why exfiltration is so easy.
Linux admin
The OUTPUT chain, with DNS as the rule everyone forgets.
Developer (Compose)
List every service your app calls. That list becomes your egress policy.
Other clouds
Like the outbound rules of a security group, which default to allow-all in AWS but here are deny-all once isolated.

2. DNS is egress too

Every name lookup is a UDP (sometimes TCP) packet to CoreDNS on port 53, in kube-system. With default-deny egress, that's blocked, and everything that uses a hostname fails.

Allow DNS once per namespace, for all pods.

Complete the DNS allow rule.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
  namespace: orders
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: kube-system }
          podSelector:
            matchLabels: { k8s-app: kube-dns }
      ports:
        - protocol: UDP
          port: ?
        - protocol: TCP
          port: 53
  • 53
  • 5353 That's multicast DNS, not cluster DNS.
  • 443 CoreDNS listens on 53.
  • 8053 Not the Service port.
UDP and TCP 53 to the CoreDNS pods (label k8s-app: kube-dns) in kube-system. Large responses fall back to TCP, so allow both.

3. Diagnose the timeout

After the platform team rolled out default-deny, orders-api logs this. What's missing?

2026-11-03T10:22:41Z ERROR db: dial tcp: lookup orders-sql.privatelink.database.windows.net on 172.16.0.10:53:
read udp 192.168.4.17:41522->172.16.0.10:53: i/o timeout
  1. The SQL firewall blocks the cluster The failure is at the DNS lookup, before any SQL connection.
  2. An egress allow for DNS (UDP/TCP 53 to kube-dns in kube-system)
  3. An ingress allow on the database Azure SQL isn't a pod; and the lookup fails before that.
  4. CoreDNS is down Possible in general, but right after default-deny, missing DNS egress is far more likely.
lookup … on 172.16.0.10:53: i/o timeout = the pod can't reach the cluster DNS Service IP. Add allow-dns, then an egress rule for the SQL private endpoint (next step).

4. Egress to Azure services

Azure services aren't pods, so selectors can't match them. You have two options:

  • Private endpoints (recommended): the service has a stable private IP in your VNet, so allow its subnet with ipBlock and the port.
  • Public endpoints: their IPs are large, shared and changing. ipBlock rules become huge and fragile. This is where FQDN policies help (step 6).
podSelector:
  matchLabels: { app: orders-api }
policyTypes: [Egress]
egress:
  - to:
      - ipBlock: { cidr: 10.20.5.0/27 }     # private endpoints: SQL, Key Vault
    ports:
      - port: 1433
      - port: 443

5. Workload identity needs egress

Pods using workload identity (lesson 5.6) must reach Microsoft Entra ID (login.microsoftonline.com) on 443 to exchange tokens. That's a public, changing endpoint.

With strict egress, you need either an FQDN-based allow or a broad 443 rule kept in check by the cluster's firewall (lesson 5.3).

6. Why FQDN rules need more than NetworkPolicy

Standard NetworkPolicy only knows IPs and ports. "Allow api.payments-provider.example" can't be written.

Cilium can, by watching DNS answers and allowing the resolved IPs. On AKS, that's part of Advanced Container Networking Services with the Cilium dataplane, using CiliumNetworkPolicy with toFQDNs.

Alternatively, enforce FQDN egress centrally in Azure Firewall (lesson 5.3).

apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: orders-api-to-payments
  namespace: orders
spec:
  endpointSelector:
    matchLabels: { app: orders-api }
  egress:
    - toFQDNs:
        - matchName: api.payments-provider.example
      toPorts:
        - ports: [ { port: "443", protocol: TCP } ]

7. Blocking the metadata endpoint

Azure's instance metadata service (169.254.169.254) can hand out tokens for the node's identities. Pods rarely need it; with workload identity they shouldn't.

Strict egress (allow-lists only) blocks it automatically. If you allow broad egress, add except: [169.254.169.254/32] to the ipBlock.

9. Testing a flow

kubectl exec -n web deploy/web -- wget -qO- -T 3 http://orders-api.orders/healthz    # expect ok
kubectl exec -n web deploy/web -- nc -zv -w 3 postgres.db 5432                      # expect timeout
kubectl exec -n orders deploy/orders-api -- nslookup kubernetes.default             # DNS works?

Distroless images have no shell or tools, so use kubectl debug with a tools image, sharing the pod's network (Chapter 14).

Egress, sorted

  • Egress rules mirror ingress; both ends must allow.
  • Always allow DNS: UDP+TCP 53 to k8s-app=kube-dns in kube-system.
  • Azure services: private endpoints + ipBlock; FQDNs need Cilium (ACNS) or Azure Firewall.
  • Workload identity needs egress to Entra ID; block 169.254.169.254.
