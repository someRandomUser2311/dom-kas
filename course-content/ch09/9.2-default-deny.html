Default-deny

You'll be able to write the default-deny policy for a namespace, predict what it breaks, and use it as the starting point for every namespace.

1. Start from "nothing allowed"

Allow-lists are only safe if the starting point is "deny". A default-deny policy selects every pod in a namespace and allows nothing. Every pod becomes isolated in both directions.

Every flow the app needs must then be added deliberately.

Windows/IIS admin
Like setting Windows Firewall to "block all inbound and outbound", then adding rules per application.
Linux admin
iptables -P INPUT DROP; iptables -P OUTPUT DROP, per namespace.
Developer (Compose)
Your app's calls will fail until someone adds an allow for each dependency. Plan for that.
Other clouds
Like a security group with no rules, attached to everything in the namespace.

2. The policy

Complete the selector that matches every pod in the namespace.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: orders
spec:
  podSelector: ?
  policyTypes:
    - Ingress
    - Egress
  • {}
  • "*" Selectors don't take wildcards.
  • all Not valid; it would be read as the string "all".
  • [] A selector is a map, not a list.
An empty selector {} means "every pod in this namespace". With both policy types and no ingress or egress rules, nothing is allowed either way.

3. Ingress-only vs both

  • policyTypes: [Ingress] only: nothing can reach pods, but they can still call out anywhere. That's a common first step.
  • [Ingress, Egress]: full lockdown. It stops data exfiltration and lateral movement from a compromised pod, but you must allow every outbound dependency, including DNS.

4. Apply it and watch

In the matrix, apply default-deny (Ingress + Egress) to namespace orders.

Success when the policy is applied and every cell to and from orders-api and orders-worker has turned ✗, including their DNS column. Cells between web and db stay ✓ (not affected).
The policy only affects pods in its own namespace. Apply one per namespace.

5. What breaks first?

After applying full default-deny to orders, what's the first error orders-api logs when it tries to reach the database at postgres.db.svc.cluster.local?

  1. Connection refused on 5432 It doesn't get that far.
  2. A DNS lookup timeout: it can't even resolve the database's name
  3. Authentication failed No connection is made at all.
  4. Nothing; same-cluster traffic is exempt Nothing is exempt from an egress default-deny.
Egress default-deny blocks the pod's calls to CoreDNS on port 53. Every name lookup fails, which makes it look like "everything is broken". Lesson 9.4 adds the DNS allow.

6. Every namespace, from day one

Contoso puts default-deny.yaml in the namespace template (lesson 8.2). Every new namespace starts locked, and the app's allow policies are shipped alongside its manifests.

Adding default-deny later, to a busy namespace, means finding every flow first. Use flow logs (lesson 9.5) to discover them.

7. What about kube-system?

Don't apply default-deny to kube-system or other add-on namespaces unless the add-on documents its required flows. You'll break CoreDNS, metrics and more.

Lock down your namespaces; leave platform namespaces to their own guidance.

8. Allow-all exists too

An empty rule (ingress: [{}]) allows everything. It's occasionally useful for debugging, but because policies are additive it also cancels any default-deny. Watch for it in reviews.

spec:
  podSelector: {}
  policyTypes: [Ingress]
  ingress:
    - {}

9. Checking policies

$ kubectl get networkpolicy -n orders
NAME           POD-SELECTOR   AGE
default-deny   <none>         3m
$ kubectl describe networkpolicy default-deny -n orders
Spec:
  PodSelector:     <none> (Allowing the specific traffic to all pods in this namespace)
  Allowing ingress traffic:
    <none> (Selected pods are isolated for ingress connectivity)
  Allowing egress traffic:
    <none> (Selected pods are isolated for egress connectivity)
  Policy Types: Ingress, Egress

Default-deny, sorted

  • podSelector: {} + policyTypes: [Ingress, Egress] + no rules = deny all.
  • One per namespace you own, from day one.
  • Egress deny breaks DNS first.
  • Leave kube-system alone; watch for allow-all rules.
