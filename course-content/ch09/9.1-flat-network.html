The flat network & isolation

You'll be able to explain Kubernetes' default "anything can talk to anything" network, and exactly when a pod becomes isolated by a NetworkPolicy.

1. Everything can reach everything

Kubernetes' network model says every pod can reach every other pod, across nodes and namespaces, without NAT. That makes things easy to get working.

It also means a compromised web pod can connect straight to the database, the payments service, or anything else. Namespaces don't change that (lesson 8.1).

2. A NetworkPolicy, in one sentence

A NetworkPolicy selects some pods (with podSelector, in its namespace) and lists traffic that's allowed to or from them. It has no "deny" rules at all.

It needs a policy engine to enforce it (lesson 9.5). Without one, policies are accepted and silently ignored.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web
  namespace: orders
spec:
  podSelector:
    matchLabels:
      app: orders-api
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: web
      ports:
        - port: 8080

3. Isolation: the key idea

A pod starts non-isolated: all traffic is allowed.

The moment any policy selects it with Ingress in policyTypes, the pod becomes isolated for ingress. From then on, only traffic that some policy explicitly allows can reach it. Everything else is dropped.

Egress works the same way, independently.

4. Predict the side effect

Starting from the open cluster, you apply only the allow-web policy above. Can orders-worker or a db pod still connect to orders-api:8080?

  1. Yes; the policy only adds an allow for web It adds an allow, and it makes orders-api isolated, so everything not allowed is now denied.
  2. No. orders-api is now isolated for ingress; only traffic from namespace web on port 8080 is allowed
  3. Only orders-worker, because it's in the same namespace Same-namespace traffic gets no special treatment.
  4. The policy fails to apply It's valid.
A single allow policy is also an implicit deny for everything else to the selected pods. That surprises many people the first time.

5. Policies are additive

If several policies select the same pod, their allows are added together (a union). There's no order and no priority, and no policy can ever block something another allows.

So the safe pattern is: deny everything (lesson 9.2), then add small, focused allow policies, one per flow.

6. Both ends matter

A connection from A to B must be allowed by:

  • A's egress rules, if A is isolated for egress;
  • B's ingress rules, if B is isolated for ingress.

With default-deny everywhere, every flow needs two allows: one egress on the client side and one ingress on the server side.

Reply traffic for an allowed connection is handled automatically. Policies are stateful.

7. What policies select

  • Policies apply to pods (by labels) in their own namespace. Services don't matter; traffic is matched after Service translation to pod IPs and ports.
  • So ports means the pod's port (8080), not the Service port (80).
  • Node and host-network traffic, and traffic from outside the cluster, are handled per engine. Use ipBlock for external ranges.

9. Zero trust, briefly

"Zero trust" means not trusting traffic because of where it comes from (inside the cluster) and allowing only what's needed, verified every time.

NetworkPolicies are the network layer of that. Identity-based controls, such as a service mesh's mTLS, and app-level auth complete it.

Isolation, sorted

  • By default every pod can reach every pod.
  • A pod selected by a policy with Ingress (or Egress) becomes isolated in that direction: only listed allows pass.
  • Policies only allow, and they add up; there are no deny rules and no ordering.
  • Both ends must allow a flow; ports are pod ports.
