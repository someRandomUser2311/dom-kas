Allow rules & selector semantics

You'll be able to write precise allow rules with pod and namespace selectors and ports, and avoid the single-dash mistake that opens far more than you meant.

1. Anatomy of an ingress rule

Each item in ingress is one allow rule. It has two parts:

  • from: a list of peers, each a podSelector, a namespaceSelector, both, or an ipBlock.
  • ports: a list of ports and protocols on the destination pod.

Traffic is allowed if it matches any peer in from and any entry in ports.

Windows/IIS admin
Like a firewall rule with a "remote addresses" list and a "local ports" list, except remotes are chosen by labels, not IPs.
Linux admin
Each rule is like -s <set> --dport <port> -j ACCEPT, where the set is computed from labels.
Developer (Compose)
Think "who may call my service, on which port", declared next to your Deployment.
Other clouds
Like security-group rules that reference other security groups instead of CIDRs.

2. Pods in the same namespace

A podSelector on its own, inside from, matches pods in the policy's own namespace.

podSelector:
  matchLabels: { app: orders-api }
policyTypes: [Ingress]
ingress:
  - from:
      - podSelector:
          matchLabels: { app: orders-worker }
    ports:
      - protocol: TCP
        port: 8080

3. Pods in another namespace

A namespaceSelector on its own matches all pods in the matching namespaces.

Every namespace automatically carries the label kubernetes.io/metadata.name: <name>, so you can select a namespace by name reliably.

from:
  - namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: web

4. AND vs OR: the most important detail

Inside from, the YAML dashes decide the meaning:

  • One list item containing both namespaceSelector and podSelector = AND: pods with this label in namespaces with that label.
  • Two list items, one for each = OR: any pod in those namespaces, or pods with that label in the policy's own namespace.

One extra dash changes "only the web pods in namespace web" into "everything in namespace web, plus some local pods".

AND (one item)OR (two items)
from:
  - namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: web
    podSelector:
      matchLabels:
        app: web
from:
  - namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: web
  - podSelector:
      matchLabels:
        app: web

5. Find the dash

This policy was meant to allow only app=web pods from namespace web. Tap the line that turned it into an OR.

ingress:
  - from:
      - namespaceSelector:
          matchLabels:
            kubernetes.io/metadata.name: web
      - podSelector:
          matchLabels:
            app: web
    ports:
      - port: 8080
The - before podSelector starts a second peer. Remove the dash and indent podSelector to line up with namespaceSelector, making one peer with both selectors (AND).

6. Write the precise rule

With default-deny already in orders, allow only app=web pods in namespace web to reach orders-api on TCP 8080.

Live matrix. Success when web/web → orders/orders-api:8080 is ✓, while a test pod web/debug (no app=web label), orders/orders-worker and db/postgres → orders-api are all ✗, and web → orders-api:9090 is ✗.
Solution 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web-to-orders-api
  namespace: orders
spec:
  podSelector:
    matchLabels: { app: orders-api }
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: web }
          podSelector:
            matchLabels: { app: web }
      ports:
        - protocol: TCP
          port: 8080
The AND form plus a port gives exactly one flow. Remember that web's namespace also has default-deny egress, so it needs a matching egress allow (next lesson).

7. Ports

  • port can be a number or a named container port (http).
  • protocol defaults to TCP; add UDP explicitly when needed (DNS uses both).
  • endPort allows a range (port: 30000, endPort: 30100).
  • No ports at all means all ports.

8. ipBlock for things outside the cluster

ipBlock matches IP ranges, with optional except holes. Use it for traffic to or from things that aren't pods: a VNet subnet, a database's private endpoint, an on-premises range.

Don't use it for pod IPs; they change. Use selectors.

egress:
  - to:
      - ipBlock:
          cidr: 10.20.5.0/27
    ports:
      - port: 5432

9. Which flows are open?

Namespace orders has default-deny Ingress only (egress is open everywhere), plus this policy. Which connections to orders-api:8080 succeed?

podSelector:
  matchLabels: { app: orders-api }
policyTypes: [Ingress]
ingress:
  - from:
      - namespaceSelector:
          matchLabels: { kubernetes.io/metadata.name: web }
      - podSelector:
          matchLabels: { app: orders-worker }
    ports:
      - port: 8080
  1. web/web → orders-api
  2. web/debug (any pod in web) → orders-api
  3. orders/orders-worker → orders-api
  4. db/postgres → orders-api Neither peer matches.
  5. payments/orders-worker → orders-api A podSelector alone only matches pods in the policy's own namespace (orders).
Two peers = OR: anything in namespace web, or orders-worker in orders.

10. Label your namespaces deliberately

Selecting by kubernetes.io/metadata.name is precise. Selecting by your own labels (team: shop) is flexible, but anyone who can label namespaces can join the group.

Keep namespace labels under platform-team control; that's another reason the platform team creates namespaces.

11. Let the gateway in

Traffic from the gateway (Chapter 8) must be allowed too. For in-cluster gateways, select the gateway's namespace and pods. For Application Gateway for Containers, allow its subnet with ipBlock.

from:
  - namespaceSelector:
      matchLabels: { kubernetes.io/metadata.name: gateway-infra }

12. One policy per flow

Contoso writes one small policy per allowed flow, named after it:

  • allow-web-to-orders-api
  • allow-orders-api-to-postgres
  • allow-dns

Each is easy to review, and policies being additive means they combine cleanly.

Allow rules, sorted

  • from peers OR together; ports restrict the destination pod's ports.
  • One peer with namespaceSelector + podSelector = AND; separate peers = OR.
  • A podSelector alone means the policy's own namespace; use kubernetes.io/metadata.name for exact namespaces.
  • ipBlock for non-pod ranges; one small policy per flow.
