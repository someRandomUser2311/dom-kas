Incident drills (4 multi-step scenarios)

Each answer reveals the next piece of output. The first-reveal score counts toward the predict weight.

Drill 1 · "Checkout is down." Step 1: kubectl get pods -n orders shows all orders-api pods Running 0/1. Next command?

  1. kubectl describe pod → reveals "Readiness probe failed: … connect: connection refused" on /readyz
  2. Delete all pods
  3. Scale to 0
Step 2 then shows the app logging "listening on 127.0.0.1:8080" since 1.5.1, a bind-address regression. Fix: roll back, then bind to 0.0.0.0.

Drill 2 · "Deploy failed." The log shows Forbidden for user 6c1f… on deployments in orders. Step 1: what changed?

  1. Check recent role assignment changes: the IaC PR moved the role to the wrong namespace scope
  2. The cluster upgrade
  3. The app code
Restore the AKS RBAC Writer assignment at /namespaces/orders via IaC.

Drill 3 · "Pods pending after scale-out." Events: "max node group size reached". Step 1?

  1. Check the pool's max and vCPU quota, then raise max (IaC) and check subnet IPs
  2. Add tolerations
  3. Delete pods
Step 2 shows that quota allows only 2 more nodes, so request a quota increase as well.

Drill 4 · "Intermittent 5xx after policy rollout." The web logs show timeouts to orders-api. Step 1?

  1. Compare the policy matrix: the new default-deny in web lacks the egress allow to orders-api
  2. Raise memory
  3. Restart CoreDNS
"Intermittent" because only new pods picked up policy-enforced paths while connections were cycling. Add the egress allow.

Write lab: fix the broken bundle

Brief: A bundle of Deployment + Service + ConfigMap + NetworkPolicy for orders-api has 5 planted bugs:

  • a readiness path the app doesn't serve;
  • a Service targetPort mismatch;
  • a missing ConfigMap key;
  • a selector typo;
  • a NetworkPolicy that doesn't allow web → orders-api:8080.

Fix them. Graded by manifest-lint, cross-ref and netpol-eval.

  • The readiness probe path is /readyz on the named port.
  • The Service targetPort matches containerPort.
  • Every configMapKeyRef key exists in the ConfigMap.
  • The Service selector matches the pod template labels.
  • The netpol matrix allows web → orders-api:8080 and DNS; everything else stays denied.
  • The fix doesn't replace the NetworkPolicy with allow-all (no ingress: [{}], and default-deny is still present).
  • The Service ends with ready endpoints (selector matches and readiness passes in the simulation).

Walkthrough: a full incident

  1. 02:14: the OrdersApiHighErrorRate alert pages on-call; the Grafana dashboard shows 5xx at 8%.
  2. "What changed?": the canary of 1.6.0 was promoted at 01:50.
  3. Mitigate: kubectl rollout undo; errors drop within 3 minutes.
  4. Diagnose: ContainerLogV2 KQL shows "timeout calling payments" only in 1.6.0; the new HTTP client has no keep-alive, causing SNAT exhaustion (lesson 5.3).
  5. Post-mortem notes: timeline, impact, root cause, action items (connection reuse, NAT gateway, a canary check on the payments error rate).
