Running but unreachable

You'll be able to follow a request hop by hop (client → gateway → Service → endpoints → pod) and find exactly where it breaks.

1. Pods are green, users get errors

Everything shows Running, yet https://shop.contoso.example/api returns 503 or times out. The request passes through several hops, and any one of them can be the broken link:

  1. DNS → the gateway's IP;
  2. the gateway → the route;
  3. route → Service;
  4. Service → endpoints (ready pods);
  5. network policy → pod port;
  6. the app.
A request drawn as a dot moving client → Gateway → HTTPRoute → Service → EndpointSlice → NetworkPolicy → Pod. Each hop has an inspector showing the real output for it. In each scenario one hop is broken and lit red only after the learner inspects it; the learner clicks the hop they think is broken.
Windows/IIS admin
Like tracing a request through the load balancer, ARR, the site binding, then the app: check each hop.
Linux admin
dig → curl the LB → the proxy config → the backend's listen port → iptables.
Developer (Compose)
More hops than Compose's port mapping, so test each one in turn.
Other clouds
Same chain; the gateway product differs.

2. Work from the inside out

Test the pod directly first, then add one hop at a time:

  • kubectl port-forward pod/… 8080:8080 → does the app answer?
  • kubectl port-forward svc/orders-api 8080:80 → does the Service reach it?
  • From another pod: wget orders-api.orders → do DNS and network policy allow it?
  • Through the gateway: curl https://shop…

The first hop that fails is the broken one.

3. Diagnose: readiness

What's wrong?

$ kubectl get pods -n orders -l app=orders-api
NAME                         READY   STATUS    RESTARTS   AGE
orders-api-7d9c5f6b8-2xk9p   0/1     Running   0          20m
orders-api-7d9c5f6b8-q8w4m   0/1     Running   0          20m
$ kubectl get endpointslices -n orders -l kubernetes.io/service-name=orders-api
NAME               ADDRESSTYPE   PORTS   ENDPOINTS   AGE
orders-api-x7k2p   IPv4          8080    <unset>     12d
$ kubectl describe pod orders-api-7d9c5f6b8-2xk9p -n orders | grep -i readiness
    Readiness:  http-get http://:http/ready delay=0s timeout=1s period=5s #success=1 #failure=3
  Warning  Unhealthy  kubelet  Readiness probe failed: HTTP probe failed with statuscode: 404
  1. The selector is wrong A selector mismatch wouldn't make the pods 0/1 ready.
  2. The readiness probe checks /ready, which returns 404, so no pod is ever ready and the Service has no endpoints
  3. The pods crash 0 restarts.
  4. NetworkPolicy The kubelet's probes aren't blocked by NetworkPolicy, and the result here is an HTTP 404.
The app serves /readyz. Fix the probe path. Ready pods then appear in the EndpointSlice and traffic flows.

4. Diagnose: targetPort

Pods are ready and endpoints are listed, but calls fail. Why?

$ kubectl get endpointslices -n orders -l kubernetes.io/service-name=orders-api
NAME               ADDRESSTYPE   PORTS   ENDPOINTS                 AGE
orders-api-x7k2p   IPv4          80      10.244.1.12,10.244.2.7    12d
$ kubectl exec -n web deploy/web -- wget -qO- -T 3 http://orders-api.orders/healthz
wget: can't connect to remote host (10.0.142.17): Connection refused
$ kubectl get pod orders-api-7d9c5f6b8-2xk9p -n orders -o jsonpath='{.spec.containers[0].ports}'
[{"containerPort":8080,"name":"http","protocol":"TCP"}]
  1. The Service's targetPort is 80 (EndpointSlice port 80), but the container listens on 8080
  2. DNS fails The name resolved to the ClusterIP.
  3. NetworkPolicy blocks it A blocked connection usually times out; "refused" means nothing is listening on that port.
  4. The pods aren't ready They're listed as endpoints.
"Connection refused" = reached the pod, but nothing listens on that port. "Timeout" = dropped on the way, often by a policy.

5. Diagnose: NetworkPolicy

What's wrong?

$ kubectl exec -n web deploy/web -- wget -qO- -T 3 http://orders-api.orders/healthz
wget: download timed out
$ kubectl port-forward -n orders svc/orders-api 8080:80 &  curl -s localhost:8080/healthz
ok
$ kubectl get networkpolicy -n orders
NAME                      POD-SELECTOR     AGE
default-deny              <none>           2h
allow-dns                 <none>           2h
allow-gateway-to-api      app=orders-api   2h
  1. The app is broken port-forward reaches it fine.
  2. Default-deny is on in orders, and there's no policy allowing traffic from namespace web to orders-api (and maybe no egress allow in web)
  3. DNS The request got to the wget timeout stage after resolving; allow-dns exists.
  4. targetPort That would be "refused", not a timeout.
port-forward bypasses NetworkPolicy (it goes through the API server and kubelet), so it's a good way to separate "app broken" from "path blocked". Add the web → orders-api allows on both sides (lesson 9.3).

6. Gateway route not attached

$ curl -s -o /dev/null -w "%{http_code}\n" https://shop.contoso.example/api/healthz
404
$ kubectl get httproute orders-api -n orders -o jsonpath='{range .status.parents[*].conditions[*]}{.type}={.status} ({.reason}){"\n"}{end}'
Accepted=False (NotAllowedByListeners)
ResolvedRefs=True (ResolvedRefs)

A 404 from the gateway itself means no route matched. The route status shows it was never attached: allowedRoutes doesn't include namespace orders (lesson 8.4).

7. Find the broken hop

In the follow-the-packet widget, scenario "Black Friday": requests to /api return 503. Inspect hops until you find the broken one, then click it.

Scenario data: Gateway OK; HTTPRoute Accepted and ResolvedRefs True; Service selector app: orders-api, version: green; EndpointSlice empty; pods labelled version: blue. Success when the learner clicks the Service → EndpointSlice hop. Clicking a healthy hop shows its good output and "not here".
A blue/green switch to a colour with no pods (lesson 11.2). The gateway returns 503 because the backend has no endpoints.

8. Status codes as clues

From the gatewayUsually means
404No route matched (host or path, or route not attached)
503The route matched, but the backend has no ready endpoints
502The backend connection failed (wrong port, app reset the connection)
504The backend was too slow (timeout)

9. DNS outside the cluster

Don't forget the first hop. nslookup shop.contoso.example must return the gateway's address. Stale DNS after recreating a gateway or LoadBalancer is a classic cause of "it works for some people".

10. Refused vs timeout

  • Refused: you reached the target IP, but nothing listens on that port. Check targetPort, containerPort and the app's bind address (0.0.0.0, not 127.0.0.1).
  • Timeout: packets were dropped on the way. Check NetworkPolicy, NSGs and firewalls, or a wrong IP.

Unreachable, sorted

  • Inside-out: pod → Service → in-cluster client → gateway → DNS.
  • Not ready → no endpoints; wrong targetPort → refused; policy → timeout; route not attached → gateway 404.
  • port-forward bypasses NetworkPolicy, which helps isolate it.
  • Use status codes and route conditions as clues.
