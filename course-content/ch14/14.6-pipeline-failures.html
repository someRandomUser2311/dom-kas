When the pipeline deploy fails

You'll be able to read a failed deploy step's log, tell a cluster problem from a pipeline problem, and turn on extra diagnostics.

1. Read the log bottom-up

A failed step's last lines say that it failed. The real cause is usually a few lines above, in the tool's own output (kubectl, helm, az).

Classify it first:

  • Can't connect: network or DNS.
  • Not allowed: identity or RBAC.
  • Rejected: the manifest or a policy.
  • Didn't become healthy: the app.
GitHub Actions
Same reading habits; ACTIONS_STEP_DEBUG is the debug switch there.
GitLab CI
Job logs, with CI_DEBUG_TRACE for verbose mode (careful: it can print secrets).
Jenkins
Console output; the same four categories of failure.
Classic pipelines
Same task logs and the same system.debug variable.

2. Diagnose: rollout timeout

The deploy step failed. Where's the problem?

##[section]Starting: KubernetesManifest (deploy)
deployment.apps/orders-api configured
service/orders-api unchanged
/usr/local/bin/kubectl rollout status Deployment/orders-api --timeout 0s --namespace orders
Waiting for deployment "orders-api" rollout to finish: 1 out of 3 new replicas have been updated...
...
error: deployment "orders-api" exceeded its progress deadline
##[error]Error: error: deployment "orders-api" exceeded its progress deadline
##[section]Finishing: KubernetesManifest (deploy)
  1. The service connection is wrong The apply succeeded ("configured"), so connection and permissions worked.
  2. The manifests applied, but the new pods never became ready. It's an app or config problem: switch to the cluster triage (14.1–14.4)
  3. The agent ran out of disk Nothing points to the agent.
  4. kubectl is the wrong version It ran fine.
"configured" then a rollout timeout = Kubernetes accepted the change, but the new version isn't healthy. Roll back (lesson 11.1), then debug the pods.

3. Diagnose: forbidden

What's wrong?

Error from server (Forbidden): error when retrieving current configuration of:
Resource: "apps/v1, Resource=deployments", GroupVersionKind: "apps/v1, Kind=Deployment"
Name: "orders-api", Namespace: "orders"
from server for: "/home/vsts/work/_temp/Deployment_orders-api.yaml": deployments.apps "orders-api" is forbidden:
User "6c1f…" cannot get resource "deployments" in API group "apps" in the namespace "orders":
User does not have access to the resource in Azure. Update role assignment to allow access.
  1. The namespace doesn't exist That would be NotFound.
  2. The service connection's identity lacks an AKS RBAC role (e.g. Writer) on namespace orders
  3. The agent can't reach the cluster It reached the API server, which answered 403.
  4. The YAML is invalid It was parsed fine.
Grant "Azure Kubernetes Service RBAC Writer" on $AKS_ID/namespaces/orders to the pipeline identity (lesson 5.5), ideally in IaC (lesson 12.5).

4. Diagnose: image not found

Build and deploy both passed, but the rollout timed out. The pod events show "not found" for contosoacr.azurecr.io/orders-api:$(Build.BuildId), with that text literally in the tag. Why?

  1. The registry is down The tag is literally the unexpanded text.
  2. The variable wasn't expanded where it was used, for example in a file the pipeline doesn't process, or in a template expression context, so the literal string became the tag
  3. AcrPull is missing That would be 401.
  4. The Docker task failed The Build stage passed and pushed the numeric tag.
Azure Pipelines macro syntax $(…) only expands in task inputs and scripts, not inside files in your repo. Set the image with containers: on KubernetesManifest, kustomize edit set image, or --set image.tag= (lesson 10.6).

5. Can't connect

Unable to connect to the server: dial tcp: lookup aks-orders-prod-x7y8z9.privatelink.westeurope.azmk8s.io: no such host

A private cluster reached from an agent that can't resolve its private DNS name (lesson 6.5). The job ran on the wrong pool, or the agent VNet's DNS isn't set up.

6. Rejected by policy

Error from server (Forbidden): error when creating "deployment.yaml": admission webhook "validation.gatekeeper.sh"
denied the request: [azurepolicy-k8sazurev2containerallowedimages-…] Container image orders-api:1.5.0 for
container api has not been allowed.

A Forbidden from an admission webhook is a policy decision, not RBAC. The manifest breaks a rule. Here the image isn't from the approved registry (the short name lacks contosoacr.azurecr.io/). Chapters 15–16 cover these policies.

7. More detail: system.debug

Queue the run with the variable system.debug = true (or tick "Enable system diagnostics") to get verbose task logs: the exact commands, the inputs as resolved, and HTTP details.

Secret variables stay masked, but review logs before sharing them.

8. Make failures obvious

  • Always run rollout status (or helm --wait), so a bad release fails the pipeline instead of passing silently.
  • Print useful context on failure: kubectl get pods and kubectl describe of failing pods, and recent events, in a step with condition: failed().
  • Link the run to the environment's deployment history and the alert dashboard.
- script: |
    kubectl get pods -n orders -o wide
    kubectl events -n orders --types=Warning | tail -30
  displayName: Diagnostics on failure
  condition: failed()

Pipeline failures, sorted

  • Classify: can't connect (DNS/network), Forbidden (RBAC), denied by webhook (policy), timeout (app health).
  • "configured" + rollout timeout → debug the pods, roll back.
  • $(var) doesn't expand inside repo files; set images through tasks or tools.
  • system.debug for detail; always wait for rollouts; dump diagnostics on failure.
