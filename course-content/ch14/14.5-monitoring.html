Monitoring AKS

You'll be able to turn on AKS logs and metrics, know which data source answers which question, query logs with KQL, and write alerts people don't ignore.

1. Three kinds of telemetry

  • Metrics: numbers over time (CPU, request rate, error rate). Cheap, good for alerts and dashboards.
  • Logs: events and text (container stdout, Kubernetes events, audit logs). For investigating.
  • Traces: one request's path across services (OpenTelemetry → Application Insights). For distributed latency.
Windows/IIS admin
Perfmon counters (metrics), Event Viewer and IIS logs (logs), and Application Insights (traces), all centralised.

Prometheus (metrics), journald/ELK (logs), Jaeger (traces), offered as managed Azure services.

3. Which source answers which question?

Match each question to where you'd look.

Who deleted the orders-api Deployment last night?Control-plane audit logs (kube-audit-admin → AKSAuditAdmin)
What did the app log just before it crashed?Container logs (ContainerLogV2)
Is the 5xx rate above 1% right now?Managed Prometheus metrics
Why didn't the cluster autoscaler add a node at 02:00?Control-plane logs (cluster-autoscaler category)
Which pods were OOMKilled this week?KubeEvents / KubePodInventory (Container Insights)
Metrics for "is something wrong", logs for "what and why", audit for "who".

4. Audit logs: who did what

Which control-plane log category should Contoso enable to answer "who deleted this Deployment?" without the cost of logging every read request?

  1. kube-apiserver API server operational logs, not a per-request audit trail.
  2. kube-audit-admin
  3. kube-audit Includes all requests, reads too, so it's much bigger and pricier. Use it only when you need reads.
  4. guard Entra ID authentication and authorization decisions, useful too, but not the change record.
kube-audit-admin excludes get/list/watch, keeping the writes (create, update, patch, delete) at a fraction of the volume.

5. KQL basics

Log Analytics uses KQL: a table, then a pipeline of operators (where, project, summarize, order by).

ContainerLogV2
| where TimeGenerated > ago(30m)
| where PodNamespace == "orders" and ContainerName == "api"
| where LogMessage has "FATAL"
| project TimeGenerated, PodName, LogMessage
| order by TimeGenerated desc

Find who deleted Deployments in namespace orders.

AKSAuditAdmin
| ? Verb == "delete" and ObjectRef.resource == "deployments" and ObjectRef.namespace == "orders"
| project TimeGenerated, User.username, ObjectRef.name, SourceIps
  • where
  • filter KQL's filter operator is where.
  • select That's SQL; KQL uses project for columns.
  • grep Not KQL.
where filters rows; project picks columns.

6. The four golden signals

For each user-facing service, track:

  • Latency (p95/p99, successful vs failed);
  • Traffic (requests per second);
  • Errors (5xx rate);
  • Saturation (CPU and memory against limits, queue depth).

Expose them from the app (/metrics, scraped by managed Prometheus), and build one Grafana dashboard per service.

sum(rate(http_requests_total{namespace="orders",app="orders-api",code=~"5.."}[5m]))
/ sum(rate(http_requests_total{namespace="orders",app="orders-api"}[5m]))

7. Alerts that matter

  • Alert on symptoms users feel, such as a high error rate or latency (SLO burn), not on every pod restart.
  • Turn on the recommended alerts for AKS: node NotReady, pods OOMKilled, CPU/memory saturation, PV usage.
  • Every alert needs an owner and a runbook link. An alert nobody acts on trains people to ignore alerts.
  • Route by severity: page for user impact, email or ticket for slow-burning issues (certificates expiring in 14 days).

8. A Prometheus alert rule

- alert: OrdersApiHighErrorRate
  expr: |
    sum(rate(http_requests_total{app="orders-api",code=~"5.."}[5m]))
    / sum(rate(http_requests_total{app="orders-api"}[5m])) > 0.02
  for: 10m
  labels: { severity: page, team: orders }
  annotations:
    summary: "orders-api 5xx above 2% for 10 minutes"
    runbook: "https://dev.azure.com/contoso/orders/_wiki/runbooks/high-error-rate"

This same signal is what the canary check (lesson 11.4) and the environment's "Query Azure Monitor alerts" gate use.

9. Cost control

  • Log ingestion is the usual cost surprise. Collect less: filter namespaces in the agent's ConfigMap or data collection rule, and drop chatty debug logs.
  • Use the Basic logs tier for high-volume, rarely queried tables.
  • Metrics are much cheaper than logs, so count things in metrics and keep the details in logs.
  • Set retention per table.

10. Monitoring as code

Workspaces, data collection rules, alert rules and Grafana dashboards are Azure resources. Define them in Terraform or Bicep (Chapters 12–13), next to the cluster, so every environment gets the same monitoring.

Monitoring, sorted

  • Container Insights (logs, events, inventory) + managed Prometheus (metrics) + Grafana + diagnostic settings (control plane).
  • Audit: kube-audit-admin for "who changed what".
  • KQL: table | where | project | summarize.
  • Golden signals; alert on symptoms, with owners and runbooks; watch ingestion cost.
