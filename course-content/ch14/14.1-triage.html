A triage method

You'll be able to work through any broken workload in the same order, every time, and use logs from crashed containers and ephemeral debug containers.

1. Don't guess, follow the path

Under pressure, people restart things at random. A fixed order is faster:

  1. get: what's the state? (kubectl get deploy,rs,pods -n orders)
  2. describe: what does Kubernetes say about it? (conditions, the last state, events)
  3. events: what happened recently, in order?
  4. logs: what did the app say? (including --previous)
  5. exec / debug: look from inside.
Windows/IIS admin
It's like Services snap-in → Event Viewer → the app's log files → RDP onto the box, in that order.
Linux admin
It's systemctl status → journalctl → app logs → nsenter/strace, translated to Kubernetes.
Developer (Compose)
docker compose ps → docker inspect → logs → exec, plus a controller layer on top.
Other clouds
Identical on EKS and GKE. Cloud specifics only come in for image pulls, load balancers and identity.

2. Top-down: Deployment → ReplicaSet → Pod → container

Start at the top. If the Deployment says 0/3 available, check its ReplicaSets: did the new one create pods at all? Quota and admission errors show up only on the ReplicaSet (lesson 8.2). Then go to the pods, then the containers in them.

$ kubectl get deploy,rs,pods -n orders -l app=orders-api
NAME                         READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/orders-api   2/3     1            2           12d

NAME                                    DESIRED   CURRENT   READY   AGE
replicaset.apps/orders-api-5b6f4c9d7    1         1         0       6m
replicaset.apps/orders-api-7d9c5f6b8    2         2         2       3d

NAME                              READY   STATUS             RESTARTS      AGE
pod/orders-api-5b6f4c9d7-kx8q2    0/1     CrashLoopBackOff   5 (40s ago)   6m
pod/orders-api-7d9c5f6b8-2xk9p    1/1     Running            0             3d
pod/orders-api-7d9c5f6b8-q8w4m    1/1     Running            0             3d

Read it: a rollout is in progress, the new ReplicaSet's single pod is crash-looping, and the old pods are still serving. Users are fine. The new version is broken.

3. Events are short-lived

Events are kept for about an hour by default, then they're gone. Look at them early, and send them to Log Analytics (Container Insights) so they survive.

kubectl events sorts them properly and can filter by object.

kubectl events -n orders --for pod/orders-api-5b6f4c9d7-kx8q2
kubectl events -n orders --types=Warning

4. Logs of the container that died

In a crash loop, the current container has just started and may have logged nothing yet. The reason it died is in the previous container's logs.

Show the logs of the previous (crashed) instance of pod orders-api-5b6f4c9d7-kx8q2 in namespace orders.

kubectl logs orders-api-5b6f4c9d7-kx8q2 -n orders --previous

Also accepted: -p for --previous; --namespace; -c api; flags in any order.

With several containers, add -c <name>.
$ kubectl logs orders-api-5b6f4c9d7-kx8q2 -n orders --previous
2026/11/05 10:12:01 starting orders-api 1.5.0
2026/11/05 10:12:01 FATAL: required env var PAYMENTS_URL is not set

5. Look from inside: kubectl debug

Distroless images have no shell (lesson 1.5). kubectl debug adds an ephemeral container with tools to a running pod.

It shares the pod's network, and, with --target, its process namespace. You can then curl localhost, check DNS, and see the app's processes, without changing the image.

kubectl debug -it orders-api-7d9c5f6b8-2xk9p -n orders \
  --image=busybox:1.36 --target=api -- sh
# inside: wget -qO- localhost:8080/readyz; nslookup postgres.db; ps

For a pod that crashes too fast to attach to, kubectl debug pod/x --copy-to=x-debug --container=api -- sh makes a copy with a changed command. For node problems: kubectl debug node/<name> -it --image=…. Ephemeral containers need RBAC permission on pods/ephemeralcontainers, which you won't have in prod by default. That's good.

6. Put the steps in order

A Deployment shows 0/3 available. Order your first steps.

  1. kubectl get deploy,rs,pods to see where it's stuck
  2. kubectl describe the failing pod (or the ReplicaSet if there are no pods)
  3. Read the recent Warning events
  4. kubectl logs --previous if containers are restarting
  5. kubectl debug to test from inside, if still unclear
Cheap, broad checks first; deeper tools only when needed.

8. What changed?

Most incidents follow a change. Ask early: what was deployed, applied or upgraded recently?

  • kubectl rollout history and helm history.
  • The pipeline's environment deployment history.
  • The AKS activity log, for upgrades and node-image updates.

A recent bad change is often fixed fastest by rolling it back, then investigating calmly.

9. Mitigate first, then diagnose

If users are affected, restore service first: roll back, scale up, or fail over. Then find the cause. Keep notes as you go (commands, times, findings); they become the post-mortem.

Triage, sorted

  • get → describe → events → logs (--previous) → debug.
  • Top-down: Deployment → ReplicaSet → Pod → container.
  • Events expire within about an hour; ship them to Log Analytics.
  • kubectl debug adds tools without changing the image.
  • Ask "what changed?"; mitigate, then diagnose.
