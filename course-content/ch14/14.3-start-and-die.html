Pods that start and die

You'll be able to diagnose CrashLoopBackOff, OOMKilled and probe-driven restarts from logs, exit codes and events.

1. CrashLoopBackOff explained

The container starts and then exits. The kubelet restarts it, waiting longer each time: 10 s, 20 s, 40 s… up to 5 minutes. CrashLoopBackOff is that waiting state. It's a symptom, not a cause.

The cause is in three places:

  • the previous container's logs;
  • its exit code;
  • the events (probe failures).
Windows/IIS admin
Like an app pool hitting rapid-fail protection: something crashes it repeatedly, and the event log and app logs say what.
Linux admin
Like systemd's Restart=always with RestartSec backing off. Check ExecMainStatus = the exit code.
Developer (Compose)
Same as a Compose service with restart: always that keeps exiting. docker logs = kubectl logs --previous.
Other clouds
Identical everywhere.

2. Exit codes

Match each exit code to its usual meaning.

0Exited normally, but a Deployment's container should never exit
1General application error (read the logs)
137Killed with SIGKILL (128 + 9): OOMKilled, or killed after the grace period
143Terminated by SIGTERM (128 + 15), normally during shutdown
127Command not found: a wrong command/args, or a missing binary
Exit codes above 128 mean "killed by signal (code − 128)".

3. Diagnose: the app error

What's wrong?

$ kubectl describe pod orders-api-5b6f4c9d7-kx8q2 -n orders | grep -A4 "Last State"
    Last State:     Terminated
      Reason:       Error
      Exit Code:    1
$ kubectl logs orders-api-5b6f4c9d7-kx8q2 -n orders --previous
2026/11/05 10:12:01 starting orders-api 1.5.0
2026/11/05 10:12:01 connecting to database host=orders-db.postgres.database.azure.com
2026/11/05 10:12:31 FATAL: failed to connect: dial tcp 10.20.5.9:5432: i/o timeout
  1. Out of memory The exit code is 1, not 137.
  2. The app can't reach the database on 5432 and exits, most likely an egress NetworkPolicy or a database firewall rule
  3. The image is wrong It started and logged its version.
  4. A liveness probe kills it That would show "Liveness probe failed" events, and usually exit code 137 or 143.
A timeout to a private IP points at network policy (lesson 9.4) or the database firewall or private endpoint. Test from inside with kubectl debug and nc -zv 10.20.5.9 5432.

4. Diagnose: the bad command

What's wrong?

    Last State:     Terminated
      Reason:       StartError
      Message:      failed to create containerd task: failed to create shim task: OCI runtime create failed:
                    runc create failed: unable to start container process: exec: "/app/orders-api": stat
                    /app/orders-api: no such file or directory: unknown
      Exit Code:    128
  1. The command points to /app/orders-api, but the image's binary is /orders-api
  2. Missing permissions That would say "permission denied".
  3. The node is broken The runtime is working fine; the path is wrong.
  4. The ConfigMap is missing That gives CreateContainerConfigError.
An override of command in the manifest no longer matches the image (lesson 1.1's Dockerfile uses /orders-api). Remove the override, or fix the path.

5. OOMKilled

The pod restarts every ~20 minutes under load. What's the cause, and the first fix?

    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137
    Limits:
      memory:  256Mi
$ kubectl top pod orders-api-7d9c5f6b8-2xk9p -n orders
NAME                         CPU(cores)   MEMORY(bytes)
orders-api-7d9c5f6b8-2xk9p   310m         251Mi
  1. Raise the CPU limit CPU is throttled, never OOM-killed.
  2. Memory grows to the 256Mi limit and the kernel kills it. Raise the memory request and limit from measured peaks, and check for a leak
  3. Add a liveness probe It'd still be killed at the limit.
  4. Delete the pod The next one hits the same limit.
If memory climbs steadily over hours, it's a leak: raising the limit only delays it. Container Insights' memory charts per pod show the pattern.

6. Probe-driven restarts

Restarts climb on every pod at the same time, but there's nothing in the app logs. Why?

Events:
  Warning  Unhealthy  kubelet  Liveness probe failed: Get "http://10.244.1.12:8080/health/db": context deadline exceeded
  Normal   Killing    kubelet  Container api failed liveness probe, will be restarted
  1. The app crashes The kubelet is killing it, not the app exiting.
  2. The liveness probe calls the database health endpoint; the slow database makes it time out, so every pod is restarted
  3. Readiness is failing Readiness doesn't restart pods.
  4. Out of memory There'd be an OOMKilled reason.
The death spiral from lesson 3.3. Point liveness at /healthz (the process only), and increase timeoutSeconds.

7. Containers that exit 0

A Deployment's container that exits successfully still gets restarted, and still crash-loops. That happens when the process daemonises (runs in the background and the main process exits), or when a script finishes. Containers must run their main process in the foreground.

8. Missing configuration at runtime

An app that checks its config on start ("PAYMENTS_URL is not set", lesson 14.1) exits 1 straight away. That's a good design: failing fast beats running half-configured. Fix the ConfigMap or Secret, and the rollout recovers.

9. Stop the crash loop while you investigate

  • If a rollout caused it: kubectl rollout undo. Old pods are still serving with maxUnavailable: 0.
  • To keep a pod alive for inspection, use kubectl debug --copy-to with -- sleep 3600.
  • Don't "fix" it by removing probes or limits. That hides the problem and causes new ones.

10. Node-level causes

If many unrelated pods on one node fail, look at the node: kubectl describe node for conditions (MemoryPressure, DiskPressure), and evictions in events. AKS's node auto-repair replaces nodes that are NotReady for too long.

Start and die, sorted

  • CrashLoopBackOff = restarts with back-off; the cause is in logs --previous, the exit code and events.
  • 1 = app error; 137 = SIGKILL (OOM); 143 = SIGTERM; 127/128 = command problems.
  • OOM: measure, then right-size, and watch for leaks.
  • Liveness on dependencies = synchronised restarts.
  • Roll back first if a release caused it.
