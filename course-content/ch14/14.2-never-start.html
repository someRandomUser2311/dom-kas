Pods that never start

You'll be able to diagnose Pending, ImagePullBackOff and CreateContainerConfigError from real describe output, and pick the right fix.

1. Three ways to never start

  • Pending: the pod isn't scheduled, or is waiting for a volume. The scheduler's events explain why.
  • ImagePullBackOff: scheduled, but the kubelet can't fetch the image.
  • CreateContainerConfigError: the image is there, but something the container needs (a ConfigMap or Secret key) is missing.

In every case, the answer is in kubectl describe pod's Events.

Windows/IIS admin
Like a service that won't start because the server is full, the installer can't be downloaded, or a config file is missing. The event log says which.
Linux admin
Scheduling failure ≈ no host fits; image pull ≈ the package repository is unreachable; config error ≈ a missing EnvironmentFile.
Developer (Compose)
docker compose up fails on pull or on a missing env file in much the same way.
Other clouds
The messages match EKS and GKE, apart from registry authentication details.

2. Pending: diagnose #1

What's the cause?

Name:       orders-worker-6b9d7c8f4-v2m8k
Status:     Pending
Containers:
  worker:
    Requests:  cpu: 4, memory: 2Gi
Events:
  Type     Reason            From               Message
  Warning  FailedScheduling  default-scheduler  0/5 nodes are available: 2 node(s) had untolerated taint
           {CriticalAddonsOnly: true}, 3 Insufficient cpu. preemption: 0/5 nodes are available:
           2 Preemption is not helpful for scheduling, 3 No preemption victims found for incoming pod.
  Normal   NotTriggerScaleUp cluster-autoscaler pod didn't trigger scale-up: 1 max node group size reached
  1. It needs a toleration for CriticalAddonsOnly Those are the system nodes; apps should stay off them.
  2. It requests 4 CPUs; the user nodes don't have that free, and the user pool is already at its autoscaler max
  3. The image is wrong It isn't scheduled yet, so no pull was attempted.
  4. The scheduler is down The scheduler is clearly answering.
Fix: lower the request if 4 CPUs isn't really needed (check usage), or raise the pool's max count, or add a bigger pool. The system-node taint is working as intended.

3. Pending: diagnose #2 (volumes)

What's the cause?

Events:
  Warning  FailedScheduling  default-scheduler  0/5 nodes are available: 1 node(s) had volume node affinity conflict,
           2 node(s) had untolerated taint {CriticalAddonsOnly: true}, 2 Insufficient memory.
$ kubectl get pv pvc-7f2… -o jsonpath='{.spec.nodeAffinity}'
{"required":{"nodeSelectorTerms":[{"matchExpressions":[{"key":"topology.kubernetes.io/zone","operator":"In","values":["westeurope-1"]}]}]}}
  1. The pod's disk is in zone 1; the only zone-1 user node is full, so the pod can't run anywhere its disk can attach
  2. The PVC isn't bound The PV exists and is bound; the issue is its zone.
  3. The StorageClass is wrong The class worked; LRS disks are simply zonal.
  4. Memory limits are too low "Insufficient memory" refers to node capacity against requests.
Zonal disks pin pods to a zone (lesson 3.4). Make sure each zone has spare capacity (autoscaler min per zone), or use ZRS disks for workloads that must move between zones.

4. ImagePullBackOff: diagnose #3

What's the cause?

Events:
  Normal   Pulling   kubelet  Pulling image "contosoacr.azurecr.io/orders-api:1.5.0"
  Warning  Failed    kubelet  Failed to pull image "contosoacr.azurecr.io/orders-api:1.5.0": rpc error: code = NotFound
           desc = failed to pull and unpack image "contosoacr.azurecr.io/orders-api:1.5.0": failed to resolve reference
           "contosoacr.azurecr.io/orders-api:1.5.0": contosoacr.azurecr.io/orders-api:1.5.0: not found
  Warning  Failed    kubelet  Error: ErrImagePull
  Normal   BackOff   kubelet  Back-off pulling image "contosoacr.azurecr.io/orders-api:1.5.0"
  1. The kubelet lacks AcrPull That would be 401 Unauthorized, not "not found".
  2. The tag 1.5.0 doesn't exist in the registry: never pushed, or a typo
  3. DNS for the registry fails The registry answered.
  4. The node is out of disk That's a different message.
Check with az acr repository show-tags -n contosoacr --repository orders-api. Usually the build failed or pushed a different tag. The pipeline should deploy the tag it just pushed (lesson 10.6).

6. CreateContainerConfigError: diagnose #4

The pod shows CreateContainerConfigError. What's the cause?

Events:
  Warning  Failed  kubelet  Error: couldn't find key PAYMENTS_URL in ConfigMap orders/orders-api-config
  1. The ConfigMap doesn't exist It exists; the message says a key is missing from it.
  2. The Deployment references key PAYMENTS_URL, which isn't in orders-api-config
  3. The image is wrong The image pulled fine; the container couldn't be configured.
  4. RBAC blocks ConfigMaps The kubelet can read the ConfigMaps its pods use.
Add the key, or mark the reference optional: true if the app can live without it. With Kustomize's configMapGenerator, check that the overlay actually includes the key (kubectl kustomize).

7. Pending forever with no events?

If a pod shows nothing from the scheduler, check two things:

  • Is there a scheduler for it? A custom schedulerName nobody runs leaves pods Pending with no events.
  • Does the pod exist at all? Look at the ReplicaSet's events for quota or admission rejections (lesson 8.2) and policy denials (Chapter 15).

8. Admission rejections look different

$ kubectl describe rs orders-api-5b6f4c9d7 -n orders | tail -2
  Warning  FailedCreate  replicaset-controller  Error creating: admission webhook "validation.gatekeeper.sh" denied
           the request: [azurepolicy-k8sazurev3allowedimages] Container image docker.io/library/nginx:latest for
           container web has not been allowed.

The pod was never created. A policy (Chapter 16) rejected it. The fix is in the manifest, not the cluster.

9. Init containers

Init:0/1 or Init:CrashLoopBackOff means an init container hasn't finished (lesson 2.1). Read its logs: kubectl logs pod -c <init-container-name>. A wait-for-database loop stuck because of a network policy is a classic case.

10. Fix and verify

After a fix, watch it land: kubectl rollout status for template changes, or kubectl get pods -w. For changes outside the pod (AcrPull, quota, DNS), the kubelet or ReplicaSet controller retries automatically with back-off, so it can take a minute. Deleting the stuck pod forces an immediate retry.
