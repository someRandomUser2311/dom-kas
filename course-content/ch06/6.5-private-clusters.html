Private clusters

You'll be able to explain how a private AKS cluster's API server is reached, fix the DNS problems that come with it, and pick a way in for people and pipelines.

1. No public API server

In a private cluster, the API server has no public endpoint. AKS creates a private endpoint for it in your node subnet, with a private IP such as 10.20.0.4. Only networks that can route to that IP, and resolve its name, can manage the cluster.

az aks create ... --enable-private-cluster
Windows/IIS admin
Like taking remote management off the internet completely: you must be on the corporate network, or use a jump server, to administer it.
Linux admin
The API server is now only on an internal interface; you need a bastion or VPN.
Developer (Compose)
Your laptop can't kubectl directly unless it's on the VPN. That's the point.
Other clouds
Like EKS with endpoint private access only, or a GKE private cluster with no public endpoint.

2. Private doesn't mean isolated

"Private cluster" is only about the API server. It doesn't by itself mean:

  • nodes have no internet: egress is the outbound type (lesson 5.3);
  • apps are private: that depends on your Services and gateways;
  • the registry is private: that's ACR's private endpoint (lesson 6.3).

A fully private design combines all of them.

3. DNS is the hard part

The API server's name looks like aks-orders-prod-x7y8z9.privatelink.westeurope.azmk8s.io. AKS creates a private DNS zone, privatelink.westeurope.azmk8s.io, containing an A record pointing at the private IP. By default the zone is linked to the cluster's VNet only.

Any client in another VNet (a hub, a peered agent VNet, on-premises through a DNS forwarder) must be able to resolve that zone. Otherwise the name isn't found, even if the network route works.

A network diagram: a spoke VNet with AKS and its private endpoint; a hub VNet with a DNS resolver and Azure Firewall; a peered "agents" VNet; a laptop on VPN; a Microsoft-hosted agent on the internet. 4. Diagnose the DNS failure

A self-hosted agent in a peered VNet runs kubectl apply. What's wrong?

E1103 10:14:22 memcache.go:265] couldn't get current server API group list:
Get "https://aks-orders-prod-x7y8z9.privatelink.westeurope.azmk8s.io:443/api?timeout=32s":
dial tcp: lookup aks-orders-prod-x7y8z9.privatelink.westeurope.azmk8s.io on 168.63.129.16:53: no such host
  1. The agent lacks an RBAC role That would be a 403 after connecting; this fails at name lookup.
  2. The private DNS zone isn't linked to the agent's VNet (or its custom DNS doesn't forward to Azure DNS for that zone)
  3. VNet peering is missing Peering problems show as a timeout after DNS succeeds.
  4. Authorized IP ranges block the agent Authorized ranges don't apply to private clusters.
"no such host" = DNS. Link privatelink.westeurope.azmk8s.io to the agent VNet, or, in hub-and-spoke, use a central zone linked to the hub and point spokes' DNS at a hub DNS Private Resolver. Then check the route (peering), then RBAC.

5. Hub-and-spoke DNS done right

In enterprise networks, a central team owns DNS:

  • a custom private DNS zone in a hub subscription, passed to AKS with --private-dns-zone <zone-id>;
  • the cluster identity gets Private DNS Zone Contributor on that zone;
  • all spokes and on-premises resolve through the hub's Azure DNS Private Resolver.

Decide this before creating the cluster. The DNS zone option can't simply be changed later.

6. Way in #1: a jump box

A small VM in the VNet (or a peered one), reached through Azure Bastion, with az and kubectl installed. Engineers connect to it and run commands from there.

It's simple and familiar, but it's another VM to patch, and access must be controlled.

7. Way in #2: az aks command invoke

az aks command invoke sends a command through Azure's management API. AKS runs it in a temporary pod inside the cluster and returns the output.

There's no network path to the API server needed and no VNet access. It needs your Azure role on the cluster and nothing else, which makes it great for occasional admin tasks and emergencies.

It isn't built for high-volume or long-running work, and it's slower than kubectl.

az aks command invoke -g rg-orders-prod -n aks-orders-prod \
  --command "kubectl get pods -n orders"

# send files along and apply them
az aks command invoke -g rg-orders-prod -n aks-orders-prod \
  --command "kubectl apply -f deployment.yaml -n orders" \
  --file deployment.yaml

8. Way in #3: agents inside the network

For pipelines, run the agent inside the network, in the same or a peered VNet with DNS resolving:

  • Managed DevOps Pools: Azure creates and recycles agent VMs in your subnet, so you don't patch agents yourself. Recommended.
  • Self-hosted agents on a VM Scale Set (the older "scale set agents").
  • Self-hosted agents running as pods, possibly in the cluster itself (careful: an agent that deploys the cluster it runs on).
GitHub Actions
Same pattern: self-hosted runners, or Azure private networking for GitHub-hosted runners, inside the VNet.
GitLab CI
A GitLab runner deployed into the VNet.
Jenkins
Your Jenkins agents need a route and DNS into the VNet. Same rules.
Classic pipelines
Deployment groups and agents work the same; just place them in the VNet.

9. Get the agent working

In the network diagram, place the release pipeline's agent so it can deploy to the private aks-orders-prod.

Success when the agent is a Managed DevOps Pool (or self-hosted agent) in the AKS VNet, or in a peered VNet with the private DNS zone linked or resolvable via the hub resolver, so both lights are green. Feedback per position:
  • Microsoft-hosted: "No route to a private IP."
  • Peered VNet without the DNS link: "no such host."
  • Laptop off VPN: "No route."
Two conditions, both required: a network route to the private endpoint, and DNS that resolves the privatelink name. RBAC is the third check once connected.

10. Way in #4: API Server VNet Integration

API Server VNet Integration places the API server directly into a delegated subnet of your VNet, reached through an internal load balancer instead of a private endpoint.

It can be switched between private and public access without recreating the cluster, and node-to-API traffic stays inside your VNet.

DNS and agent placement rules are the same as for private clusters. Check its current regional availability when choosing it.

11. "Public FQDN" for private clusters

The --enable-public-fqdn option adds a public DNS name that resolves to the cluster's private IP. That avoids private DNS zone links for clients that already have a network route.

It's a convenience trade-off. The API is still only reachable over the private network, but the private IP is now discoverable through public DNS.

12. Connection checklist

  1. DNS: nslookup <api fqdn> from the client returns the private IP.
  2. Route: nc -vz <private ip> 443 succeeds (peering, UDRs, NSGs, firewall).
  3. Identity: kubectl auth can-i … returns yes (Azure RBAC).

Private clusters, sorted

  • The API server becomes a private endpoint; there's no public access.
  • DNS (privatelink.<region>.azmk8s.io) must resolve from every client VNet; "no such host" = DNS.
  • Ways in: jump box + Bastion, az aks command invoke, Managed DevOps Pools / self-hosted agents in the VNet, VPN.
  • API Server VNet Integration is the alternative design.
  • Check in order: DNS → route → RBAC.
