ACR hardening

You'll be able to take a registry off the public internet, limit access per repository, keep it tidy, and know what that means for your build agents.

1. A registry is a high-value target

Whoever can push to your registry can run code in your clusters. Whoever can pull can read your images, including anything accidentally baked into them.

Hardening ACR means two things:

  • shrink who can reach it: network;
  • shrink what each identity can do: permissions.
Windows/IIS admin
Like moving the build share off the DMZ and onto an internal-only network, with per-folder permissions.
Linux admin
Like a package repository reachable only from inside the network, behind proper authentication.
Developer (Compose)
Your laptop may no longer reach the registry directly. That's on purpose.
Other clouds
Like ECR with VPC endpoints and a repository policy, or Artifact Registry with VPC Service Controls.

2. Private endpoints (Premium)

A private endpoint gives the registry an IP inside your VNet, such as 10.20.5.4, with DNS from the privatelink.azurecr.io private zone. AKS nodes then pull over the VNet.

Then set public network access to Disabled. The registry is no longer reachable from the internet at all.

A registry has two endpoints, and both get private IPs: the login server and a regional data endpoint (contosoacr.westeurope.data.azurecr.io), where image layers come from.

az network private-endpoint create -g rg-orders-net -n pe-contosoacr \
  --vnet-name vnet-orders --subnet snet-private-links \
  --private-connection-resource-id $(az acr show -n contosoacr --query id -o tsv) \
  --group-id registry --connection-name contosoacr

az acr update -n contosoacr --public-network-enabled false

The private DNS zone privatelink.azurecr.io must be linked to every VNet that needs to resolve the registry: the AKS VNet, the build agent's VNet, or a hub VNet whose DNS the spokes use.

3. The build agent problem

Contoso disables public access on ACR. The pipeline, running on a Microsoft-hosted agent, still runs docker push contosoacr.azurecr.io/orders-api:1.5.0. What happens?

  1. It works, because the agent runs in Azure Microsoft-hosted agents run in Microsoft's network, not in your VNet.
  2. The push fails: the agent can only reach the public endpoint, which is now disabled
  3. It works, because the pipeline uses a service connection The service connection proves identity; it doesn't provide a network path.
  4. It pushes to a public mirror instead There's no such fallback.
Locking down a resource's network means everything that talks to it must be inside the network: AKS nodes and build agents. Use a self-hosted agent or a Managed DevOps Pool in your VNet, or az acr build with a dedicated agent pool. It's the same lesson as private clusters (6.5).

4. Trusted services and firewall rules

Between "fully public" and "fully private" there are two middle grounds:

  • Firewall rules that allow specific public IP ranges.
  • Allow trusted Microsoft services, which lets certain Azure services, such as Defender scanning and ACR Tasks with managed identity, reach a locked-down registry.

Use them sparingly. Private endpoints are the clean answer.

5. Least privilege per repository

By default, roles like AcrPush and AcrPull apply to every repository in the registry.

Newer ACR repository permissions use role assignments with ABAC conditions (for example, "Container Registry Repository Writer" only on repositories starting with orders/). One team's pipeline can then push only its own images.

Scope maps and tokens also exist, for clients that can't use Entra ID. They're useful, but they're stored credentials.

6. Keeping it tidy

Every build pushes a new image, and storage grows forever. Two tools keep it in check:

  • acr purge as a scheduled ACR task, for example: delete tags older than 30 days, keep the last 10.
  • A retention policy for untagged manifests.

Never purge the tags or digests that production is running. Lock them with --write-enabled false, or exclude them with a filter.

az acr task create -r contosoacr -n purge-old \
  --cmd "acr purge --filter 'orders-api:^ci-.*' --ago 30d --keep 10 --untagged" \
  --schedule "0 3 * * Sun" --context /dev/null

7. Geo-replication

Premium registries can replicate to other regions. Clusters in each region pull from a nearby replica under the same login server, and the registry survives a regional outage.

Contoso, in one region, doesn't need it yet.

8. Requirement → feature

Match each requirement to the ACR feature.

The registry must not be reachable from the internetPrivate endpoint + public network access disabled
Team A's pipeline may only push to teamA/*Repository permissions with ABAC conditions
Clusters in two regions pull locallyGeo-replication
Storage keeps growing from CI imagesA scheduled acr purge task
Only signed images may be deployedImage signing + admission policy (Chapter 16)
Network, permissions, availability, hygiene and supply-chain trust are five separate controls.

ACR hardening, sorted

  • Private endpoint (Premium) + public access disabled; link the privatelink.azurecr.io zone.
  • Build agents must be inside the network too.
  • Repository-scoped permissions (ABAC); avoid tokens and the admin user.
  • Purge old tags on a schedule; geo-replicate for multi-region.
  • Signing and admission policy come in Chapter 16.
