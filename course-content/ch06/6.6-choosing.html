Choosing & deploying

You'll be able to pick the right API server exposure for a given organisation, and say exactly what changes in the deploy step for each option.

2. A decision tree

  1. Does policy forbid any public management endpoint? → Private (or VNet Integration).
  2. Do you already have a hub network, private DNS and agents in Azure? → private is cheap for you; prefer it.
  3. Are all clients (people, agents) at known, fixed IPs? → Public + authorized IPs.
  4. Small team, no network platform yet? → Public, with Entra ID + RBAC and local accounts disabled, then move up.

3. Scenario: a bank

A bank's security standard says "no management interfaces reachable from the internet". It has a hub-and-spoke network with Azure Firewall and on-premises connectivity. Which option?

  1. Public with Entra ID The endpoint is still on the internet.
  2. Public + authorized IPs Still a public endpoint, just filtered.
  3. Private cluster (or API Server VNet Integration in private mode), with agents in Managed DevOps Pools
  4. Any; RBAC is enough The standard is about network exposure, not just auth.
The hub network and DNS already exist, so private adds little extra effort.

4. Scenario: a startup

A five-person startup, fully remote, no VPN, deploys with Azure Pipelines on Microsoft-hosted agents. What's a sensible start?

  1. Public API server with Entra ID + Azure RBAC, local accounts disabled, and humans with read-only access by default
  2. Private cluster They'd need agents in a VNet, DNS and a way in, a lot of platform work for five people.
  3. Public + authorized IPs With home IPs and hosted agents changing constantly, the list would never be right.
  4. Public with local accounts Static admin credentials are the bigger risk.
Strong identity first; network restrictions once there are fixed IPs or a private network to rely on.

5. Scenario: an internal tool

An internal HR tool on AKS. Staff always work from the office or over the corporate VPN, which has two fixed egress IPs. Builds run on a Managed DevOps Pool with a NAT gateway. Cheapest acceptable option?

  1. Public with no restrictions It works, but you can easily do better here.
  2. Public + authorized IP ranges (office, VPN, NAT gateway IP)
  3. Private cluster Fine, but more effort than needed for this case.
  4. Disable the API server Not possible.
All clients have fixed IPs, so an allow-list is easy to keep accurate.

7. Deploying with command invoke

#!/usr/bin/env bash
set -euo pipefail
RG=rg-orders-prod
CLUSTER=aks-orders-prod

# runs inside the cluster through the Azure management API, with no network path to the API server needed
az aks command invoke -g "$RG" -n "$CLUSTER" \
  --command "kubectl apply -n orders -f k8s/base/" \
  --file .        # attaches the current folder; paths in --command are relative to it

It's good for small teams or as a fallback. For regular, high-volume releases, an in-VNet agent is faster and gives normal kubectl output and rollout status.

8. What's required for private deploys

Contoso's release pipeline must deploy to the private aks-orders-prod using KubernetesManifest@1. Select everything that's required.

  1. An agent with a network route to the API server's private endpoint (e.g. a Managed DevOps Pool in a peered VNet)
  2. DNS on that agent resolves the privatelink.westeurope.azmk8s.io name
  3. The service connection's identity has an AKS RBAC role on the target namespace
  4. Authorized IP ranges containing the agent's IP Authorized ranges don't apply to private clusters.
  5. The ACR admin user enabled Never needed; the kubelet identity pulls.
  6. A public IP on the agent VM The agent needs outbound access to Azure DevOps, not a public IP.
Route + DNS + identity: the same three checks as lesson 6.5, step 12.

9. Contoso's choice

  • Dev: public API server, Entra ID + Azure RBAC, local accounts off, authorized IPs for the office and the agent pool's NAT IP.
  • Prod: private cluster in a spoke VNet, a central private DNS zone in the hub, and a Managed DevOps Pool in a peered agents VNet. Humans read-only, with PIM for changes.

Chapter 7 builds the pipeline that deploys to both.

Choosing, sorted

  • Public → public + authorized IPs → private / VNet Integration: more protection, more platform work.
  • Let policy, existing network, and client IPs decide.
  • Private deploys need route + DNS + identity; command invoke is the fallback.
