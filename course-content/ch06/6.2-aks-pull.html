Letting AKS pull

You'll be able to connect a cluster to ACR so images pull without any secrets, and diagnose an ImagePullBackOff in under a minute.

1. Who pulls the image?

Lesson 5.4 answered this: the kubelet on each node pulls images, using the cluster's kubelet identity. So that identity needs AcrPull on the registry.

No passwords, no imagePullSecrets, nothing in your manifests.

Windows/IIS admin
Like giving a server's computer account read access to a file share, instead of mapping the share with a stored password.
Linux admin
The node authenticates to the registry with its own managed identity token, much like an instance-profile credential helper.
Developer (Compose)
No docker login on the nodes. Azure handles it per node.
Other clouds
Like the EKS node role having ECR read permissions, or the GKE node service account reading Artifact Registry.

2. --attach-acr

One command assigns AcrPull on the registry to the cluster's kubelet identity. You need permission to create role assignments on the registry (Owner, User Access Administrator, or RBAC Administrator).

az aks update -g rg-orders-dev -n aks-orders-dev --attach-acr contosoacr

# equivalent explicit role assignment (what IaC does in Chapters 12–13)
KUBELET_ID=$(az aks show -g rg-orders-dev -n aks-orders-dev --query identityProfile.kubeletidentity.objectId -o tsv)
ACR_ID=$(az acr show -n contosoacr --query id -o tsv)
az role assignment create --assignee-object-id "$KUBELET_ID" --assignee-principal-type ServicePrincipal \
  --role AcrPull --scope "$ACR_ID"

Verify it with az aks check-acr -g rg-orders-dev -n aks-orders-dev --acr contosoacr.azurecr.io, which runs a pull test from a node.

3. Why not imagePullSecrets?

imagePullSecrets work on any Kubernetes, but they're a stored credential, per namespace, that expires and leaks.

On AKS with ACR, managed-identity pulls are simpler and safer. Keep image pull secrets for third-party registries that support nothing else.

4. Diagnose the pull failure

A new cluster can't start orders-api. What's wrong?

$ kubectl get pods -n orders
NAME                         READY   STATUS             RESTARTS   AGE
orders-api-6d8f7c9b5-x2kq7   0/1     ImagePullBackOff   0          3m
$ kubectl describe pod orders-api-6d8f7c9b5-x2kq7 -n orders | tail -5
  Warning  Failed     2m (x4 over 3m)  kubelet  Failed to pull image "contosoacr.azurecr.io/orders-api:1.4.2":
           failed to authorize: failed to fetch anonymous token: unexpected status from GET request to
           https://contosoacr.azurecr.io/oauth2/token?scope=repository%3Aorders-api%3Apull: 401 Unauthorized
  Warning  Failed     2m (x4 over 3m)  kubelet  Error: ErrImagePull
  Normal   BackOff    1m (x6 over 3m)  kubelet  Back-off pulling image "contosoacr.azurecr.io/orders-api:1.4.2"
  1. The tag 1.4.2 doesn't exist A missing tag gives "not found" / "manifest unknown", not 401.
  2. The kubelet identity has no AcrPull on contosoacr, so the pull is unauthorised
  3. The registry is down The registry answered, with a 401.
  4. DNS for the registry fails DNS worked: there was an HTTP response.
401 = authentication/authorisation; "not found" = wrong name or tag; "no such host" or timeouts = DNS or network (often private endpoints, lesson 6.3).

5. The fix

What fixes the error above?

  1. Add an imagePullSecret with your personal credentials It would work, with your credentials, until you leave the company.
  2. az aks update -g rg-orders-dev -n aks-orders-dev --attach-acr contosoacr
  3. Enable the ACR admin user That creates a shared password, which is the opposite of what we want.
  4. Give your user AcrPull Your user isn't the one pulling.
After the role assignment propagates (a minute or two), the kubelet's next retry succeeds, with no redeploy needed.

6. Pull errors at a glance

Message containsUsual cause
401 UnauthorizedNo AcrPull for the kubelet identity
not found / manifest unknownWrong repository or tag, or the image was never pushed
no such hostTypo in the registry name, or private DNS not resolving (private endpoint)
i/o timeout / 403 from the data endpointNetwork blocked: firewall, public access disabled with no private path
no match for platform in manifestImage built for arm64 on an amd64 node, or vice versa

7. Across subscriptions and tenants

  • Another subscription, same tenant: fine. Assign AcrPull on the registry; --attach-acr accepts the registry's resource ID.
  • Another tenant: managed identities can't cross tenants. Use a multi-tenant app registration with an image pull secret, or replicate images into a registry in your own tenant. Avoid it when you can.

8. Pull performance

  • Keep the registry in the cluster's region, or geo-replicate it (Premium).
  • Small images pull faster. Remember the multi-stage build from lesson 1.1.
  • imagePullPolicy: IfNotPresent (the default for non-latest tags) reuses images already on the node.
  • Artifact Streaming (Premium) can start large containers before the whole image is downloaded.

Pulling, sorted

  • The kubelet identity pulls; give it AcrPull with --attach-acr or IaC.
  • No imagePullSecrets for ACR.
  • 401 = permission; not found = name or tag; no such host or timeout = DNS or network.
  • az aks check-acr tests it end to end.
