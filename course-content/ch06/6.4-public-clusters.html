Public clusters done right

You'll be able to explain what a "public" AKS cluster exposes, protect its API server with identity and authorized IP ranges, and see why hosted build agents complicate that.

1. What "public" means

By default an AKS cluster's API server has a public address: aks-orders-dev-dns-1a2b3c.hcp.westeurope.azmk8s.io. Anyone on the internet can open a TLS connection to it.

That's about the management API only. Your apps are exposed (or not) separately, through LoadBalancer Services and gateways. And a "public cluster" says nothing about whether nodes have public IPs; they don't.

Windows/IIS admin
It's like exposing a server's remote management port to the internet. It's protected by strong authentication, but still visible.
Linux admin
Like SSH on a public IP with key-only auth: secure if configured well, but you might still want to firewall it.
Developer (Compose)
The Docker daemon socket was never public; Kubernetes' API is designed to be remote, so it has real auth.
Other clouds
Same as the EKS public endpoint or the GKE public control plane, each with an optional CIDR allow-list.

2. Layer 1: identity

Reaching the endpoint isn't the same as using it. Every request needs a valid Entra ID token and an Azure RBAC role (lesson 5.5).

With local accounts disabled, there is no other credential. For many teams, a public endpoint with strong identity is acceptable.

3. Layer 2: authorized IP ranges

Authorized IP ranges limit which source IPs may connect to the API server at all. Everyone else gets a connection timeout, before authentication even happens.

Typical entries:

  • the office's egress IPs;
  • the VPN gateway;
  • the build agents' egress IPs;
  • the cluster's own outbound IP, which AKS adds automatically.

Restrict aks-orders-dev (in rg-orders-dev) to the office range 203.0.113.0/24 and the VPN IP 198.51.100.7/32.

az aks update -g rg-orders-dev -n aks-orders-dev --api-server-authorized-ip-ranges 203.0.113.0/24,198.51.100.7/32

Also accepted: long forms of -g/-n; ranges in either order.

Ranges are comma-separated with no spaces. Pass an empty string ("") to remove all restrictions.

4. Outside the range

You're working from a café, not on the VPN. The cluster allows only the office and VPN ranges. You run kubectl get pods.

  1. Forbidden (403) You never reach authentication; the connection itself is dropped.
  2. The command hangs, then fails with a timeout (dial tcp …:443: i/o timeout)
  3. It works, because you have the RBAC role The IP check happens before identity is even looked at.
  4. kubelogin asks you to sign in again Authentication isn't the problem.
A timeout to the API server from a new location almost always means authorized IP ranges. Connect to the VPN, or use az aks command invoke (lesson 6.5), which goes through Azure's management plane rather than straight to the API server.

5. The hosted-agent problem

Microsoft-hosted Azure Pipelines agents run on a huge, shared pool of Azure IPs that changes weekly. Allow-listing "all hosted agents" means allowing large parts of Azure. That's barely better than no restriction, and it's easy to break.

The options:

  • A self-hosted agent or Managed DevOps Pool with a known egress IP (a NAT gateway). Allow just that IP.
  • A step that briefly adds the agent's current IP, then removes it. It's fragile, and the pipeline then needs rights to change the cluster.
  • Moving to a private cluster with agents inside the VNet (next lesson).
GitHub Actions
GitHub-hosted runners have the same problem. Larger runners with static IPs, or self-hosted runners, solve it.
GitLab CI
Shared SaaS runners have changing IPs too; use group runners in your own network.
Jenkins
Your Jenkins agents already have known IPs, so allow-listing them is easy. Here, Managed DevOps Pools give you the same.
Classic pipelines
Same agents and same problem; nothing differs between classic and YAML here.

6. Limits of authorized ranges

  • They apply only to public API servers. Private clusters don't use them.
  • They limit who can connect, not who can authenticate. They're a second layer, not a replacement for RBAC.
  • There's a cap on how many ranges you can list. Ranges are usually managed in IaC so changes are reviewed.

7. Deploying to a public cluster

- task: KubernetesManifest@1
  inputs:
    action: deploy
    connectionType: azureResourceManager
    azureSubscriptionConnection: sc-orders-dev      # workload identity federation
    azureResourceGroup: rg-orders-dev
    kubernetesCluster: aks-orders-dev
    namespace: orders
    manifests: k8s/base/*.yaml

The pipeline's identity needs an AKS RBAC role on the namespace, and the agent's IP must be allowed. If either is missing, you get Forbidden or a timeout.

8. A public cluster checklist

  • Entra ID + Azure RBAC; local accounts disabled.
  • Authorized IP ranges: office, VPN, and the agents' fixed egress IPs.
  • Build agents with a known IP, not the shared hosted pool.
  • API server audit logs sent to Log Analytics (Chapter 14).

9. When public isn't enough

Regulated industries often require that the management API has no public endpoint at all. That's a private cluster, and it changes how everyone, and every pipeline, reaches it. That's next.

Public clusters, sorted

  • "Public" = the API server has a public endpoint; nodes and apps are separate decisions.
  • Layer 1: Entra ID + RBAC. Layer 2: authorized IP ranges.
  • Outside the range → connection timeout, not 403.
  • Hosted agents are hard to allow-list; use agents with a fixed egress IP.
