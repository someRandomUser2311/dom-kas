Git & pull requests for pipelines

You'll be able to explain how branches, pull requests and branch policies decide what reaches production, and keep secrets and state files out of Git.

1. main is what ships

In this course, the main branch is the source of truth: whatever is on main gets built and deployed. Nobody pushes to main directly.

Instead, work happens on a feature branch and arrives through a pull request (PR). That's where review and automated checks happen.

The same flow works in Azure Repos and GitHub. Azure Pipelines can build from either.

git switch -c feature/add-health-probe
# …edit k8s/base/deployment.yaml…
git add k8s/base/deployment.yaml
git commit -m "Add readiness probe to orders-api"
git push -u origin feature/add-health-probe
# then open a pull request into main
GitHub Actions
Same flow. Azure DevOps "branch policies" are the equivalent of GitHub branch protection rules and rulesets.
GitLab CI
A GitLab merge request = a pull request; protected branches = branch policies.
Jenkins
Multibranch pipelines discover branches and PRs the same way. Here the hosting service, not Jenkins, enforces the rules.
Classic pipelines
Classic build pipelines used the same branch policies; the YAML pipeline just lives in the repo now.

2. Branch policies protect main

A branch policy (Azure Repos) or branch protection rule (GitHub) sets conditions a PR must meet before it can merge:

  • Required reviewers: at least one or two approvals, possibly from specific groups (code owners).
  • Build validation: a pipeline runs on the PR and must succeed.
  • Comment resolution: every review comment must be resolved.
  • Linked work item: often required in Azure Boards shops.

Build validation is where your pipeline earns its keep: tests, linting, terraform plan, image scans. They all run before a single line reaches main.

3. Why pipelines are triggered by branches and PRs

Two events start most pipelines:

  • A PR is opened or updated: run the checks. Build and test, but never deploy to production.
  • A merge to main: run the full pipeline. Build, push the image, deploy to dev, then promote to prod after approval.

This split keeps production changes reviewed and tested, while still giving developers fast feedback on every push to their branch.

Put the flow from idea to deployment in order.

  1. Create a feature branch and commit the change
  2. Push the branch and open a pull request into main
  3. The build validation pipeline runs on the PR
  4. A reviewer approves and the PR merges into main
  5. The CI/CD pipeline runs on main and deploys
Validation happens before the merge; deployment happens after it. Nothing reaches main without passing both review and checks.

4. What must never be committed

Git keeps history forever. A secret committed once and deleted in the next commit is still in the history, and anyone with read access can find it. If a secret is ever pushed, rotate it; rewriting history is not enough.

Keep these out of Git with a .gitignore:

  • Secrets: .env files, keys, kubeconfigs.
  • Terraform state (*.tfstate), which can contain secrets in plain text.
  • Tool caches (.terraform/).

Do commit .terraform.lock.hcl: it pins provider versions.

# secrets and local config
.env
*.pem
kubeconfig*

# Terraform
.terraform/
*.tfstate
*.tfstate.*
*.tfplan

Which of these must never be committed?

  1. terraform.tfstate
  2. .env containing a database password
  3. A kubeconfig copied from ~/.kube/config
  4. .terraform.lock.hcl Commit this one: it pins provider versions so every run uses the same ones.
  5. azure-pipelines.yml This is code and belongs in the repo; it should contain no secrets.
  6. A service principal's client secret in a script
State files, env files, kubeconfigs and secrets all grant access or reveal it. Pipelines get secrets at run time from service connections and Key Vault instead (Chapters 7 and 15).

5. Commit hygiene that pipelines like

  • Small PRs: one change, easy to review, quick to validate, and easy to revert.
  • Clear messages: say what changed and why. The pipeline run page shows them.
  • Path-based triggers (Chapter 7) let a docs-only change skip the image build. That works best when changes are kept separate.
  • Enable secret scanning or push protection where your platform offers it (GitHub Advanced Security, or GitHub Advanced Security for Azure DevOps).

Git for pipelines, sorted

  • Work on a feature branch; reach main only through a PR.
  • Branch policies require reviewers and a passing build validation pipeline.
  • PRs run checks; merges to main run the deploy.
  • Never commit secrets, kubeconfigs or Terraform state; rotate anything that leaks.
