Azure fundamentals for DevOps

You'll be able to explain where resources live in Azure, which kinds of identity exist, and how a role assignment gives an identity exactly the access it needs.

1. The resource hierarchy

Everything in Azure sits in one tree:

  • Tenant: your organisation's Microsoft Entra ID directory (formerly Azure AD). It holds users, groups and app identities.
  • Management groups (optional): folders of subscriptions, used to apply policy and access at scale.
  • Subscriptions: the unit of billing and of quotas. Contoso has sub-orders-nonprod and sub-orders-prod.
  • Resource groups: a folder of resources that share a lifecycle, such as rg-orders-dev.
  • Resources: an AKS cluster, a container registry, a VNet.
An expandable tree: Tenant → management group "Contoso" → two subscriptions → resource groups (rg-orders-dev, rg-orders-prod, rg-shared) → resources (AKS, ACR, Key Vault, VNet). Clicking a node shows its resource ID, e.g. /subscriptions/…/resourceGroups/rg-orders-dev/providers/Microsoft.ContainerService/managedClusters/aks-orders-dev.
Windows/IIS admin
Entra ID is the cloud cousin of Active Directory, but it has no OUs and no Group Policy. Management groups and resource groups are where you organise things instead.
Linux admin
Think of the tree as a filesystem: permissions set on a directory apply to everything under it.
Developer (Compose)
A resource group is roughly "one Compose project": things you create and delete together.
Other clouds
A subscription ≈ an AWS account or a GCP project. A resource group has no exact AWS equivalent; it's closest to a CloudFormation stack's set of resources. Careful: deleting a resource group deletes everything in it.

2. Regions and availability zones

A region is a set of datacentres in one area, such as westeurope or eastus2. Most resources live in one region.

Many regions have three availability zones: separate datacentres with their own power and cooling. Spreading AKS nodes across zones 1, 2 and 3 keeps the app running if one datacentre fails.

You choose zones when you create a node pool, and you can't change them afterwards. Chapter 4 covers this.

3. Four kinds of identity

Anything that calls Azure must prove who it is. There are four kinds of identity:

  • User: a person who signs in.
  • Group: a set of users (and other identities). Assign access to groups, not to individuals.
  • Service principal: an identity for an application, created from an app registration. It authenticates with a secret, a certificate, or a federated credential (no secret at all; Chapter 7 uses this for pipelines).
  • Managed identity: an identity Azure creates and manages for a resource. There's no secret for you to store or rotate.
    • System-assigned: tied to one resource, and deleted with it.
    • User-assigned: a standalone resource you can attach to several resources. AKS uses these.

Match each identity type to its best use.

UserAn engineer opening the portal

Prefer managed identities for Azure resources and federated credentials for external systems like pipelines. Both avoid secrets that can leak.

4. RBAC = who + role + scope

Access in Azure is a role assignment, made of three parts:

  • Who: a user, group, service principal or managed identity.
  • Role: a named set of allowed actions, such as Reader or AcrPull.
  • Scope: where it applies: a management group, subscription, resource group or single resource.

Assignments are inherited downwards. Reader on a subscription means Reader on every resource group and resource in it.

Least privilege means picking the narrowest role at the lowest scope that still works.

az role assignment create \
  --assignee "<pipeline-sp-app-id>" \
  --role Contributor \
  --scope /subscriptions/<sub-id>/resourceGroups/rg-orders-dev
Assignment mode: pick an identity, a role and a node in the tree. Every node the assignment reaches lights up, so inheritance is visible.

5. Give the pipeline just enough

The dev pipeline must create and update resources in rg-orders-dev, and nothing else. Make the assignment in the scope tree.

Success when the identity sp-orders-pipeline-dev has Contributor at exactly rg-orders-dev. Feedback for common misses:
  • Subscription scope: "This also reaches rg-orders-prod and rg-shared."
  • Owner: "Owner can also grant access to others. The pipeline doesn't need that."
  • Reader: "Reader can't create anything."
Contributor at the resource group lets the pipeline manage everything in that group, but nothing outside it, and it can't grant access to anyone.

6. Control plane vs data plane roles

The three classic roles manage resources:

  • Owner: everything, including assigning roles to others.
  • Contributor: create, change and delete resources, but it can't assign roles.
  • Reader: view only.

Many services also have data-plane roles for what's inside a resource:

  • AcrPull and AcrPush to pull or push images.
  • Key Vault Secrets User to read secrets.
  • The Azure Kubernetes Service RBAC … roles to act inside a cluster.

Being Contributor on a registry doesn't by itself mean you should push images to it. Grant AcrPush for that.

To let an identity assign roles without making it Owner, use Role Based Access Control Administrator. You can add a condition that limits which roles it may assign, for example only AcrPull.

Your Terraform pipeline runs as Contributor on rg-orders-dev. It fails when creating the AcrPull assignment for the cluster. Why?

  1. AcrPull can only be assigned in the portal Any role can be assigned from the CLI, Terraform or Bicep.
  2. Contributor can't create role assignments; that needs Owner, User Access Administrator, or Role Based Access Control Administrator
  3. The resource group is the wrong scope for AcrPull AcrPull is normally assigned on the registry itself, but scope isn't what blocks a Contributor.
  4. The cluster doesn't exist yet Terraform orders the operations; the error here is a permissions error.
Creating role assignments needs Microsoft.Authorization/roleAssignments/write, which Contributor explicitly lacks. The safe fix is Role Based Access Control Administrator, with a condition that limits it to the roles the pipeline is allowed to hand out.

7. Signing in from the CLI

az login signs you in (it opens a browser, or prints a device code). One account can see many subscriptions, so always check which one is active before you change anything.

In pipelines you never run az login yourself. The AzureCLI@2 task signs in with the service connection (Chapter 7).

az login
az account show --query name -o tsv           # which subscription am I in?
az account set --subscription sub-orders-nonprod
az group list -o table

Switch the active subscription to sub-orders-nonprod.

az account set --subscription sub-orders-nonprod

Also accepted: -s for --subscription, or the subscription ID instead of the name.

Every later az command uses this subscription unless you pass --subscription explicitly.

Azure, sorted

  • Tenant (Entra ID) → management groups → subscriptions → resource groups → resources.
  • Regions contain availability zones; choose zones when you create a node pool.
  • Use managed identities for Azure resources and federated credentials for pipelines.
  • RBAC = who + role + scope, inherited downwards; use the narrowest role at the lowest scope.
  • Contributor can't assign roles; data-plane roles like AcrPull control what's inside a resource.
