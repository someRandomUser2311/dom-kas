How you'll be graded

You'll know exactly which graders run on which files, how partial credit works, and what counts as a critical failure.

1. Check all

The project editor has a tab for every file. Check all runs every grader and produces a readiness report: a score per file, every failed rule with file, line and a link to the lesson, and ⛔ marks on critical failures. Run it as often as you like.

3. Partial credit

Each file's score is the share of its rules that pass. The project score is the weighted sum. You pass at 80% with no critical rule failing. A 95% submission with a secret in Git still fails.

4. Critical rules (⛔)

These are the critical rules from every chapter's labs:

  • No secrets anywhere in the repo (Dockerfile ENV/ARG, ConfigMaps, values, tfvars/bicepparam, pipelines).
  • Containers run as non-root; no privileged containers.
  • Service selectors match pod labels.
  • Liveness doesn't depend on the database; memory limits are set.
  • Default-deny in every app namespace; nothing outside orders-api and orders-worker reaches the database.
  • The cluster: local accounts disabled, Entra ID + Azure RBAC, private.
  • Prod deploys only through a deployment job with an approved environment; the canary failure hook rejects.
  • The scan runs before deploy and fails on fixable HIGH/CRITICAL; no signing keys in the repo.
  • Terraform applies the saved plan (or Bicep deploys only after an approved what-if).
  • No wildcard RBAC and no ClusterRoleBinding for the deploy identity.

5. Solutions and integrity

Viewing the reference solution caps the project at 60%, as with any lab, so it can't pass. Your results are stored in your browser, and the course-complete page says so plainly: it's a completion record, not a verified certificate.
