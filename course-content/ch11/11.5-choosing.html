Choosing a strategy

You'll be able to pick a release strategy for a given risk, budget and team, and know when a feature flag is the better tool.

2. Feature flags: release ≠ deploy

Deployment strategies manage technical risk: does the new build run? Business risk is different: will customers like the new checkout? Feature flags handle that better.

Deploy the code switched off, then turn it on for 5% of users, a country, or internal staff, without a deployment. Turning it off is instant.

Azure App Configuration's feature manager is one option.

3. Database changes constrain everything

Every strategy except a full stop-and-replace runs two versions against one database. A schema change that breaks the old version breaks rollback for all strategies.

Expand/contract (lesson 11.2) is required whichever strategy you choose.

4. Scenarios

An internal reporting tool, 3 replicas, used by 20 people in office hours. Releases weekly. Small team, basic monitoring. Strategy?

  1. A rolling update with readiness probes and maxUnavailable: 0
  2. Blue/green with double capacity The cost and complexity outweigh the benefit for 20 internal users.
  3. An automated multi-step canary Too little traffic to measure, and basic metrics.
  4. Recreate (stop everything first) Unnecessary downtime.
Rolling is the right default when the stakes and traffic are modest.

Contoso's orders-api: thousands of requests per minute, revenue-critical, good Prometheus metrics, and a platform team. Strategy?

  1. Rolling only Every user is exposed as the rollout proceeds.
  2. An automated canary (10% → 50% → 100%) with metric checks and auto-reject
  3. Manual blue/green on Friday nights Manual and late. Automation and a small blast radius are better.
  4. Deploy straight to 100% No safety net.
High traffic gives fast, statistically meaningful signals, which is exactly what a canary needs.

5. Match scenario to strategy

Match each scenario to the best tool.

A new version must be fully smoke-tested in production infrastructure before any user sees it, and rollback must be instantBlue/green
A risky performance change on a high-traffic APICanary
A redesigned checkout the business wants to try on 5% of customersFeature flag
A routine patch release of a low-traffic internal serviceRolling update
Strategies combine: Contoso does canary releases of code whose new features are behind flags.

6. Prerequisites for any of them

  • Readiness probes that mean "can serve traffic".
  • 2+ replicas and a PDB.
  • Backward-compatible APIs and schemas.
  • Metrics per version, and a rollback you've practised.

7. Contoso's policy

  • Dev: rolling, on every merge.
  • Prod: canary 10% → 50% → 100% with automated checks, behind a prod approval.
  • Big features behind flags.
  • Blue/green only for the yearly major database migration, with expand/contract.

Choosing, sorted

  • Rolling: simple default. Blue/green: instant switch, double cost. Canary: smallest blast radius, needs metrics.
  • Feature flags separate release from deploy, for business risk.
  • Database compatibility constrains every strategy.
