Rollout in the pipeline

You'll be able to write a canary deployment job with lifecycle hooks, gate each step on health signals, and make failure reject the canary automatically.

1. Deployment strategies in YAML

Chapter 7 used strategy: runOnce. A deployment job can also use rolling (for VM targets) or canary, which runs the deploy cycle once per increment (e.g. 10%, then 50%), followed by a final 100%.

Each cycle has lifecycle hooks, which are named places to put steps.

GitHub Actions
There's no built-in canary strategy; you'd script stages with jobs and environments. Here the hooks are built in.
GitLab CI
Like incremental rollouts (rollout 10% jobs), but with explicit pre/post hooks.
Jenkins
Like a scripted pipeline with stages per percentage and post-conditions for failure.
Classic pipelines
Similar to deployment gates and post-deployment conditions on release stages.

2. The hooks

HookRunsTypical use
preDeployOnce, before any incrementBake manifests, run migrations (expand)
deployEach incrementDeploy the canary at $(strategy.increment)%
routeTrafficEach increment, after deployShift traffic (e.g. update weights)
postRouteTrafficEach increment, after routingHealth checks: wait, query metrics, smoke test
on: failureIf any step failedReject the canary / roll back
on: successWhen all increments passedPromote the canary

Order the hooks as they run for one increment, starting from the job's beginning.

  1. preDeploy
  2. deploy
  3. routeTraffic
  4. postRouteTraffic
  5. on: success or on: failure
deploy → routeTraffic → postRouteTraffic repeats for every increment; on: runs once at the end.

3. The canary job

jobs:
  - deployment: canary
    environment: prod.orders          # prod environment, orders namespace resource
    pool: { name: mdp-orders-prod }
    strategy:
      canary:
        increments: [10, 50]
        preDeploy:
          steps:
            - checkout: self
            - task: KubernetesManifest@1
              name: bake
              inputs: { action: bake, renderType: kustomize, kustomizationPath: k8s/overlays/prod }
        deploy:
          steps:
            - task: KubernetesManifest@1
              inputs:
                action: deploy
                strategy: canary
                percentage: $(strategy.increment)
                namespace: orders
                manifests: $(bake.manifestsBundle)
                containers: contosoacr.azurecr.io/orders-api:$(Build.BuildId)
        postRouteTraffic:
          steps:
            - script: ./scripts/check-canary.sh --minutes 10 --max-error-ratio 2.0
              displayName: Compare canary vs stable
        on:
          failure:
            steps:
              - task: KubernetesManifest@1
                inputs: { action: reject, strategy: canary, namespace: orders, manifests: $(bake.manifestsBundle) }
          success:
            steps:
              - task: KubernetesManifest@1
                inputs: { action: promote, strategy: canary, namespace: orders, manifests: $(bake.manifestsBundle), containers: contosoacr.azurecr.io/orders-api:$(Build.BuildId) }

With an environment Kubernetes resource (prod.orders), the task uses the environment's connection and you can drop the connection inputs. Otherwise, add connectionType: azureResourceManager and the cluster inputs, as in Chapter 10.

4. The automatic rollback

If the health check in postRouteTraffic fails, which line removes the canary?

The on: failure hook runs action: reject, which deletes the canary (and baseline) workloads. Stable never stopped serving.

5. A health check that can fail

check-canary.sh queries Azure Monitor (Prometheus metrics, Chapter 14) for the 5xx ratio of canary pods vs stable pods over the last N minutes. It exits non-zero if the canary is worse than the threshold, and that failure triggers on: failure.

A health step that only sleeps proves nothing.

CANARY=$(query 'sum(rate(http_requests_total{app="orders-api",track="canary",code=~"5.."}[10m])) / sum(rate(http_requests_total{app="orders-api",track="canary"}[10m]))')
STABLE=$(query 'sum(rate(http_requests_total{app="orders-api",track="stable",code=~"5.."}[10m])) / sum(rate(http_requests_total{app="orders-api",track="stable"}[10m]))')
awk -v c="$CANARY" -v s="$STABLE" -v m="$MAX" 'BEGIN { exit !(c <= (s + 0.001) * m) }'

6. Environment checks as gates

Checks on the prod environment run before the job starts, and can also be re-evaluated:

  • Approvals: a human says go.
  • Query Azure Monitor alerts: block if any alert is firing for the service.
  • Business hours: only deploy within a window.
  • Exclusive lock: one deploy at a time per environment.
  • Required template: the pipeline must extend the approved template.

7. Watch the stages

The Chapter 7 stage simulator, extended: the prod stage expands into preDeploy → [deploy → routeTraffic → postRouteTraffic] × increments (10, 50) → on:success/failure. A toggle "canary errors at 50%" makes postRouteTraffic fail on the second increment, and the reject step runs.

8. Gateway-weighted canaries in a job

To use precise HTTPRoute weights instead of replica ratios: in deploy, roll out orders-api-canary at full size; in routeTraffic, patch the HTTPRoute weights to $(strategy.increment); in on: success, update stable and set weights to 100/0; in on: failure, set weights to 100/0 and scale the canary to 0.

9. Pause for a human

Add a ManualValidation@1 step in an agentless job between increments, or rely on an environment approval before the stage, for teams that want a person to look at the dashboard before 50%.

10. Timeouts and concurrency

  • Give the job a timeoutInMinutes longer than all the health windows added together.
  • Use an exclusive lock check so a second release can't start while a canary is in flight.

11. After the canary

On success, the canary becomes stable, and the release is done when the stable rollout finishes. Record the deployment, with the build, commit and image digest, on the environment. Azure DevOps shows it in the environment's deployment history.

Pipeline rollouts, sorted

  • strategy: canary with increments; hooks preDeploy → (deploy → routeTraffic → postRouteTraffic)× → on success/failure.
  • percentage: $(strategy.increment); on: failure → reject; on: success → promote.
  • Health checks must be able to fail: compare canary vs stable metrics.
  • Environment checks: approvals, Azure Monitor alerts, exclusive lock.
