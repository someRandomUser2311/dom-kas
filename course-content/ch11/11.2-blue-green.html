Blue/green

You'll be able to run two full versions side by side, switch all traffic at once, roll back in seconds, and handle the database changes that make it hard.

1. Two complete environments

In blue/green, the current version (blue) keeps running at full size while the new version (green) is deployed alongside it, also at full size, and tested.

Then traffic switches all at once from blue to green. If anything's wrong, you switch back just as fast.

Windows/IIS admin
Like App Service deployment slots: deploy to staging, warm it up, swap.
Linux admin
Like pointing a load balancer's backend pool, or a symlink, from the old release directory to the new one.
Developer (Compose)
Run app-blue and app-green, then repoint the proxy.
Other clouds
Like CodeDeploy blue/green for ECS, or swapping target groups.

2. Two Deployments, one label apart

Both Deployments run the same app with a different version label and image.

metadata:
  name: orders-api-green
spec:
  replicas: 4
  selector:
    matchLabels: { app: orders-api, version: green }
  template:
    metadata:
      labels: { app: orders-api, version: green }
    spec:
      containers:
        - name: api
          image: contosoacr.azurecr.io/orders-api:1.5.0

3. The switch: a Service selector

The live Service selects version: blue. Changing that one value to green moves all new connections to the green pods within seconds.

A second Service, orders-api-preview, always points at the idle colour, so you can test green before switching.

Tap the line that sends production traffic to the new version.

apiVersion: v1
kind: Service
metadata:
  name: orders-api
  namespace: orders
spec:
  selector:
    app: orders-api
    version: green
  ports:
    - port: 80
      targetPort: 8080
Flipping version in the live Service's selector is the whole switch. With the Gateway API you'd instead change the HTTPRoute's backendRefs from orders-api-blue to orders-api-green.

4. The flow

  1. Blue (1.4.2) serves production; green doesn't exist or is scaled to 0.
  2. Deploy green (1.5.0) at full size; wait for ready.
  3. Test green through orders-api-preview: smoke tests, a manual check.
  4. Switch the live Service selector to green.
  5. Watch metrics. If they're bad, switch back to blue.
  6. After a safe period, scale blue to 0. It becomes the next "green".

5. Rollback speed and cost

What's the main trade-off of blue/green compared with a rolling update?

  1. Slower rollback Rollback is the fastest of all: one selector change.
  2. Near-instant switch and rollback, at the cost of running double capacity during the release
  3. It doesn't work with Services A Service selector is the simplest way to do it.
  4. Users see mixed versions That's rolling and canary; blue/green switches everyone at once.
Double the pods, so double the requests on the cluster, possibly with the autoscaler adding nodes. That's the price of a clean, instant switch.

6. The database problem

Blue and green share the same database. If 1.5.0 renames a column, blue breaks the moment green migrates, and you can't switch back.

The fix is expand/contract migrations:

  1. Expand: add the new column and keep the old one. Both versions work.
  2. Deploy and switch to the new version, which writes both columns or reads the new one.
  3. Contract: once blue is retired for good, remove the old column in a later release.

The same rule applies to rolling and canary releases, which also run two versions at once.

7. Long-lived connections and state

A selector switch only affects new connections. Long-lived connections (WebSockets, gRPC streams) stay on blue until they close. In-memory sessions on blue are lost on switch, so keep session state in a shared store.

8. Blue/green in a pipeline

- script: |
    set -euo pipefail
    COLOR=$(kubectl get svc orders-api -n orders -o jsonpath='{.spec.selector.version}')
    NEXT=$([ "$COLOR" = blue ] && echo green || echo blue)
    kubectl set image deploy/orders-api-$NEXT api=contosoacr.azurecr.io/orders-api:$(Build.BuildId) -n orders
    kubectl scale deploy/orders-api-$NEXT --replicas=4 -n orders
    kubectl rollout status deploy/orders-api-$NEXT -n orders --timeout=5m
    ./smoke-test.sh http://orders-api-preview.orders
    kubectl patch svc orders-api -n orders -p "{\"spec\":{\"selector\":{\"app\":\"orders-api\",\"version\":\"$NEXT\"}}}"
  displayName: Blue/green switch

Put an approval check before the switch step, or after the smoke test, if a human should decide.

9. A selector typo

If the switch sets version: Green (capital G), the Service matches no pods and every request fails, instantly, for everyone. Script the switch, verify the endpoints right after (kubectl get endpointslices), and switch back automatically if they're empty.

Blue/green, sorted

  • Two full Deployments; a Service selector or route decides which gets traffic.
  • Instant switch and rollback; double capacity while both run.
  • Test green through a preview Service before switching.
  • Expand/contract database changes; external session state.
