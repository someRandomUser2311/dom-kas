Rolling updates in depth

You'll be able to calculate exactly how a rolling update proceeds, tune it for zero downtime within a capacity budget, and make it stop on its own when the new version is bad.

2. The two limits

During the rollout, Kubernetes keeps both limits true at all times:

  • Total pods ≤ replicas + maxSurge.
  • Available pods ≥ replicas − maxUnavailable.

Percentages are converted to pod counts: maxSurge rounds up, maxUnavailable rounds down. With 4 replicas and the default 25%/25%, that's surge 1, unavailable 1.

Both can't be 0, or nothing could move.

3. Predict the pod counts

4 replicas, maxSurge: 1, maxUnavailable: 0. You change the image. What's the maximum total number of pods, and the minimum number available, during the rollout?

  1. 4 total, 3 available That's surge 0 / unavailable 1.
  2. 5 total, never fewer than 4 available
  3. 8 total, 4 available That would be maxSurge 4 (100%).
  4. 5 total, 3 available maxUnavailable 0 keeps all 4 available.
One extra pod at a time: start a new one, wait until it's ready, remove an old one, repeat. It's slow but capacity never dips. That's the usual production choice.

6. Readiness gates everything

"Available" means ready (and ready for at least minReadySeconds). Without a readiness probe, a container counts as ready the moment it starts, before the app has loaded anything. The rollout then races ahead, removing old pods while new ones can't serve yet.

"Rolling updates are always zero-downtime" is only true with a real readiness probe and enough capacity.

7. minReadySeconds: catch slow failures

Some bad versions pass readiness, then crash 20 seconds later. minReadySeconds: 30 makes a new pod count as available only after it's been ready for 30 seconds without failing.

A version that crashes shortly after starting then never becomes available, so the rollout stalls before it touches more old pods.

spec:
  replicas: 4
  minReadySeconds: 30
  progressDeadlineSeconds: 300
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0

8. When the new version is broken

With maxUnavailable: 0, a new pod that never becomes ready means the rollout stops after the first new pod. The four old pods keep serving.

After progressDeadlineSeconds, the Deployment reports ProgressDeadlineExceeded. Kubernetes does not roll back by itself. The pipeline notices (kubectl rollout status fails) and runs kubectl rollout undo, or Helm's --atomic does.

$ kubectl get deploy orders-api -n orders
NAME         READY   UP-TO-DATE   AVAILABLE   AGE
orders-api   4/4     1            4           12d
$ kubectl get deploy orders-api -n orders -o jsonpath='{.status.conditions[?(@.type=="Progressing")].reason}'
ProgressDeadlineExceeded

9. Rollback

kubectl rollout status deploy/orders-api -n orders --timeout=5m \
  || { kubectl rollout undo deploy/orders-api -n orders; exit 1; }

The rollback is itself a rolling update back to the previous ReplicaSet, using the same safe limits.

10. Pause and resume

kubectl rollout pause freezes a rollout midway, leaving some new and some old pods running. That's a crude canary for a quick look. kubectl rollout resume continues. Lesson 11.3 shows the precise way.

11. Mixed versions during a rollout

During any rolling update, old and new versions serve traffic at the same time. API changes, message formats and database schema must work with both, which is called backward compatibility. Lesson 11.2 covers database changes.

Rolling updates, sorted

  • Total ≤ replicas + maxSurge (rounds up); available ≥ replicas − maxUnavailable (rounds down).
  • Production default: maxSurge: 1 (or 25%), maxUnavailable: 0.
  • Readiness and minReadySeconds decide "available"; bad versions stall the rollout.
  • Kubernetes doesn't auto-rollback; the pipeline (or Helm --atomic) does.
  • Old and new run together; stay backward compatible.
