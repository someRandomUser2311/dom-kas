Canary

You'll be able to send a small, precise share of traffic to a new version, compare it with the stable one, and promote or abort it.

1. Test in production, carefully

Staging never matches production's real traffic. A canary release sends a small share of real users, say 10%, to the new version. You watch error rates and latency, then increase the share step by step or abort.

A bad release hurts 10% of requests for a few minutes, not everyone.

Windows/IIS admin
Like App Service slot "traffic routing" percentages, or adding one server with the new build to the farm and watching it.
Linux admin
Like weighted upstreams in nginx or HAProxy.
Developer (Compose)
No Compose equivalent; this needs a traffic-splitting proxy.
Other clouds
Like ALB weighted target groups, or Cloud Run traffic splitting.

2. Two ways to split traffic

MethodHowPrecision
Replica ratioRun 1 canary pod next to 9 stable pods behind one ServiceCoarse: ≈10% only if the counts work out, and connection reuse skews it
Weighted routingThe gateway or mesh splits by weight between two ServicesExact, independent of pod counts

"Canary = 1 pod out of N" is the coarse form. With 2 replicas, the smallest replica-based canary is 33% or 50%, hardly small.

3. Weighted HTTPRoute

With the Gateway API (Chapter 8), run two Deployments and two Services, orders-api-stable and orders-api-canary, and split with weights. Then change only the weights to progress: 90/10 → 50/50 → 0/100.

rules:
  - matches:
      - path: { type: PathPrefix, value: /api }
    backendRefs:
      - name: orders-api-stable
        port: 80
        weight: 90
      - name: orders-api-canary
        port: 80
        weight: 10
A weight slider (stable vs canary), a request generator, and two live charts: error rate and p95 latency, one line per version. Buttons: "Promote" (move toward 100% canary) and "Abort" (back to 0%). Scenarios include a healthy canary and one that starts throwing 5xx errors at 10%.

4. Abort the bad canary

In the canary dashboard, start at 10%. The canary's error rate climbs to 8% while stable stays at 0.2%. Do the right thing.

Success when the learner presses Abort (weights back to 100/0) within the simulated observation window, without promoting first. Promoting gives: "You just sent 50% of users to a version with 40× the error rate."
Compare the canary against stable at the same time, not against yesterday. A canary is only useful if you're willing to stop it.

5. What to measure

  • Error rate (5xx share) of canary vs stable.
  • Latency (p95/p99) of canary vs stable.
  • Saturation: CPU and memory of canary pods.
  • Business signals where you can, such as checkout success rate.

Decide the thresholds before the release: for example, "abort if canary 5xx > 2× stable for 5 minutes". Chapter 14 builds these metrics; lesson 11.4 automates the decision.

6. The KubernetesManifest canary strategy

Azure Pipelines' KubernetesManifest@1 has a built-in canary. With strategy: canary and percentage, it creates a -canary Deployment (and optionally a -baseline) next to the stable one. Later, an action: promote or action: reject step finishes or undoes it.

With the default trafficSplitMethod: pod the split is by replica ratio, which is coarse. With smi it uses an SMI TrafficSplit, which needs a mesh that supports it.

Deploy a canary that takes 10% (by replica ratio).

- task: KubernetesManifest@1
  inputs:
    action: deploy
    strategy: canary
    ?: 10
    namespace: orders
    manifests: $(bake.manifestsBundle)
    containers: contosoacr.azurecr.io/orders-api:$(Build.BuildId)
  • percentage
  • weight weight belongs to HTTPRoute backendRefs, not this task.
  • increments increments is part of the deployment job's strategy (lesson 11.4), not the task.
  • replicas The task computes canary replicas from the percentage.
Inside a canary deployment job, use percentage: $(strategy.increment) so each increment sets it.

7. Baseline: a fair comparison

A brand-new canary pod differs from long-running stable pods: cold caches, fresh memory. The task can also start a baseline Deployment, new pods running the old version. Comparing canary with baseline isolates the effect of the code change.

8. The Istio add-on alternative

With AKS's Istio-based service mesh add-on, a VirtualService (or a Gateway API HTTPRoute) splits traffic by weight, header or cookie. That allows "internal users first" canaries, and the mesh's telemetry gives per-version metrics for free. It's more machinery, but the most precise control.

9. Header-based canaries

Weights pick users at random. Match on a header (x-canary: true, set for employees or beta testers) to send a chosen group to the canary first. Lesson 8.4's header matches do exactly this.

10. Sticky users

With pure weights, one user's requests can bounce between versions: the page is from v1 and the API call from v2. If that breaks your app, use header or cookie-based routing, or make sure both versions are compatible with each other (lesson 11.2, step 6).

11. Promote

Once the canary has run at 100% (or passed every step), make it the new stable: update orders-api-stable's image to the canary's, reset the weights to 100/0, and scale the canary to 0. With KubernetesManifest, action: promote does this; action: reject removes the canary and baseline.

12. Canary checklist

  • Precise split: weights (Gateway API or mesh), not replica ratios, when the percentage matters.
  • Per-version metrics with thresholds decided in advance.
  • Compatible versions (API, schema, sessions).
  • An automated abort path (next lesson).

Canary, sorted

  • Send a small share of real traffic to the new version; compare with stable; step up or abort.
  • Weighted backendRefs for exact splits; replica ratios are coarse.
  • KubernetesManifest@1: strategy: canary, percentage, then promote/reject.
  • A baseline makes the comparison fair; headers allow targeted canaries.
