Predict the outcome (3)

1 · 4 replicas, surge 1, unavailable 0. The new version's readiness probe always fails.

  1. All 4 replaced; outage
  2. 1 new pod stuck not-ready; 4 old pods keep serving; ProgressDeadlineExceeded later
  3. Automatic rollback
  4. 2 old pods removed
Nothing old is removed until something new is available.

2 · Blue/green switch sets the Service selector to version: Green; the pods are labelled green.

  1. Traffic goes to green
  2. No endpoints: every request fails until the selector is fixed or reverted
  3. Traffic stays on blue
  4. Kubernetes corrects the case
Labels are case-sensitive. Verify endpoints right after switching.

3 · KubernetesManifest@1 canary, percentage: 10, pod-based split, stable at 2 replicas.

  1. Exactly 10% of traffic to the canary
  2. 1 canary pod next to 2 stable, so roughly a third of connections hit the canary
  3. No canary pods
  4. The task fails
Pod-based canaries are coarse at low replica counts.

Write lab: a canary deployment job

Brief: Write the DeployProd stage of azure-pipelines.yml as a canary release of orders-api. Graded by pipeline-rules and stage-sim.

  • A deployment job with strategy: canary.
  • increments with at least two steps below 100 (e.g. [10, 50]).
  • The deploy hook uses KubernetesManifest@1 with strategy: canary and percentage: $(strategy.increment).
  • A postRouteTraffic (or routeTraffic) step runs a health check that can fail (not just a delay).
  • on: failure runs action: reject.
  • on: success runs action: promote.
  • The job targets the prod environment (with approval), and the stage runs only on main after the earlier stages succeed.
  • The image tag comes from $(Build.BuildId).
Reference solution

The template in lesson 11.4, step 3, used from a DeployProd stage with dependsOn: DeployDev and the condition and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main')).

Walkthrough: canary 10% → metrics → promote

  1. The approval is granted; preDeploy bakes the manifests.
  2. The 10% increment: orders-api-canary appears; the check compares 5xx ratios for 10 minutes.
  3. The 50% increment, the same check.
  4. on: success promotes: stable now runs the new image; the canary and baseline are removed.
  5. Replay with an injected error at 50%: the check fails, on: failure rejects, and stable is untouched.

Try it locally

11.1 Watch a rollout.

kubectl apply -f lab/examples/ch11/rolling.yaml          # 4 replicas, surge 1, unavailable 0
kubectl get pods -l app=roll -w &
kubectl set image deploy/roll app=localhost:5001/orders-api:1.0.1
kubectl set image deploy/roll app=localhost:5001/orders-api:broken-readiness

Expected: pods replaced one at a time; then the broken version stalls with 1 pod 0/1 Running and 4 old pods untouched.

Cleanup: kill %1; kubectl delete -f lab/examples/ch11/rolling.yaml

11.2 Blue/green switch.

kubectl apply -f lab/examples/ch11/bluegreen.yaml        # deploy-blue, deploy-green, svc (selector blue)
kubectl run c --rm -it --image=busybox:1.36 --restart=Never -- sh -c 'for i in 1 2 3; do wget -qO- bg/version; done'
kubectl patch svc bg -p '{"spec":{"selector":{"app":"bg","version":"green"}}}'
kubectl run c --rm -it --image=busybox:1.36 --restart=Never -- sh -c 'for i in 1 2 3; do wget -qO- bg/version; done'

Expected: blue ×3, then green ×3.

Cleanup: kubectl delete -f lab/examples/ch11/bluegreen.yaml

11.3 Weighted canary (needs ./lab/addons/gateway.sh from Chapter 8).

kubectl apply -f lab/examples/ch11/canary-route.yaml     # stable + canary Deployments/Services + HTTPRoute 90/10
./lab/addons/gateway-port-forward.sh 8080 &
for i in $(seq 200); do curl -s -H "Host: shop.local" localhost:8080/version; echo; done | sort | uniq -c

Expected: roughly 180 stable and 20 canary. Edit the weights to 50/50 and run again.

Cleanup: kill %1; kubectl delete -f lab/examples/ch11/canary-route.yaml
