Services

You'll be able to give a set of pods a stable address, choose the right Service type, wire port to targetPort, and debug a Service with no endpoints.

1. Pods come and go; the address must not

orders-api has three pods, each with its own IP. Every rollout, crash or scale-up changes them. The web frontend can't keep a list of pod IPs.

A Service gives a group of pods one stable virtual IP and DNS name, and load-balances connections across whichever pods currently match its selector.

A client pod sends requests to the Service orders-api (ClusterIP 10.0.142.17:80). Each request animates to one of the three matching pods, on port 8080. Buttons: "kill a pod" (traffic shifts to the rest), "scale to 5", and "break the selector" (requests fail, and the endpoint list goes empty).
Windows/IIS admin
Like an NLB or ARR virtual IP in front of a web farm, except membership is decided by labels and updates itself.
Linux admin
A virtual IP that kube-proxy (iptables/IPVS) or eBPF (Cilium) rules translate to a pod IP on each node. There's no proxy process in the path.
Developer (Compose)
In Compose, the service name resolves to the containers automatically. In Kubernetes you create that name explicitly, as a Service object.
Other clouds
Same object as on EKS and GKE. Only type: LoadBalancer differs: on AKS it creates an Azure Load Balancer rule.

2. A ClusterIP Service

The default type is ClusterIP: an address reachable only inside the cluster. That's exactly right for orders-api, which only web calls.

apiVersion: v1
kind: Service
metadata:
  name: orders-api
  namespace: orders
spec:
  type: ClusterIP
  selector:
    app: orders-api
  ports:
    - name: http
      port: 80
      targetPort: 8080

3. port vs targetPort

  • port: the port clients use on the Service (http://orders-api:80).
  • targetPort: the port on the pod the traffic is forwarded to. It must be where the container actually listens, usually its containerPort.

targetPort can also be a name that matches a named container port. Then the pod can change port numbers without the Service changing.

The container listens on 8080; clients should call port 80. Complete the Service.

  ports:
    - port: 80
      ?: 8080
  • targetPort
  • containerPort containerPort belongs in the pod spec, not the Service.
  • nodePort nodePort opens a port on every node; that's a different thing.
  • hostPort hostPort is a pod setting to avoid.
Service port 80 → pod targetPort 8080. If you omit targetPort, it defaults to the same value as port, a common source of "connection refused".

4. Endpoints: who's behind the Service right now

Kubernetes keeps a list of the IP:port pairs behind each Service, in EndpointSlice objects. Only pods that match the selector and are Ready are included.

Check it whenever a Service "doesn't work". The older kubectl get endpoints still works but is deprecated; prefer kubectl get endpointslices.

$ kubectl get endpointslices -n orders -l kubernetes.io/service-name=orders-api
NAME               ADDRESSTYPE   PORTS   ENDPOINTS                            AGE
orders-api-x7k2p   IPv4          8080    10.244.1.12,10.244.2.7,10.244.3.9    3d

5. Diagnose: no endpoints

web gets "connection refused" calling orders-api. Here's what you see. What's the root cause?

$ kubectl get endpointslices -n orders -l kubernetes.io/service-name=orders-api
NAME               ADDRESSTYPE   PORTS     ENDPOINTS   AGE
orders-api-x7k2p   IPv4          <unset>   <unset>     5m
$ kubectl get svc orders-api -n orders -o jsonpath='{.spec.selector}'
{"app":"orders-api","tier":"api"}
$ kubectl get pods -n orders --show-labels
NAME                         READY   STATUS    LABELS
orders-api-7d9c5f6b8-2xk9p   1/1     Running   app=orders-api,pod-template-hash=7d9c5f6b8
orders-api-7d9c5f6b8-q8w4m   1/1     Running   app=orders-api,pod-template-hash=7d9c5f6b8
  1. The pods aren't ready They're 1/1 Running.
  2. The Service selector requires tier=api, which the pods don't have
  3. The targetPort is wrong A wrong targetPort still gives endpoints; it fails differently.
  4. The Service is in the wrong namespace Both are in orders.
Every label in a Service selector must be on the pod. Either add tier: api to the pod template or remove it from the selector. Empty endpoints almost always mean a selector mismatch or no ready pods.

6. NodePort

NodePort opens the same port (30000–32767) on every node and forwards it to the Service. It's mostly a building block: LoadBalancer Services use it underneath.

On AKS you rarely use it directly. Nodes usually have no public IPs, and exposing node ports is a security smell.

7. LoadBalancer

LoadBalancer asks the cloud for an external load balancer. On AKS, the cloud-controller-manager adds a frontend IP and rule to the cluster's Azure Load Balancer, which then appears in EXTERNAL-IP.

Add the annotation service.beta.kubernetes.io/azure-load-balancer-internal: "true" to get a private IP from your VNet instead.

One public IP per Service gets expensive and messy. For HTTP apps, you usually expose a single Gateway or Ingress instead (Chapter 8).

$ kubectl get svc -n orders
NAME         TYPE           CLUSTER-IP     EXTERNAL-IP    PORT(S)        AGE
orders-api   ClusterIP      10.0.142.17    <none>         80/TCP         3d
web          LoadBalancer   10.0.88.203    20.50.12.34    80:31452/TCP   3d

8. Headless Services

Set clusterIP: None and you get a headless Service: no virtual IP and no load balancing. DNS returns the individual pod IPs instead.

StatefulSets use this so each replica has its own stable name (db-0.db.orders.svc.cluster.local). Clients like database drivers that do their own load balancing want it too.

9. Which type?

Match each need to the Service type.

web calls orders-api inside the clusterClusterIP
A TCP service must be reachable from the internet with its own IPLoadBalancer
Only VMs in the same VNet should reach itLoadBalancer with the internal annotation
Each database replica must be addressable by nameHeadless (clusterIP: None)
ClusterIP is the default and the most common. Pods talk to each other through ClusterIP Services; LoadBalancer is only for traffic from outside.

10. Reaching a ClusterIP from your laptop

For debugging, kubectl port-forward tunnels a local port to a Service (or pod) through the API server. Nothing gets exposed publicly.

kubectl port-forward svc/orders-api -n orders 8080:80
# in another terminal
curl -s localhost:8080/healthz

11. Session affinity and traffic policy

  • Connections are spread across pods. sessionAffinity: ClientIP keeps one client on one pod, but design apps so they don't need it.
  • Load balancing is per connection, not per request. A client with one long-lived HTTP/2 or gRPC connection talks to one pod. Chapter 8's gateways balance per request.
  • externalTrafficPolicy: Local on a LoadBalancer Service keeps the client's source IP, at the cost of uneven spreading.

Services, sorted

  • A Service = stable IP and DNS name in front of pods chosen by a label selector.
  • port is the Service's port; targetPort is where the container listens.
  • EndpointSlices list the ready pods behind it; empty means a selector mismatch or no ready pods.
  • ClusterIP (default, internal), NodePort (building block), LoadBalancer (Azure LB; internal with an annotation), headless (pod IPs via DNS).
  • port-forward for debugging; Gateways (Chapter 8) for HTTP from outside.
