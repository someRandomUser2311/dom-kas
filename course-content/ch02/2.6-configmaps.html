ConfigMaps

You'll be able to move configuration out of the image into a ConfigMap, inject it as environment variables or files, and predict what happens when it changes.

1. One image, many environments

The same orders-api:1.4.2 image runs in dev and prod. What differs between them is configuration: log level, feature flags, the payment provider's URL.

Baking config into the image would mean one image per environment, which defeats "build once, deploy everywhere".

A ConfigMap holds non-secret configuration as key-value pairs. Pods read it at start-up.

apiVersion: v1
kind: ConfigMap
metadata:
  name: orders-api-config
  namespace: orders
data:
  LOG_LEVEL: info
  PAYMENTS_URL: https://payments.contoso.example/api
  FEATURE_EXPRESS_SHIPPING: "false"
  appsettings.json: |
    {
      "Orders": { "MaxItems": 50, "Currency": "EUR" }
    }
Windows/IIS admin
Like moving appSettings out of web.config into something managed per environment, the way transforms did for each build, except here it's at deploy time.
Linux admin
Like files in /etc/orders/ managed by config management, delivered into the container.
Developer (Compose)
Like environment: and env_file: in Compose, plus the ability to mount whole config files.
Other clouds
Similar to SSM Parameter Store or Runtime Config, but stored inside the cluster. For Azure-wide config there's Azure App Configuration.

2. One key as an environment variable

env[].valueFrom.configMapKeyRef reads one key from a ConfigMap into one environment variable.

Complete the reference so LOG_LEVEL comes from the ConfigMap.

env:
  - name: LOG_LEVEL
    valueFrom:
      ?:
        name: orders-api-config
        key: LOG_LEVEL
  • configMapKeyRef
  • configMapRef configMapRef is used under envFrom to load the whole map.
  • secretKeyRef That reads from a Secret.
  • fieldRef fieldRef reads pod fields such as its name or IP.
Use configMapKeyRef for one key → one variable. Add optional: true if the pod may start without it.

3. The whole map with envFrom

envFrom turns every key into an environment variable with the same name. It's convenient, but you can't see in the Deployment which variables the app gets. Keys that aren't valid variable names, like appsettings.json, are skipped.

envFrom:
  - configMapRef:
      name: orders-api-config

4. Keys as files: a volume mount

Mount a ConfigMap as a volume, and each key becomes a file whose content is the value. That's the natural way to deliver a whole config file such as appsettings.json.

items picks which keys to mount; without it, every key becomes a file.

spec:
  containers:
    - name: api
      image: contosoacr.azurecr.io/orders-api:1.4.2
      volumeMounts:
        - name: config
          mountPath: /etc/orders
          readOnly: true
  volumes:
    - name: config
      configMap:
        name: orders-api-config
        items:
          - key: appsettings.json
            path: appsettings.json

Tap the line that decides where the file appears inside the container.

mountPath: /etc/orders. With path: appsettings.json, the app reads /etc/orders/appsettings.json.

5. What happens when the ConfigMap changes?

This difference catches nearly everyone:

  • Mounted files are updated in place by the kubelet, eventually (usually within a minute). The app must re-read the file to notice.
  • Environment variables are set once, when the container starts. They never change in a running container.

Files mounted with subPath don't update either.

You change LOG_LEVEL from info to debug in the ConfigMap and apply it. orders-api reads it through configMapKeyRef. What do the running pods see?

  1. debug within a minute That's what mounted files do; env vars are fixed at start.
  2. Still info, until the pods are restarted
  3. The pods restart automatically to pick it up Kubernetes doesn't restart pods when a ConfigMap changes.
  4. An error, because the ConfigMap is in use ConfigMaps can be changed at any time.
Run kubectl rollout restart deployment/orders-api to pick up new env values. Chapter 10 shows how Helm and Kustomize trigger this automatically with a hash in the name or an annotation.

6. Restarting to pick up changes

kubectl apply -f k8s/base/configmap.yaml
kubectl rollout restart deployment/orders-api -n orders
kubectl rollout status deployment/orders-api -n orders

rollout restart adds a timestamp annotation to the pod template. That counts as a template change, so you get a normal rolling update with no downtime.

7. Immutable ConfigMaps

Set immutable: true and the ConfigMap's data can never be changed; you create a new one with a new name instead. This prevents accidental edits and reduces load on the API server in big clusters.

Kustomize's configMapGenerator uses exactly this pattern: a hash-suffixed name per version (Chapter 10).

8. What doesn't belong in a ConfigMap

  • Secrets. Passwords, connection strings with credentials, API keys. Anyone who can read the ConfigMap sees them, and ConfigMaps are often readable by many. Use Secrets (next lesson), or better, Key Vault (Chapter 15).
  • Large data. A ConfigMap is limited to 1 MiB in total.
  • Per-pod values. Use the Downward API (fieldRef) for a pod's own name, namespace or IP.

9. Creating ConfigMaps from files

kubectl create configmap orders-api-config -n orders \
  --from-literal=LOG_LEVEL=info \
  --from-file=appsettings.json \
  --dry-run=client -o yaml > k8s/base/configmap.yaml

--dry-run=client -o yaml writes the manifest instead of creating it, so it goes into Git rather than straight into the cluster.

ConfigMaps, sorted

  • A ConfigMap holds non-secret config, so one image fits every environment.
  • configMapKeyRef for one variable; envFrom for all; a volume for files.
  • Mounted files update eventually; env vars only change on restart (rollout restart).
  • No secrets, nothing over 1 MiB; consider immutable: true.
