ReplicaSets & Deployments

You'll be able to write a Deployment, explain how it rolls out a new version through ReplicaSets, and roll back a bad release.

1. Three layers

You write a Deployment. It creates a ReplicaSet, which creates Pods.

  • ReplicaSet: "keep N identical pods running". That's all it does.
  • Deployment: manages ReplicaSets over time. Each version of your pod template gets its own ReplicaSet, and the Deployment moves traffic from the old to the new by scaling them.

You almost never create a ReplicaSet directly.

Windows/IIS admin
Like a web farm behind a load balancer where updates drain and replace servers one at a time, except it's automatic and takes seconds.
Linux admin
Think of a ReplicaSet as "N copies of a systemd unit across hosts", and a Deployment as the release process on top.
Developer (Compose)
deploy.replicas in Compose sets a count; a Deployment adds versioned rollouts and rollback.
Other clouds
Like an auto-scaling group with a launch-template version and an instance refresh.

2. A Deployment manifest

A Deployment has three key parts in its spec:

  • replicas: how many pods.
  • selector: which pods it owns.
  • template: a full pod spec (metadata and spec) used to create every pod.

Deployments live in the apps API group.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
  namespace: orders
spec:
  replicas: 3
  selector:
    matchLabels:
      app: orders-api
  template:
    metadata:
      labels:
        app: orders-api
    spec:
      containers:
        - name: api
          image: contosoacr.azurecr.io/orders-api:1.4.2
          ports:
            - containerPort: 8080

3. The selector must match the template

The Deployment's selector.matchLabels must match the labels in template.metadata.labels. If they don't, the API server rejects the Deployment. Unlike a Service, a Deployment won't let you create pods it couldn't find.

In apps/v1 the selector is also immutable. To change it, you delete and recreate the Deployment.

In the manifest above, tap the line that must match selector.matchLabels.

The pod template's label app: orders-api (under template.metadata.labels). Every pod the Deployment creates carries it, so the selector finds them.

4. A rolling update

Change anything in the template, usually the image, and the Deployment starts a rollout:

  1. It creates a new ReplicaSet for the new template.
  2. It scales the new ReplicaSet up and the old one down, a few pods at a time.
  3. It only removes old pods once new ones are ready.

Changing replicas alone doesn't start a rollout. It just scales the current ReplicaSet.

Two ReplicaSet columns: old (1.4.2) and new (1.5.0). The learner changes the image and steps through the rollout. Pods appear as tiles moving through ContainerCreating → Ready, and old pods move to Terminating. A counter shows available pods, which never drops below the minimum. Sliders for maxSurge and maxUnavailable change the pace.

5. maxSurge and maxUnavailable

The default strategy is RollingUpdate, with two knobs. Both can be a number or a percentage, and both default to 25%.

  • maxSurge: how many extra pods may exist above replicas during the update.
  • maxUnavailable: how many pods may be missing below replicas.

With 3 replicas, maxSurge: 1 and maxUnavailable: 0, there are always 3 ready pods, at the cost of one extra pod during the rollout.

The other strategy, Recreate, stops all old pods first. That means downtime, but it's useful when two versions must never run at once.

spec:
  replicas: 3
+ strategy:
+   type: RollingUpdate
+   rollingUpdate:
+     maxSurge: 1
+     maxUnavailable: 0

6. Order of events

You change the image from 1.4.2 to 1.5.0 (3 replicas, maxSurge 1, maxUnavailable 0). Put the events in order.

  1. A new ReplicaSet for 1.5.0 is created
  2. The new ReplicaSet scales to 1; a 1.5.0 pod starts
  3. The 1.5.0 pod becomes Ready
  4. The old ReplicaSet scales down from 3 to 2
  5. Repeat until the new ReplicaSet has 3 and the old has 0
With maxUnavailable: 0, an old pod is only removed after a new one is ready. Readiness, which Chapter 3 defines with probes, is what makes rollouts safe.

7. Watching a rollout

$ kubectl set image deployment/orders-api api=contosoacr.azurecr.io/orders-api:1.5.0 -n orders
deployment.apps/orders-api image updated
$ kubectl rollout status deployment/orders-api -n orders
Waiting for deployment "orders-api" rollout to finish: 1 out of 3 new replicas have been updated...
Waiting for deployment "orders-api" rollout to finish: 2 out of 3 new replicas have been updated...
deployment "orders-api" successfully rolled out
$ kubectl get rs -n orders
NAME                    DESIRED   CURRENT   READY   AGE
orders-api-7d9c5f6b8    0         0         0       3d
orders-api-5b6f4c9d7    3         3         3       40s

The old ReplicaSet stays, scaled to 0, so a rollback is instant. revisionHistoryLimit (default 10) controls how many old ones are kept.

kubectl set image is handy for demos, but in real work you change the YAML and re-apply it. In Chapter 7, a pipeline does this.

8. Rollout history and rollback

Each template change is a numbered revision. If 1.5.0 is broken, kubectl rollout undo scales the previous ReplicaSet back up. It's the same rolling process, in reverse.

$ kubectl rollout history deployment/orders-api -n orders
REVISION  CHANGE-CAUSE
1         <none>
2         <none>

Version 1.5.0 returns errors. Roll orders-api back to the previous revision.

kubectl rollout undo deployment/orders-api -n orders

Also accepted: deployment orders-api or deploy/orders-api; --namespace orders; --to-revision=1.

The previous ReplicaSet scales back up. Afterwards, fix the manifest in Git too. Otherwise the next pipeline run re-deploys 1.5.0.

9. A rollout that never finishes

If new pods never become ready (a bad image, a crash, a failing probe), the rollout stalls. With maxUnavailable: 0, the old pods keep serving, so users are fine.

After progressDeadlineSeconds (default 600), the Deployment's status reports ProgressDeadlineExceeded. kubectl rollout status exits with an error, which is how a pipeline step knows to fail.

$ kubectl rollout status deployment/orders-api -n orders --timeout=5m
Waiting for deployment "orders-api" rollout to finish: 1 out of 3 new replicas have been updated...
error: deployment "orders-api" exceeded its progress deadline

10. Scaling

Change replicas in the YAML and apply it, or use kubectl scale deployment/orders-api --replicas=5 for a quick test.

For production, run at least 2 replicas so one pod can be lost or replaced without downtime. In Chapter 3 an autoscaler takes over this number.

11. Other workload controllers, briefly

  • StatefulSet: stable pod names (db-0, db-1) and a disk per pod, for databases and queues.
  • DaemonSet: one pod on every node (or every matching node), for log agents and node monitoring.
  • Job / CronJob: run to completion, once or on a schedule, for migrations and reports.

orders-api is stateless, so it's a Deployment.

Deployments, sorted

  • Deployment → ReplicaSet (one per template version) → Pods.
  • selector.matchLabels must match the template labels, and it's immutable.
  • Template changes roll out gradually; maxSurge and maxUnavailable set the pace.
  • rollout status, history and undo; old ReplicaSets make rollback instant.
  • Stalled rollouts hit progressDeadlineSeconds; run 2+ replicas in production.
