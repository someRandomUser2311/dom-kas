Write lab: orders-api Deployment + Service + ConfigMap

Brief: Write three files in k8s/base/ for orders-api in namespace orders. The container listens on 8080 and reads LOG_LEVEL from a ConfigMap; the Service is internal on port 80. Graded by manifest-lint and cross-ref.

  • All three parse, with correct apiVersion/kind pairs.
  • The Deployment's selector.matchLabels matches its template labels.
  • The Service selector matches the pod template labels (otherwise no traffic reaches the app).
  • The Service's targetPort equals the container's containerPort (number or name).
  • The ConfigMap referenced by configMapKeyRef exists, with that key.
  • The image isn't :latest or untagged.
  • replicas ≥ 2.
  • No credentials in the ConfigMap (no keys or values that look like passwords, tokens or connection strings with Password=).
  • The Service type is ClusterIP (or omitted).
Reference solution 
apiVersion: v1
kind: ConfigMap
metadata:
  name: orders-api-config
  namespace: orders
data:
  LOG_LEVEL: info
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
  namespace: orders
  labels:
    app: orders-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: orders-api
  template:
    metadata:
      labels:
        app: orders-api
    spec:
      containers:
        - name: api
          image: contosoacr.azurecr.io/orders-api:1.4.2
          ports:
            - name: http
              containerPort: 8080
          env:
            - name: LOG_LEVEL
              valueFrom:
                configMapKeyRef:
                  name: orders-api-config
                  key: LOG_LEVEL
---
apiVersion: v1
kind: Service
metadata:
  name: orders-api
  namespace: orders
spec:
  selector:
    app: orders-api
  ports:
    - name: http
      port: 80
      targetPort: http

Walkthrough: apply, scale, roll out, roll back

  1. kubectl apply -f k8s/base/ -n orders, then kubectl get deploy,rs,pods,svc -n orders.
  2. kubectl scale deploy/orders-api --replicas=5: the same ReplicaSet grows.
  3. Change the image to 1.5.0 in the YAML, apply it, and watch kubectl rollout status and two ReplicaSets.
  4. 1.5.0 fails readiness: the rollout stalls, and the old pods keep serving.
  5. kubectl rollout undo deploy/orders-api, then fix Git.

kubectl get pods -l app=orders-api,env=prod --show-labels
kubectl get pods -l 'env in (dev,staging),!canary'

Expected: two pods for the first query, three for the second.

Cleanup: kubectl delete -f lab/examples/ch02/labelled-pods.yaml

2.3 Roll out and roll back.

kubectl create deployment oa --image=localhost:5001/orders-api:1.0.0 --replicas=3
kubectl set image deploy/oa orders-api=localhost:5001/orders-api:does-not-exist
kubectl rollout status deploy/oa --timeout=30s; kubectl get pods
kubectl rollout undo deploy/oa && kubectl rollout status deploy/oa

Expected: the new pod shows ErrImagePull/ImagePullBackOff, the 3 old pods keep running, and after the undo everything is healthy.

Cleanup: kubectl delete deploy oa

2.4 Empty endpoints, then port-forward.

kubectl create deployment oa --image=localhost:5001/orders-api:1.0.0
kubectl create service clusterip oa-svc --tcp=80:8080   # selector app=oa-svc: wrong on purpose
kubectl get endpointslices -l kubernetes.io/service-name=oa-svc
kubectl patch svc oa-svc -p '{"spec":{"selector":{"app":"oa"}}}' && kubectl port-forward svc/oa-svc 8080:80

Expected: <unset> endpoints at first; after the patch, curl localhost:8080/healthz returns ok in another terminal.

Cleanup: Ctrl-C, then kubectl delete deploy oa svc oa-svc
