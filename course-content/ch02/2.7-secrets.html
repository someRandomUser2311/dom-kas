Secrets

You'll be able to use a Secret in a pod, explain exactly how much (and how little) protection a Secret gives, and keep secret values out of Git.

1. A Secret looks like a ConfigMap

A Secret holds sensitive values: passwords, tokens, keys, TLS certificates. It's used like a ConfigMap, as env vars or mounted files. The values in data are base64-encoded.

apiVersion: v1
kind: Secret
metadata:
  name: orders-db
  namespace: orders
type: Opaque
data:
  username: b3JkZXJzX2FwcA==
  password: UzNjcmV0LVBhc3N3MHJk
Windows/IIS admin
Think of an encrypted connectionStrings section, except a Secret is not encrypted by default. Careful: the name promises more than it delivers.
Linux admin
Like a 0600 file: protection comes from who can read it, not from the content being scrambled.
Developer (Compose)
Similar to Compose secrets mounted at /run/secrets. The source must still be kept out of Git.
Other clouds
Same as EKS and GKE. The real vault is Azure Key Vault (Chapter 15), like AWS Secrets Manager or GCP Secret Manager.

2. base64 is not encryption

base64 is an encoding. It turns any bytes into safe text characters, and anyone can reverse it with one command. It doesn't hide anything.

$ echo 'UzNjcmV0LVBhc3N3MHJk' | base64 -d
S3cret-Passw0rd

A colleague says "it's fine to commit this Secret manifest to Git, the values are encoded". Are they right?

  1. Yes, base64 is a form of encryption base64 has no key; anyone can decode it.
  2. No: base64 is reversible by anyone, so committing it is the same as committing the plain password
  3. Yes, if the repository is private Everyone with repo access, and every clone and backup, now has the password, forever.
  4. Yes, because Kubernetes encrypts it on apply Whatever happens in the cluster, the Git copy stays readable.
Treat a Secret manifest with real values exactly like a plain-text password. If one was committed, rotate the password.

3. So what does a Secret protect?

Secrets are still better than ConfigMaps for sensitive values:

  • RBAC can treat them separately. Many roles can read ConfigMaps but not Secrets.
  • Mounted Secrets live in memory (tmpfs) on the node, never on its disk.
  • A Secret is only sent to nodes running pods that use it.
  • Encryption at rest can be added for etcd. On AKS, etcd is on encrypted storage, and you can add KMS etcd encryption with your own Key Vault key.

But anyone who can get secrets in a namespace, or create a pod there, can read them. RBAC is the real protection (Chapter 15).

4. Use a Secret as an env var

Read the database password from the orders-db Secret.

env:
  - name: DB_PASSWORD
    valueFrom:
      ?:
        name: orders-db
        key: password
  • secretKeyRef
  • configMapKeyRef That reads a ConfigMap.
  • secretRef secretRef goes under envFrom for the whole Secret.
  • vaultRef There's no such field.
Same shape as configMapKeyRef. Prefer mounting Secrets as files: env vars can leak through crash dumps, debug endpoints and child processes.

5. Or mount it as files

containers:
  - name: api
    volumeMounts:
      - name: db
        mountPath: /var/run/secrets/orders-db
        readOnly: true
volumes:
  - name: db
    secret:
      secretName: orders-db
      defaultMode: 0400

The app reads /var/run/secrets/orders-db/password. Like ConfigMaps, mounted Secrets update when the Secret changes, so rotation works without a restart if the app re-reads the file.

6. stringData for writing

When creating a Secret you can use stringData with plain values; the API server encodes them into data.

That's convenient, but it makes the danger obvious: this file contains the password in clear text and must never be committed.

apiVersion: v1
kind: Secret
metadata:
  name: orders-db
  namespace: orders
stringData:
  username: orders_app
  password: S3cret-Passw0rd

7. Spot the leak

This manifest is in the Contoso repository. Tap the line that leaks a credential.

containers:
  - name: api
    image: contosoacr.azurecr.io/orders-api:1.4.2
    env:
      - name: LOG_LEVEL
        valueFrom:
          configMapKeyRef: { name: orders-api-config, key: LOG_LEVEL }
      - name: DB_CONNECTION
        value: "Server=orders-db;User Id=orders_app;Password=S3cret-Passw0rd"
      - name: DB_PASSWORD_FILE
        value: /var/run/secrets/orders-db/password
The DB_CONNECTION value contains the password inline, in Git and in the Deployment that anyone with read access can see. Build the connection string from a Secret, or better, use a managed identity with no password at all (Chapter 15). The last line is just a path, which is fine.

8. Other Secret types

  • kubernetes.io/tls: a certificate and key (tls.crt, tls.key), used by Ingress and Gateways (Chapter 8).
  • kubernetes.io/dockerconfigjson: registry credentials for imagePullSecrets. On AKS you normally don't need it, because the kubelet identity gets AcrPull (Chapter 6).
  • Opaque: anything else.

9. Where Secrets should really come from

Hand-made Secrets raise the question: where does the value come from, and who rotates it? This course's answer, built up later:

  • Chapter 7: pipelines get credentials from service connections and Key Vault-linked variable groups, never from YAML.
  • Chapter 15: pods read secrets straight from Azure Key Vault with the Secrets Store CSI driver and workload identity. Even better, they use managed identities so many secrets disappear altogether.

Secrets, sorted

  • Secrets are base64-encoded, not encrypted: never commit real values.
  • They're protected by RBAC, tmpfs mounts and etcd encryption at rest (AKS: encrypted storage, optional KMS).
  • secretKeyRef for an env var; prefer a read-only volume mount.
  • Watch for credentials hiding in plain value: fields and connection strings.
  • Long term: Key Vault and managed identities (Chapter 15).
