Labels & selectors

You'll be able to label objects consistently, write equality-based and set-based selectors, and spot the label typo that silently breaks an app.

1. Labels are the glue

A label is a key: value pair in an object's metadata.labels. Labels don't do anything on their own; they're tags.

But almost every connection in Kubernetes is made by selecting objects by their labels, not by name:

  • a Deployment finds its pods;
  • a Service finds the pods to send traffic to;
  • a NetworkPolicy finds the pods it protects.
metadata:
  name: orders-api-7d9c5f6b8-2xk9p
  labels:
    app: orders-api
    tier: api
    env: prod
    version: "1.4.2"
Windows/IIS admin
Like Azure resource tags, or AD group membership: a Service "targets everything tagged app=orders-api", whoever those happen to be right now.
Linux admin
Like Ansible inventory groups, but evaluated live, every time.
Developer (Compose)
Compose links by service name. Kubernetes links by labels, so pods can come and go without anything being re-pointed.
Other clouds
Same as EKS and GKE. Don't confuse them with AWS tags or GCP labels on cloud resources; these live inside the cluster.

2. Label rules and conventions

  • Keys can have a prefix: app.kubernetes.io/name. Values are short strings (63 characters max); quote numbers such as "1.4.2".
  • Use a consistent set. The recommended labels are app.kubernetes.io/name, /instance, /version, /component, /part-of and /managed-by. Helm adds them automatically (Chapter 10).
  • This course uses the short app, tier and env labels to keep examples readable.

Annotations look similar, but they're for non-identifying information, such as a build URL or a tool setting. You can't select on them.

3. Equality-based selectors

The simplest selector lists labels that must all match. Extra labels on the pod don't matter.

In YAML that's matchLabels. On the command line it's -l app=orders-api,tier=api, where a comma means AND.

!= means "not equal".

selector:
  matchLabels:
    app: orders-api
    tier: api
A grid of 8 pods with label chips: orders-api api pods in dev and prod, web frontend pods in dev and prod, an orders-worker, and one pod labelled app: order-api (typo). Above the grid is an editable selector (YAML or -l syntax). Pods that match light up live, and a counter shows "selected: N".

4. Pick exactly the right pods

Write a selector that picks only the orders-api pods running in prod.

Success when exactly the two pods labelled app=orders-api, env=prod are selected. Hints: selecting all orders-api pods → "Narrow it to prod"; selecting the web prod pods too → "Every listed label must match: add app".
Solution
matchLabels:
  app: orders-api
  env: prod

Or on the command line: -l app=orders-api,env=prod

A selector is an AND of all its labels. Add labels to narrow it.

5. Set-based selectors

For "one of several values", use set-based selectors:

  • In and NotIn: the value is in, or not in, a list.
  • Exists and DoesNotExist: the key is present or absent.

In YAML that's matchExpressions. On the command line: -l 'env in (dev,staging)', or -l '!canary' for "no canary label".

Deployments and most newer objects accept both forms. A Service's selector accepts only plain equality.

selector:
  matchLabels:
    app: orders-api
  matchExpressions:
    - key: env
      operator: In
      values: [dev, staging]
    - key: canary
      operator: DoesNotExist

6. Labels on the command line

kubectl get pods -n orders -l app=orders-api --show-labels
kubectl get pods -n orders -l 'env in (dev,staging)'
kubectl get pods -n orders -L env,version         # labels as columns
kubectl label pod orders-api-7d9c5f6b8-2xk9p -n orders debug=true

Adding a label by hand, as in the last line, is fine for a quick experiment. Labels that matter belong in the manifest.

7. The silent typo

A selector that matches nothing is not an error. Kubernetes happily keeps an empty set. Nobody warns you; things just quietly don't work.

--- Service selector
selector:
  app: order-api       # missing "s"
--- Pod template labels
labels:
  app: orders-api

The Service's selector has a typo (order-api). What happens when you apply both files?

  1. kubectl apply rejects the Service The YAML is valid, so the API server accepts it.
  2. Both are created, but the Service has no endpoints, so requests to it fail
  3. The Service finds the pods anyway because the names are close Matching is exact: no fuzzy matching.
  4. The pods crash The pods are fine; nothing is sending them traffic.
This is one of the most common Kubernetes bugs. The tell-tale sign is an empty endpoints list (lesson 2.4). The write labs make this a critical rule.

8. Don't let selectors overlap

If two Deployments' selectors match the same pods, the controllers fight over them, scaling each other's pods up and down.

Always include a label unique to that workload, typically app, in both the selector and the pod template.

9. Labels you'll meet on AKS

Nodes carry labels too, and later chapters select on them:

  • kubernetes.io/os=linux
  • topology.kubernetes.io/zone=westeurope-1
  • kubernetes.azure.com/agentpool=user
  • kubernetes.azure.com/mode=system

Chapter 3 uses them to place pods in zones and on the right node pool.

Labels, sorted

  • Labels are tags; selectors connect objects by matching them.
  • matchLabels = all must match; matchExpressions adds In/NotIn/Exists/DoesNotExist.
  • Service selectors are equality-only.
  • A selector that matches nothing fails silently; check labels exactly.
  • Use a unique app label so selectors never overlap.
