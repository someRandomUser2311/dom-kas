Pods

You'll be able to write a Pod manifest, explain what containers in the same pod share, and use init containers and sidecars.

1. The smallest thing Kubernetes runs

Kubernetes doesn't run containers on their own. It runs pods. A pod is a wrapper around one or more containers that are always scheduled together, on the same node.

Most pods have exactly one container: your app. Extra containers are for helpers that must live right next to it.

Windows/IIS admin
A pod is closer to "one server running one site" than to "one process": it has its own IP address and can host a helper service beside the main one.
Linux admin
A pod is a set of processes sharing one network namespace, so one IP and one localhost, plus shared volumes.
Developer (Compose)
Close to one Compose service. Careful: two Compose services talk over the network by service name; two containers in one pod talk over localhost.
Other clouds
Same as an ECS task with several containers.

2. Every manifest starts the same way

Every Kubernetes object has four top-level fields:

  • apiVersion: which API group and version defines this kind. Pods are in the core group, so it's just v1.
  • kind: the type of object.
  • metadata: its name, namespace and labels.
  • spec: what you want.
apiVersion: ?
kind: Pod
metadata:
  name: orders-api
  namespace: orders

Fill in the apiVersion for a Pod.

  • v1
  • apps/v1 apps/v1 is for Deployments, ReplicaSets and StatefulSets.
  • core/v1 The core group is written without a group name: just v1.
  • pod/v1 There's no pod API group.
Core objects such as Pod, Service, ConfigMap, Secret and Namespace use v1. Check any kind with kubectl api-resources.

3. The container list

spec.containers is a list. Each item needs a name and an image. ports documents the port the app listens on; it's informational, but tools and people rely on it.

apiVersion: v1
kind: Pod
metadata:
  name: orders-api
  namespace: orders
  labels:
    app: orders-api
spec:
  containers:
    - name: api
      image: contosoacr.azurecr.io/orders-api:1.4.2
      ports:
        - containerPort: 8080

4. Containers in a pod share a network

Every pod gets one IP address. All its containers share it, along with the port space and localhost.

That means two containers in one pod can't both listen on port 8080, and they talk to each other at localhost:port.

Containers in a pod can also share volumes, so one can write files the other reads.

A pod drawn as a box with one IP badge (10.244.1.12). Inside are two containers, api (:8080) and log-agent (:2020), with a shared emptyDir volume between them. Clicking "api → localhost:2020" animates a call that never leaves the pod.

The api container needs to call a helper in the same pod on port 2020. Which address?

  1. log-agent:2020 Container names aren't DNS names; that only works between Compose services.
  2. localhost:2020
  3. The node's IP on port 2020 That would only work with a host port, which you should avoid.
  4. A Service is required first Services are for reaching other pods.
Containers in one pod share a network namespace, so localhost reaches all of them.

5. Init containers: run first, then exit

Init containers run before the app containers, one at a time, and each must exit successfully. Use them for setup:

  • waiting for a database
  • running a schema migration
  • fetching a file

While they run, the pod shows Init:0/1. If one fails, Kubernetes retries it, and the app never starts until it succeeds.

spec:
  initContainers:
    - name: wait-for-db
      image: busybox:1.36
      command: ["sh", "-c", "until nc -z orders-db 5432; do echo waiting; sleep 2; done"]
  containers:
    - name: api
      image: contosoacr.azurecr.io/orders-api:1.4.2
      ports:
        - containerPort: 8080

Tap the line that starts the section of containers that must finish before the app starts.

initContainers run to completion, in order, before any container in containers starts.

6. Sidecars: helpers that run alongside

A sidecar is a helper that runs for the pod's whole life: a log shipper, a proxy, a certificate refresher.

Kubernetes has native sidecars: an init container with restartPolicy: Always. It starts before the app containers and keeps running beside them, and it stops after them. This is the recommended form on current Kubernetes versions.

spec:
  initContainers:
    - name: log-agent
      image: fluent/fluent-bit:3.1
      restartPolicy: Always        # makes it a native sidecar
  containers:
    - name: api
      image: contosoacr.azurecr.io/orders-api:1.4.2

Before native sidecars, helpers were simply listed as a second entry in containers. That still works, but there's no start order, and a never-ending sidecar can stop a Job from finishing.

7. Pods are disposable

A pod is never repaired or moved. If it dies, or its node dies, it's replaced by a new pod with a new name and a new IP.

That's why you almost never create bare pods. You create a Deployment (lesson 2.3), which keeps the right number of pods running. And you never hard-code a pod's IP: you use a Service (lesson 2.4).

8. Pod phases and restarts

  • Pending: accepted, but not yet running (waiting for a node, pulling the image, or running init containers).
  • Running: at least one container is running.
  • Succeeded / Failed: all containers have exited (for batch work).

The pod's restartPolicy (default Always) restarts crashed containers inside the same pod on the same node, with a growing delay. That delay is what CrashLoopBackOff means.

9. Apply it and look

$ kubectl apply -f pod.yaml
pod/orders-api created
$ kubectl get pod orders-api -n orders
NAME         READY   STATUS     RESTARTS   AGE
orders-api   0/1     Init:0/1   0          4s
$ kubectl get pod orders-api -n orders
NAME         READY   STATUS     RESTARTS   AGE
orders-api   1/1     Running    0          21s

READY 1/1 counts app containers that are ready. Native sidecars aren't counted in the ready total.

Pods, sorted

  • A pod is one or more containers scheduled together, sharing one IP, localhost and volumes.
  • Every manifest has apiVersion, kind, metadata and spec; Pods use v1.
  • Init containers run to completion first; native sidecars are init containers with restartPolicy: Always.
  • Pods are replaced, never repaired. Use Deployments to run them and Services to reach them.
