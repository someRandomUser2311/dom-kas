Containers in 10 minutes

You'll be able to explain images, containers, layers, registries, tags and digests, and read a multi-stage Dockerfile for orders-api.

1. "It works on my machine"

Contoso's orders-api is a small web API written in Go. It listens on port 8080 and stores orders in a database.

To run it, a server needs the right runtime, the right libraries and the right config. Get one wrong and it fails, typically only in production.

A container image packages the app with everything it needs to run: its files, libraries and default settings. If it runs from the image on your laptop, it runs from the same image on any machine with a container runtime.

Windows/IIS admin
Instead of installing IIS, the .NET runtime and the app on each server and hoping they match, you ship one sealed package. Careful: almost all Kubernetes workloads are Linux containers. Windows containers exist (AKS supports Windows node pools) but are a special case.
Linux admin
A container is an ordinary Linux process isolated with namespaces and limited with cgroups. It is not a VM: there's no separate kernel.
Developer (Compose)
You know this part already. Skim it for the vocabulary (layers, digests) the rest of the course uses.
Other clouds
Same OCI images you'd push to ECR or Artifact Registry. On Azure the registry is ACR (Chapter 6).

2. Image vs container

An image is a read-only template: a filesystem plus metadata (which command to run, which port, which user). It's built once.

A container is a running instance of an image, with its own thin writable layer on top. You can run many containers from one image.

When a container is removed, its writable layer goes with it. Anything the app wrote inside the container is gone. That's why data lives in databases and volumes (Chapter 3), never in the container.

docker build -t orders-api:1.0.0 .     # image: built once
docker run -d -p 8080:8080 orders-api:1.0.0   # container #1
docker run -d -p 8081:8080 orders-api:1.0.0   # container #2, same image

3. A Dockerfile, line by line

A Dockerfile is the recipe for an image. Each instruction does one thing:

  • FROM: the base image to start from.
  • WORKDIR: the directory later instructions run in.
  • COPY: files from your project into the image.
  • RUN: a command executed at build time.
  • EXPOSE: documents the port the app listens on.
  • USER: which user the app runs as.
  • CMD or ENTRYPOINT: what runs when the container starts.
FROM golang:1.23
WORKDIR /src
COPY . .
RUN go build -o /orders-api ./cmd/orders-api
EXPOSE 8080
CMD ["/orders-api"]

Which instruction picks the starting image?

? golang:1.23
WORKDIR /src
  • FROM
  • RUN RUN executes a command inside the image being built.
  • COPY COPY adds files; it needs an image to copy into.
  • CMD CMD is the start command, used at run time.
Every Dockerfile starts with FROM (a build may have several, one per stage).

4. Layers and the build cache

Each instruction that changes files (COPY, RUN, ADD) creates a layer. Layers are cached: if an instruction and everything before it are unchanged, the build reuses the cached layer instead of re-running it.

Once one layer changes, every layer after it is rebuilt.

So order matters. Copy the files that change rarely, such as the dependency list (go.mod, go.sum), and download dependencies first. Copy the source code last.

The Dockerfile drawn as a stack of layers, each with a "cached" or "rebuilt" badge. The learner can "edit a source file" or "add a dependency" and watch which layers turn orange (rebuilt), with an estimated build time. A toggle switches between the naïve order (COPY . . first) and the cache-friendly order.
FROM golang:1.23
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download          # cached until go.mod/go.sum change
COPY . .                     # source changes only rebuild from here
RUN go build -o /orders-api ./cmd/orders-api

5. Find the cache breaker

Every code change makes this build download all dependencies again. Tap the line responsible.

FROM golang:1.23
WORKDIR /src
COPY . .
RUN go mod download
RUN go build -o /orders-api ./cmd/orders-api
COPY . . copies all source before go mod download. Any file change invalidates that layer, and so every layer after it, including the dependency download. Copy go.mod/go.sum first.

6. Multi-stage builds: small, safe images

The golang image has a compiler, a shell and package tools, and is hundreds of megabytes. None of that is needed to run the binary, and every extra tool is something an attacker could use.

A multi-stage build compiles in one stage and copies only the result into a minimal final stage. Here the final stage is a distroless image: no shell, no package manager, and it runs as a non-root user.

# build stage
FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/orders-api ./cmd/orders-api

# runtime stage
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/orders-api /orders-api
EXPOSE 8080
USER nonroot:nonroot
ENTRYPOINT ["/orders-api"]

CGO_ENABLED=0 produces a statically linked binary that needs no C libraries, so it runs on the static distroless image. Chapter 16 adds image scanning and signing on top of this.

7. Registries, repositories and tags

Images are stored in a registry. An image reference has up to four parts:

contosoacr.azurecr.io / orders-api : 1.4.2
      registry             repository    tag

With no registry, Docker assumes Docker Hub. With no tag, it assumes latest.

A tag is just a label that points to an image, and it can be moved. Pushing a new image as 1.4.2 silently replaces what 1.4.2 meant.

latest is not special: it's simply the default tag name. Nothing guarantees it's the newest image.

docker tag orders-api:1.0.0 contosoacr.azurecr.io/orders-api:1.0.0
docker push contosoacr.azurecr.io/orders-api:1.0.0

8. Digests: the name that can't change

Every image also has a digest: a SHA-256 hash of its content, such as sha256:3f5a…. Change one byte and the digest changes.

A reference like orders-api@sha256:3f5a… always means exactly the same image, byte for byte. That's why production manifests and base images are often pinned by digest.

image: contosoacr.azurecr.io/orders-api:1.4.2@sha256:3f5a9c0d…   # tag for humans, digest for the runtime

Why is image: orders-api@sha256:… safer in production than image: orders-api:latest?

  1. Digests download faster Download speed is the same; the bytes are identical.
  2. The digest always refers to the same image content; latest can be repointed at any time
  3. latest is always an old image latest is whatever was last pushed with that tag, which could be anything.
  4. Kubernetes refuses latest It accepts it, but it also changes the default pull policy to Always.
With a digest, every node and every restart runs exactly the image you tested. With latest, two pods in the same Deployment can end up running different code.

9. Where containers fit in this course

From here on, orders-api is an image in a registry. In Chapter 6 that registry is Azure Container Registry, and in Chapter 7 a pipeline builds and pushes the image on every merge.

Kubernetes never builds images. It pulls them and runs containers from them. Its job, as the next lesson shows, is everything that happens after docker run.

Containers, sorted

  • Image = read-only template; container = a running instance with a throwaway writable layer.
  • Each file-changing instruction makes a cached layer; once one changes, every later layer rebuilds. Copy the dependency list first and the source last.
  • Multi-stage builds ship only the binary, in a minimal non-root image.
  • registry/repository:tag; tags can move, and latest is just a name.
  • A digest pins the exact image content.
