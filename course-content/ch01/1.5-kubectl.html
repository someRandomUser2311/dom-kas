kubectl essentials

You'll be able to use the dozen kubectl commands that cover most day-to-day work: reading, applying, inspecting, logs and exec.

1. The shape of every command

Nearly every kubectl command has the same shape:

kubectl <verb> <resource> [name] [flags]

The verb is what to do: get, describe, apply, delete, logs, exec.

The resource is the kind of object: pods, deployments, services. Short names work too: po, deploy, svc, no (nodes), ns (namespaces).

A scripted terminal against a sample cluster with the orders namespace running orders-api (3 pods) and web (2 pods). Steps 2–10 each pre-fill a command; the learner presses Enter and sees realistic output. Free typing of any command used in this lesson also works.
Windows/IIS admin
The verb-resource order is the reverse of PowerShell's Get-Process. Think kubectl get pods ≈ Get-Pod.
Linux admin
Same pattern as systemctl status nginx: a verb, then a target.
Developer (Compose)
kubectl get pods ≈ docker compose ps, kubectl logs ≈ docker compose logs, kubectl exec ≈ docker compose exec.
Other clouds
Identical on EKS and GKE. Only getting credentials differs: on AKS it's az aks get-credentials.

2. get: list things

get lists objects in a table.

  • -n orders picks the namespace.
  • -A (--all-namespaces) shows every namespace.
  • -o wide adds columns such as the pod's IP and node.
  • -l app=orders-api filters by label.
  • -w keeps watching for changes.
$ kubectl get pods -n orders -o wide
NAME                          READY   STATUS    RESTARTS   AGE   IP            NODE
orders-api-7d9c5f6b8-2xk9p    1/1     Running   0          3h    10.244.1.12   aks-user-1234-vmss000000
orders-api-7d9c5f6b8-q8w4m    1/1     Running   0          3h    10.244.2.7    aks-user-1234-vmss000001
orders-api-7d9c5f6b8-z5t2n    1/1     Running   2          3h    10.244.3.9    aks-user-1234-vmss000002
web-6c8f9d7b5-h4j2k           1/1     Running   0          3h    10.244.1.13   aks-user-1234-vmss000000

List the pods in the orders namespace, including the node each one runs on.

kubectl get pods -n orders -o wide

Also accepted: po/pod for pods, --namespace orders, --output wide, flags in any order.

-o wide adds the IP and NODE columns.

3. -o yaml: see the whole object

-o yaml (or -o json) prints the complete object as the API server stores it, spec and status included. It's the most honest answer to "what does the cluster actually have?"

-o jsonpath='{…}' picks one field, which is handy in scripts.

kubectl get deployment orders-api -n orders -o yaml
kubectl get pod orders-api-7d9c5f6b8-2xk9p -n orders -o jsonpath='{.status.podIP}'

4. describe: the human-readable story

describe shows an object's key fields plus its recent events: scheduled, pulled the image, started, probe failed. When something is wrong, check here first.

OOMKilled with exit code 137 means the container used more memory than its limit and was killed. Chapter 3 covers memory limits.

5. apply -f: create or update from a file

kubectl apply -f file.yaml sends the file's objects to the API server. They're created if they don't exist, and updated to match the file if they do. Run it again unchanged and nothing happens.

-f also accepts a folder (-f k8s/) or a URL. This is the declarative way you'll use everywhere.

$ kubectl apply -f k8s/ -n orders
deployment.apps/orders-api configured
service/orders-api unchanged
configmap/orders-api-config created

kubectl create and kubectl run are imperative alternatives. They're fine for experiments, but avoid them for anything that should live in Git.

6. delete

kubectl delete removes objects by name (kubectl delete deployment orders-api), by file (-f), or by label (-l).

Remember lesson 1.4: deleting a pod owned by a Deployment just causes a replacement. Delete the Deployment to stop the app.

Always double-check the namespace and context before deleting. There's no undo.

7. logs: what the app printed

Containers should write logs to standard output; Kubernetes captures it.

  • --tail=50: the last 50 lines.
  • -f: follow live.
  • -c: pick a container in a multi-container pod.
  • --previous: the logs of the container before it last restarted. That's essential for crash loops.
  • deploy/orders-api: read logs from one pod of a Deployment without looking up a pod name.

Show the last 50 log lines of pod orders-api-7d9c5f6b8-z5t2n in namespace orders.

kubectl logs orders-api-7d9c5f6b8-z5t2n -n orders --tail=50

Also accepted: --tail 50, --namespace orders, flags in any order.

Add --previous to see why the last container instance died.

8. exec: run a command inside a container

kubectl exec -it pod -- command runs a command inside a running container. Everything after -- is the command. -it makes it interactive, for a shell.

Our orders-api image is distroless, so it has no shell. Use kubectl debug to attach a temporary debugging container instead (Chapter 14). Minimal images make this a deliberate trade-off.

kubectl exec -it web-6c8f9d7b5-h4j2k -n orders -- sh
kubectl exec web-6c8f9d7b5-h4j2k -n orders -- cat /etc/nginx/conf.d/default.conf

9. explain: built-in documentation

Forgot a field name? kubectl explain describes any field of any resource, straight from the cluster's own API schema. It always matches your cluster's version.

$ kubectl explain deployment.spec.strategy
GROUP:      apps
KIND:       Deployment
FIELD: strategy <DeploymentStrategy>
DESCRIPTION:
    The deployment strategy to use to replace existing pods with new ones.
FIELDS:
  rollingUpdate	<RollingUpdateDeployment>
  type	<string>

10. Pick the right command

Match each task to the command you'd use.

Why is this pod stuck in Pending?kubectl describe pod
Why did the container crash before it restarted?kubectl logs --previous
Roll out the updated manifests in k8s/kubectl apply -f k8s/
What fields does spec.template.spec accept?kubectl explain
Which node is each pod on?kubectl get pods -o wide
Use describe for events, logs for app output, get -o wide for placement, and explain for the schema.

11. Saving keystrokes safely

  • Shell completion: source <(kubectl completion bash) (or zsh). Tab-complete resource names.
  • Default namespace for the current context: kubectl config set-context --current --namespace=orders. Then you can drop -n, but always know which namespace you're in (next lesson).
  • --dry-run=client -o yaml prints what a command would create, without creating it. It's useful for generating starter YAML.

kubectl, sorted

  • kubectl <verb> <resource> [name] [flags].
  • get (-o wide, -o yaml, -n, -A, -l, -w), describe for events.
  • apply -f to create or update declaratively; delete carefully.
  • logs (--tail, -f, --previous), exec -it … -- cmd.
  • explain documents any field.
