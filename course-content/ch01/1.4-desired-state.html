Desired state & reconciliation

You'll be able to explain the idea everything in Kubernetes is built on: you declare what you want, and controllers keep making it true.

1. Two ways to give instructions

Imperative: you say what to do. "Start a container. Start another. Now stop that one." If something breaks later, nobody remembers what the end result was supposed to be.

Declarative: you say what you want. "There should be 3 copies of orders-api 1.4.2." The system works out the steps, and keeps working on them.

Kubernetes is declarative at its core. You write the desired result in YAML; the cluster's job is to make it so and keep it so.

Windows/IIS admin
Like PowerShell DSC or Group Policy: you describe the configuration, and an agent keeps re-applying it. Kubernetes checks far more often, usually within seconds.
Linux admin
Like Ansible or Puppet, but with a loop that never stops instead of a run you trigger.
Developer (Compose)
docker compose up is declarative once: it creates what the file says, then stops caring. Kubernetes never stops caring.
Other clouds
Like an auto-scaling group's "desired capacity", applied to every kind of object.

2. Every object has a spec and a status

Almost every Kubernetes object has two halves:

  • spec: what you want. You write it.
  • status: what is. Kubernetes writes it, and you only read it.

If spec and status differ, a controller is (or should be) working to close the gap.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
spec:
  replicas: 3
  template:
    spec:
      containers:
        - name: api
          image: contosoacr.azurecr.io/orders-api:1.4.2
status:
  replicas: 3
  readyReplicas: 2
  availableReplicas: 2

3. Which half is yours?

In the file above, tap a line that Kubernetes writes and you should never edit.

readyReplicas is under status, so it's reported by the controller. Here it says only 2 of the 3 desired pods are ready; something is still being fixed. (Any line under status: is accepted.)

4. The reconciliation loop

Every controller runs the same loop, forever:

  1. Observe: what does the cluster look like right now?
  2. Compare: how is that different from the spec?
  3. Act: take one step to close the gap.
  4. Repeat.

Controllers don't run a script once. They react to any difference, whatever caused it: a crash, a deleted pod, a lost node, or you changing the spec.

5. Try it: break things

In the reconcile widget, set replicas to 3, then delete one of the running pods.

Success when the learner has deleted a pod and watched the controller create a replacement, so the count is back at 3. The pod's name changes; the count doesn't.
The controller saw 2 pods where the spec says 3, and created one. The new pod has a new name and a new IP. Nothing about the old pod is "restored".

6. Deleting a pod doesn't delete the app

You run kubectl delete pod orders-api-7d9c5-abcde. The pod belongs to a Deployment with replicas: 3. What happens?

  1. The app now has 2 pods until someone redeploys The ReplicaSet controller notices within seconds.
  2. A new pod with a different name is created to get back to 3
  3. The same pod restarts with the same name Deleted pods are gone; the replacement is a brand-new pod.
  4. The Deployment is deleted too Deleting a child never deletes its owner.
To really remove the app, delete (or scale down) the Deployment. Deleting a pod is a common way to force a fresh start.

7. Change the spec, not the pods

To change anything, edit the spec and re-apply it. To ship version 1.5.0, change the image line and run kubectl apply. The Deployment controller notices the difference and rolls pods over to the new image.

If you change a pod directly, the controller will undo or replace your change the next time it compares. So the YAML in Git is the real definition of the app. That's the idea behind GitOps, and behind the pipelines in Chapter 7.

spec:
  replicas: 3
  template:
    spec:
      containers:
        - name: api
-         image: contosoacr.azurecr.io/orders-api:1.4.2
+         image: contosoacr.azurecr.io/orders-api:1.5.0

8. Owners and garbage collection

Objects created by controllers record their owner in metadata.ownerReferences: a Pod is owned by a ReplicaSet, which is owned by a Deployment.

When an owner is deleted, Kubernetes deletes its children automatically. That's why kubectl delete deployment orders-api removes everything in one go.

metadata:
  name: orders-api-7d9c5-abcde
  ownerReferences:
    - kind: ReplicaSet
      name: orders-api-7d9c5
      controller: true

9. Status tells you why

When spec and status don't match for a long time, something is blocking the controller. Status, events and kubectl describe tell you what:

  • a pod stuck in Pending (no node has room);
  • ImagePullBackOff (wrong image name or no permission to pull);
  • CrashLoopBackOff (the app keeps exiting).

Reading these is a core skill. Chapter 14 is built around it.

Desired state, sorted

  • Declarative: you write the result you want, not the steps.
  • spec is yours; status is Kubernetes'.
  • Controllers loop forever: observe, compare, act.
  • Deleting a pod just makes the controller create a new one; change the spec to change the app.
  • Owners clean up their children; status and events explain any gap.
