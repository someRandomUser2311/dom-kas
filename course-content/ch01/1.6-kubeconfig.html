kubeconfig & contexts

You'll be able to read a kubeconfig, switch between clusters safely, and avoid the classic "ran it against production" accident.

1. How does kubectl know which cluster?

kubectl reads a kubeconfig file, by default ~/.kube/config. The KUBECONFIG environment variable can point to a different file, or to several files that are merged.

A kubeconfig has three lists and one pointer:

  • clusters: where each API server is, and the certificate to trust.
  • users: how to authenticate (a certificate, a token, or a plugin such as kubelogin for Entra ID).
  • contexts: a named pairing of cluster + user, plus a default namespace.
  • current-context: the one kubectl uses right now.
apiVersion: v1
kind: Config
clusters:
  - name: aks-orders-dev
    cluster:
      server: https://aks-orders-dev-dns-1a2b3c.hcp.westeurope.azmk8s.io:443
      certificate-authority-data: LS0tLS1CRUdJTi…
  - name: aks-orders-prod
    cluster:
      server: https://aks-orders-prod-dns-9f8e7d.hcp.westeurope.azmk8s.io:443
      certificate-authority-data: LS0tLS1CRUdJTi…
users:
  - name: clusterUser_rg-orders-dev_aks-orders-dev
    user:
      exec:
        command: kubelogin
        args: [get-token, --login, azurecli, --server-id, 6dae42f8-4368-4678-94ff-3960e28e3630]
  - name: clusterUser_rg-orders-prod_aks-orders-prod
    user:
      exec:
        command: kubelogin
        args: [get-token, --login, azurecli, --server-id, 6dae42f8-4368-4678-94ff-3960e28e3630]
contexts:
  - name: aks-orders-dev
    context:
      cluster: aks-orders-dev
      user: clusterUser_rg-orders-dev_aks-orders-dev
      namespace: orders
  - name: aks-orders-prod
    context:
      cluster: aks-orders-prod
      user: clusterUser_rg-orders-prod_aks-orders-prod
current-context: aks-orders-prod

Like having saved RDP connections to several servers, except one is always "currently open" and every command goes to it.

2. Which cluster are you pointed at?

You're about to run kubectl delete -f k8s/. Tap the line that tells you which cluster it will hit.

current-context: aks-orders-prod. This command would run against production. That one line is the most important line in the file.

3. Getting AKS credentials

az aks get-credentials downloads a cluster's connection details and merges them into your kubeconfig. It also makes that cluster the current context.

On clusters that use Entra ID (Chapter 5), the "user" entry runs kubelogin, which gets a token from your az login session. Your Azure identity and its roles decide what you can do.

az aks get-credentials --resource-group rg-orders-dev --name aks-orders-dev
# Merged "aks-orders-dev" as current context in /home/you/.kube/config

4. Listing and switching contexts

  • kubectl config get-contexts lists contexts; * marks the current one.
  • kubectl config current-context prints just the current one.
  • kubectl config use-context NAME switches.
  • kubectl --context NAME … uses a context for one command only, without switching.
$ kubectl config get-contexts
CURRENT   NAME              CLUSTER           AUTHINFO                                       NAMESPACE
          aks-orders-dev    aks-orders-dev    clusterUser_rg-orders-dev_aks-orders-dev       orders
*         aks-orders-prod   aks-orders-prod   clusterUser_rg-orders-prod_aks-orders-prod
          kind-kq           kind-kq           kind-kq

Switch the current context to aks-orders-dev.

kubectl config use-context aks-orders-dev

Only this form is accepted (use-context takes no flags here).

Every following kubectl command now goes to the dev cluster, in its default namespace orders.

5. The classic accident

An engineer debugs production in the morning. After lunch they "clean up the dev namespace" with kubectl delete -f k8s/. The current context is still production.

It's one of the most common serious Kubernetes incidents. The fix isn't "be more careful". It's habits that make the mistake hard to make.

6. Habits that prevent it

  • Show the context in your prompt. Tools like kube-ps1, starship or oh-my-posh display (aks-orders-prod:orders) on every line.
  • Keep production in a separate kubeconfig file and use it explicitly: KUBECONFIG=~/.kube/prod kubectl ….
  • Use --context in scripts instead of relying on the current context.
  • Give humans read-only access to production. Changes go through pipelines (Chapter 7) and Azure RBAC (Chapter 5).

Which habit most reliably prevents running a command against the wrong cluster?

  1. Running kubectl config current-context before important commands It helps, but it relies on remembering every time.
  2. Read-only access to production, with changes made only through pipelines, plus the context shown in the prompt
  3. Naming the production context with capital letters Easier to notice, but nothing stops the command.
  4. Deleting the kubeconfig every evening Painful, and the mistake can still happen during the day.
Combine a visible warning (the prompt) with a hard guardrail (no write access). The pipeline, not a laptop, is the only thing that changes production.

7. Kubeconfigs are credentials

A kubeconfig can contain secrets: client certificates or tokens. One copied from az aks get-credentials --admin grants cluster-admin to anyone who has it.

  • Never commit a kubeconfig (lesson 0.5).
  • Prefer Entra ID users with kubelogin, so the file holds no long-lived secret.
  • Disable local accounts on AKS (Chapter 5) so --admin credentials don't exist at all.

8. Your local lab context

If you set up the local lab in lesson 0.6, kind added a context called kind-kq. Switch to it before running any "Try it locally" box, and back to your real clusters afterwards.

kubectl config use-context kind-kq
kubectl get nodes

kubeconfig, sorted

  • clusters + users → contexts; current-context decides where commands go.
  • az aks get-credentials merges a cluster in; Entra ID clusters use kubelogin.
  • get-contexts, use-context, and --context for one command.
  • Prevent accidents: context in the prompt, separate prod kubeconfig, read-only humans, pipelines for changes.
  • A kubeconfig is a credential: never commit it.
