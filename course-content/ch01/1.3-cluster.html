The cluster: control plane & nodes

You'll be able to name every component of a Kubernetes cluster, say what each one does, and trace a kubectl apply all the way to a running container.

1. Two halves

A Kubernetes cluster has two halves:

  • The control plane is the brain. It stores what you asked for, decides where things run, and keeps checking that reality matches.
  • The nodes (worker machines) are the muscle. They run your containers.

You almost never talk to the nodes directly. You talk to the control plane, and it talks to the nodes.

2. kube-apiserver: the front door

The API server is the only component everyone talks to: kubectl, pipelines, the other control-plane components and every node.

For every request it:

  • checks who you are (authentication);
  • checks whether you're allowed (authorisation, RBAC);
  • validates the object;
  • stores it.

It's a REST API: kubectl get pods is really an HTTPS GET /api/v1/namespaces/default/pods.

3. etcd: the cluster's memory

etcd is a distributed key-value database that holds every object in the cluster: Deployments, Pods, Secrets, everything. Only the API server reads and writes it.

If etcd is lost without a backup, the cluster forgets everything it was supposed to run. On AKS, Azure runs and backs up etcd for you.

4. kube-scheduler: choosing a node

When a new pod has no node yet, the scheduler picks one. It filters out nodes that can't fit the pod (not enough CPU or memory, wrong labels, taints). Then it scores the rest and writes its choice back to the API server.

The scheduler only decides. It doesn't start anything.

5. kube-controller-manager and cloud-controller-manager

The controller manager runs dozens of controllers. Each is a loop that watches one kind of object and makes reality match it:

  • the Deployment controller creates ReplicaSets;
  • the ReplicaSet controller creates pods;
  • the node controller notices dead nodes.

The cloud-controller-manager connects Kubernetes to the cloud. On AKS it creates Azure load balancer rules when you make a LoadBalancer Service, and it tells Kubernetes when an Azure VM behind a node is gone.

6. On every node: kubelet, runtime, kube-proxy

  • kubelet: the node's agent. It watches the API server for pods assigned to its node, asks the runtime to start their containers, runs health probes, and reports status back.
  • Container runtime (containerd on AKS and kind): actually pulls images and runs containers. Kubernetes itself never runs a container directly.
  • kube-proxy: programs the node's networking rules so traffic to a Service reaches its pods. Some network setups, such as Cilium on AKS, replace it.

Older clusters used Docker Engine as the runtime through a shim called dockershim. It was removed in Kubernetes 1.24. Images built with Docker still run unchanged, because they're standard OCI images.

7. Follow a kubectl apply

Now put it together. You run kubectl apply -f deployment.yaml for 3 replicas of orders-api.

"Follow a kubectl apply" animation, one click per hop:
  1. kubectl → API server (auth, validate).
  2. API server → etcd (Deployment stored).
  3. Deployment controller sees it and creates a ReplicaSet.
  4. ReplicaSet controller creates 3 Pods with no node.
  5. Scheduler assigns each Pod to a node.
  6. The kubelet on each chosen node sees its Pod.
  7. containerd pulls the image and starts the container.
  8. The kubelet reports the Pod as Running.

8. Put it in order

Order the steps from kubectl apply to a running container.

  1. The API server validates the Deployment and stores it in etcd
  2. The Deployment controller creates a ReplicaSet
  3. The ReplicaSet controller creates Pods
  4. The scheduler assigns each Pod to a node
  5. The kubelet on that node asks containerd to start the container
No component calls the next one directly. Each one watches the API server and reacts to changes. That's why Kubernetes keeps working when parts are slow or restarting.

9. What if part of the control plane is down?

The scheduler crashes for ten minutes. What happens to orders-api's three running pods?

  1. They stop Running pods are managed by the kubelet on each node, which doesn't need the scheduler.
  2. They keep running; only new pods wait in Pending until the scheduler is back
  3. They move to other nodes Nothing is moving them; moving pods would need the scheduler anyway.
  4. kubectl stops working kubectl talks to the API server, which is still up.
Running workloads don't depend on the control plane minute to minute. A control-plane outage stops changes, not the app. Even with the API server down, pods keep serving traffic.

10. Namespaces: folders for objects

Objects live in namespaces, which work like folders.

  • The control-plane add-ons live in kube-system.
  • Your apps live in namespaces you create, such as orders.
  • If you don't say, kubectl uses default.

11. In AKS, Azure runs the top half

On AKS, the whole control plane runs in an Azure-managed environment you can't see or log into: API server, etcd, scheduler and controller managers. Azure patches it, scales it and backs it up.

You see only the nodes, which are Azure VMs in your subscription, and the add-ons that run on them.

That split, what Azure manages and what you own, is the whole of Chapter 4.

The cluster, sorted

  • Control plane:
    • API server: the front door, which does auth and validation.
    • etcd: stores every object.
    • Scheduler: picks a node for each new pod.
    • Controllers: reconcile reality with what was asked for.
    • Cloud controller: talks to Azure.
  • Nodes: the kubelet runs pods through containerd; kube-proxy routes Service traffic.
  • Components only talk through the API server, by watching for changes.
  • Running pods survive control-plane outages; changes wait.
  • In AKS, Azure runs the control plane.
