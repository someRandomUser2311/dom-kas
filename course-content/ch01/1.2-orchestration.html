Why orchestration?

You'll be able to name the five problems one container host can't solve on its own, and the Kubernetes feature that solves each.

1. One VM, one docker run

Contoso's first production setup:

  • one Linux VM
  • Docker installed
  • one command, docker run -d -p 80:8080 orders-api:1.0.0

It works on launch day. Over the next few steps, things go wrong one at a time. For each, ask yourself: who fixes this?

A single VM with one orders-api container and a traffic gauge. Buttons: "Container crashes", "VM reboots", "Black Friday traffic", "Deploy v1.1", "Add a second service". You've likely used ECS or Cloud Run, which solve these problems in their own way. Kubernetes solves them in a portable way.

2. Problem 1: the container crashes

A bug makes orders-api exit at 2 am. Docker's restart policy (--restart=always) brings it back on this VM.

But what if the bug is a hang: the process is alive and not answering? Docker sees a running process and does nothing.

Kubernetes restarts failed containers, and it can run health probes that detect "alive but broken" and restart those too (Chapter 3).

3. Problem 2: the machine dies

The VM's host has a hardware fault. The VM is gone, and so is the only copy of the app.

Restart policies can't help: they run on the machine that just died.

An orchestrator manages a pool of machines, called nodes. When one disappears, it re-creates the lost containers on the others.

The single VM reboots at 3 am for patching. With only Docker, what brings orders-api back?

  1. Nothing, ever Docker's restart policy does start it again once the VM is back.
  2. Docker's restart policy, but only after the VM is back up. Until then, the app is down.
  3. Another VM takes over automatically Only if something manages several machines, which is what an orchestrator does.
With one machine, there's always downtime while it's away. Kubernetes runs replicas on several nodes, so one node rebooting doesn't take the app down.

4. Problem 3: more traffic

Black Friday triples the traffic. You need more copies of the app, quickly, spread across machines, with traffic shared between them.

By hand that means:

  • starting containers on other VMs
  • picking free ports
  • updating a load balancer
  • removing it all again afterwards

Kubernetes scales replicas with one number. It can also do it automatically from CPU or other metrics, using the HorizontalPodAutoscaler (Chapter 3).

5. Problem 4: deploying a new version

Version 1.1 is ready. With one container, you stop the old one and start the new one, and users see errors in between. If 1.1 is broken, you scramble to bring 1.0 back.

Kubernetes does rolling updates. It starts new pods, waits until they're ready, then removes old ones a few at a time. A bad version can be rolled back with one command (Chapter 2, and Chapter 11 for safer strategies).

6. Problem 5: finding each other

Contoso adds a web frontend that calls orders-api. Which IP and port should it call? Containers come and go, and their addresses change every time.

Kubernetes gives each set of pods a stable name and virtual IP, called a Service, plus cluster DNS. web calls http://orders-api and always reaches a healthy copy.

7. Bonus problem: wasted machines

With one app per VM, most VMs sit at 10–20% CPU. Packing several apps onto shared machines saves money, but someone must decide where each one fits.

That decision is bin-packing, and the Kubernetes scheduler makes it automatically. It places each pod on a node with enough free CPU and memory, based on the requests you declare (Chapter 3).

Each of these is a controller or component you'll meet in the next two lessons.

9. What Kubernetes is not

  • It's not a build tool: it runs images, it doesn't make them.
  • It doesn't make your app scalable by magic: an app that keeps state in memory or on local disk still needs work.
  • It's not free to run: someone operates the cluster. On AKS, Azure takes the hardest part (Chapter 4).
  • It's not always the right answer: a single small app may be better on Azure Container Apps or App Service. This course is for when you need Kubernetes.

Orchestration, sorted

  • One host can't survive its own failure, scale out, update without downtime, or find services.
  • Kubernetes manages a pool of nodes and gives you restarts, rescheduling, scaling, rolling updates, Services and bin-packing.
  • You describe what you want; Kubernetes keeps working to make it true (lesson 1.4).
