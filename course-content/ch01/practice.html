What is orders-api:latest?

  1. Always the newest image pushed to the repository
  2. Whatever image was last pushed with the tag "latest", which may not be the newest
  3. A digest
  4. An error; tags must be numbers

Why pin images by digest?

  1. Digests are shorter
  2. A digest always refers to exactly the same image content
  3. Registries delete tagged images
  4. Kubernetes requires it

  1. Go requires that order
  2. So code changes don't invalidate the cached dependency layer
  3. It makes the image smaller
  4. It's needed for multi-stage builds
Once a layer changes, every later layer rebuilds.

Scenario 2: the scheduler is down. You scale orders-api from 3 to 5. What do the pods look like?

  1. 5 Running
  2. 3 Running, 2 Pending with no node
  3. 0 Running
  4. 3 Running, and the scale command fails
The ReplicaSet controller still creates the 2 new pods, but nothing assigns them a node until the scheduler returns.

Scenario 3: node 2 (running 1 of 3 orders-api pods) loses power. What happens over the next few minutes?

  1. Nothing; the pod is shown as Running forever
  2. The node becomes NotReady; after a timeout its pod is evicted and replaced on another node
  3. All pods restart
  4. The Deployment is deleted
The node controller marks the node NotReady after about 40 seconds. Pods are evicted after a toleration timeout (5 minutes by default) and recreated elsewhere. Two replicas keep serving traffic in the meantime.

Write lab: a Dockerfile for orders-api

Brief: Write a production-ready Dockerfile for orders-api (Go, main package at ./cmd/orders-api, listens on 8080). Graded by yaml-rules (text mode).

FROM golang:latest
WORKDIR /src
COPY . .
ENV DB_PASSWORD=Sup3rS3cret!
RUN go build -o /orders-api ./cmd/orders-api
CMD ["/orders-api"]
  • Uses a multi-stage build (at least two FROM lines; the final stage copies --from the build stage).
  • Base images are pinned to a version tag or digest; no :latest and no untagged images.
  • Dependencies are downloaded before the full source is copied (COPY go.mod go.sum before COPY . .).
  • EXPOSE 8080 is present.
  • No secrets in ENV or ARG (no keys matching password, secret, token, key with a literal value).
  • The final stage runs as a non-root USER (a non-zero UID or a named non-root user such as nonroot).
  • Uses ENTRYPOINT or CMD in exec (JSON array) form.
Reference solution 
FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/orders-api ./cmd/orders-api

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/orders-api /orders-api
EXPOSE 8080
USER nonroot:nonroot
ENTRYPOINT ["/orders-api"]

The database password is supplied at run time from a Kubernetes Secret, and later from Key Vault (Chapter 15). It's never baked into the image.

Walkthrough: a kubectl tour of a running cluster

A narrated, scripted terminal (not graded). Each command runs against the sample cluster with a short explanation of what to notice:

  1. kubectl config current-context: always start here.
  2. kubectl get nodes -o wide: node names, versions, internal IPs.
  3. kubectl get ns, then kubectl get all -n orders.
  4. kubectl describe deploy orders-api -n orders: replicas, strategy, events.
  5. kubectl get rs,pods -n orders -l app=orders-api: the ownership chain.
  6. kubectl logs deploy/orders-api -n orders --tail=20.
  7. kubectl get pods -n kube-system: the add-ons Azure runs on your nodes.
  8. kubectl explain pod.spec.containers.resources: preview of Chapter 3.

Try it locally

Optional boxes for the kind lab from lesson 0.6. Never graded; tick "I tried it" for 5 XP.

1.1 Build, run and push orders-api. From the course repo's apps/orders-api folder:

docker build -t localhost:5001/orders-api:1.0.0 .
docker run -d --rm --name oa -p 8080:8080 localhost:5001/orders-api:1.0.0 && curl -s localhost:8080/healthz
docker push localhost:5001/orders-api:1.0.0
docker images --digests localhost:5001/orders-api

Expected: ok from the health check, then a sha256:… digest after the push.

Cleanup: docker stop oa

On AKS: the registry is ACR, and pushing needs AcrPush (Chapter 6).

1.3 See the control plane.

kubectl get pods -n kube-system -o wide

Expected: etcd-kq-control-plane, kube-apiserver-…, kube-scheduler-… and kube-controller-manager-… on the control-plane node, plus kube-proxy and CoreDNS.

Cleanup: none.

On AKS: the control-plane pods are hidden; you'll only see add-ons like CoreDNS and kube-proxy (or Cilium).

1.4 Watch reconciliation.

kubectl create deployment demo --image=localhost:5001/orders-api:1.0.0 --replicas=3
kubectl get pods -l app=demo -w &
kubectl delete $(kubectl get pods -l app=demo -o name | head -1) --wait=false

Expected: in the watch, pods go Terminating while new pods appear as ContainerCreating → Running.

Cleanup: kill %1; kubectl delete deployment demo

1.5 The essentials, for real.

kubectl create deployment demo --image=localhost:5001/orders-api:1.0.0

Expected: one pod on a worker node, events showing the ReplicaSet scaled up, and startup log lines.

Cleanup: kubectl delete deployment demo
