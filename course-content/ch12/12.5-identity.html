Identity & role assignments

You'll be able to create every identity and role assignment from Chapter 5 in Terraform: the cluster identity, AcrPull for the kubelet, and a workload identity with its federated credential.

1. The cluster identity, first

Create the user-assigned identity and give it Network Contributor on the node subnet. The cluster must not be created before that grant exists, or it can fail to manage its network. This is one of the rare cases where depends_on is right: the cluster references the identity, but not the role assignment.

resource "azurerm_user_assigned_identity" "aks" {
  name                = "id-aks-${local.name_suffix}"
  location            = azurerm_resource_group.main.location
  resource_group_name = azurerm_resource_group.main.name
}

resource "azurerm_role_assignment" "aks_network" {
  scope                = azurerm_subnet.aks_nodes.id
  role_definition_name = "Network Contributor"
  principal_id         = azurerm_user_assigned_identity.aks.principal_id
  principal_type       = "ServicePrincipal"
}

# in aks.tf, on azurerm_kubernetes_cluster.main:
#   depends_on = [azurerm_role_assignment.aks_network]   # hidden dependency

2. AcrPull for the kubelet

The kubelet identity is created by AKS. Its object ID is exported as an attribute of the cluster.

resource "azurerm_role_assignment" "kubelet_acr_pull" {
  scope                = data.azurerm_container_registry.shared.id
  role_definition_name = "AcrPull"
  principal_id         = azurerm_kubernetes_cluster.main.kubelet_identity[0].object_id
  principal_type       = "ServicePrincipal"
}

Tap the reference to the identity that actually pulls images.

kubelet_identity[0].object_id, not the cluster's identity block. That's the same distinction as lesson 5.4. kubelet_identity is a list with one item, hence the [0].

3. A workload identity

resource "azurerm_user_assigned_identity" "orders_api" {
  name                = "id-orders-api-${var.environment}"
  location            = azurerm_resource_group.main.location
  resource_group_name = azurerm_resource_group.main.name
}

resource "azurerm_federated_identity_credential" "orders_api" {
  name                = "fc-${azurerm_kubernetes_cluster.main.name}-orders-api"
  resource_group_name = azurerm_resource_group.main.name
  parent_id           = azurerm_user_assigned_identity.orders_api.id
  issuer              = azurerm_kubernetes_cluster.main.oidc_issuer_url
  subject             = "system:serviceaccount:orders:orders-api"
  audience            = ["api://AzureADTokenExchange"]
}

output "orders_api_client_id" {
  value = azurerm_user_assigned_identity.orders_api.client_id   # goes into the ServiceAccount annotation
}

4. Fix the subject

The app moved to namespace orders-prod in prod, still with ServiceAccount orders-api. Make the federated credential subject follow the environment without hard-coding it twice.

Graded by iac-rules: with environment=prod the subject renders system:serviceaccount:orders-prod:orders-api; with dev it renders system:serviceaccount:orders:orders-api. A local.app_namespace or a variable is accepted.
Solution 
locals {
  app_namespace = local.is_prod ? "orders-prod" : "orders"
}
# …
  subject = "system:serviceaccount:${local.app_namespace}:orders-api"
The subject must match the namespace and ServiceAccount exactly (lesson 5.6). Generating both the subject and the manifests' namespace from the same value prevents drift.

5. Key Vault access via RBAC

resource "azurerm_role_assignment" "orders_api_kv" {
  scope                = azurerm_key_vault.main.id
  role_definition_name = "Key Vault Secrets User"
  principal_id         = azurerm_user_assigned_identity.orders_api.principal_id
  principal_type       = "ServicePrincipal"
}

Create the vault with rbac_authorization_enabled = true (the RBAC permission model) so access is granted with role assignments like this, not with vault access policies.

6. Who can create role assignments?

The infra pipeline's apply fails. Why?

│ Error: authorization.RoleAssignmentsClient#Create: Failure responding to request: StatusCode=403
│ Code="AuthorizationFailed" Message="The client '3f2a…' with object id '3f2a…' does not have authorization
│ to perform action 'Microsoft.Authorization/roleAssignments/write' over scope
│ '/subscriptions/…/resourceGroups/rg-orders-shared/providers/Microsoft.ContainerRegistry/registries/contosoacr'"
  1. The ACR doesn't exist The scope resolved fine; the action was denied.
  2. The pipeline identity is only Contributor; creating role assignments needs RBAC Administrator (ideally with a condition limiting which roles), User Access Administrator, or Owner, on that scope
  3. AcrPull can't be assigned by Terraform It can, with the right permission.
  4. OIDC tokens can't create role assignments Authentication worked; authorisation failed.
Same lesson as 0.4. Grant the pipeline identity "Role Based Access Control Administrator" on the needed scopes, with a condition allowing only AcrPull, Network Contributor and Key Vault Secrets User, so it can't make itself Owner.

7. Propagation delay

A new role assignment can take a few minutes to take effect everywhere. A resource that uses the permission right after it's granted can fail on the first apply and succeed on a re-run. principal_type = "ServicePrincipal" avoids one class of replication errors for new identities. Don't paper over it with sleep; re-running apply is fine, because Terraform is idempotent.

8. Role assignment names

Every role assignment in Azure has a GUID name. Terraform generates one and records it in state, so re-applies don't create duplicates. Bicep doesn't keep state, which is why Chapter 13 must compute deterministic names with guid().

10. Outputs for the app side

The app pipeline needs a few values from infra: the ServiceAccount's client ID, the ACR login server, and the cluster name. Read them from Terraform outputs (terraform output -raw orders_api_client_id), or publish them as pipeline variables. Never copy them by hand.

Identity in Terraform, sorted

  • A user-assigned cluster identity + Network Contributor on the subnet; depends_on for that hidden dependency.
  • AcrPull to kubelet_identity[0].object_id.
  • Workload identity: azurerm_user_assigned_identity + azurerm_federated_identity_credential (issuer = oidc_issuer_url, exact subject).
  • The pipeline needs RBAC Administrator (conditioned) to create role assignments; expect propagation delays.
