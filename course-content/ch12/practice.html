Predict the outcome (4)

1 · count over ["a","b","c"] node pools; remove "a".

  1. Destroy pool a
  2. [0] becomes b and [1] becomes c (replaced), [2] destroyed: all three pools touched
  3. No changes
  4. Error
That's why for_each exists.

2 · Portal drift: someone set the system pool from 3 to 4 nodes (no ignore_changes). Next plan?

  1. No changes
  2. Update in place 4 → 3
  3. Replace the cluster
  4. Error
Code wins; record intentional changes in code.

3 · Rename azurerm_kubernetes_cluster.main → .orders without a moved block.

  1. Rename in place
  2. Plan: destroy main, create orders, so the whole cluster is recreated (blocked if prevent_destroy is set)
  3. No changes
  4. Import automatically
Always add moved when refactoring.

4 · Two pipeline runs start apply on the same state at the same moment.

  1. Both apply, merging changes
  2. One gets the lock; the other fails with "Error acquiring the state lock"
  3. State is corrupted
  4. Both wait forever
Locking protects state; exclusive locks queue the runs.

Write lab A: the Contoso cluster in Terraform

Brief: Write versions.tf, main.tf, variables.tf and outputs.tf in infra/terraform/envs/dev. They create the resource group, VNet and node subnet, Log Analytics, the AKS cluster with a user pool, AcrPull for the kubelet on the shared contosoacr (data source), and the orders-api workload identity with a federated credential. Graded by iac-rules (Terraform). The same requirement set is used for Bicep in Chapter 13.

  • The azurerm provider is pinned with a ~> constraint; required_version is set.
  • An azurerm remote backend is configured with use_azuread_auth (no access keys).
  • Overlay networking: network_plugin = "azure" and network_plugin_mode = "overlay".
  • OIDC issuer and workload identity enabled.
  • Azure RBAC enabled for Kubernetes authorization.
  • local_account_disabled = true.
  • The system pool spans zones 1, 2, 3 with at least 2 nodes and critical add-ons only.
  • AcrPull is assigned to kubelet_identity[0].object_id on the registry.
  • The federated credential uses oidc_issuer_url and subject system:serviceaccount:orders:orders-api.
  • No secrets in variable defaults or .tfvars (no password, secret, key or token values).
  • environment has a validation allowing only dev/prod.
Reference solution

Assemble lessons 12.2 (versions, network), 12.3 (variables, locals, outputs), 12.4 (cluster, pool, ACR data source), 12.5 (identities) and the backend from 12.7.

Write lab B: the infra pipeline

Brief: Write infra-pipeline.yml for infra/terraform/envs/prod. Graded by pipeline-rules.

  • PR checks: fmt -check, validate, and a lint or security scan step.
  • A Plan stage runs terraform plan -out=<file> and publishes the file as an artifact.
  • Apply runs in a deployment job with an environment.
  • Apply uses the saved plan file (terraform apply <file>), never -auto-approve without a plan.
  • Apply runs only after an approval (the environment) and only on main.
  • Authentication uses a service connection with OIDC (ARM_USE_OIDC); no ARM_CLIENT_SECRET.
Reference solution

Lesson 12.8, steps 2–5, combined into one file with a PR trigger on infra/terraform/**.

Walkthrough: init → plan → apply → drift → fix

  1. terraform init against the remote backend; plan -var-file=dev.tfvars -out=tfplan; read the plan.
  2. apply tfplan (~8 minutes); terraform output.
  3. Change the user pool's max count in the portal.
  4. terraform plan shows ~ max_count, the drift.
  5. Decide: revert (apply) or adopt (change the code and apply). Never leave it.
