HCL basics

You'll be able to write Terraform's configuration language: blocks, arguments, references and version constraints, and build Contoso's resource group and network.

1. Blocks and arguments

HCL (HashiCorp Configuration Language) is made of blocks: a type, zero or more labels, and a body in braces. Inside the body are arguments (name = value) and nested blocks.

A resource block has two labels: the resource type (from the provider) and a local name you choose.

resource "azurerm_resource_group" "main" {
  name     = "rg-orders-dev"
  location = "westeurope"
}
Portal/ARM
Each resource block is one item in an ARM template's resources array, without the JSON noise.
az CLI scripts
az group create -n rg-orders-dev -l westeurope becomes a block you can re-run safely.
CloudFormation
Like a Resources: entry: the logical ID is the local name, and Type is the resource type.
Pulumi
Like new azure.resources.ResourceGroup("main", {...}), but declarative HCL.

2. The terraform block

The terraform block pins the Terraform version and declares which providers to download, with version constraints. ~> 4.0 means "4.x, at least 4.0, below 5.0", so you get fixes but no breaking major upgrade.

terraform {
  required_version = ">= 1.9"
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 4.0"
    }
  }
}

3. The provider block

provider "azurerm" configures how to talk to Azure. The features {} block is required, even when empty. The 4.x provider also needs a subscription ID, from the block or the ARM_SUBSCRIPTION_ID environment variable. Credentials come from the environment (your az login, or the pipeline's OIDC), never from the file.

+provider "azurerm" {
+  features {}
+  subscription_id = var.subscription_id
+}

4. Spot the constraint

Tap the line that stops a future terraform init from silently pulling azurerm 5.0.

terraform {
  required_version = ">= 1.9"
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 4.0"
    }
  }
}
~> 4.0 allows 4.x only. Together with the committed lock file, provider upgrades only happen when someone runs terraform init -upgrade and commits the result.

5. References

Refer to another resource's attributes with <type>.<name>.<attribute>. Terraform reads these references to work out the order: the resource group first, then anything that refers to it.

Put the VNet in the same resource group, using a reference rather than a hard-coded string.

resource "azurerm_virtual_network" "main" {
  name                = "vnet-orders-dev"
  resource_group_name = ?
  location            = azurerm_resource_group.main.location
  address_space       = ["10.20.0.0/16"]
}
  • azurerm_resource_group.main.name
  • "rg-orders-dev" It works, but there's no dependency, so Terraform may try to create the VNet before the group exists.
  • main.name The resource type is part of the address.
  • ${resource_group} Not HCL reference syntax.
References create implicit dependencies: Terraform creates the group first, and destroys it last.

7. Types and expressions

  • Strings "…"; numbers; booleans true/false.
  • Lists ["1", "2", "3"]; maps { env = "dev" }.
  • Interpolation: "aks-${var.app}-${var.environment}".
  • Conditionals: var.environment == "prod" ? "Standard" : "Free".
  • Functions: lower(), merge(), cidrsubnet("10.20.0.0/16", 6, 0), and many more.

8. When you need depends_on

Explicit depends_on is only for hidden dependencies, where one resource needs another but doesn't reference any of its attributes. A typical example: a resource that only works after a role assignment has been created.

The subnet uses virtual_network_name = azurerm_virtual_network.main.name. Do you need depends_on = [azurerm_virtual_network.main]?

  1. Yes, always list dependencies That's noise; the reference already creates the dependency.
  2. No: the reference is already an implicit dependency
  3. Only for destroy Implicit dependencies apply to destroy order as well.
  4. Only in modules Same rule everywhere.
Prefer references. Use depends_on sparingly, with a comment saying why.

9. Files and formatting

Terraform reads every .tf file in the folder as one configuration; file names are just for humans. terraform fmt rewrites files in the canonical style; terraform fmt -check fails CI when someone forgot.

12. Comments

# or // for single lines, /* … */ for blocks. Explain why (a depends_on, an ignore_changes), not what.

HCL, sorted

  • Blocks with labels; arguments name = value.
  • terraform { required_providers } with ~> constraints; provider "azurerm" { features {} }.
  • References (type.name.attr) create implicit dependencies; depends_on only for hidden ones.
  • fmt and validate on every change.
