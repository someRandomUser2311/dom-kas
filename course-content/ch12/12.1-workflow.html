Why IaC, and the Terraform workflow

You'll be able to explain what infrastructure as code fixes, run Terraform's init → plan → apply loop, and read a plan's symbols.

1. Click-ops drifts

Chapters 4–6 built Contoso's cluster with CLI commands. That was fine for learning. In production it isn't:

  • Nobody can say exactly what prod looks like.
  • Dev and prod drift apart.
  • A changed setting has no review or history.
  • Rebuilding after a disaster is guesswork.

Infrastructure as code describes the desired infrastructure in files. A tool makes reality match them. Sound familiar? It's lesson 1.4's desired state, applied to Azure.

Portal/ARM
Instead of clicking through the portal (or exporting ARM JSON afterwards), you write the definition first, and the portal becomes read-only for you.
az CLI scripts
Scripts say how, step by step, and break when re-run. Terraform says what, and works out the steps each time, including updates and deletes.
CloudFormation
Same idea. Terraform keeps its own state file instead of the cloud tracking a "stack", and it works across many providers.
Pulumi
Same model (state, plan/preview, apply); HCL instead of a general-purpose language.

2. What goes in IaC, and what doesn't

  • Infra pipeline (Terraform): resource groups, network, ACR, the AKS cluster and node pools, Log Analytics, identities and role assignments, Key Vault.
  • App pipeline (Chapters 7–11): what runs inside the cluster: Deployments, Services, routes, policies.

They change at different speeds and need different permissions, so they're kept separate.

3. Terraform in one picture

You write .tf files. Terraform compares three things:

  • your code (desired);
  • its state (what it created last time);
  • Azure (what really exists).

It then proposes the changes needed. A provider plugin (azurerm for Azure) knows how to talk to each API.

OpenTofu is the open-source fork of Terraform, created after Terraform's licence change. Everything in this chapter works the same in both.

4. The loop

terraform init      # download providers and modules, configure the state backend
terraform plan      # show what would change (nothing changes yet)
terraform apply     # make the changes (asks to confirm, or applies a saved plan)
terraform destroy   # delete everything this configuration manages

Put a first deployment in order.

  1. Write the .tf files
  2. terraform init
  3. terraform plan
  4. Review the plan
  5. terraform apply
init runs once per working directory (and again when providers, modules or the backend change). Plan and review on every change.

5. Reading a plan

Terraform will perform the following actions:

  # azurerm_resource_group.main will be created
  + resource "azurerm_resource_group" "main" {
      + location = "westeurope"
      + name     = "rg-orders-dev"
    }

  # azurerm_kubernetes_cluster.main will be updated in-place
  ~ resource "azurerm_kubernetes_cluster" "main" {
      ~ sku_tier = "Free" -> "Standard"
    }

  # azurerm_kubernetes_cluster_node_pool.user must be replaced
-/+ resource "azurerm_kubernetes_cluster_node_pool" "user" {
      ~ vm_size = "Standard_D4ds_v5" -> "Standard_D8ds_v5" # forces replacement
    }

Plan: 2 to add, 1 to change, 1 to destroy.
A small configuration on the left (editable values) and the resulting plan on the right. Changing a tag shows ~; changing a node pool's VM size or zones shows -/+ with "forces replacement"; removing a block shows -; adding one shows +.

6. Match the symbols

Match each plan symbol to its meaning.

+Create
~Update in place
-/+Destroy, then create a replacement
-Destroy
<=Read (a data source)
Always look for -/+ and - on stateful resources (clusters, databases, disks) before approving. "forces replacement" on a node pool means its nodes and pods get recreated.

7. Providers and the lock file

init downloads providers into .terraform/, and records their exact versions and checksums in .terraform.lock.hcl.

Commit the lock file, so everyone and every pipeline uses the same provider build. Never commit .terraform/, which is a cache.

Which files belong in Git?

  1. main.tf, variables.tf, outputs.tf
  2. .terraform.lock.hcl
  3. dev.tfvars (non-secret values only)
  4. .terraform/ A local cache of downloaded providers.
  5. terraform.tfstate State goes in a remote backend; it can contain secrets (lesson 12.7).
  6. tfplan A saved plan is a pipeline artifact, not source, and can contain sensitive values.
Lesson 0.5's .gitignore already covers .terraform/, *.tfstate and *.tfplan.

8. Idempotent by design

Run apply twice with no code change and the second run does nothing: "No changes. Your infrastructure matches the configuration." That's the property CLI scripts lack, and why pipelines can safely run Terraform on every merge.

9. Where Contoso's code lives

infra/terraform/
├─ versions.tf        # terraform + provider requirements, backend
├─ main.tf            # resource group, network, ACR, Log Analytics
├─ aks.tf             # cluster + node pools
├─ identity.tf        # role assignments, workload identities
├─ variables.tf
├─ outputs.tf
├─ dev.tfvars
└─ prod.tfvars

10. The CLI still has a place

IaC doesn't mean never touching the CLI. You still use az and kubectl to look, debug, and run one-off operations such as az aks command invoke. What you stop doing is changing managed infrastructure by hand. Every change goes through code.

The workflow, sorted

  • IaC = desired infrastructure in reviewed files; no more click-ops drift.
  • init → plan → (review) → apply; destroy when done.
  • Plan symbols: + ~ -/+ - <=. Watch for replacements.
  • Commit .tf, the lock file and non-secret tfvars; never .terraform/, state or plans.
  • Infra and app pipelines stay separate.
