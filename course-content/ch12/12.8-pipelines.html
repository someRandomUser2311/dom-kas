Terraform in Azure Pipelines

You'll be able to build an infra pipeline that checks every PR, saves a plan, waits for approval, and applies exactly that plan, authenticating with OIDC and no secrets.

1. Two pipelines for infra

  • PR validation: on every PR touching infra/terraform/: fmt -check, validate, tflint, a security scan, and a plan posted for reviewers.
  • Main: on merge: plan and save it → approval → apply that saved plan.

They're separate from the app pipeline (Chapters 7–11): different triggers, permissions and pace.

GitHub Actions
The same pattern as terraform plan on pull_request and apply behind an environment protection rule. OIDC is azure/login with federated credentials.
GitLab CI
Like GitLab's Terraform templates: plan as an artifact, apply as a manual job.
Jenkins
Plan in one stage, input approval, apply the stashed plan file.
Classic pipelines
Build pipeline produces the plan artifact; release pipeline applies it after a pre-deployment approval.

2. PR checks

- script: terraform fmt -check -recursive
  displayName: Format
- script: terraform init -backend=false && terraform validate
  displayName: Validate
- script: tflint --recursive
  displayName: Lint (tflint with the azurerm ruleset)
- script: trivy config --exit-code 1 --severity HIGH,CRITICAL .
  displayName: Security scan (or Checkov)

A plan for the PR (read-only credentials) shows reviewers the real impact. Post its summary to the PR or the run summary.

3. Authentication with OIDC

Use a workload identity federation service connection (Chapter 7), with no client secret. The azurerm provider and backend accept OIDC through environment variables.

The simplest route is AzureCLI@2 with addSpnToEnvironment: true. It exposes $servicePrincipalId, $tenantId and a federated $idToken to your script.

- task: AzureCLI@2
  displayName: terraform ${{ parameters.command }}
  inputs:
    azureSubscription: sc-orders-infra-prod       # WIF service connection
    scriptType: bash
    scriptLocation: inlineScript
    addSpnToEnvironment: true
    workingDirectory: infra/terraform/envs/prod
    inlineScript: |
      set -euo pipefail
      export ARM_USE_OIDC=true
      export ARM_OIDC_TOKEN="$idToken"
      export ARM_CLIENT_ID="$servicePrincipalId"
      export ARM_TENANT_ID="$tenantId"
      export ARM_SUBSCRIPTION_ID="$(az account show --query id -o tsv)"
      terraform init -input=false
      ${{ parameters.script }}

That $idToken is short-lived, so very long applies can outlive it. The providers can instead fetch fresh tokens from Azure DevOps themselves: set ARM_OIDC_AZURE_SERVICE_CONNECTION_ID to the service connection's ID and pass SYSTEM_ACCESSTOKEN: $(System.AccessToken). Microsoft's Terraform tasks for Azure Pipelines also support WIF connections.

4. The plan stage

- stage: Plan
  jobs:
    - job: plan
      pool: { name: mdp-orders-prod }
      steps:
        - template: templates/terraform.yml
          parameters:
            command: plan
            script: |
              terraform plan -input=false -var-file=prod.tfvars -out=tfplan
              terraform show -no-color tfplan > plan.txt
        - publish: infra/terraform/envs/prod/tfplan
          artifact: tfplan
        - publish: infra/terraform/envs/prod/plan.txt
          artifact: plan-text

5. The apply stage

- stage: Apply
  dependsOn: Plan
  condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
  jobs:
    - deployment: apply
      environment: infra-prod             # approval check: platform leads
      pool: { name: mdp-orders-prod }
      strategy:
        runOnce:
          deploy:
            steps:
              - checkout: self
              - download: current
                artifact: tfplan
              - template: templates/terraform.yml
                parameters:
                  command: apply
                  script: terraform apply -input=false $(Pipeline.Workspace)/tfplan/tfplan

Tap the line that guarantees the approver approved exactly what gets applied.

Applying the saved plan file applies precisely the reviewed changes. A plain terraform apply would re-plan, possibly including changes that appeared after the approval.

6. Why the saved plan matters

Why apply tfplan instead of running terraform apply -auto-approve in the apply stage?

  1. It's faster Speed isn't the point.
  2. Someone may have merged another change, or Azure drifted, between plan and apply. A re-plan could apply changes nobody reviewed
  3. -auto-approve is deprecated It isn't.
  4. Saved plans skip state locking Apply still locks state.
If state changed after the plan was made, Terraform refuses the old plan ("Saved plan is stale"). Re-run the pipeline to plan again.

7. Arrange the stages

Arrange the infra pipeline so apply can never run without an approved, saved plan.

Stage cards: "fmt/validate/lint/scan", "plan -out=tfplan + publish artifact", "approval (environment infra-prod)", "apply tfplan", plus decoys "apply -auto-approve" and "plan again in apply stage". Success when the order is checks → plan+publish → approval → apply tfplan, with both decoys discarded. The plan artifact is drawn moving between the stages.
Checks → plan (saved) → human approval of that plan → apply exactly that plan.

8. The plan file is sensitive

A plan file contains the planned values, which can include secrets, like state. Keep pipeline artifacts retained only briefly, and restrict who can download them. Never post the raw plan to a public place. plan.txt for reviewers is made with terraform show, which hides sensitive values.

9. Permissions for the pipeline identity

  • Contributor on the environment's resource groups.
  • Role Based Access Control Administrator, conditioned to the few roles it assigns (lesson 12.5).
  • Storage Blob Data Contributor on the state container.
  • A separate, read-only identity for PR plans (Reader + Storage Blob Data Reader), so an unreviewed PR can't change anything.

10. Concurrency

Two runs applying at once would fight over state. State locking stops the second one, but it's better to queue. Add an exclusive lock check on the infra-prod environment, and use lockBehavior: sequential in the pipeline.

11. Dev first, then prod

The full main pipeline plans and applies dev, then plans prod, waits for approval, and applies prod. Each environment folder has its own backend key and service connection. A module change reaches dev first; prod only after dev applied cleanly.

12. Scheduled drift detection

schedules:

13. Where this fits

Infra pipeline: cluster, network, ACR, identities. App pipeline (Chapters 7–11): manifests. The capstone (Chapter 17) grades both: infra-pipeline.yml for the apply flow, and azure-pipelines.yml for the release.

Terraform pipelines, sorted

  • PRs: fmt, validate, tflint, a security scan, and a read-only plan.
  • Main: plan -out=tfplan → publish → approval (deployment job + environment) → apply tfplan.
  • OIDC via a WIF service connection (ARM_USE_OIDC and friends); no secrets.
  • Plans are sensitive; least-privilege identities; exclusive locks; scheduled drift checks.
