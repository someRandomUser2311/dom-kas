State

You'll be able to explain what Terraform state is, store it safely in Azure, refactor and import without destroying anything, and detect drift.

1. What state is

Terraform keeps a state file that maps each resource address in your code (azurerm_kubernetes_cluster.main) to the real Azure resource ID. It also caches each resource's attributes.

That's how Terraform knows which resources it manages, and what to update or delete.

Lose the state and Terraform forgets everything. The next plan wants to create it all again, and fails on name clashes.

Three columns: Code, State and Azure, with lines linking each resource across them. The learner can rename in code, change a value in the portal, delete from state or delete in Azure, and see what terraform plan would propose for each.
Portal/ARM
ARM has no state file: Azure itself is the record (that's Bicep's model, Chapter 13). Terraform keeps its own.
az CLI scripts
Scripts have no memory at all, which is why they can't safely delete or rename.
CloudFormation
CloudFormation keeps "state" inside the stack, managed by AWS. Terraform's state is a file you must store and protect.
Pulumi
Same idea as Pulumi's state backend (Pulumi Cloud or self-managed blob storage).

2. State contains secrets

State holds every attribute of every resource, including secrets in plain text: generated passwords, storage account keys, kubeconfig credentials if you read them. sensitive = true only hides values in output; the state still contains them.

Treat the state file like a password vault.

3. The azurerm backend

Store state remotely, in an Azure Storage blob, created once outside this configuration and protected:

  • a private endpoint, or restricted network access;
  • versioning and soft delete on;
  • access only for the pipeline identity and the platform admins.

The backend uses Entra ID auth (no storage keys) and blob-lease locking, so two runs can't write at once.

terraform {
  backend "azurerm" {
    resource_group_name  = "rg-tfstate"
    storage_account_name = "sttfstatecontoso"
    container_name       = "tfstate"
    key                  = "orders/prod.tfstate"
    use_azuread_auth     = true
    use_oidc             = true
  }
}

4. Locks

A pipeline run fails at plan. What's going on?

│ Error: Error acquiring the state lock
│
│ Error message: state blob is already locked
│ Lock Info:
│   ID:        2b6c3c1e-9a7d-4c1b-8f0e-6e1f0d2a7b44
│   Path:      tfstate/orders/prod.tfstate
│   Operation: OperationTypeApply
│   Who:       vsts@agent-mdp-0003
│   Created:   2026-11-05 16:40:12 UTC
  1. The storage account is down It answered: the blob is leased.
  2. Another apply holds the lock. Either it's still running, or it was killed without releasing the lease
  3. The state is corrupted Locking is working exactly as designed.
  4. The pipeline lacks permissions That gives a 403.
First check whether another run is active. If the earlier run really died, release the lease with terraform force-unlock <ID>, but only after confirming no one else is applying. Pipeline concurrency limits (exclusive lock checks) prevent most of these.

5. Never edit state by hand

Don't download and edit the JSON. Use the CLI (terraform state list, show, rm), or better, the declarative blocks below. They're reviewed in PRs and show up in the plan.

6. Renaming without destroying: moved

Rename azurerm_kubernetes_cluster.main to .orders and Terraform sees one resource removed and another added. It would destroy and recreate the cluster. A moved block tells it they're the same thing.

You renamed the cluster resource to azurerm_kubernetes_cluster.orders. Add what's needed so the plan shows no destroy.

Graded by simulated plan: success when the plan for the cluster shows "has moved to azurerm_kubernetes_cluster.orders" with 0 to destroy.
Solution 
moved {
  from = azurerm_kubernetes_cluster.main
  to   = azurerm_kubernetes_cluster.orders
}
moved also works for moving resources into a module (to = module.aks.azurerm_kubernetes_cluster.this) and for changing a count resource to a for_each one.

7. Adopting existing resources: import

Contoso's first cluster was created by hand in Chapter 4. To bring it under Terraform without recreating it, write the resource block and an import block with its Azure ID. Plan, adjust the code until the plan shows no changes, then apply.

import {
  to = azurerm_kubernetes_cluster.main
  id = "/subscriptions/<sub>/resourceGroups/rg-orders-dev/providers/Microsoft.ContainerService/managedClusters/aks-orders-dev"
}

terraform plan -generate-config-out=generated.tf writes a starting resource block for imported resources. Clean it up before committing.

8. Drift

Someone scales the system pool to 5 in the portal during an incident. The next terraform plan compares code (3) with reality (5), and proposes changing it back. terraform plan -refresh-only shows drift without proposing fixes. It's useful as a scheduled drift report.

The code says node_count = 3 for the system pool. Someone set it to 5 in the portal. What does the next normal plan show?

  1. Nothing; Terraform only looks at its state Plan refreshes from Azure first.
  2. An in-place update: node_count: 5 → 3
  3. Replace the cluster The node count updates in place.
  4. An error Drift isn't an error.
Code wins. If the change was right, put it in the code; if the field is managed elsewhere (the autoscaler), ignore it (next step).

9. lifecycle

  • ignore_changes: don't fight another controller. If the cluster autoscaler manages a pool, ignore its node_count.
  • prevent_destroy: a plan that would destroy this resource fails. Use it for the cluster, the state storage and the registry.
  • create_before_destroy: build the replacement first.
  lifecycle {
    prevent_destroy = true
    ignore_changes  = [default_node_pool[0].node_count]
  }

10. removed blocks

To stop managing something without deleting it, for example handing a resource to another team's configuration, use a removed block with lifecycle { destroy = false }. It leaves Terraform's state, and stays in Azure.

11. One state per environment, small blast radius

Separate keys (orders/dev.tfstate, orders/prod.tfstate) and separate root folders mean a broken dev run can never touch prod state. Splitting very large configurations (network, shared, cluster) also keeps plans fast and failures contained.

12. Reading other states

To use the network team's VNet ID, prefer a data source (look it up by name) over terraform_remote_state. Reading another team's state needs read access to their whole state file, secrets included.

State, sorted

  • State maps code to real resources and contains secrets; protect it like a vault.
  • azurerm backend: Entra ID auth, OIDC, blob-lease locking; one key per environment.
  • moved for renames, import to adopt, removed to let go; no hand edits.
  • Plan shows drift; -refresh-only reports it; lifecycle for prevent_destroy and ignore_changes.
