Variables, locals, outputs & data sources

You'll be able to make one configuration serve dev and prod with validated variables, compute names with locals, expose outputs, and look up existing resources.

1. Input variables

A variable block declares an input, with a type, an optional default and a description. Use it as var.<name>.

variable "environment" {
  type        = string
  description = "Environment name: dev or prod."
}

variable "location" {
  type    = string
  default = "westeurope"
}

variable "user_pool" {
  type = object({
    vm_size   = string
    min_count = number
    max_count = number
  })
}
Portal/ARM
Like ARM template parameters with types, plus a parameters file per environment.
az CLI scripts
Like the variables at the top of your script, but typed and validated.
CloudFormation
Like Parameters with AllowedValues.
Pulumi
Like stack config values (pulumi config).

2. Validation

Add a validation so environment can only be dev or prod, with a helpful error message.

An HCL editor with the variable block above. Graded by iac-rules: a validation block whose condition rejects any value other than dev/prod (tested with "test", "Prod" and "dev") and has an error_message.
Solution 
variable "environment" {
  type        = string
  description = "Environment name: dev or prod."
  validation {
    condition     = contains(["dev", "prod"], var.environment)
    error_message = "environment must be \"dev\" or \"prod\"."
  }
}
A typo like -var environment=Prod now fails at plan time, before it creates oddly named resources.

3. Sensitive variables

sensitive = true hides the value in plan and apply output. It does not encrypt it, and the value still ends up in state (lesson 12.7).

Never give secrets a default, and never put them in a committed .tfvars. Better still, avoid passing secrets at all: use managed identities and Key Vault references.

4. Values per environment

environment = "dev"
user_pool = {
  vm_size   = "Standard_D4ds_v5"
  min_count = 1
  max_count = 3
}
environment = "prod"
user_pool = {
  vm_size   = "Standard_D4ds_v5"
  min_count = 3
  max_count = 10
}
terraform plan -var-file=prod.tfvars -out=tfplan

5. Which value wins?

Highest priority first:

  1. -var and -var-file on the command line (in order; the last one wins);
  2. *.auto.tfvars (alphabetical);
  3. terraform.tfvars;
  4. TF_VAR_<name> environment variables;
  5. the variable's default.

location has default = "westeurope"; TF_VAR_location=northeurope is set; terraform.tfvars says location = "swedencentral"; you run terraform plan -var location=uksouth. Which value is used?

  1. westeurope
  2. northeurope
  3. swedencentral
  4. uksouth
Command-line -var beats everything. Pipelines usually pass exactly one -var-file, so there's one source of truth per environment.

6. Locals for names and tags

locals are computed values used in many places: naming conventions, the common tag set, environment-dependent settings. Use them as local.<name>.

locals {
  name_suffix = "orders-${var.environment}"
  is_prod     = var.environment == "prod"
  tags = {
    app         = "orders"
    environment = var.environment
    managed_by  = "terraform"
  }
}

resource "azurerm_resource_group" "main" {
  name     = "rg-${local.name_suffix}"
  location = var.location
  tags     = local.tags
}

7. Outputs

output blocks expose values after apply: for people (terraform output), for pipelines (terraform output -raw), and for parent modules. Mark them sensitive when needed.

output "aks_name" {
  value = azurerm_kubernetes_cluster.main.name
}
output "oidc_issuer_url" {
  value = azurerm_kubernetes_cluster.main.oidc_issuer_url
}
output "acr_login_server" {
  value = azurerm_container_registry.main.login_server
}

8. Data sources: read what exists

A data block reads something Terraform doesn't manage: the current identity and tenant, a hub VNet owned by another team, a Key Vault created elsewhere. Refer to it as data.<type>.<name>.

Tap the block that looks up an existing resource instead of creating one.

data "azurerm_client_config" "current" {}

data "azurerm_key_vault" "shared" {
  name                = "kv-contoso-shared"
  resource_group_name = "rg-contoso-shared"
}

resource "azurerm_role_assignment" "kv_reader" {
  scope                = data.azurerm_key_vault.shared.id
  role_definition_name = "Key Vault Secrets User"
  principal_id         = azurerm_user_assigned_identity.orders_api.principal_id
}
data "azurerm_key_vault" "shared" reads it. Terraform will never change or delete it. (The first data block, azurerm_client_config, also reads: it returns who Terraform is running as.)

9. Environment-dependent settings

sku_tier                = local.is_prod ? "Standard" : "Free"
private_cluster_enabled = local.is_prod

Keep such switches few and obvious, and drive them from var.environment through locals, not scattered conditionals.

10. Types catch mistakes

type = object({...}), list(string), map(number) and friends reject wrongly shaped values at plan time. Add optional() attributes with defaults for flexible objects. They work like Bicep's user-defined types (Chapter 13).

11. Don't over-variable

Not everything should be a variable. Security baselines (local accounts disabled, Azure RBAC on, OIDC on) should be hard-coded, so no environment can turn them off by accident. Make variable only what genuinely differs between environments.

Variables & friends, sorted

  • variable with type, description, validation; sensitive hides output but isn't encryption.
  • One .tfvars per environment; -var/-var-file wins over everything.
  • locals for names, tags and switches; output for results; data to read existing resources.
  • Hard-code the security baseline.
