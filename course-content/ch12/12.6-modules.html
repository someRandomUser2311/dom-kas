Repetition & modules

You'll be able to create many similar resources safely with for_each, generate optional blocks with dynamic, package code as modules, use Azure Verified Modules, and lay out environments.

1. Many node pools

Contoso now wants several user pools: general, memory-heavy, and spot. Copying the resource block three times would drift. Instead, describe them in a map and let Terraform loop over it.

variable "node_pools" {
  type = map(object({
    vm_size   = string
    min_count = number
    max_count = number
    spot      = optional(bool, false)
  }))
}
node_pools = {
  general = { vm_size = "Standard_D4ds_v5", min_count = 3, max_count = 10 }
  memory  = { vm_size = "Standard_E8ds_v5", min_count = 0, max_count = 4 }
}
Portal/ARM
Like ARM copy loops, keyed by name instead of index.
az CLI scripts
Like a for loop over az aks nodepool add, except removing an item also removes the pool.
CloudFormation
CloudFormation has no native loop (beyond the newer Fn::ForEach transform); Terraform's is built in.
Pulumi
A normal language loop, but keyed resources matter just as much there.

2. for_each

for_each creates one instance per map key. Inside the block, each.key is the key and each.value the object. Each instance has an address like azurerm_kubernetes_cluster_node_pool.user["memory"].

resource "azurerm_kubernetes_cluster_node_pool" "user" {
  for_each              = var.node_pools
  name                  = each.key
  kubernetes_cluster_id = azurerm_kubernetes_cluster.main.id
  mode                  = "User"
  vm_size               = each.value.vm_size
  zones                 = ["1", "2", "3"]
  auto_scaling_enabled  = true
  min_count             = each.value.min_count
  max_count             = each.value.max_count
  priority              = each.value.spot ? "Spot" : "Regular"
}

3. Why not count?

count = length(var.pools) also loops, but it addresses instances by position: [0], [1], [2]. Remove an item from the middle of the list and everything after it shifts down one position. Terraform sees a different pool at each index and replaces them.

Pools are defined with count over ["general", "memory", "gpu"]. You remove "memory". What does the plan show?

  1. Destroy only the memory pool That's what for_each would do.
  2. [1] is changed from memory to gpu (replaced, since name and size force replacement), and [2] is destroyed
  3. No changes The list changed.
  4. Everything is destroyed [0] is unchanged.
With for_each, removing memory only plans - user["memory"]. Use count only for "0 or 1 copies" switches.

4. dynamic blocks

Some nested blocks are optional or repeated, like the dev-only api_server_access_profile in lesson 12.4. dynamic "name" { for_each = … content { … } } generates the block zero or more times.

dynamic "api_server_access_profile" {
  for_each = local.is_prod ? [] : [1]       # one block in dev, none in prod
  content {
    authorized_ip_ranges = var.authorized_ip_ranges
  }
}

Use dynamic sparingly. Configuration full of dynamic blocks is hard to read; often a plain block with a conditional argument is clearer.

5. Modules: reusable packages

A module is a folder of .tf files with variables (inputs) and outputs. Your root configuration calls it with a module block. Contoso wraps "an AKS cluster the Contoso way" into modules/aks, so every team gets the same baseline.

infra/terraform/
├─ modules/
│  └─ aks/
│     ├─ main.tf        # cluster, pools, role assignments
│     ├─ variables.tf   # name, environment, subnet_id, node_pools, …
│     └─ outputs.tf     # cluster_id, oidc_issuer_url, kubelet_object_id
├─ envs/
│  ├─ dev/main.tf       # calls the module with dev values
│  └─ prod/main.tf

6. Calling a module

module "aks" {
  source       = "../../modules/aks"
  name         = "aks-orders-prod"
  environment  = "prod"
  subnet_id    = azurerm_subnet.aks_nodes.id
  acr_id       = data.azurerm_container_registry.shared.id
  node_pools   = var.node_pools
  admin_group  = var.aks_admin_group_id
}

output "oidc_issuer_url" {
  value = module.aks.oidc_issuer_url
}

Hard-code the security baseline inside the module (Azure RBAC, local accounts off, OIDC on). Callers can't turn it off, because there's no variable for it.

7. Azure Verified Modules

Azure Verified Modules (AVM) are Microsoft-maintained modules on the Terraform Registry, such as Azure/avm-res-containerservice-managedcluster/azurerm. They follow consistent conventions and are tested. Always pin the version: a module upgrade can change many resources at once.

Pin the registry module to an exact minor version.

module "aks" {
  source  = "Azure/avm-res-containerservice-managedcluster/azurerm"
  ? = "0.3.1"
  # …
}
  • version
  • ref ?ref= is used inside Git source URLs, not for registry modules.
  • tag Not a module argument.
  • required_version That's for Terraform itself.
Registry modules take a version argument. Git modules pin with ?ref=v1.2.0 in the source. Review the changelog before bumping either.

8. Your module or AVM?

  • AVM: broad, maintained, consistent, and it exposes almost every option.
  • Your own module: small and opinionated, exposing only Contoso's choices.

A common middle ground is a thin Contoso module that wraps AVM with your defaults.

9. Environments: folders or workspaces?

Workspaces give one configuration several state files (terraform workspace select prod). Folders give each environment its own root module and state.

Folders usually win for environments:

  • each environment has its own backend key and permissions;
  • it's always obvious which one you're changing;
  • prod can pin a module version that dev is already testing.

Why do most teams prefer one folder per environment over workspaces for dev and prod?

  1. Workspaces are deprecated They're supported; they're just a poor fit for environment separation.
  2. Separate state, credentials and versions per environment, and the environment you're changing is explicit in the path
  3. Folders are faster Speed is the same.
  4. Workspaces can't use remote state They can.
A wrong terraform workspace is the IaC version of the wrong kubectl context (lesson 1.6).

10. Module outputs and dependencies

Outputs are how modules talk. A reference like module.aks.kubelet_object_id creates a dependency on just the resources behind that output. Keep module interfaces small: a few inputs, a few outputs.

11. for_each over resources from another module

for_each keys must be known at plan time. A map built from values computed during apply (such as IDs of resources not created yet) gives "Invalid for_each argument". Key by static names, and look up IDs in the value.

12. Version everything

  • required_version for Terraform.
  • required_providers with ~>, plus the committed lock file.
  • A pinned version (or ?ref=) for every module.
  • Upgrades as deliberate PRs, with the plan reviewed.

Modules, sorted

  • for_each over maps (stable keys); count only for on/off.
  • dynamic blocks for optional nested blocks; use them sparingly.
  • Modules: inputs, outputs, a hard-coded baseline; AVM pinned by version.
  • One folder per environment; pin every version.
