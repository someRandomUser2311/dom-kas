Pod security

You'll be able to enforce the Pod Security Standards on a namespace, and write a securityContext that passes the "restricted" level.

1. What a pod could do

By default a container can run as root, gain more privileges, write anywhere in its filesystem, and use a broad set of Linux capabilities.

A privileged pod, or one using the host's network or filesystem, can take over the node, and from there reach other pods' secrets.

Pod security limits what any pod is allowed to request.

Windows/IIS admin
Like running app pools as low-privilege identities instead of LocalSystem, enforced for every site.
Linux admin
Non-root users, no setuid escalation, dropped capabilities, seccomp, a read-only root: standard host hardening, per container.
Developer (Compose)
Like user:, read_only: true, cap_drop: [ALL] and security_opt: no-new-privileges in Compose.
Other clouds
The same Pod Security Admission on EKS and GKE (GKE Autopilot enforces much of it by default).

2. Pod Security Standards

LevelAllowsUse for
privilegedAnythingSystem add-ons that genuinely need host access
baselineBlocks known escalations (privileged, hostNetwork/hostPID, hostPath, added dangerous capabilities)A minimum for everything
restrictedBaseline plus: must run as non-root, no privilege escalation, drop ALL capabilities, a seccomp profile, limited volume typesYour apps: the target for Contoso

3. Enforcing by namespace label

The built-in Pod Security Admission controller reads labels on each namespace. There are three modes per level:

  • enforce: reject violating pods.
  • audit: allow, but record the violation in the audit log.
  • warn: allow, but show a warning to whoever applied it.

Make namespace orders reject any pod that doesn't meet the restricted level.

apiVersion: v1
kind: Namespace
metadata:
  name: orders
  labels:
    ?: restricted
    pod-security.kubernetes.io/warn: restricted
  • pod-security.kubernetes.io/enforce
  • pod-security.kubernetes.io/audit Audit only records violations; pods still run.
  • podsecuritypolicy PodSecurityPolicy was removed in Kubernetes 1.25.
  • security.aks.azure.com/level Not a real label.
Pair enforce with warn, so people see why something would be rejected before it is.

4. warn isn't protection

In warn (or audit) mode, violating pods are created and run. Warnings are good for rolling a level out ("which of our apps would break?"), but only enforce protects you.

$ kubectl apply -f debug-pod.yaml -n orders
Warning: would violate PodSecurity "restricted:latest": allowPrivilegeEscalation != false (container "debug" must set
securityContext.allowPrivilegeEscalation=false), runAsNonRoot != true (pod or container "debug" must set
securityContext.runAsNonRoot=true)
pod/debug created

5. The hardened securityContext

spec:
  automountServiceAccountToken: false     # unless the app calls the Kubernetes API
  securityContext:
    runAsNonRoot: true
    runAsUser: 65532
    runAsGroup: 65532
    fsGroup: 65532
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: api
      image: contosoacr.azurecr.io/orders-api:1.4.2
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
      volumeMounts:
        - name: tmp
          mountPath: /tmp
  volumes:
    - name: tmp
      emptyDir: {}

UID 65532 is the nonroot user of the distroless image from lesson 1.1. A read-only root filesystem means anything the app writes goes to a mounted emptyDir, such as /tmp.

6. What each field stops

FieldStops
runAsNonRootRunning as UID 0 inside the container
allowPrivilegeEscalation: falsesetuid binaries and similar tricks gaining more privileges
capabilities.drop: [ALL]Kernel capabilities like NET_RAW, SYS_ADMIN
seccompProfile: RuntimeDefaultRarely needed, dangerous system calls
readOnlyRootFilesystemAttackers writing tools or changing binaries in the container

7. Make it pass

Edit the pod spec until it passes the restricted level.

A pod spec editor with a live checker listing each restricted rule as ✓/✗. The starting spec has no securityContext and runs as root, with NET_ADMIN added. Success when every restricted rule passes (runAsNonRoot, allowPrivilegeEscalation false, drop ALL, no added capabilities except NET_BIND_SERVICE, seccomp RuntimeDefault or Localhost, no privileged, no host namespaces or hostPath).
readOnlyRootFilesystem isn't required by restricted, but Contoso requires it too (and Chapter 16's policies check it).

8. Images must cooperate

If an image's entrypoint needs root, for example to bind port 80 or write to /var, it fails under restricted: "container has runAsNonRoot and image will run as root". Fix the image (a non-root user, listen on 8080), not the policy. Lesson 1.1's Dockerfile already does.

9. Exceptions

Some add-ons need more (log agents reading host paths). Put them in their own namespace with baseline or privileged, owned by the platform team. Never relax an app namespace to make one pod work.

10. Rolling it out

  1. Label every app namespace with warn and audit = restricted.
  2. Collect the warnings and audit events, and fix the manifests.
  3. Switch to enforce, in dev first, then prod.

11. Pod Security and Azure Policy

Pod Security Admission covers the standard levels. For anything beyond them (allowed registries, required labels, no latest, resource limits), use admission policies: the Azure Policy add-on or Kyverno (Chapter 16). They work together.

Pod security, sorted

  • Levels: privileged / baseline / restricted; modes: enforce / audit / warn, set with namespace labels.
  • warn and audit let violating pods run; only enforce protects.
  • Restricted: runAsNonRoot, allowPrivilegeEscalation false, drop ALL, seccomp RuntimeDefault; add readOnlyRootFilesystem.
  • Fix images, not policies; isolate the exceptions.
