Secrets from Key Vault

You'll be able to deliver Key Vault secrets to pods with the Secrets Store CSI driver and workload identity, keep them out of Git entirely, and handle rotation.

1. The problem with hand-made Secrets

Lesson 2.7 showed that Kubernetes Secrets are only base64. The bigger problem is the workflow: someone must create them, and the value has to come from somewhere, often a laptop or a pipeline variable.

Rotation is manual, and there's no central audit of who read what.

Azure Key Vault fixes the source: one place, access by identity, audit logs, rotation, and versioning.

Windows/IIS admin
Like moving connection strings out of web.config into a central vault the app reads at start-up, with its own identity.
Linux admin
Like HashiCorp Vault Agent writing secrets to a tmpfs file for the service.
Developer (Compose)
Instead of a .env file, secrets appear as files in /mnt/secrets at runtime.
Other clouds
The same Secrets Store CSI driver works with AWS Secrets Manager and GCP Secret Manager providers.

2. How it fits together

  1. The Key Vault secrets provider add-on installs the Secrets Store CSI driver and the Azure provider on every node.
  2. A SecretProviderClass says which vault, which objects, and which identity.
  3. The pod mounts a CSI volume referencing that class.
  4. When the pod starts, the driver authenticates as the pod's workload identity (lesson 5.6), fetches the secrets, and writes them to a tmpfs mount.
az aks enable-addons -g rg-orders-prod -n aks-orders-prod -a azure-keyvault-secrets-provider \
  --enable-secret-rotation

3. The SecretProviderClass

Complete the class so it uses the orders-api workload identity.

apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: orders-api-kv
  namespace: orders
spec:
  provider: azure
  parameters:
    ?: "6c1f2a9e-0000-4b1d-9c55-1a2b3c4d5e6f"
    keyvaultName: kv-orders-prod
    tenantId: "72f988bf-0000-41af-91ab-2d7cd011db47"
    objects: |
      array:
        - |
          objectName: payments-api-key
          objectType: secret
        - |
          objectName: orders-db-password
          objectType: secret
  • clientID
  • userAssignedIdentityID That's for the kubelet or add-on identity mode, not workload identity.
  • serviceAccount The SA comes from the pod, not the class.
  • clientSecret The whole point is no secret.
With workload identity, clientID is the managed identity's client ID, the same one annotated on the pod's ServiceAccount.

4. Mount it

serviceAccountName: orders-api            # annotated with the client ID (lesson 5.6)
containers:
  - name: api
    volumeMounts:
      - name: kv
        mountPath: /mnt/secrets
        readOnly: true
volumes:
  - name: kv
    csi:
      driver: secrets-store.csi.k8s.io
      readOnly: true
      volumeAttributes:
        secretProviderClass: orders-api-kv

Tap the line that links this volume to the Key Vault configuration.

The secretProviderClass volume attribute must match the class name in the same namespace. The app then reads /mnt/secrets/payments-api-key.

5. Diagnose a mount failure

The pod is stuck in ContainerCreating. Why?

Events:
  Warning  FailedMount  kubelet  MountVolume.SetUp failed for volume "kv" : rpc error: code = Unknown desc = failed to
  mount secrets store objects for pod orders/orders-api-7d9c5f6b8-2xk9p, err: rpc error: code = Unknown desc = failed
  to mount objects, error: failed to get objectType:secret, objectName:payments-api-key, objectVersion:: GET
  https://kv-orders-prod.vault.azure.net/secrets/payments-api-key/: StatusCode=403 -- Original Error:
  {"error":{"code":"Forbidden","message":"Caller is not authorized to perform action on resource. …
  Action: 'Microsoft.KeyVault/vaults/secrets/getSecret/action'","innererror":{"code":"ForbiddenByRbac"}}}
  1. The SecretProviderClass name is wrong The driver found the class and called Key Vault.
  2. The managed identity has no Key Vault data-plane role: grant "Key Vault Secrets User" on the vault
  3. The secret doesn't exist That would be 404 SecretNotFound.
  4. Workload identity isn't set up The token exchange worked; the caller is authenticated but not authorised.
ForbiddenByRbac = authentication worked, authorisation didn't. Add the role assignment in IaC (lessons 12.5 and 13.4). An AADSTS error instead would mean the federated credential is wrong.

6. Files vs synced Kubernetes Secrets

Mounted files are the default, and the best option: the secret exists only in the pod's tmpfs.

If an app needs an env var, or an Ingress needs a TLS Secret, add secretObjects to the class. The driver then also creates a Kubernetes Secret, while at least one pod mounts the volume.

That means "Key Vault means no Kubernetes Secret ever exists" is false once you use sync, so RBAC on Secrets still matters.

secretObjects:
  - secretName: orders-db
    type: Opaque
    data:
      - objectName: orders-db-password
        key: password

7. Rotation

With --enable-secret-rotation, the driver re-reads Key Vault periodically (every 2 minutes by default) and updates the mounted files, and synced Secrets.

  • Apps must re-read the file to see the new value.
  • Env vars from a synced Secret only change after a restart (lesson 2.6).

8. Even better: no secret at all

Many "secrets" are only there to authenticate to Azure services. With workload identity, the app can use Entra ID auth directly, so there's no password to store or rotate:

  • Azure SQL and PostgreSQL with Entra ID users;
  • Storage, Service Bus and Cosmos DB with RBAC.

Keep Key Vault for the secrets you can't remove, such as third-party API keys.

9. Alternatives

  • The SDK directly (SecretClient + DefaultAzureCredential, lesson 5.6): no driver; the app fetches what it needs.
  • Azure App Configuration with Key Vault references, for config and feature flags in one place.
  • External Secrets Operator (community): syncs Key Vault to Kubernetes Secrets.

10. Lock the vault down

  • RBAC permission model; one vault per app and environment (or tightly scoped roles).
  • A private endpoint and public access disabled, so the AKS VNet reaches it privately.
  • Soft delete and purge protection on; diagnostic logs to Log Analytics.

11. The full Contoso chain

Key Vault secret ← "Key Vault Secrets User" ← id-orders-api ← federated credential (system:serviceaccount:orders:orders-api) ← ServiceAccount annotation ← pod label → CSI volume → /mnt/secrets. No secret value in Git, in pipeline variables, or in any manifest.

Key Vault secrets, sorted

  • Add-on + SecretProviderClass (clientID, keyvaultName, tenantId, objects) + CSI volume.
  • Authenticated by workload identity; 403 ForbiddenByRbac = a missing Key Vault role.
  • Prefer mounted files; secretObjects sync creates a real Kubernetes Secret.
  • Rotation updates files; best of all, remove secrets with Entra ID auth.
