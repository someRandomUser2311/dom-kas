Chapter 15 · Lesson 15.7 · ~8 steps · ~10 min

Threat-model recap

You'll be able to walk an attacker's path from a malicious pull request to Contoso's production data, and name the control that stops each hop.

1. The attacker's goal

An attacker has a contributor's Git credentials, for example from a phished laptop. They want the orders database. Let's follow every hop they'd need, and see what stops each one.

Windows/IIS admin
Like walking an attack path in a tiered AD model: each tier boundary needs its own control.
Linux admin
Defense in depth: no single control is trusted to stop everything.
Developer (Compose)
Your PRs and your images are the first hops; the habits from this course close them.
Other clouds
The same kill chain applies to every CI/CD and Kubernetes platform.

2. The hops, in order

Order the attack path.

  1. Push a malicious change to a branch
  2. Get the change into a pipeline run with production credentials
  3. Deploy a malicious image or manifest to the prod cluster
  4. From the running pod, reach other workloads or the node
  5. Read secrets or the database and send them out
Each hop is a chance to stop them.

3. A control for every hop

Match each hop to the control that stops it.

Push to a branchBranch policies: reviewers + build validation on main (lesson 0.5)
Use prod credentials from a branchBranch control + required template on the service connection (15.6)
Deploy a malicious imageSigned images only + allowed-registry admission policy (Chapter 16)
Escape the pod or move laterallyPod Security restricted + default-deny NetworkPolicy (15.3, Chapter 9)
Read secrets and exfiltrateWorkload identity per app + Key Vault RBAC + egress control (5.6, 15.4, 5.3)
Any single control can fail; the chain needs all of them to fail at once.

4. Detection at each stage

  • Azure DevOps audit: checks removed, permissions changed.
  • AKS audit logs (kube-audit-admin): unexpected creates or deletes.
  • Defender for Containers: suspicious processes, crypto-mining.
  • Key Vault logs: unusual secret reads.
  • Azure Firewall logs: unusual egress destinations.

5. The insider pipeline

What if the attacker modifies the platform template itself? That repository needs the strongest branch policies (two reviewers from the platform team), and the "required template" check should pin a protected branch or tag of it.

6. Supply chain is the next frontier

A malicious dependency or base image bypasses all the PR-based controls, because the code looks fine. Chapter 16 adds scanning, SBOMs, signing and admission policies to close that gap.

7. Practice: tabletop

Contoso runs a quarterly tabletop exercise. Pick a hop, assume its control failed, and check whether the next control and the detections would catch it. Gaps become backlog items.

Threat model, sorted

  • Branch → pipeline credentials → deploy → pod → data: five hops.
  • A control at each: branch policies, resource checks, signing and admission, pod security and network policy, identity and Key Vault and egress.
  • Detection at each stage; protect the template repo; supply chain next.
