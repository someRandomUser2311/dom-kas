Kubernetes RBAC

You'll be able to write Roles and bindings that grant exactly what's needed, understand how scope works, and check any permission with kubectl auth can-i.

1. Why native RBAC still matters

Azure RBAC (lesson 5.5) covers people and pipelines on AKS. Kubernetes' own RBAC is still needed for:

  • ServiceAccounts: identities of pods and in-cluster tools such as operators and CI agents;
  • custom, fine-grained permissions the four built-in Azure roles don't express;
  • clusters that use Entra ID authentication with Kubernetes RBAC authorization.

Kubernetes RBAC is allow-only, like NetworkPolicy: no rule means no access.

Windows/IIS admin
Roles are like permission sets on an OU; bindings are like adding a group to it. There's no "Deny" entry: if nothing grants it, it's denied.
Linux admin
Like sudoers rules: a subject, the allowed commands (verbs) and the objects (resources).
Developer (Compose)
Docker has no per-API permissions; this is how a pod's ServiceAccount is limited.
Other clouds
The same Kubernetes RBAC on EKS and GKE; only the human identity mapping differs.

2. A Role: rules

A Role lists rules, each made of apiGroups + resources + verbs. Core resources (pods, services, configmaps) are in the group ""; Deployments are in apps.

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: deployer
  namespace: orders
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  - apiGroups: [""]
    resources: ["services", "configmaps"]
    verbs: ["get", "list", "create", "update", "patch"]

3. A RoleBinding: who gets it

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: deployer
  namespace: orders
subjects:
  - kind: ServiceAccount
    name: deployer
    namespace: ci
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: deployer

Subjects can be ServiceAccounts, Users or Groups (with Entra ID, groups are identified by their object IDs). roleRef can't be changed after creation; recreate the binding instead.

4. Role vs ClusterRole, RoleBinding vs ClusterRoleBinding

Defined whereGrants where
Role + RoleBindingOne namespaceThat namespace
ClusterRole + RoleBindingCluster-wide definitionOnly the RoleBinding's namespace
ClusterRole + ClusterRoleBindingCluster-wideEvery namespace, plus cluster-scoped resources

Binding a reusable ClusterRole (like the built-in edit or view) with a RoleBinding is a common, safe pattern. A ClusterRoleBinding is rarely what an app or pipeline needs.

5. Grant the deployer

Give ServiceAccount ci/deployer the rights to manage Deployments (get, list, watch, create, update, patch) only in namespace orders.

An RBAC editor plus a test table. Success when these all hold:
  • patch deployments -n orders: allow
  • patch deployments -n payments: deny
  • delete deployments -n orders: deny
  • get secrets -n orders: deny
  • create clusterroles: deny
Each result shows the rule and binding that granted it, or "no rule".
A Role in orders plus a RoleBinding for the ServiceAccount from namespace ci.

6. The wildcard that over-grants

This Role was meant to let the deployer manage the app. Tap the line that makes it far too powerful.

rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "patch"]
  - apiGroups: [""]
    resources: ["*"]
    verbs: ["get", "list", "create", "update", "patch"]
resources: ["*"] in the core group includes secrets and pods/exec, and with create it allows creating pods that mount any secret or ServiceAccount in the namespace. Always list resources explicitly.

7. Dangerous permissions

Some permissions are much stronger than they look:

  • create pods: run anything as any ServiceAccount in the namespace, and mount its secrets.
  • get/list secrets: read every credential in the namespace.
  • pods/exec: a shell in any pod, with its identity.
  • escalate, bind, impersonate: grant yourself more.
  • Anything cluster-wide on nodes, clusterroles, validatingwebhookconfigurations.

8. Check with auth can-i

kubectl auth can-i <verb> <resource> asks the API server. Add --as to test another subject; impersonation itself needs permission. --list shows everything.

Check whether ServiceAccount deployer in namespace ci can delete Deployments in namespace orders.

kubectl auth can-i delete deployments -n orders --as=system:serviceaccount:ci:deployer

Also accepted: --namespace; deployment/deploy; --as system:serviceaccount:ci:deployer.

Expected answer: no. The Role doesn't include delete.

9. ServiceAccount hygiene

  • Every app gets its own ServiceAccount (it already has one, for workload identity, lesson 5.6).
  • Most apps need no Kubernetes API access at all. Set automountServiceAccountToken: false on the pod, unless the app calls the API or uses workload identity, which needs its own projected token and still works.
  • Never grant the default ServiceAccount anything.

10. Built-in ClusterRoles

ClusterRoleBound with a RoleBinding gives
viewRead most objects (no secrets)
editCreate and change most objects, including secrets and pods/exec (no RBAC changes)
adminEverything in the namespace, including Roles and RoleBindings
cluster-adminEverything, everywhere. Never for apps or pipelines

11. Audit existing access

kubectl get rolebindings,clusterrolebindings -A -o wide | grep -E "cluster-admin|system:serviceaccount"
kubectl auth can-i --list --as=system:serviceaccount:ci:deployer -n orders

Tools like rbac-lookup or kubectl-who-can answer "who can read secrets in orders?" Run such an audit regularly.

12. RBAC in Git

Roles and bindings are YAML: keep them in k8s/rbac/, reviewed in PRs, applied by the platform pipeline. A binding added by hand during an incident should be removed, or written into Git, the same day.

Kubernetes RBAC, sorted

  • Rules = apiGroups + resources + verbs; allow-only.
  • A ClusterRole bound by a RoleBinding is namespace-scoped; ClusterRoleBindings are cluster-wide. Rarely needed.
  • Avoid wildcards; watch create pods, secrets, exec, escalate, bind, impersonate.
  • kubectl auth can-i … --as to verify; one SA per app; no automounted tokens unless needed.
