Securing Azure DevOps

You'll be able to protect service connections, environments, pools and variable groups with checks, so that only reviewed code on main, using the approved template, can reach production.

1. YAML is code anyone can change

A YAML pipeline lives in the repo. Anyone who can push a branch can change the YAML, for example to add a step that uses the prod service connection.

The defence isn't hiding the YAML. It's putting checks on the protected resources themselves. Checks are configured in Azure DevOps, outside the repo, so a branch can't remove them.

GitHub Actions
Environment protection rules (required reviewers, deployment branches), plus OIDC subject claims tied to an environment and branch.
GitLab CI
Protected environments, protected branches and protected variables.
Jenkins
Folder-scoped credentials and restricted job permissions, which are much harder to get right.
Classic pipelines
Release approvals and gates lived in the release definition; YAML moves them onto resources.

2. Protected resources

These can carry checks and pipeline permissions:

  • service connections;
  • environments;
  • agent pools;
  • variable groups;
  • secure files;
  • repositories.

A stage that uses a protected resource waits until all its checks pass.

3. The checks

CheckEnsures
ApprovalsNamed people or groups approve (optionally not the person who queued the run)
Branch controlOnly runs from allowed branches (e.g. refs/heads/main), and optionally only protected branches
Required templateThe pipeline must extends an approved template
Business hoursOnly within a time window
Exclusive lockOne run at a time
Query Azure Monitor alerts / Invoke REST API / Azure FunctionExternal health or compliance gates

4. A feature branch tries prod

The stage simulator with checks. A run from feature/x modifies the YAML to deploy to prod using sc-orders-prod. The learner toggles checks on the service connection and the environment (branch control, required template, approval) and replays: the stage either runs (red, bad) or is blocked with the check that blocked it.

Configure checks so that only runs from main, using templates/secure-pipeline.yml@platform, can deploy to prod, and only after approval.

Success when:
  • sc-orders-prod has branch control (main only) and required template;
  • the prod environment has an approval plus branch control.
Then the replay from feature/x is blocked, a run from main that doesn't use the template is blocked, and a run from main with the template waits for approval.
Put checks on the service connection too, not only the environment. Otherwise a job that doesn't target the environment could still use the connection.

5. Pipeline permissions

By default, a protected resource must be authorized for each pipeline that uses it. Don't click "Grant access to all pipelines" on prod service connections, variable groups or pools. Authorize only the release pipeline.

6. Limit job authorization scope

Every job gets a token (System.AccessToken) for the Azure DevOps APIs. Turn these settings on, at organisation and project level:

  • Limit job authorization scope to current project for non-release and release pipelines;
  • Protect access to repositories in YAML pipelines, so a pipeline can only check out repositories it's explicitly granted.

A compromised job then can't read other projects' code or settings.

7. Builds from forks

For public or GitHub-hosted repos, a PR from a fork runs code written by anyone. Keep the defaults:

  • don't make secrets available to fork builds;
  • require a team member's comment or approval before fork PRs run.

Run fork PRs only on Microsoft-hosted agents, never on self-hosted agents inside your network.

8. Variable groups and secrets

Link variable groups to Key Vault instead of storing secrets in Azure DevOps. Protect them with checks like any other resource. Remember: secret variables are masked in logs, but a malicious step can still send them elsewhere. Access control on who can run with them is the real protection.

9. Agents are a target too

Self-hosted agents and Managed DevOps Pools inside your network can reach private resources. Use separate pools for prod deploys, protect them with checks, and use ephemeral agents (Managed DevOps Pools recycle them) so one job can't leave something behind for the next.

10. Which setting stops what?

A developer pushes feature/x with YAML that adds az aks command invoke … delete ns orders, using sc-orders-prod in a normal job (no environment). What stops it?

  1. The prod environment's approval The job doesn't target the environment, so that check never applies.
  2. Branch control (main only) and required template on the sc-orders-prod service connection
  3. The PR policy on main The branch isn't merged; CI on the feature branch still runs its YAML.
  4. Nothing can stop it Resource checks exist exactly for this.
Protect the credential, not just the environment.

11. Audit

Azure DevOps auditing records changes to checks, permissions and service connections. Stream it to Log Analytics or your SIEM, and alert when someone removes a check from a prod resource.

Azure DevOps security, sorted

  • Checks live on resources (service connections, environments, pools, variable groups), outside the YAML.
  • Branch control + required template + approvals on both the prod service connection and the environment.
  • Authorize resources per pipeline; limit job token scope; protect repository access.
  • Fork builds without secrets; separate, ephemeral agent pools; audit changes.
