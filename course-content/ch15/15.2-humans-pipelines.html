Who can do what: humans and pipelines

You'll be able to design access for every team and pipeline on Contoso's clusters, including break-glass access, and spot over-privileged setups.

2. Groups, never individuals

Assign roles to Entra ID groups. People join and leave groups through the identity process (and access reviews), not through cluster changes. Either Azure RBAC role assignments or Kubernetes RoleBindings work, as long as the subject is a group.

3. The pipeline is a high-value identity

The release pipeline can change production. If it's cluster-admin, anyone who can change the pipeline's YAML, or compromise an agent, owns the cluster.

Scope it to the namespaces it deploys, with the verbs it needs. Nothing cluster-wide.

GitHub Actions
Same principle for OIDC federated credentials: one credential per repo and environment, with a narrow role.
GitLab CI
Use the GitLab agent's per-project authorization, not one cluster-admin token for every project.
Jenkins
Avoid one shared kubeconfig credential with admin rights for all jobs.
Classic pipelines
Old "Kubernetes service connections" often used admin kubeconfigs. Replace them.

4. Service connection types

  • Azure Resource Manager (WIF): an Entra ID identity. The task gets cluster credentials through Azure, and Azure RBAC on the cluster decides what it may do. Recommended.
  • Kubernetes service connection with a kubeconfig or ServiceAccount token: a stored credential that must be rotated. Avoid it, especially with admin kubeconfigs, which don't exist anyway when local accounts are disabled.

5. The safest setup

Which pipeline identity setup is safest for deploying orders-api to prod?

  1. A Kubernetes service connection with the cluster's admin kubeconfig A stored credential with full power.
  2. An ARM service connection with a client secret, Contributor on the subscription A secret, and far too broad.
  3. An ARM service connection using workload identity federation, with AKS RBAC Writer on the orders namespace only, usable only from main via the approved template
  4. The developer's personal account Personal, unaudited, and gone when they leave.
No secret, minimal scope, and protected by Azure DevOps checks (lesson 15.6).

6. Spot the over-privilege

Select every over-privileged setup.

  1. The release pipeline's SA is bound to cluster-admin with a ClusterRoleBinding
  2. All developers have AKS RBAC Cluster Admin on prod permanently
  3. The infra pipeline is Owner on the subscription
  4. Developers have AKS RBAC Reader on prod Reasonable for troubleshooting.
  5. The platform team activates Cluster Admin via PIM with approval Just-in-time and audited: good.
  6. The app's ServiceAccount has edit on its namespace although the app never calls the Kubernetes API
Every standing permission is a risk. Grant the minimum, and make anything powerful temporary.

7. Break-glass access

If Entra ID is unavailable, or a misconfiguration locks everyone out, you need a way in.

A break-glass Entra group has Cluster Admin. Its accounts:

  • have long, vaulted credentials and phishing-resistant MFA;
  • are excluded from conditional-access policies that could lock them out;
  • trigger an alert every time they sign in.

az aks command invoke (lesson 6.5) is also useful in emergencies, because it works through Azure's management plane.

8. Access reviews

Schedule Entra ID access reviews for the groups with cluster roles, quarterly for prod. Combine them with the audit-log query from lesson 14.5 to see what each group actually used.

9. Defense in depth

Least privilege doesn't stop a legitimate identity from deploying something bad. That's what Pod Security (next lesson), admission policies (Chapter 16) and pipeline checks (lesson 15.6) are for.

Humans and pipelines, sorted

  • Groups → roles, scoped to namespaces; read-only in prod by default; PIM for more.
  • Pipeline: WIF ARM connection, namespace-scoped Writer, never cluster-admin.
  • Avoid Kubernetes service connections with stored kubeconfigs.
  • Break-glass group, alerted; regular access reviews.
