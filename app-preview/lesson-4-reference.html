Service connections, service principals & ACR

⏱ 20 min·Token-flow walkthrough·Simulated Azure DevOps form

Your pipeline needs to push an image to ACR and deploy to AKS. Both are protected Azure resources. So how does a pipeline prove who it is, without anyone pasting a password into the YAML?

The answer is a chain of three ideas: an identity in Entra ID, a service connection in Azure DevOps that uses it, and RBAC roles on the Azure resources.

The identity: who is the pipeline?

TermWhat it isAnalogy
App registrationThe global definition of an application in Entra ID (client ID, credentials, federated credentials).The job description
Service principalThe app's identity inside your tenant. This is what RBAC roles are assigned to. "SP" for short.The employee badge
Managed identityA service principal whose credentials Azure manages for you. No secrets to rotate.A badge that renews itself
Service connectionAn Azure DevOps object that stores how to authenticate as one of the above, so pipelines can reference it by name.The key card reader config

How the pipeline gets a token

Compare the two credential types. Workload identity federation is the recommended default: no secret exists anywhere, so there's nothing to leak or rotate.

Least-privilege RBAC for an AKS pipeline

An identity with no roles can authenticate but can't do anything. Give each identity exactly what it needs, scoped as narrowly as possible:

WhoRoleScopeWhy
Pipeline SPAcrPushThe ACRPush (and pull) images. Not Contributor!
Pipeline SPAzure Kubernetes Service Cluster User RoleThe AKS clusterDownload a kubeconfig (az aks get-credentials)
Pipeline SPAzure Kubernetes Service RBAC WriterNamespace ordersCreate and update workloads, with Azure RBAC for Kubernetes enabled
AKS kubelet identityAcrPullThe ACRNodes pull images. Granted by az aks update --attach-acr
🚫
Anti-pattern: a single SP with Owner on the subscription, shared by every pipeline, with a two-year client secret. If it leaks, an attacker owns everything. Scope narrowly, prefer federation, and don't "grant access to all pipelines".

ACR in one screen

Azure Container Registry is a private Docker registry. Its login server looks like <name>.azurecr.io, and images are referenced as kqacr.azurecr.io/orders-api:1427. In a pipeline you usually reference ACR through a Docker Registry service connection (as Docker@2 did in lesson 2) or through an ARM connection with az acr login.

You'll run exactly these commands against the local floci-az emulator in the terminal lab at the end of this chapter.
