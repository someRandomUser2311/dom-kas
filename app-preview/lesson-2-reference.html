Anatomy of azure-pipelines.yml

⏱ 18 min·Annotated YAML explorer·"Find it" challenge

Every YAML pipeline is a tree: pipeline → stages → jobs → steps. A stage is a logical phase (Build, Deploy). A job is a unit of work that runs on one agent. A step is one task or script inside that job. Hold that hierarchy in your head and any pipeline becomes readable.

    Things that trip everyone up

    ⚠️
    Implicit structure. If you only write steps:, Azure Pipelines wraps them in one implicit job inside one implicit stage. Fine for CI; you'll want explicit stages once you deploy.
    ⚠️
    Deployment jobs don't check out code. A deployment: job skips checkout by default. Need your k8s/*.yaml? Add - checkout: self, or publish them as a pipeline artifact.
    ⚠️
    Stages run in order by default. Without dependsOn, each stage depends on the one above it. dependsOn: [] makes a stage start in parallel.
    ⚠️
    Jobs don't share a disk. Each job may run on a different agent. Pass files between jobs with pipeline artifacts, and values with output variables.
