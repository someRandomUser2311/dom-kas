Variables, secrets & templates

⏱ 18 min·Expression timeline·Template expander

Azure Pipelines has three ways to read a variable, and they are evaluated at different moments. Mixing them up is the #1 source of "but the variable is set!" bugs.

When is each syntax evaluated?

SyntaxNameEvaluatedUse it for
${{ }}Template expressionCompile time, before the run startsParameters, ${{ if }} / ${{ each }} to shape the pipeline itself
$[ ]Runtime expressionAt runtime, when the job/stage startsVariable values and conditions that depend on outputs of earlier jobs
$( )MacroJust before each task runsTask inputs and scripts; the everyday choice

Secrets: never in YAML

🔐 Secret variables

Defined in the pipeline UI or in a variable group and marked 🔒. Masked as *** in logs. Not mapped into scripts as environment variables automatically; you must map them explicitly with env:.

🗝️ Variable group → Key Vault

A library variable group can be linked to Azure Key Vault. Secrets are fetched at runtime with the service connection's identity, and rotation happens in Key Vault, not in Azure DevOps.

⚠️
Masking is not security. A script can still leak a secret by base64-encoding it or writing it to an artifact. Limit who can edit pipelines, and protect variable groups with approvals and pipeline permissions.

Templates: write it once, reuse it everywhere

Templates let a platform team publish a hardened "golden path" that every service reuses. Two flavours: include (insert steps/jobs/stages from a file) and extends (your pipeline must fit inside a template that controls the overall structure, which is great for security).

This is what Azure Pipelines actually runs after compile-time expansion. In the run UI you can download it via Download full YAML.
