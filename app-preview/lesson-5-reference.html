Stages, conditions, environments & approvals

⏱ 22 min·Live pipeline simulator·Strategy comparison

A real delivery pipeline isn't a straight line. Security scans run in parallel with the build, dev deploys happen on every branch, prod deploys only from main and only after someone approves, and the team gets notified when anything breaks. All of that comes from four tools: dependsOn, condition, environments and checks.

Conditions cheat sheet

ConditionRuns when…
succeeded()All dependencies succeeded. This is the default if you write no condition.
failed()At least one dependency failed. Use it for notifications and rollbacks.
succeededOrFailed()Dependencies finished, whatever the result, unless the run was cancelled. Good for publishing test results.
always()Always, even if cancelled. Use it for cleanup.
and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))Succeeded and the run is for main. ⚠️ Writing a custom condition replaces the default, so include succeeded() yourself!
ne(variables['Build.Reason'], 'PullRequest')Skip for PR validation runs, e.g. never deploy from a PR.

Environments, approvals & checks

An environment (environment: prod) is an Azure DevOps object that represents a deployment target. It gives you deployment history (which commit is in prod right now?) and, most importantly, checks that run before any job targeting it can start:

✅ Approvals

Named people or groups must approve. Can block the requester from approving their own run.

🌿 Branch control

Only runs from refs/heads/main (or release branches) may deploy here.

🕘 Business hours

Deploy only Mon–Thu, 09:00–16:00. No Friday-night surprises.

🔒 Exclusive lock

Only one run deploys to prod at a time; later runs queue or replace older ones.

🌐 Invoke REST / Azure Function

Ask an external system ("is there an open incident?") before proceeding.

📋 Required template

Only pipelines extending your approved, secure template may deploy.

💡
Why checks live on the environment, not in YAML: the YAML is editable by anyone who can push a branch. If approvals were YAML, a developer could just delete them. Checks are owned by whoever administers the environment.

Deployment strategies

Run the deploy hook once. For Kubernetes this is the most common choice, because the Kubernetes Deployment object already does a rolling update (maxSurge / maxUnavailable).

Replaces the app on a few targets at a time. In Azure Pipelines the rolling strategy is meant for VM resources in an environment, not for Kubernetes. On AKS, use runOnce and let the Deployment roll.

Send a slice of traffic to the new version first. KubernetesManifest@1 creates -canary and -baseline workloads; you then promote on success or reject on failure.
