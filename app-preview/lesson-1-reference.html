CI/CD and where Azure Pipelines fits

⏱ 12 min·1 interactive diagram·1 knowledge check

In earlier chapters you deployed to AKS by hand with docker build, docker push and kubectl apply. That works for a single change on a quiet afternoon. It falls apart when ten engineers push twenty changes a day: someone forgets to run the tests, someone tags an image latest, and someone deploys from their laptop with uncommitted code.

CI/CD turns those manual steps into an automated, repeatable and auditable process that runs on every change.

CI
Continuous Integration

Every push is built and tested automatically, so broken code is caught within minutes, not at release time.

CD
Continuous Delivery

Every green build produces a deployable artifact (for us, a container image in ACR). Going to production is a button press.

CD
Continuous Deployment

Same as delivery, but with no human button. Every green build goes all the way to production automatically.

Azure DevOps in one minute

Azure Pipelines is one service inside Azure DevOps, a separate product from the Azure portal. An Azure DevOps organization holds projects, and each project can use these services:

ServiceWhat it doesUsed in this course?
ReposGit hosting (GitHub works just as well)Mentioned
PipelinesBuilds, tests and deploys your code: CI/CDThis chapter
ArtifactsPackage feeds (npm, NuGet, Maven, pip)Mentioned
BoardsWork items, sprints, KanbanNo
Test PlansManual & exploratory testingNo
💡
No Azure subscription needed to use Azure DevOps. An Azure DevOps organization only needs a Microsoft account and is free for small teams. The Azure subscription only matters for what your pipeline deploys to (AKS, ACR…). In this course, those targets are emulated locally by floci-az.

Classic pipelines vs YAML pipelines

Azure Pipelines has two ways to define a pipeline. You will see both in real companies, but every new pipeline should be YAML.

🖱️ Classic (UI designer)
  • Built by clicking in the web UI
  • Separate "Build" and "Release" pipelines
  • Hard to review, diff or reuse
  • Still common in older projects
📄 YAML (pipeline as code) Recommended
  • Lives in your repo as azure-pipelines.yml
  • Reviewed in pull requests, versioned with the code
  • Build and deploy in one multi-stage file
  • Reusable through templates
